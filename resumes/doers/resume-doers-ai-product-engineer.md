## 소개

AI에게 구현을 맡기고, 어떤 제품을 만들지와 결과물을 받아들일 기준을 직접 판단하며 일합니다. 실무에서는 여러 제품의 프론트엔드를 맡아 요구사항의 빈틈을 채우고, 에이전트가 반복해서 놓치는 부분을 skills, 테스트, lint rule로 정리해 왔습니다.

최근에는 같은 방식을 개인 프로젝트로 넓혀 웹과 API, DB, 배포 구성을 함께 만들고 있습니다. 기술의 장단점과 낯선 동작은 에이전트에게 물어 이해를 넓히고, 코드와 문서도 확인합니다. 대안별 이점과 비용을 비교해 어떤 방식을 적용할지 판단합니다. 화면이 어색하거나 구조가 의도와 다르면 완성본을 다시 요청합니다.

## 지원동기

AI로 구현 속도가 빨라지면서 어떤 기능이 필요한지, 무엇을 빼고 어디까지 검증할지 판단하는 일이 더 중요해졌습니다. 개인 프로젝트에서는 기능과 디자인을 바꾸며 서버와 인프라까지 다뤘고, 실무에서는 출시 뒤 오류와 운영 요청까지 처리해 왔습니다. 두어스에서 PO와 제품을 함께 만들며 이 경험을 넓히고, 사용자 반응으로 다음 결정을 내리는 일을 더 깊게 하고 싶습니다.

## AI로 만든 개인 프로젝트 | 2026.10 – 현재

사진 커뮤니티와 게임 커뮤니티를 Yarn workspace 모노레포에서 개발하고 있습니다. 제품 방향과 화면 검토, 기술 선택과 구현 검증을 맡고, 코드와 테스트 작성은 코딩 에이전트에 맡깁니다. 두 제품 모두 초기 사용자 검증을 준비하는 단계입니다.

### 기능과 디자인 결정

- 사진 대회에서 상시 그룹 피드로 방향을 바꿨습니다. 홈에는 가입한 그룹의 최신 게시물을, MY에는 가입 그룹을 두고 공개 탐색과 선택 참여 대회를 더했습니다. 그룹과 게시물을 행사 종료일에 묶지 않도록 바꿨습니다.
- 참고 서비스의 디자인을 그대로 옮긴 결과에서는 실제 스토리 기능도 없는데 프로필에 테두리가 붙고, 순위가 사진을 가렸습니다. 불필요한 장식을 빼고 정보 위치를 수정했습니다. 게시물 작업 버튼은 메뉴로 모았습니다.
- 게임 커뮤니티에서는 프로필 설정에 합칠 수 있는 별도 설정 메뉴와 의미 없는 LIVE 표시를 덜어냈습니다. 모바일 로그인과 가입 정보 입력은 독립 페이지로 바꾸고, 신고, 사용자 차단, 관리자 문의 흐름을 추가했습니다.

### 캐시와 파일 업로드

- 사진 서비스는 GraphQL과 Apollo, 게임 서비스는 REST와 TanStack Query를 사용합니다. API 계약과 브라우저 캐시를 서비스별로 유지하고, 사용자별 데이터와 공개 SSR 캐시를 구분했습니다.
- 게임 게시글을 수정해도 공개 캐시가 남지 않도록 NestJS 쓰기와 Next.js Route Handler의 태그 만료를 연결했습니다. DB 변경과 무효화 대상을 함께 저장하고, 전달 실패는 재시도합니다. 늦게 끝난 이전 요청이 새 무효화 기록을 지우지 않도록 revision을 비교합니다.
- 미디어는 S3 직접 업로드로 전환했습니다. 게임 서비스의 파일 완료 처리는 HEAD와 앞 4KB 검사, ETag 조건부 복사로 구성해 전체 파일을 API 메모리에 올리지 않도록 했습니다. 서버에서 처리하는 기존 multipart와 프로필 변환에는 프로세스당 동시 3개, 대기 12개 상한을 뒀습니다.

### 테스트와 배포 구성

- 도메인 규칙은 Vitest, API와 DB는 Supertest와 격리 PostgreSQL, 브라우저 흐름은 Playwright로 나눴습니다. 테스트 러너와 설정은 각 앱이 소유하고 루트는 실행만 위임하도록 했습니다.
- 공용 ESLint 패키지를 TypeScript로 만들고 FSD 경계, 공개 API, 컴포넌트의 직접 fetch와 상태 중복을 검사합니다. 규칙 옆에 RuleTester와 fixture를 두고, Next.js와 Vite, Expo에 적용 범위를 나눴습니다.
- 최소 비용 배포 대안과 CD 준비 순서를 AI와 검토한 뒤 EC2 한 대, 외부 RDS, 서비스별 S3 구성을 정했습니다. Terraform으로 네트워크와 리소스, 권한을 코드화하고 mock provider 테스트를 붙였습니다. 실제 AWS 적용과 운영 부하 검증은 별도 단계로 두고 있습니다.

#### AI 개발 workflow | 2026.04 – 현재

처음에는 에이전트의 코드를 전부 읽었고, 반복해서 달라지는 구현 방식은 skills와 lint rule로 보완했습니다. 7월부터는 기능 명세와 회귀 테스트를 같은 작업 흐름에 넣었습니다. 지금은 아래 과정을 거치고, 부족한 결과는 반려해 다시 확인합니다.

티켓과 plan 검토 → 테스트 작성 → 에이전트 구현과 에이전트 코드 리뷰 → 변경분 테스트, lint, typecheck → 직접 diff 리뷰와 화면 동작 확인 → 전체 CI(테스트, knip, lint)

- 요구사항과 Figma를 먼저 보고 빠진 동작을 담당자와 확인합니다. 에이전트 리뷰의 critical 항목은 자동 수정하도록 하고, 제출된 코드와 테스트에서 요구사항 누락과 코드 컨벤션, 실제 사용성을 검토합니다.
- 명세는 `*.spec`, 운영과 QA 오류는 `*.test`에 나눠 씁니다. 새 테스트 패턴은 제품 코드를 깨뜨려 실패하는지도 확인합니다.
- 공통 Bottom Sheet에서는 diff를 읽고도 헤더까지 스크롤되는 문제를 놓쳤습니다. 본문만 스크롤되도록 고치고 레이아웃 회귀 테스트를 추가했습니다. 코드 확인과 화면 확인을 각각 거칩니다.
