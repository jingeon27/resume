## 실무에서 검증 방식을 바꾼 경험

현재 실무에서는 요구사항과 Figma를 먼저 보고, 빠진 동작은 담당자와 논의한 뒤 아래 순서로 작업합니다.

티켓과 plan 검토 → 테스트 작성 → 에이전트 구현과 에이전트 코드 리뷰 → 변경분 테스트, lint, typecheck → 직접 diff 리뷰와 화면 동작 확인 → 전체 CI(테스트, knip, lint) → QA 더블 체크 요청

에이전트가 완성본을 제출하면 검토하고 부족한 부분은 수정을 요청해 다시 확인합니다. 기능 개발과 리팩터링에서는 변경된 제품 코드와 테스트를 읽습니다. 새 기능은 BDD 형식의 `*.spec`에 컴포넌트별 기대 동작을 적고 누락을 검토하며, 운영이나 QA 오류는 `*.test`에 재현합니다. 새 테스트 패턴은 제품 코드를 일부러 깨뜨려 실패하는지도 확인합니다.

[테스트 도입과 검증 기준](https://blog.bambyul.com/ko/blog/테스트-코드를-도입하면서-세운-기준) | [AI 개발 workflow](https://blog.bambyul.com/ko/blog/ai가-코드를-잘-짜기-시작했는데-제가-덜-바빠지지는-않았어요)

### 테스트가 확인하는 화면을 다시 확인했습니다

**담당과 기여:** 테스트의 전제와 실제 앱 설정의 차이를 확인하고 오류 상황별 검증 기준을 보완했습니다. 에이전트가 작성한 테스트가 실제 화면을 확인하는지 검토한 사례입니다.

**문제 상황**

관리자 서비스의 테스트용 QueryClient가 실제 앱과 다르게 조회 오류를 처리하고 있었습니다. 실제 앱에서는 오류 경계에 가려질 UI를 테스트에서는 볼 수 있어, 테스트가 통과해도 같은 화면을 보장하지 못했습니다.

**해결 방법**

통과한 assertion만으로 판단하지 않고 테스트가 어떤 QueryClient와 데이터 상태에서 화면을 띄우는지 확인했습니다. 설정을 앱과 맞춘 뒤 처음 데이터를 받지 못한 경우와 기존 데이터를 재조회하다 실패한 경우를 나눴습니다. 첫 조회 실패는 오류 경계가 처리하고, 재조회 실패는 기존 화면 전체를 가리지 않는지 확인하도록 했습니다.

**트레이드오프**

앱과 같은 오류 처리 조건에 맞추면서 첫 조회 실패와 재조회 실패의 데이터를 따로 준비해야 했습니다. 테스트 준비는 늘지만 실제 앱에서 도달할 수 있는 화면을 확인하는 조건을 우선했습니다.

**결과 및 배운 점**

QueryClient 설정을 맞춘 뒤 데이터가 없는 실패와 기존 데이터가 있는 실패를 구분해 확인했습니다. 테스트의 성공 여부와 테스트가 실제 앱의 조건을 보장하는지는 함께 검토해야 했습니다.

### 코드 리뷰에서 놓친 스크롤을 회귀 테스트로 남겼습니다

**담당과 기여:** 에이전트 구현의 스크롤 회귀를 diff에서 놓쳤고, 수정과 브라우저 검증 기준 보완을 맡았습니다.

**문제 상황**

공통 Bottom Sheet를 바꿀 때 에이전트가 본문과 헤더를 함께 스크롤되게 구현한 것을 diff에서 놓쳤습니다.

**해결 방법**

검증할 대상을 본문의 스크롤과 헤더의 위치로 나눠, 본문만 스크롤되도록 고치고 브라우저 레이아웃 회귀 테스트를 추가했습니다. 함수의 반환값으로는 확인할 수 없는 배치였으므로 화면을 띄워 동작을 확인하는 과정도 보완했습니다.

**트레이드오프**

스크롤과 레이아웃은 diff나 함수 테스트만으로 확인하기 어려워 브라우저 테스트와 화면 확인이 필요했습니다. 코드 검증 외에 화면을 띄우는 검증 비용을 추가했습니다.

**결과 및 배운 점**

본문만 스크롤되는 동작을 고치고 브라우저 레이아웃 회귀 테스트로 남겼습니다. 변경된 코드를 읽었더라도 화면의 배치와 스크롤을 확인하는 단계가 필요했습니다.

## 개인 프로젝트에서 직접 정한 제품 방향

실무에서 다듬은 workflow를 가져와 두 제품을 만들고 있습니다. 개인 프로젝트에는 QA 더블 체크 요청 단계가 없습니다. 낯선 기술은 에이전트에게 대안과 비용, 동작 원리를 묻고 코드와 문서를 함께 보며 선택합니다.

작업 목표와 plan 검토 → 테스트 작성 → 에이전트 구현과 에이전트 코드 리뷰 → 변경분 테스트, lint, typecheck → 직접 diff 리뷰와 화면 동작 확인 → 전체 CI

![별사대 그룹 게시물과 Game Mate의 프로필 수정 화면](assets/ai-experience/09-product-interactions.png)

*2026년 10월 30일 최신 작업 코드의 실제 화면을 다시 촬영했습니다. 게시물과 계정, 가격은 촬영용 테스트 데이터입니다.*

### 별사대는 대회가 없어도 사진을 모을 수 있게 바꿨습니다

**담당과 기여:** 직접 사용한 경험에서 제품 방향을 다시 정하고, 상시 그룹과 홈/탐색의 요구사항, 기존 데이터와 링크의 보존 조건을 정했습니다. 에이전트의 화면과 API/DB 변경을 검토했습니다.

**문제 상황**

친구끼리 사진을 올리고 투표하는 대회로 시작했습니다. 직접 써 보니 대회가 열릴 때만 들어오는 서비스보다 평소에도 사진을 모을 공간이 있으면 좋겠다고 생각했습니다.

**해결 방법**

대회가 열리는 주기와 사진을 올리는 주기를 분리하기로 했습니다. 기간 제한 없이 사진과 동영상, 합성 이미지를 올리는 상시 그룹으로 바꾸고 대회는 그 안의 선택 기능으로 남겼습니다.

홈에는 가입한 그룹의 새 게시물을 보여 주고 그룹 목록은 MY로 옮겼습니다. 초대 링크 없이 공개 그룹을 찾는 탐색 화면도 추가했습니다. 기존 대회와 사진 데이터, 이전 링크는 보존하고 대회는 그룹 안에서 필요할 때 여는 기능으로 남겼습니다.

![기간제 사진 대회를 상시 그룹으로 바꾼 제품 방향](assets/ai-experience/02-product-direction.png)

화면에서는 사진을 가리는 순위와 실제로 없는 스토리 기능의 테두리를 빼도록 요청했습니다. 참고한 서비스의 장식을 그대로 가져오기보다 사진을 보고 반응하는 흐름에 필요한 요소를 골랐습니다. 공개 그룹은 누구나 내용을 볼 수 있게 하고 비공개 그룹은 가입 승인을 거치게 했습니다.

![별사대의 최신 그룹 생성과 공개 탐색 화면](assets/ai-experience/11-photo-group-flow.png)

*그룹 이름과 소개, 공개 범위를 입력하는 실제 생성 페이지와 공개 그룹 탐색입니다. 격리 환경에서 만든 그룹을 표시합니다.*

**트레이드오프**

기간제 대회는 참가와 투표, 종료 시점이 분명하지만 대회가 없을 때는 공유할 흐름이 제한됩니다. 상시 그룹으로 바꿔 평소에도 올릴 수 있게 한 대신 공개 범위와 가입 승인, 탐색을 계속 관리해야 합니다. 대회를 그룹 안의 선택 기능으로 남기면서 기존 사진과 링크도 보존해 과거 데이터와 새 화면의 연결을 함께 유지했습니다.

**결과 및 배운 점**

상시 그룹과 홈 피드, 공개 탐색을 구현하고 기존 대회와 사진, 이전 링크를 보존했습니다. 직접 사용한 경험을 바탕으로 제품 방향과 필요한 변경 범위를 정했습니다.

출시 후 확인할 가설은 대회가 없어도 친구들과 사진을 모으는지, 초대와 반응이 재방문으로 이어지는지입니다. 가입 → 첫 게시물 → 좋아요 → 재방문 흐름의 측정을 준비했으며 실사용 성과는 아직 확인하지 않았습니다.

### Game Mate는 친추 판매와 코칭을 연결하려고 시작했습니다

**담당과 기여:** 가격과 조건 확인에서 문의까지의 제품 범위와 가입/프로필 흐름을 정했습니다. UI 변경에 필요한 DB 필드와 API/SDK 계약까지 함께 검토했습니다.

**문제 상황**

친추 판매와 게임 코칭을 원하는 사람이 모집 조건과 가격을 확인하고 상대에게 문의할 수 있는 제품을 만들려고 시작했습니다.

**해결 방법**

첫 구현의 완료 지점을 가격과 조건을 확인한 뒤 상대에게 문의하는 데 뒀습니다. 친추 판매는 판매 금액을 표시하고, 코칭은 코치와 수강생 모두 모집 글을 쓸 수 있게 했습니다. 수강료는 시간당, 월 단위, 목표 달성까지로 나누고 1:1 채팅으로 문의하도록 만들었습니다.

가입 때 게임 프로필 연결은 선택 사항으로 뒀습니다. 로그인과 가입 정보 입력은 별도 페이지로 나누고, 짧은 화면에서도 완료 버튼은 하단에 남기고 입력 본문만 스크롤되게 했습니다. 프로필 수정은 Bottom Sheet로 모으고 자기소개 DB 필드와 API 계약, SDK도 함께 바꿨습니다. 운영자 문의와 인증 요청은 관리자 1:1 채팅으로 받도록 했습니다.

가입 정보를 별도 페이지로 나누면 입력에 화면을 사용할 수 있지만 로그인에서 가입 완료까지의 이동과 값 유지를 따로 관리해야 합니다. 프로필 수정은 현재 화면을 유지하는 Bottom Sheet로 모은 대신 열기와 닫기, 수정 중인 값과 확정값의 경계를 처리해야 합니다.

## 글 저장과 캐시 갱신의 실패를 나눴습니다

**담당과 기여:** Game Mate의 Next.js 캐시 도입 범위와 저장 성공의 기준, 재시도/경합 조건을 정했습니다. 에이전트에게 갱신 대안과 비용을 묻고 구현과 DB 통합 테스트를 검토했습니다.

**문제 상황**

검토할 조건은 글은 저장됐는데 캐시 만료 호출만 실패하는 경우였습니다. 이를 저장 실패로 응답하면 사용자가 같은 글을 다시 작성할 수 있습니다.

**해결 방법**

먼저 브라우저의 Query 캐시와 Next.js의 공개 페이지 캐시를 나눴습니다. 화면에서 mutation이 끝났다고 서버의 공개 캐시까지 바뀌는 것은 아니어서, NestJS의 저장 결과를 Next.js Route Handler에 전달해 해당 태그를 만료하는 방식을 선택했습니다.

그다음 저장 성공과 만료 호출 성공의 의미를 나눴습니다. 변경 내용과 만료 태그를 같은 DB 트랜잭션에 저장해 글만 저장되고 재시도할 정보가 사라지는 경우를 막았습니다. 커밋 뒤 만료 호출을 시도하되 호출이 실패해도 저장 성공으로 응답하고, 남은 태그만 다시 처리하도록 했습니다.

![데이터와 캐시 만료 태그를 함께 저장하고 호출 실패는 재시도하는 흐름](assets/ai-experience/04-cache-invalidation.png)

이전 호출을 기다리는 사이 같은 태그에 새 수정이 생길 수도 있습니다. 늦게 끝난 호출이 새 대기 기록까지 지우지 않도록 revision이 같은 경우에만 삭제합니다.

브라우저의 Query 캐시와 Next.js 서버 캐시는 각각 갱신합니다. 공개 글만 쿠키 없이 캐시하고 사용자별 상태는 별도로 조회합니다. 별사대도 공개 SEO 조회에만 서버 캐시를 적용하고 개인화된 Apollo 요청은 no-store로 유지합니다.

**트레이드오프**

일정 시간마다 만료하면 단순하지만 사용자가 방금 수정한 글이 바로 바뀌지 않을 수 있습니다. 저장 직후 태그 만료를 시도하는 방식을 택했고 호출 실패와 재시작, 경합에 대비한 DB 대기 기록과 revision을 추가했습니다.

이 구조도 저장 성공 응답 시 모든 공개 캐시가 최신이라는 보장은 하지 않습니다. 저장을 다시 시키는 대신 실패한 만료 호출만 복구하도록 정했고, 그 사이 공개 화면에 이전 값이 보일 수 있는 비용을 받아들였습니다.

**결과 및 배운 점**

트랜잭션이 롤백되면 글과 대기 기록이 모두 남지 않는지, 만료 호출이 실패해도 글은 저장되고 재시작 뒤 대기 기록을 처리하는지 통합 테스트에 넣었습니다. 이전 호출이 늦게 끝나도 새 revision의 대기 기록을 지우지 않는 조건도 검증 대상으로 정했습니다.

사용자에게 반환하는 저장 결과를 먼저 정한 뒤, 복구해야 할 작업과 경합 조건을 나눠 구현했습니다. 캐시를 붙이는 작업이 저장 실패 안내와 중복 작성에 어떤 영향을 줄지도 함께 검토했습니다.

## 파일을 받는 서버와 검사 범위를 정했습니다

**담당과 기여:** API 서버의 파일 처리 상한에서 S3 직접 업로드로 전환하는 범위와 서비스별 파일 확정 정책을 정했습니다. 에이전트가 작성한 업로드/검사 코드와 실제 S3 검증 결과를 검토했습니다.

**문제 상황**

처음에는 API 서버가 파일을 받으며 동시 처리 3개, 대기 12개로 제한했습니다. 처리 개수를 제한해도 파일 전체가 API를 거친다는 구조는 남아 있어 업로드 경로 자체를 바꿀 필요가 있었습니다.

**해결 방법**

게시물과 채팅 파일, 프로필 사진까지 브라우저에서 S3로 직접 보내도록 바꿔 API가 파일 전체를 메모리에 올리지 않게 했습니다. 경로를 바꾸면서 서버가 어떤 파일을 최종 객체로 인정할지도 별도로 정했습니다.

Game Mate에서는 직접 업로드한 파일의 확정 조건도 검토했습니다. POST 정책에 크기와 형식을 제한하고 HEAD와 파일 앞 4KB를 검사합니다. 검사 뒤 파일이 바뀌는 경우를 막으려고 ETag가 일치할 때만 최종 객체로 복사합니다.

![서버 처리 상한에서 S3 직접 업로드와 파일 확정으로 바꾼 흐름](assets/ai-experience/05-upload-concurrency.png)

**트레이드오프**

별사대는 원본을 보관하고 HEAD로 크기와 형식만 확인합니다. 파일 내용 검사와 별도 객체 복사는 하지 않아 서명 정책이 만료되기 전 같은 키의 파일이 다시 올라올 수 있습니다. 두 서비스가 같은 검증을 한다고 묶지 않고 각 정책의 범위를 구분했습니다.

API가 파일 전체를 받는 부담은 줄지만 업로드와 확정 요청이 나뉘고 S3 정책과 객체 상태를 확인해야 합니다. Game Mate의 검사와 조건부 복사를 별사대의 HEAD 검사와 같은 수준으로 설명하지 않았습니다.

**결과 및 배운 점**

초기에는 S3 대역으로 반복 검증했고 Game Mate의 게시물과 프로필, 채팅 파일은 실제 AWS S3에서도 업로드와 완료, 원본 일치와 Range 조회를 확인했습니다. 10월 26일에는 개발과 통합 테스트의 S3 대역을 제거하고 실행별 객체 경로로 격리하도록 바꿨습니다. 전환 후 통합 검증에는 해당 경로의 AWS 권한 설정이 필요합니다.

업로드 완료 응답만으로 끝내지 않고 실제 S3의 원본 일치와 Range 조회까지 확인했습니다. 파일을 보내는 경로를 바꾸면서 서버 부하뿐 아니라 확정 시점의 검사 범위도 따로 정했습니다.

## 반복되는 판단을 코드 구조와 검사에 남겼습니다

**담당과 기여:** 두 제품의 공유 UI와 앱별 책임을 나누고 반복되는 구현 기준을 skills와 lint rule로 정리했습니다. 공통화 범위와 규칙의 적용 대상을 정하고 에이전트의 구현과 RuleTester/fixture를 검토했습니다.

**문제 상황**

두 제품에서 함께 쓸 UI와 앱마다 달라야 하는 라우팅, 조회, 완료 동작을 구분할 필요가 있었습니다. 파일 배치와 공통 코드 사용처럼 반복되는 판단도 구현마다 다시 설명하지 않도록 남기고 싶었습니다.

**해결 방법**

두 제품을 같은 Yarn workspace 모노레포에서 관리하면서 공통 디자인 시스템과 lint 설정을 분리했습니다. 색과 글자 스타일, 버튼과 입력창, Dialog는 함께 쓰고 피드와 라우팅, 데이터 조회는 앱별로 유지합니다. 공통 UI를 수정하면 두 앱에서 확인합니다.

Game Mate의 작성과 수정은 같은 필드를 입력하지만 완료 후 동작이 달랐습니다. 입력 필드만 공유하고 작성 후 페이지 이동과 수정 후 창 닫기는 각 화면에 남겼습니다. 공통 컴포넌트에 완료 동작의 예외 분기가 계속 늘지 않도록 책임을 나눈 것입니다.

반복된 검토 사항도 같은 방식으로 나눴습니다. 파일 배치와 공통 코드 사용처럼 맥락이 필요한 기준은 skills에 적고 FSD 의존 방향과 공개 API, 컴포넌트의 직접 fetch와 중복 오버레이 상태는 lint rule로 검사합니다. 규칙 자체는 RuleTester와 fixture로 테스트합니다.

![서비스마다 다른 API와 캐시를 유지하고 UI와 lint 기준을 공유한 구조](assets/ai-experience/03-service-architecture.png)

서버 데이터는 별사대의 Apollo와 Game Mate의 TanStack Query에 두고 폼은 RHF와 Zod, 오버레이는 overlay-kit으로 관리합니다.

**트레이드오프**

각 앱에서 UI를 따로 구현하면 독립적으로 바꾸기 쉽지만 같은 수정도 두 번 반영해야 합니다. 공통 디자인 시스템으로 모아 반복을 줄이는 대신 변경 후 두 앱에서 확인해야 합니다. 작성과 수정은 입력 필드만 공유하고 완료 후 페이지 이동과 창 닫기는 각 화면에 남겨 공통 코드에 예외 분기가 쌓이지 않게 했습니다.

정적으로 판정할 수 있는 import 방향과 직접 fetch는 lint rule로 막지만 규칙 자체의 테스트와 예외 관리도 필요합니다. 작성과 수정의 책임을 어디까지 나눌지처럼 맥락이 필요한 판단은 자동으로 고정하지 않고 skills와 코드 리뷰에 남깁니다.

**결과 및 배운 점**

공통 디자인 시스템과 lint 설정을 분리하고 RuleTester와 fixture로 규칙을 검증했습니다. 공통화 범위는 겉모양보다 함께 바뀌는 동작을 기준으로 정하고, 앱마다 다른 책임은 남겨 뒀습니다.

### GraphQL과 REST에서 계약을 확인하는 방법

**담당과 기여:** 서비스별 API 계약과 캐시의 검증 기준을 정했습니다. 타입 생성, 런타임 응답 검사와 실제 캐시 테스트가 각각 무엇을 보장하는지 확인하며 에이전트의 구현을 검토했습니다.

**문제 상황**

별사대는 GraphQL과 Apollo, Game Mate는 REST와 TanStack Query를 사용합니다. 같은 게시물을 목록과 상세가 함께 읽을 때 값이 일치하는지, 페이지를 다시 조회할 때 예전 목록이 섞이지 않는지 확인해야 했습니다. 생성된 타입만으로 서버 계약과 화면 캐시까지 검증했다고 볼 수 없어 확인할 경계를 나눴습니다.

**해결 방법**

별사대는 NestJS의 schema-first GraphQL을 사용합니다. 도메인별 스키마와 resolver를 나누고 웹의 쿼리 문서에서 GraphQL Code Generator로 타입이 붙은 Document를 만듭니다. 모든 연산과 fragment를 서버 스키마와 대조하고 연산 이름이 겹치지 않는지도 검사합니다. 서버는 쿼리 깊이와 필드, alias 수를 제한합니다.

Apollo 캐시는 객체 id를 기준으로 갱신하고 자식 컴포넌트는 `useFragment`로 필요한 값을 읽습니다. 사진 목록의 페이지네이션과 좋아요의 낙관적 갱신은 실제 InMemoryCache에 데이터를 써서 확인합니다. 도메인별 캐시 정책을 합칠 때 같은 필드를 중복 정의하면 실패하도록 했습니다.

RSC의 `PreloadQuery` 결과를 브라우저로 넘기고 화면은 같은 조회를 구독합니다. 개인화된 요청과 공개 SEO 요청을 분리하고, mutation 일부가 저장된 뒤 다른 필드가 실패해 응답의 `data`가 null이 되는 경우도 공개 캐시 만료 조건에서 다룹니다.

Game Mate는 OpenAPI에서 생성한 Orval SDK와 Zod 응답 검증을 사용합니다. ID와 권한, 세션처럼 잘못 읽으면 안 되는 값은 검증에 실패하면 요청을 실패로 처리하고 화면 표시용 필드에만 기본값을 허용했습니다. 조회와 mutation options는 필요한 곳에서 조합하고 서버 데이터를 별도 UI 상태로 복제하지 않게 했습니다.

**트레이드오프**

별사대는 Apollo의 정규화 캐시에서 같은 엔티티를 여러 화면이 읽도록 했습니다. 엔티티 갱신을 공유할 수 있는 대신 ID와 필드별 캐시 정책, 페이지네이션의 병합 조건을 관리해야 합니다. RSC의 사전 조회와 화면 조회도 같은 문서와 변수를 사용하도록 맞췄습니다. Game Mate는 REST SDK와 TanStack Query를 유지해 조회 키와 무효화 대상을 관리합니다. 두 방식을 유지하면서 문서 계약과 타입 생성, 캐시 테스트도 서비스별로 관리하는 비용을 감수했습니다.

응답 전체에 기본값을 넣으면 화면을 계속 보여 주기 쉽지만 ID와 권한, 세션의 잘못된 값까지 정상으로 해석할 수 있습니다. 이 값은 검증 실패 시 요청을 실패로 처리해 일부 화면이 오류로 전환되는 비용을 택했고, 화면 표시용 필드에만 기본값을 허용했습니다.

**결과 및 배운 점**

GraphQL 문서와 fragment를 서버 스키마와 대조하고 페이지네이션과 낙관적 갱신은 실제 InMemoryCache로 확인합니다. 그룹/카테고리/정렬 조건이 다른 목록이 섞이지 않는지, 첫 페이지를 갱신했을 때 이전 뒷페이지가 되살아나지 않는지도 캐시에 값을 쓰고 읽는 테스트로 확인합니다. 타입 생성과 런타임 검증, 화면 캐시 검증의 역할을 나눠 기준으로 남겼습니다.

### 테스트마다 확인할 결과를 나눴습니다

**담당과 기여:** 기대 결과와 실패 조건, 실제 연결할 DB/S3와 fixture의 경계를 정했습니다. 에이전트가 작성한 테스트의 입력과 assertion, 격리와 정리 대상을 검토합니다.

**문제 상황**

함수 테스트나 목의 성공 응답만으로 실제 폼 제출과 DB 저장, 화면 이동까지 보장할 수는 없습니다. 테스트마다 확인할 결과와 실제로 연결할 환경을 정해야 했습니다.

**해결 방법**

![함수와 UI, API와 DB, 브라우저 흐름의 검증 범위](assets/ai-experience/06-test-strategy.png)

함수와 스키마는 Vitest로, UI와 폼은 React Testing Library로 확인합니다. 단순 호출 횟수 대신 실제 폼 입력과 제출값, 캐시에 남은 값을 단언합니다. API는 Supertest 요청 뒤 DB에 저장된 결과를 확인합니다. 대회당 한 표와 동시 가입, 관리자 양도, 캐시 호출 경합처럼 권한과 동시성이 중요한 조건을 포함합니다. 브라우저 흐름은 Playwright로 검증합니다. unit과 integration 테스트는 구현 옆에 두고 설정은 앱이 소유하며 루트에서는 실행만 위임합니다.

웹과 WebView 호스트를 연결한 테스트는 글 작성과 댓글, 채팅과 화면 이동을 확인합니다. OS 기능과 외부 OAuth를 fixture로 대신한 테스트를 실기기나 실제 제공자 연동의 성공으로 해석하지 않습니다. DB와 S3의 테스트 데이터도 실행별로 나누고 해당 실행이 만든 스키마와 객체만 정리합니다.

공통 lint rule도 RuleTester와 fixture로 검사합니다. FSD 경계와 공개 API, 직접 fetch와 오버레이 상태 중복을 규칙으로 옮기되 DOM 관련 규칙은 Expo에 적용하지 않습니다. 작성과 수정의 책임을 어디서 나눌지처럼 맥락에 따라 달라지는 판단은 skills와 코드 리뷰에 남깁니다.

**트레이드오프**

실제 PostgreSQL과 S3를 쓰는 테스트는 환경 준비와 권한이 필요하고 실행별 데이터도 격리해야 합니다. OS 기능과 외부 OAuth는 fixture로 대체해 검증 범위를 제한했습니다. DOM 관련 lint rule도 Expo에는 적용하지 않습니다.

**결과 및 배운 점**

폼 입력과 제출값, 캐시에 남은 값과 DB 저장 결과를 검증하도록 범위를 나눴습니다. 같은 테스트 도구를 쓰더라도 무엇을 실제 환경에 연결했고 무엇을 대체했는지 구분해야 결과를 해석할 수 있었습니다.

## 수집 성공 응답 뒤 실제 데이터도 다시 조회했습니다

**담당과 기여:** 서비스/환경/release별 수집과 재조회 기준을 정하고 MCP 확인 결과를 검토했습니다. 중복 이벤트와 URL의 검색어 수집 문제를 수정 범위에 포함했습니다.

**문제 상황**

Sentry와 Amplitude 설정을 넣은 뒤 전송 성공만으로 수신 내용까지 확인했다고 볼 수는 없었습니다. 서비스와 실행 위치, 배포 버전을 구분해 실제로 저장된 데이터를 확인해야 했습니다.

**해결 방법**

Sentry와 Amplitude 설정을 넣은 뒤 개발용 확인 이벤트를 보내고 MCP로 다시 조회했습니다.

![오류와 Web Vitals, 사용자 행동의 수신 결과를 MCP로 다시 확인하는 흐름](assets/ai-experience/08-monitoring-mcp.png)

수집된 값은 서비스와 실행 위치, 배포 버전을 구분해 남깁니다. Sentry에서는 eventId로 오류를, Amplitude에서는 개발 프로젝트의 페이지뷰를 확인했습니다. 이 과정에서 사진 서비스의 개발 모드 중복 페이지뷰와 자동 URL 수집에 검색어가 붙는 문제를 찾아 고쳤습니다.

Web Vitals는 브라우저 테스트에서 LCP, CLS, INP, FCP, TTFB 전송을 확인합니다. 실제 Sentry로 보낸 검증용 LCP, CLS, INP span도 trace ID로 다시 조회했습니다. 경로의 ID와 검색어는 제거하고 측정값을 남깁니다. 수신 경로를 검증했습니다.

**트레이드오프**

전송 본문을 가로채면 반복 검증은 쉽지만 실제 수집 서비스의 프로젝트와 버전에 저장됐는지는 확인할 수 없습니다. 브라우저 전송 테스트에서 본문을 검사하고, 별도 확인 이벤트를 실제로 보낸 뒤 MCP로 재조회했습니다. 이 경로는 외부 서비스와 인증에 의존하고 확인용 데이터도 실제 프로젝트에 남으므로 일반 테스트와 분리했습니다.

원본 URL과 ID, 검색어를 남기면 개별 상황을 추적하기 쉽지만 사용자 입력도 수집될 수 있습니다. 이를 제거해 원문 수준의 추적 정보는 줄이고 경로 템플릿과 서비스, 환경, release와 trace ID로 확인하도록 했습니다. Web Vitals는 수집하되 fetch와 XHR, 긴 작업의 추가 수집은 꺼서 진단 범위를 제한했습니다. 이 확인용 이벤트 수신은 운영 사용자 성능 개선과 구분합니다.

**결과 및 배운 점**

MCP 재조회로 개발 모드의 중복 페이지뷰와 URL에 남는 검색어를 찾아 고쳤습니다. Web Vitals도 브라우저 전송 테스트와 실제 Sentry 수신을 나눠 확인했습니다. 전송하는 코드의 성공과 저장된 데이터의 내용을 함께 봐야 했습니다.

## 초기 비용과 복구 부담을 함께 비교했습니다

**담당과 기여:** 초기 배포 구조와 비용/복구 책임을 비교하고 DB 배치, 백업과 배포 중단 조건을 정했습니다. 에이전트가 작성한 스크립트와 Terraform 설정을 검토했으며 실제 EC2 구성 적용과 DB 백업 복구는 아직 검증하지 않았습니다.

**문제 상황**

두 서비스를 배포할 때 초기 비용과 DB 관리 범위를 함께 정해야 했습니다. Lightsail과 EC2를 비교했고 처음에는 두 서비스를 EC2 한 대에, DB는 RDS에 두려 했습니다.

**해결 방법**

처음의 EC2와 RDS 구성에서 DB도 같은 EC2로 옮기면 초기 비용을 줄일 수 있지만 DB 운영과 복구를 직접 맡아야 했습니다. 이 비용과 책임을 함께 받아들이고 PostgreSQL도 같은 EC2에서 실행하도록 구성했습니다.

![같은 EC2의 두 서비스와 PostgreSQL, 별도 EBS와 S3 백업 구성](assets/ai-experience/07-deployment.png)

DB를 직접 관리하므로 배포 실패와 DB 복구를 따로 다뤘습니다. DB 데이터는 별도 EBS에 두고 일일 스냅샷과 배포 전 S3 덤프를 준비했습니다. 복구할 덤프를 확보하지 못한 상태에서 스키마를 바꾸지 않도록 덤프 업로드 실패 시 migration을 중단합니다. CI에서 검증한 이미지는 digest로 고정하고 readiness 실패 시 이전 이미지로 되돌리도록 구성했습니다. 이미지 롤백으로 DB까지 되돌릴 수는 없어 migration과 백업은 별도로 다룹니다.

**트레이드오프**

한 대가 멈추면 두 서비스와 DB가 함께 중단되고 백업과 복구를 직접 관리해야 합니다. EBS와 S3 백업을 준비해도 이미지 롤백으로 DB까지 되돌릴 수는 없어 migration과 복구는 따로 다룹니다.

**결과 및 배운 점**

Terraform은 mock provider로 테스트하고 컨테이너 재배포와 재시작, 롤백을 확인할 smoke 테스트를 마련했습니다. 실제 AWS 리소스 적용과 운영 부하, 백업 복구는 별도로 검증해야 합니다.

배포 구성과 실패 시 중단 조건을 준비했습니다. 초기 비용 절감과 함께 늘어난 복구 책임을 명시하고, 설정 테스트와 실제 리소스 적용, 복구 검증을 구분했습니다.
