소개

사용자가 들어온 경로에서 다음 행동으로 넘어가는 흐름을 만들고, 그 흐름이 이어지는지 확인할 수 있게 사용자 행동 측정을 붙여 온 프론트엔드 엔지니어입니다. 가입 회원 약 15만 명, 주간 활성 사용자 약 1만 명의 복지몰과 병원 관리자·백오피스, 글로벌 서비스·CMS를 개발합니다. 2026년 1월부터 사내 유일한 프론트엔드 개발자이며, 4월부터 전사 프론트엔드를 단독으로 담당합니다.

개발할 때는 기준을 먼저 세웁니다. 요구사항에서 빠진 동작은 담당자와 맞추고, 상태와 조회의 책임을 나눠 읽고 검증하기 쉬운 코드를 만듭니다. AI 개발 workflow에서 반복되는 판단은 skills와 lint rule로 남기고, 에이전트가 제출한 코드와 테스트를 읽은 뒤 화면을 띄워 동작을 확인합니다.

지원동기

세이프닥 사용자는 기업 제휴 링크나 마케팅으로 들어와 소셜 로그인·본인인증·소속인증을 거친 뒤에야 예약에 닿습니다. 그 사이에서 제휴 링크의 진입·인증 처리와 이벤트 랜딩에서 쿠폰함·예약으로 넘어가는 흐름을 만들고 앱 WebView의 상담 전화·외부 예약 이동을 네이티브 브릿지로 연결했으며, 담당자가 주도한 실험에서 화면 구현과 사용자 행동 측정을 맡았습니다. 당근의 Engagement 팀은 중고거래·커뮤니티·비즈니스 사이를 채팅·알림·배너로 잇습니다. 더 많은 제품과 사용자가 만나는 곳에서 이 경험을 넓히고, 실험 결과를 동료들과 확인하며 흐름을 고쳐 가고 싶습니다.

주요 경험

  • 유입과 실험: 검색·병원 상세·프로그램 목록·예약신청 버튼의 변경을 비교할 수 있게 Amplitude 기반 A/B 테스트 환경을 구축하고, 이벤트 140개 이상을 새로 붙이거나 고쳤습니다. 소속인증 바이패스 링크·전화상담·룰렛 이벤트 실험에 화면 구현과 사용자 행동 측정으로 참여했습니다.
  • 진입 흐름의 오류: 인증한 사용자가 로그인·본인인증 화면에서 돌아갈 때 앱이 멈추는 오류를 Next.js 라우터 소스까지 따라가 훅 개수가 어긋나는 경로를 찾고, 판정을 렌더 전 proxy로 옮겼습니다.
  • 앱과 웹 연결: 앱에서 열리지 않던 상담 전화 버튼을 네이티브 브릿지로 연결하고, 외부 예약 이동에서 뒤로 가기가 WebView를 닫는 문제를 배포 전에 잡았습니다. 외부에 잘못 안내된 쿠폰함 주소는 앱 핫픽스 대신 Load Balancer 리다이렉트로 풀자고 제안해 합의했습니다.
  • 세 제품을 잇는 흐름: 병원 관리자의 프로그램 등록·검수 요청과 백오피스의 반려·승인 화면을 처음 만들고, 건강검진 예약을 세 제품에 걸쳐 3주 만에 열었습니다.
  • 상태와 조회: 서버 조회 결과를 props로 받아 무효화해도 갱신되지 않던 화면을 prefetch·hydration으로 옮겨, 서버가 준비한 데이터를 클라이언트가 같은 캐시로 이어서 갱신하게 했습니다.
  • 운영 오류: 복지몰에 Sentry를 도입하고, 57명 이상에게 75건 발생한 Bottom Sheet 크래시를 라이브러리 소스까지 추적해 고쳤습니다. 배포 뒤 18일간 0건이었습니다.
  • 개발 환경: 테스트를 도입하고 반복되는 구현 기준을 skills와 자체 lint rule로 옮겼습니다.

검색·병원 상세·프로그램 목록·예약신청 버튼의 변경을 비교할 수 있게 Amplitude 기반 A/B 테스트 환경을 구축했고, 담당자가 주도한 실험에는 화면 구현과 사용자 행동 측정으로 참여했습니다. 검색·프로그램 상세·예약·쿠폰 이벤트 140개 이상을 새로 붙이거나 고쳐, 상세에서 예약·상담으로 넘어가는지와 예약 중 날짜·시간을 고르다 나가는지를 구분하게 했습니다.

  • 소속인증 바이패스 링크: 이 링크로 들어온 사용자의 이탈을 줄이려고 로그인 전에 홈을 둘러보게 한 실험에 참여했습니다. 저는 진입·인증 처리를 개선했고, 랜딩 변경과 원복은 동료가 구현했습니다. 팀의 월간 전후 비교에서 유입 사용자는 16,369명에서 14,169명, 가입 전환율은 26.3%에서 10.6%, 예약 전환율은 0.54%에서 0.48%였습니다. 2025년 12월 31일 로그인 랜딩으로 돌아갔습니다.
  • 전화상담: 플랫폼화 전 최저가 시술과 개인별 전화상담을 제공하던 방식을 복지몰에서도 시도해 보자는 요청을 받아, 진입점과 클릭 위치를 구분하는 source를 구현했습니다. 고객센터 번호를 병원 번호로 오해하는 경우에는 상담시간을 안내했습니다. 실험 결과가 좋지 않아 종료된 뒤 코드를 정리하고 채팅상담으로 되돌렸습니다.
  • 룰렛 이벤트: 진료과 선택 → 룰렛 → 당첨 → 쿠폰함·예약·공유 흐름과 이벤트 7개를 구현했습니다. 출시 전에는 뒤로 가기로 돌아오면 Next.js가 화면 state를 복원해 룰렛이 끝난 상태로 잠기는 문제를 고치고, 이벤트 종료 시각과 누적 당첨자 수를 확정했습니다. 종료 후 페이지 방문 이벤트로 방문 사용자가 없다고 판단해 관련 코드를 제거했습니다.
  • UTM 유실: 신규 가입의 UTM이 빠지자 저장 코드를 stage까지 올렸다가, 코드로 풀면 논리상 허점이 있어 측정 방식을 더 확인했습니다. Amplitude에서 unexpected로 분류된 속성을 expected로 바꾸면 해결되는 것을 찾아 PO에게 공유했고, 코드는 운영 배포 전에 되돌렸습니다.

건강검진 서비스 내재화2026.09 – 현재

건강검진은 아임웹에서 정보를 보고 전화로 문의하던 흐름이었고, 검사 구성·기업지원 코드·예약금 흐름이 비급여 프로그램과 달라 기존 서비스로 관리하기 어려웠습니다. 제휴 병원의 요청으로 개발팀장·부팀장과 빠진 동작과 예외를 확인하며 세 제품의 프론트엔드를 맡았습니다. 9월 9일 개발을 시작해 30일 정식 오픈했습니다. 백오피스에는 검사항목·검진 구성, 기업지원 서류 확인, 결제취소·환불 승인을, 병원 관리자에는 검진 예약 관리와 결제취소 요청 접수를, 복지몰에는 검사 선택·기업 검진 코드·예약금 결제를 만들었습니다.

토스페이먼츠 결제창은 모바일에서 결과를 리다이렉트로만 돌려줘, 결제창을 다녀오면 페이지가 새로 열리고 입력이 사라졌습니다. 앱 전역 Zustand persist 대신 입력값을 결제 시도의 orderId와 함께 sessionStorage에 저장하고, 같은 주문이며 현재 Zod 스키마를 통과한 값만 한 번 복원해 이전 결제 시도나 옛 폼 값이 덮이지 않게 했습니다. 결제 준비부터 결제창이 열릴 때까지는 한 mutation으로 묶어 중복 신청을 막았고, 입력 복원과 승인 요청 실패 시 예약 목록 이동은 dev API 서버 E2E로 확인했습니다.

  • 선택 UX: 선택 수를 채우면 다음 그룹을 자동으로 열자는 요청에, 기존 선택을 수정할 때도 화면이 넘어가는 문제를 짚었습니다. 담당자와 논의해 미선택 chip만 비활성화하고, 빠져 있던 비활성 상태 디자인도 요청해 반영했습니다.
  • 부분 실패: 검사항목 일괄 저장은 일부 요청만 성공할 수 있었습니다. 이전 폼으로 재시도하면 이미 생성된 항목이 다시 전송되므로, 성공·실패 모두 서버 목록을 다시 받아 발급된 ID를 폼에 반영했습니다.
  • API 계약: 검진 구성 수정이 거절된 사례에서 삭제된 검사항목까지 조회 응답에 포함되는 것을 찾아 백엔드에 전달했고, null 필드와 요청값은 dev API 서버 응답에 맞췄습니다.

입사 당시에는 서버 컴포넌트의 ensureQuery 결과를 render props로 전달했습니다. 화면이 Query 캐시를 구독하지 않아 무효화해도 갱신되지 않았고, 조회 조건만 바꿀 때도 서버 렌더링 결과를 다시 받아야 했습니다. 2025년 5월 예약 화면부터 prefetch·hydration으로 옮겨, 서버는 초기 HTML에 필요한 데이터를 준비하고 화면은 useQuery·useSuspenseQuery로 같은 캐시를 구독해 이후 조회·갱신·무효화를 처리하게 했습니다.

  • 수집 앱: 채용 사이트 로그인 → 수집 → 중복 확인 → 업로드를 공통 단계와 사이트별 adapter로 나누는 Electron 초기 구조를 설계하고 잡플래닛·게임잡을 연동했으며, 지원자 한 명의 오류가 전체 수집을 멈추지 않게 했습니다. NestJS 도입은 Electron main 프로세스에 무겁다는 CTO 피드백으로 닷새 만에 걷어냈고, 모듈 경계·생성자 주입은 참고해 factory에서 조립했습니다. 이후 동료가 코드를 상당 부분 다시 작성했고, 제 담당 범위는 초기 구조와 사이트 연동입니다.
