소개

사용자 경험과 제품의 맥락을 살피며, 기능이 늘어나도 읽고 검증하기 쉬운 코드를 만드는 프론트엔드 엔지니어입니다. React·TypeScript·Next.js로 ATS 기반 채용솔루션과 의료복지 플랫폼을 개발했습니다.

개발할 때는 기준을 먼저 세웁니다. 요구사항에서 빠진 동작은 담당자와 논의하고, 새로운 기술은 이점과 전환·유지 비용을 살펴 선택합니다. 코드를 읽으며 상태·데이터 흐름과 변경 영향을 확인하는 것도 검증의 일부로 봅니다.

AI 개발 workflow를 개선하며 반복되는 검토 기준은 skills와 lint rule에 남깁니다. 에이전트가 제출한 코드와 테스트에서 요구사항 누락과 잠재적인 오류를 검토한 뒤, 화면을 띄워 동작을 확인합니다. 출시 뒤에는 Sentry로 수집된 오류와 VOC로 접수된 오류를 추적하고 대응합니다.

건강검진 서비스 내재화2026.09 – 현재

건강검진은 아임웹에서 정보를 보고 전화로 문의해야 했고, 기존 서비스에서는 검진 프로그램과 예약을 관리하기 어려웠습니다. 제휴 병원의 요청으로 복지몰·병원 관리자·백오피스에 검사항목 구성·기업지원 코드·예약금 결제를 추가했습니다. 세 제품의 프론트엔드를 맡아 9월 9일부터 개발했고, 30일 정식 오픈했습니다.

  • 백오피스: 검사항목을 등록하고 필수·선택 검사를 구성하는 기능을 만들었습니다. 기업지원 코드와 서류 확인, 결제내역 조회, 결제취소·환불 승인도 추가했습니다.
  • 병원 관리자: 검진 프로그램 조회와 예약 관리를 추가했습니다. 건강검진만 운영하는 병원에는 기존 프로그램 등록·검수 메뉴를 숨기고, 병원이 직접 처리할 수 없는 예약금 결제취소는 요청 접수로 안내했습니다.
  • 복지몰: 기존 프로그램 상세와 예약 신청·상세에 건강검진 기능을 추가했습니다. 검사 선택, 기업 검진 코드 입력, 토스페이먼츠 예약금 결제를 연결하고 사용자 부담금과 기업지원 내용을 구분해 보여줬습니다.
  • 검사항목 선택: 선택 수를 채우면 다음 그룹으로 이동하자는 요청에 대해, 기존 선택을 수정할 때도 강제 이동하는 불편을 짚었습니다. 담당자와 논의해 미선택 chip만 비활성화하는 방식으로 구현하고, 빠진 비활성 상태의 디자인도 요청했습니다.
  • 부분 저장·결제 실패: 일괄 등록 후 서버 목록을 다시 받아 저장된 항목의 ID를 폼에 반영하고 중복 등록을 막았습니다. 결제 입력은 Zustand persist 대신 orderId와 함께 sessionStorage에 저장해, 같은 주문이며 Zod 검증을 통과한 값만 한 번 복원합니다. 결제창에서 실패로 돌아올 때의 입력 복원과 승인 실패 시 예약 목록 이동은 dev API 서버 E2E로 확인했습니다.
  • 검진 구성 수정이 거절됐을 때, 응답에 삭제된 검사항목이 포함된 것을 찾아 백엔드에 전달했습니다. null 필드와 요청값도 dev API 서버에서 확인하며 맞췄습니다.

  • 검색·상세·예약·쿠폰 이벤트 140개 이상을 새로 붙이거나 고쳤습니다. 버튼의 진입 위치와 예약 중 날짜·시간 선택, 이탈을 구분하도록 전송 시점과 속성을 맞췄습니다.
  • 소속인증 바이패스 링크 (2025.09 – 12): 유입 사용자의 이탈을 줄이려고 로그인 전에 홈을 둘러보게 한 실험에 참여했습니다. 저는 진입·인증 처리를 개선했고, 랜딩 변경과 원복은 동료가 구현했습니다. 팀의 전후 비교에서 가입 전환율은 26.3%→10.6%였으며, 12월 31일 로그인 랜딩으로 돌아갔습니다.
  • 전화상담 (2026.06 – 07): 플랫폼화 전 최저가 시술과 개인별 전화상담을 제공하던 방식을 복지몰에서도 시도했습니다. 플로팅 버튼·하단 내비·말풍선 진입점과 클릭 이벤트의 source를 구현하고 상담시간을 안내했습니다. 실험 결과가 좋지 않아 종료된 뒤, 7월 27일 코드를 정리하고 채팅상담으로 되돌렸습니다.
  • 룰렛 (이벤트: 2026.08.04 – 08.11): 진료과 선택 → 룰렛 → 당첨 → 쿠폰함·예약·공유 흐름과 이벤트 7개를 구현했습니다. 종료 후 페이지 방문 이벤트로 방문 사용자가 없다고 판단하고, 10월 7일 관련 코드를 제거했습니다.

복지몰·관리자 서비스의 SSR·데이터 조회 개선2025.05 – 현재

입사 당시에는 서버 컴포넌트의 ensureQuery 결과를 render props로 전달했습니다. 화면이 Query 캐시를 구독하지 않아 무효화해도 갱신되지 않았고, 조회 조건을 바꿀 때도 router.push·router.replace로 서버의 렌더링 결과를 다시 받아야 했습니다.

2025년 5월 예약 화면부터 prefetch·hydration으로 바꾸고 다른 화면으로 확대했습니다. 서버는 초기 데이터를 준비하고 화면은 useQuery·useSuspenseQuery로 같은 캐시를 구독합니다. 초기 렌더링을 유지하면서 이후 조회·갱신·무효화를 클라이언트에서도 처리할 수 있게 됐습니다.

SEO는 다른 서비스와 비교해 메타데이터와 JSON-LD를 설계했습니다. 정해진 값이 없을 때 직접 채워도 되는지 확인한 뒤, 병원·시술 정보와 인근 지하철역 등 검색에 필요한 정보를 넣었습니다. Streaming 도입에 맞춰 htmlLimitedBots도 설정해 일부 미리보기 봇에는 메타데이터를 <head>로 보내고 일반 사용자의 화면은 스트리밍을 유지했습니다.

  • 로컬 개발 속도를 높이기 위해 Next.js 14→16·React 18→19로 전환했습니다. Turbopack 도입과 Next.js 16 자체의 개발 속도 개선을 함께 고려했습니다. 전환 과정에서는 비동기 API와 달라진 캐시 동작에 맞춰 기존 코드를 수정하고, 링크 직접 진입·뒤로가기·새로고침을 확인했습니다.
  • TypeScript 7 네이티브 체커를 병행해 복지몰의 타입 검사 시간을 실측 12.5초에서 1.9초로 줄였습니다. 타입 정보까지 사용하는 lint는 검사 시간이 3.3배 늘어 도입을 보류했습니다.

Next.js 라우팅·캐시 오류 대응2026.04 – 현재

  • 관리자 검색 오류는 localhost의 dev에서는 나타나지 않아 build 후 start로 재현했습니다. 목록 7개 중 6개에서 확인하고 라우터 캐시 이슈까지 추적했습니다. 서버가 검색 조건을 읽지 않는 화면이므로 같은 경로의 조건 변경은 History API로 처리해 불필요한 RSC 재요청도 줄였습니다. 수정 뒤 9월 28일까지 같은 증상의 재보고는 없었습니다.
