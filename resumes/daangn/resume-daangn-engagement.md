## 소개

복잡한 상태와 사용자 흐름을 단순하게 설계하는 데 강점이 있는 프론트엔드 엔지니어입니다. 예약·결제·쿠폰을 개발하며 어떤 값을 어디서 관리하고 언제 바꿀지 정리해 왔습니다. 요구사항이 바뀌어도 코드를 읽고 수정하기 쉬운 구조를 만듭니다.

개발할 때는 제품의 맥락과 검증 기준을 먼저 확인합니다. 요구사항에서 빠진 동작과 사용성 의견은 담당자와 논의하고 반영합니다. AI 개발 workflow에서는 제출된 코드와 테스트를 읽고 화면을 띄워 동작을 확인하며, 반복되는 판단은 skills와 lint rule에 남깁니다.

## 지원동기

예약·결제처럼 상태와 조건이 얽힌 기능을 단순한 구조로 풀어내는 일을 즐깁니다. Engagement 팀은 채팅·알림·배너로 여러 제품을 연결하고, 사용자 상태에 따라 다른 경험을 만듭니다. 이런 일을 동료들과 고민하며 재미있게 할 수 있겠다고 생각해 지원했습니다. 제가 해 온 상태 설계와 UX 개선, 실험 환경 구축 경험으로 사용자의 다음 행동이 자연스럽게 이어지도록 돕고 싶습니다.

- **개발 범위:** 백오피스의 검사항목·검진 구성·기업지원 서류 확인·결제취소·환불 승인, 병원 관리자의 검진 예약 관리·결제취소 요청 접수, 복지몰의 검사 선택·기업 검진 코드·예약금 결제를 개발했습니다.
- **결제 상태:** 결제 준비부터 토스페이먼츠 결제창을 열 때까지 한 mutation으로 묶어 중복 신청을 막았습니다. 모바일에서 결제 실패 후 돌아오면 입력이 사라져, `orderId`와 입력값을 `sessionStorage`에 저장했습니다. 같은 주문이며 Zod 검증을 통과한 값만 한 번 복원해 이전 결제 시도의 입력이 덮이지 않도록 했습니다. 입력 복원과 승인 요청 실패 시 예약 목록 이동은 dev API 서버 E2E로 확인했습니다.

#### 데이터 조회 전환과 Next.js 오류 대응 | 2025.05 – 현재

입사 당시에는 서버 컴포넌트의 `ensureQuery` 결과를 render props로 전달했습니다. 화면이 Query 캐시를 구독하지 않아 무효화해도 갱신되지 않았고, 조회 조건만 바꿀 때도 서버 렌더링 결과를 다시 받아야 했습니다. 2025년 5월 예약 화면부터 prefetch·hydration으로 옮겨, 서버는 초기 HTML에 필요한 데이터를 준비하고 화면은 `useQuery`·`useSuspenseQuery`로 같은 캐시를 구독해 이후 조회·갱신·무효화를 처리하게 했습니다.

관리자 목록에서는 조회 조건이 주소에 붙은 채 들어오면 검색이 멈췄습니다. localhost의 `dev` 실행에서는 나타나지 않아 `build` 후 `start`로 목록 7개 중 6개에서 재현했고, 업스트림 이슈와 수정 PR에서 라우터 캐시 문제를 확인했습니다. 서버가 검색 조건을 읽지 않는 화면의 같은 경로 변경은 History API로 처리했습니다. 수정 뒤 9월 28일까지 같은 증상의 재보고는 없었습니다.

- **숨겨지는 화면의 폼:** `cacheComponents` 적용 뒤 뒤로 가기로 돌아온 신청 폼에 이전 입력이 남았습니다. `<Activity>`가 화면을 언마운트하지 않고 숨기는 동작을 확인해, 숨겨질 때도 실행되는 layout effect cleanup에서 공용 폼 훅이 마운트 시점의 기본값으로 되돌리게 했습니다.
