#### 코딩 에이전트 작업 방식과 테스트 보강 | 2026.04 – 현재

4월부터 코딩 에이전트를 본격적으로 사용했습니다. 파일 위치나 상태를 어디에 둘지 같은 지적이 반복돼, 에이전트가 의도와 다르게 구현한 부분의 기준을 스킬에 남겼습니다. 정적으로 검사할 수 있는 기준은 ESLint 규칙으로 옮겼습니다. 현재 기능 개발·리팩터링은 제출된 제품 코드와 테스트를 읽고, 부족한 부분을 짚어 수정본을 다시 확인합니다.

**티켓·plan 검토 → 테스트 작성 → 에이전트 구현·에이전트 코드 리뷰 → 변경분 테스트·lint·typecheck → 제 diff 리뷰·로컬 화면 확인 → 전체 CI(테스트·knip·lint) → QA 더블 체크 요청** 순서로 진행하고, 문제가 나오면 앞 단계로 돌아갑니다.

- 새 기능의 기대 동작은 BDD 형식의 `*.spec`에 적어 컴포넌트별로 빠진 조건을 확인합니다. 운영·QA 오류는 `*.test`로 재현하고, 새 패턴의 테스트는 제품 코드를 일부러 깨뜨려 실패하는지 확인한 뒤 넣습니다.
- **lint·계약 검사(2026.08 – 09):** 복지몰의 직접 import 경고 **271건**을 정리해 9월 1일 error로 올렸습니다. 9월 29일에는 레이어 루트·동적 import를 놓치는 규칙과 테스트를 보완하도록 지시하고 결과를 확인했습니다. 추가한 테스트를 수정 전 규칙에 돌렸을 때 **8건이 실패**했습니다. 글로벌 서비스의 테스트도 응답 스키마 위반이 경고로 끝나지 않도록 바꾸고, 목 데이터를 틀리게 만들어 실패를 확인했습니다.
- worktree마다 전체 검사를 반복하니 CPU 경합이 생겼습니다. 로컬 lint·테스트는 변경 파일과 영향 범위를 중심으로 돌리고, 타입 검사는 저장소에 따라 패키지 또는 앱 단위로 유지합니다. 전체 검사는 CI에서 수행하고 결과까지 확인합니다. 타입 인지 lint는 검사 시간이 **3.3배** 늘어 도입을 보류했습니다.
