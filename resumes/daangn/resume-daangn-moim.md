건강검진은 아임웹에서 정보를 본 뒤 전화로 문의하는 별도 흐름이었습니다. 한 제휴 병원이 세이프닥에서 검진 예약을 받으려 했지만, 기존 비급여 프로그램의 등록·검수·예약 구조로는 검사 구성, 기업지원 검진, 예약금 결제를 처리하기 어려웠습니다.

개발팀장·부팀장과 전달받은 요구사항의 빠진 동작과 예외를 확인하며 **Back-Office·병원 관리자·복지몰에 걸친 건강검진 기능의 프론트엔드를 맡았습니다.** 9월 9일부터 두 주 동안 순차 개발해 **9월 23일 운영 배포, 9월 30일 정식 오픈**했고, 이후 운영 요청을 반영하고 있습니다.

- **운영팀의 검진 관리:** 검사항목과 필수·선택 검사 그룹을 등록하고 프로그램별 검진 구성을 관리하도록 만들었습니다. 기업지원 검진의 지원코드·서류 확인, 결제내역 조회와 예약금 결제취소·환불 승인도 구현했습니다. 운영팀이 저장한 검진 구성을 병원 관리자와 복지몰 상세·선택 화면에서 함께 읽도록 했습니다.
- **병원별 관리 범위:** 검진 프로그램은 운영팀이 등록하고 병원은 조회하도록 구분했습니다. 검진만 운영하는 병원에는 프로그램 등록·검수 메뉴를 숨기고, 다른 진료과도 운영하는 병원에는 기존 메뉴를 유지했습니다. 검진 예약 상세와 예약 취소를 처리하되, 예약금 결제를 직접 취소할 수 없는 조건은 ‘결제취소 요청 접수’로 안내했습니다.
- **사용자의 신청·예약 조회:** 검진 상세, 검사 선택, 공단 검진 여부·주소·기업 검진 코드 입력, 예약금 결제와 예약 상세를 개발했습니다. 비급여와 같은 상세 경로를 쓰되 내부 화면과 신청 폼을 나누고 상단바·인증 후 이동은 공유했습니다. 예약 상세에서는 선택 검사·배송지와 사용자 부담 예약금·기업지원 내용을 구분해 표시했습니다.
- **일괄 저장의 부분 실패:** 검사항목 여러 건 중 일부만 저장되면 재시도 때 이미 생성된 항목을 다시 등록할 수 있었습니다. 성공·실패 모두 서버 목록을 다시 받아 발급된 id와 저장 결과를 폼에 반영하도록 했습니다. 검진 구성을 비우는 요청이 실패한 뒤에도 남은 구성을 다시 삭제할 수 있도록 저장 흐름을 정리했습니다.
- **결제 시도별 입력 복원:** Zustand persist에 프로그램 ID·신청 내용을 남기던 방식은 이전 결제 시도나 옛 폼 값이 복원될 수 있었습니다. `orderId`와 현재 스키마를 확인하는 `sessionStorage`로 바꾸고, 같은 탭에서 돌아올 때 검사 선택·주소·희망 일시를 한 번만 복원하도록 했습니다. 주문 생성부터 토스페이먼츠 결제창이 열릴 때까지 버튼을 잠갔습니다. 결제창 실패 복귀의 입력 복원과 승인 요청 실패의 예약 목록 이동은 dev API 서버 E2E로 확인했습니다.

#### Sentry 도입과 운영 오류 추적 | 2026.08 – 09

복지몰의 브라우저·서버·Edge 오류를 모으고, 배포 버전과 사용자 영향을 확인할 수 있도록 Sentry 도입을 맡았습니다. 8월 19일부터 구현해 27일 운영에 배포한 뒤 수집 정책과 릴리스 연결을 보완했습니다.

- 화면이 뜨지 않는 오류, 작업이 막히는 오류, 재시도할 수 있는 실패를 나눠 에러 레벨을 정했습니다. 정상적인 세션 종료와 갱신 실패를 구분하고, 같은 오류가 API 처리·Error Boundary·서버 수집을 거치며 중복 전송되지 않도록 했습니다.
- `sendDefaultPii: false`만으로 헤더·쿠키·본문·URL을 모두 막을 수 없어 SDK 소스를 따라가며 전송 경로를 확인했습니다. 이벤트·breadcrumb·transaction·span에서 의료 정보와 인증 정보가 실리는 값을 제거하고, 새 수집 항목이나 열린 설정을 놓치지 않도록 타입과 단위 테스트로 고정했습니다.
- release와 브라우저 소스맵을 연결하고 Sentry API에서 artifact bundle 생성까지 확인했습니다. 서버 소스맵은 업로드 502가 발생해 8월 31일부터 제외했고, 서버 스택이 minify된 채 남는 비용을 받아들였습니다. LCP·FCP·TTFB가 실제 브라우저 envelope에 실리는지 E2E로 확인하고, 에이전트가 운영 이슈를 조회할 수 있도록 사내 Sentry MCP도 연결했습니다.
- 수집한 Bottom Sheet 드래그 크래시를 라이브러리의 null ref 접근까지 추적해 버전을 올렸습니다. 바뀐 snap point 규칙은 공통 Root에서 변환해 기존 사용처를 유지했습니다. 수정 전 **57명 이상에게 75건** 발생한 오류 그룹은 **9월 10일 수정 배포 뒤 9월 28일까지 0건**이었습니다.

#### 테스트 체계 재구축과 두 제품을 잇는 E2E | 2026.07 – 현재

기존 테스트가 실제 제품의 제출 경로나 서버 계약을 검증하지 못해 정리한 뒤, 7월 20일부터 관리자 서비스 모노레포와 복지몰의 테스트 체계를 다시 구성했습니다. 테스트 작성은 에이전트에 맡기고, 저는 계층별 검증 범위를 정하고 기대 동작·누락 조건과 검증 결과를 확인합니다.

- 순수 함수·스키마는 Vitest, 실제 UI·Query·폼 연결은 React Testing Library·MSW, 서버 계약은 dev API 테스트, 브라우저 흐름은 Playwright로 나눴습니다. 새 기능은 BDD 형식의 `*.spec`에 컴포넌트별 기대 동작을 적고 빠진 조건을 확인합니다. 운영·QA 오류는 `*.test`로 재현하고, 새 패턴의 테스트는 제품 코드를 일부러 깨뜨려 실패하는지 확인한 뒤 넣습니다.
- 제출 로직을 복제해 제품이 깨져도 통과하던 Harness를 걷어내고 실제 등록 Drawer를 렌더하도록 바꿨습니다. 무엇이든 200으로 받던 Mock도 확인한 서버 제약에 맞춰 잘못된 입력을 거절하게 했습니다. 기대값을 제품의 변환 함수로 계산하지 않아, 변환이 잘못돼도 테스트까지 같은 답을 내지 않도록 했습니다.
- 등록·수정 Drawer를 나누는 리팩터링에서 기대 payload와 UI 동작을 먼저 고정해 **잠복 버그 2건**을 찾았습니다. 등록 후 Drawer가 닫히지 않는 동작과, URL로 직접 진입하면 수정 payload의 타입이 어긋나는 동작을 수정했습니다.
- **두 앱의 업무 흐름(2026.09):** dev API 서버를 사용해 병원 관리자에서 프로그램을 등록하고 Back-Office에서 검수중·반려·승인까지 이어지는 E2E를 추가했습니다. 앱별 로그인 준비를 분리하고 테스트마다 서버 상태를 고정해 실행 순서에 의존하지 않도록 했습니다. 검진 결제도 선택한 실패 경로를 브라우저에서 확인했습니다.
- dev API 계약 테스트는 Mock을 쓰는 일반 실행과 분리하고, PR을 막지 않는 별도 단계로 돌립니다. E2E는 CI 밖에서 실행합니다. 서버 컴포넌트나 브라우저에서만 재현되는 문제를 jsdom에 억지로 넣기보다, 순수 로직을 떼거나 실제 브라우저에서 확인하는 쪽을 선택했습니다.
