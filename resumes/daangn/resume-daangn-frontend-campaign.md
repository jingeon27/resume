## 소개

React와 TypeScript로 복지몰과 관리자 서비스를 개발하는 프론트엔드 엔지니어입니다. 사용자가 인증을 거쳐 예약하고 결제하는 흐름과, 병원과 운영팀이 이를 관리하는 화면을 함께 맡고 있습니다. 직접 써 보며 찾은 불편과 요구사항에 빠진 동작은 담당자와 논의해 반영합니다. 출시 후에는 Sentry에 수집된 오류와 VOC를 확인해 문제를 고칩니다.

현재 사내 유일한 프론트엔드 개발자로 개발과 QA, 병원 관리자와 백오피스의 화면 디자인을 맡고 있습니다. AI로 구현하되 코드와 테스트를 먼저 읽고 화면을 직접 확인합니다. 반복해서 지적하는 내용은 skills와 lint rule에 남겨 다음 작업에 반영합니다. 개인 프로젝트에서는 API와 DB, 배포 구성도 맡고 있습니다.

#### 건강검진 예약 | 2026.09 – 현재

건강검진은 아임웹에서 정보를 확인한 뒤 전화로 문의해야 했습니다. 검사 구성과 기업지원 코드, 예약금 처리 방식이 비급여 프로그램과 달라 기존 서비스로 관리하기 어려웠습니다. 제휴 병원의 요청으로 기능을 개발하면서 복지몰, 병원 관리자, 백오피스의 프론트엔드를 맡았습니다. 개발팀장, 부팀장과 빠진 동작과 예외를 확인해 반영했고, 9월 9일 개발을 시작해 23일 운영에 배포한 뒤 30일 정식 오픈했습니다.

- 모바일 토스페이먼츠 결제창은 리다이렉트로 결과를 돌려줘, 돌아왔을 때 작성하던 값이 사라졌습니다. 입력값을 결제 시도의 `orderId`와 함께 sessionStorage에 저장하고, 같은 주문의 값이면서 Zod 검증을 통과한 경우에만 한 번 복원했습니다. 결제 준비와 결제창 열기는 한 mutation으로 묶어 중복 신청을 막았습니다.
- 검사를 정해진 수만큼 고르면 다음 그룹을 자동으로 열자는 요청이 있었습니다. 기존 선택을 수정할 때도 화면이 넘어가는 점을 짚고 담당자와 논의했습니다. 선택 수를 채운 그룹에서는 아직 고르지 않은 chip을 비활성화하도록 바꾸고, 빠져 있던 디자인도 요청해 반영했습니다.
- 검사항목 일괄 저장 중 일부 요청만 성공하면, 서버 목록을 다시 받아 발급된 ID를 폼에 반영했습니다. 재시도할 때 이미 저장된 항목이 중복 등록되지 않도록 했습니다.

#### 상담 채팅 | 2026.06 – 현재

관리자 서비스의 상담 채팅을 맡아 유저 상담 채팅의 입력과 실시간 연결을 개선하고, 병원 상담 채팅을 새로 만들었습니다. 대화 화면과 입력창, 실시간 연결 코드는 공유 패키지로 옮겼습니다. 백오피스와 병원 관리자는 각자의 API 함수를 전달해 같은 채팅 코드를 사용합니다.

- 채팅방의 SSE 연결은 React 외부 스토어에서 관리하고 `useSyncExternalStore`로 구독합니다. 토큰 만료 시 갱신하고, 연결이 끊기면 `last-event-id`를 기준으로 이어 받습니다. 메시지와 읽음 상태는 Query 캐시에 바로 반영합니다. 읽음 요청은 500ms 동안 모아 화면에 보인 메시지의 마지막 순번을 보냅니다.
- 첫 페이지 조회 전에 SSE를 연결해 지난 이벤트를 다시 받던 문제는 초기 조회가 끝난 뒤 마지막 순번부터 이어 받도록 고치고 회귀 테스트를 추가했습니다.
- 한글 조합 중 Enter로 메시지가 중복 전송되는 문제는 `isComposing`과 전송 중 가드로 막았습니다.

#### AI 개발 workflow와 테스트 | 2026.04 – 현재

2026년 4월부터 코딩 에이전트로 구현하고 있습니다. 같은 요구사항에도 파일 배치나 공통 코드 사용법이 달라지는 곳은 FSD 구조를 저장소에 맞게 정리했습니다. 리뷰에서 반복해서 지적한 내용은 skills에 남기고, import 방향과 공개 API, queryKey 사용은 lint rule로 검사합니다. 7월부터는 테스트 코드를 도입했습니다.

티켓과 plan 검토 → 테스트 작성 → 에이전트 구현과 에이전트 코드 리뷰 → 변경분 테스트, lint, typecheck → 직접 diff 리뷰와 화면 동작 확인 → 전체 CI(테스트, knip, lint) → QA 더블 체크 요청

- 함수와 스키마는 Vitest, UI와 폼은 React Testing Library, 브라우저 흐름은 Playwright로 테스트합니다. 새 기능은 BDD 형식의 `*.spec`에 컴포넌트별 기대 동작을 적고, 빠진 조건이 없는지 검토합니다. 운영이나 QA에서 발견한 오류는 `*.test`에 재현합니다. 새 테스트 패턴은 제품 코드를 일부러 깨뜨렸을 때 실패하는지 확인합니다. API 연동은 dev API 서버를 우선하고, 준비하기 어려운 조건에만 MSW를 씁니다.
- 테스트용 QueryClient가 앱과 다르게 오류를 처리하던 문제를 고쳤습니다. 설정을 앱과 맞추고, 처음 데이터를 받지 못한 경우와 기존 데이터를 재조회하다 실패한 경우를 나눠 확인했습니다.
- 공통 Bottom Sheet를 바꿀 때 에이전트가 제목과 버튼까지 스크롤 영역에 넣은 것을 diff를 읽고도 놓쳤습니다. 본문만 스크롤되게 고치고 브라우저 레이아웃 회귀 테스트를 추가했습니다.
- 복지몰에서 다른 화면의 코드를 직접 참조하던 62건과 슬라이스 내부를 직접 import하던 경고 271건을 정리했습니다. 이후 같은 참조가 생기면 lint error가 나도록 했습니다. 자체 lint rule은 RuleTester와 `__fixture__`, mock으로 테스트합니다.
- 병렬 worktree마다 전체 검사를 반복해 CPU 부하가 커져, 작업 중에는 변경분과 영향 범위를 먼저 검사하고 타입 검사는 앱과 패키지 단위로 진행합니다.

#### Next.js와 상태 관리 | 2025.05 – 현재

입사 당시에는 서버 컴포넌트가 `ensureQuery`로 조회한 결과를 render props로 화면에 전달했습니다. 화면이 Query 캐시를 구독하지 않아 캐시를 무효화해도 내용이 바뀌지 않았습니다. 2025년 5월 예약 화면부터 prefetch와 hydration 구조로 바꿔 나갔습니다. 서버는 초기 HTML에 필요한 데이터를 준비하고, 클라이언트는 같은 캐시를 구독해 이후 조회와 갱신을 처리하도록 했습니다.

- 인증을 마친 사용자가 로그인이나 본인인증 화면에서 돌아갈 때 앱이 멈췄고, 조사 당시 53명에게 68건의 오류가 발생했습니다. Next.js 소스를 확인하니 서버 컴포넌트의 `redirect()`가 하드 내비게이션으로 처리되면서 AppRouter의 렌더를 중단시켰고, 이때 렌더마다 훅 개수가 달라졌습니다. 진입 조건 확인과 리다이렉트를 React 렌더 전에 실행되는 proxy로 옮겼습니다.
- 관리자 목록에서 검색이 되지 않는 오류는 개발 서버에서 재현되지 않았습니다. build 후 start로 실행해 목록 7개 중 6개에서 재현하고, 업스트림 이슈와 수정 PR을 통해 라우터 캐시가 원인임을 확인했습니다. 서버가 읽지 않는 조회 조건은 History API로 변경하도록 고쳤고, 수정 뒤 9월 28일까지 같은 증상은 다시 보고되지 않았습니다.
- 예약 화면의 가족과 날짜 값이 Query 캐시, Zustand, 로컬 상태에 흩어져 있어 가족을 추가하면 선택한 일시가 어긋났습니다. 서버 목록은 Query, 입력 중인 값은 React Hook Form으로 관리하고 제출 조건은 Zod로 검증하도록 바꿨습니다. 519줄이던 예약 대상 선택 컴포넌트는 55줄로 줄었습니다.
- 공통 검색 필터에 화면별 예외가 쌓여, 각 화면에서 필요한 필터를 조합하도록 바꾸고 27개 화면에 적용했습니다. JSX가 일부 반복되는 것은 감수했습니다. Ant Design Form에는 재귀 조건부 타입과 infer를 사용한 `createTypedForm<T>`를 만들어 중첩 필드명과 값의 타입을 검사합니다.
- 공통 UI는 Headless UI에서 Radix UI로 옮겼습니다. 컴포넌트를 조합하기 쉽고 접근성 primitive를 활용할 수 있다는 점을 보고 선택했습니다. Bottom Sheet는 Compound Components와 overlay-kit으로 바꿔 본문과 하단 버튼이 같은 폼을 사용하도록 했습니다.

### 사진 커뮤니티와 글로벌 게임 커뮤니티 | 2026.10 – 현재

친구들과 사진을 모으는 별사대와 글로벌 게임 커뮤니티 Game Mate를 혼자 만들고 있습니다. 제품 방향과 화면, API, DB, 테스트 기준과 배포 구성을 직접 정하고, 구현과 테스트 작성은 코딩 에이전트에 맡깁니다. 익숙하지 않은 기술은 에이전트에게 장단점과 동작 원리를 묻고 코드와 문서로 확인한 뒤 선택합니다. 두 서비스 모두 공개 전이며 초기 사용자 검증을 준비하고 있습니다.

- 사용자가 무엇을 할 수 있는지, 공개 범위와 권한, 업로드 제한, 검증할 가설을 제품 문서에 먼저 적었습니다. 10월 13일 사진 대회 MVP로 시작했지만, 직접 써 보며 대회가 없을 때도 사진을 모을 수 있는 편이 낫다고 판단했습니다. 19일 상시 그룹 커뮤니티로 바꾸면서 기존 대회와 사진 데이터, 이전 링크는 보존했습니다.
- 가입 → 첫 게시물 → 좋아요 → 재방문 흐름을 보려고 Amplitude를 붙였습니다. 실제 수집 결과를 다시 조회해, 개발 모드에서 페이지뷰가 두 번 집계되고 URL에 검색어가 남는 문제를 찾아 고쳤습니다.
- 별사대에는 schema-first GraphQL과 Apollo Client를 사용했습니다. 서버는 NestJS, Prisma, PostgreSQL로 구성하고 도메인별로 스키마와 resolver를 나눴습니다. 웹에서는 GraphQL Code Generator로 각 쿼리와 mutation의 타입이 붙은 Document를 생성합니다. 앱의 모든 GraphQL 문서를 서버 스키마와 대조해 맞지 않으면 실패하는 계약 테스트를 뒀습니다. API의 쿼리 깊이와 필드, alias 수도 제한합니다.
- 객체의 id를 기준으로 Apollo 정규화 캐시를 갱신합니다. 자식 컴포넌트는 id를 받아 useFragment로 필요한 값을 읽습니다. 사진 목록은 offsetLimitPagination으로 이어 받고, 좋아요와 투표는 optimisticResponse로 먼저 반영합니다. 도메인별 캐시 정책을 합칠 때 같은 필드를 중복 정의하면 실패하게 했으며, 실제 InMemoryCache로 동작을 테스트합니다.
- Next.js App Router에서 RSC가 PreloadQuery로 받은 결과를 브라우저 캐시로 넘기고, 화면은 useBackgroundQuery와 useReadQuery로 같은 조회를 구독합니다. 개인화된 조회는 캐시하지 않고, 익명으로 볼 수 있는 공개 콘텐츠와 사이트맵만 서버 캐시에 둡니다. mutation 결과는 Next 프록시에서 확인해 공개 캐시를 만료합니다. 일부 필드가 저장된 뒤 다음 필드의 오류로 `data: null`이 반환되는 경우도 처리합니다.
- Game Mate는 REST와 TanStack Query로 만들었습니다. 댓글 알림을 누르면 해당 글이나 댓글로 이동하고, 읽음 처리 후 알림 개수도 갱신합니다. 두 서비스와 PostgreSQL은 EC2 한 대에서 Caddy를 통해 접근하도록 구성했습니다. CI에서 검증한 이미지를 digest로 고정해 배포하고, readiness 확인에 실패하면 이전 이미지로 되돌립니다. AWS 리소스는 Terraform으로 관리하며 mock provider로 테스트합니다.
