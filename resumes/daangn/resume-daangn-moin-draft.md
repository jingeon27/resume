#### 건강검진 서비스 내재화 | 2026.09 – 현재

건강검진은 아임웹에서 정보를 본 뒤 전화로 문의하던 서비스였습니다. 제휴 병원이 세이프닥에서 검진 예약을 받기를 요청했지만, 기존 비급여 프로그램으로는 검사 구성·기업지원 코드·예약금 흐름을 처리하기 어려웠습니다. 세 제품의 프론트엔드를 맡아 9월 9일부터 개발했고, 23일 운영 배포를 거쳐 30일 정식 오픈했습니다.

- **백오피스:** 검사항목과 필수·선택 검사 구성, 기업지원 코드·서류 확인, 결제내역 조회와 결제취소·환불 승인을 만들었습니다.
- **병원 관리자:** 검진 프로그램 조회와 예약 관리를 추가했습니다. 건강검진만 운영하는 병원에는 기존 프로그램 등록·검수 메뉴를 숨기고, 병원이 직접 처리할 수 없는 예약금 결제취소는 요청 접수로 안내했습니다.
- **복지몰:** 기존 프로그램 상세와 예약 신청·상세에 검진 흐름을 추가했습니다. 검사 선택·기업 검진 코드 입력·토스페이먼츠 예약금 결제를 연결하고, 사용자 부담금과 기업지원 내용을 구분했습니다.
- **선택 항목 수정 UX:** 정해진 수만큼 고르면 다음 그룹으로 넘기자는 요청에서, 기존 선택을 수정할 때도 강제 이동하는 점을 짚었습니다. 담당자와 논의해 미선택 chip만 비활성화하고 선택한 항목은 다시 고칠 수 있게 했으며, 빠져 있던 비활성 디자인도 요청했습니다.
- **부분 저장과 재시도:** 일괄 등록의 일부만 성공했을 때 이전 폼으로 재시도하면 중복 등록될 수 있어, 성공·실패 모두 서버 목록을 다시 받아 발급된 ID를 폼에 반영했습니다.
- **결제 실패 후 복원:** 전역 Zustand persist 대신 결제 시도별 `orderId`와 입력값을 `sessionStorage`에 저장했습니다. 같은 주문인지 확인한 뒤 현재 Zod 스키마를 통과한 값만 한 번 복원합니다. 결제창 실패 복귀의 입력 복원과 승인 요청 실패 시 예약 목록 이동은 dev API 서버 E2E로 확인했습니다.
- 검진 구성 수정이 거절됐을 때 삭제된 검사항목까지 조회 응답에 포함되는 것을 찾아 백엔드에 전달했습니다. nullable 필드와 요청 직렬화도 dev API 서버와 대조해 맞췄습니다.

#### 모바일 리뷰 개선과 WebView | 2025.06 – 2026.09

모바일로 리뷰를 직접 작성하다 키패드가 시술 목록을 가리고, 여러 항목을 골라야 하는데 하나만 고르면 닫히며, 선택한 항목도 잘 보이지 않는 문제를 발견했습니다. 2025년 6월 Jira에 정리해 PO에게 공유했습니다.

- 기획·디자인 담당자가 정한 복수 선택·체크·chip UI를 구현해 7월 10일 운영에 반영했습니다. 이후 디자인 시스템 시안의 Bottom Sheet도 적용해 8월 7일 배포했습니다. 처음 불편을 발견하고 개선한 시점은 Amplitude 도입 전입니다.
- `header`·`content`·`button`을 함수 인자로 받던 Bottom Sheet는 본문과 하단 버튼이 폼 상태를 공유하기 어려웠습니다. Compound Components와 overlay-kit으로 바꿔 같은 RHF 컨텍스트에서 조합하게 하고, 시트 안의 임시 선택은 확인할 때 바깥 폼에 반영하도록 했습니다.
- WebView에서 동작하지 않던 `tel:` 상담 버튼은 기존 네이티브 브릿지의 외부 링크 열기로 연결했습니다. 외부 예약 사이트 이동에서는 네이티브 뒤로 가기가 WebView 전체를 닫는 것을 배포 전에 확인해, 외부 사이트 열기와 웹 내부 뒤로 가기를 구분했습니다.

#### A/B 테스트 환경 구축과 실험 참여 | 2025.07 – 현재

Amplitude 기반 A/B 테스트 환경을 구축했습니다. PM이 주도한 검색·병원 상세·프로그램 목록·예약신청 버튼 등의 실험에서 화면 구현과 사용자 행동 측정을 맡았습니다.

- 검색·상세·예약·쿠폰 화면의 이벤트 140개 이상을 새로 붙이거나 고쳤습니다. 상세에서 예약·상담으로 이어지는 행동과 예약 중 날짜·시간 선택 후 이탈을 구분하도록 이벤트의 위치와 속성을 맞췄습니다.
- 전화상담 실험에서는 플로팅 버튼·하단 내비·말풍선 진입점을 구현하고 클릭 이벤트의 `source`로 위치를 구분했습니다. 고객센터 번호를 병원 번호로 오해하는 경우에는 상담시간을 안내했고, 회사가 전화상담을 종료한 뒤 채팅상담으로 되돌렸습니다.
- 전화상담·룰렛 코드를 제거하기 전 페이지 방문 이벤트를 확인했습니다. 더 이상 방문하는 사용자가 없다고 판단한 뒤 관련 코드를 정리했습니다.
- 신규 가입 UTM 유실에 대응해 저장 코드를 넣었다가 측정 방식을 더 살펴봤습니다. Amplitude에서 unexpected로 분류된 속성을 expected로 바꾸면 해결되는 것을 확인해 PO에게 공유하고, 추가 코드는 운영 배포 전에 되돌렸습니다.

#### SSR·Streaming과 클라이언트 조회 | 2026.04 – 현재

서버의 초기 조회와 화면의 조회 조건이 달라 검색 결과가 첫 HTML에 포함되지 않는 문제를 고쳤습니다. 서버·클라이언트가 같은 데이터를 읽게 하고, URL만 바꾸면 되는 화면은 서버 내비게이션과 구분했습니다.

- 검색 페이지는 서버 prefetch와 화면 훅이 같은 URL을 다른 Zod 스키마로 읽어 `queryKey`가 갈렸습니다. 같은 스키마로 조건을 만들게 하고, 시술·병원 탭과 필터·통합 검색의 네 조합에서 첫 렌더부터 서버 데이터를 읽는지 테스트했습니다.
- 복지몰 상담 화면의 `ensureQuery`·render props는 TanStack Query prefetch·hydration으로 바꿨습니다. 서버는 초기 데이터를 준비하고 클라이언트는 같은 캐시를 구독해 조회·무효화를 처리합니다.
- 이미 인증한 사용자가 로그인·본인인증 화면으로 갔다 돌아올 때 앱이 멈추는 오류는 Next.js 라우터 소스까지 추적했습니다. 서버 컴포넌트의 `redirect()`를 하드 내비게이션으로 처리하며 `AppRouter`가 훅 호출 중간에 렌더를 종료하는 경로를 확인해, 진입 판정을 렌더 전 proxy로 옮겼습니다.
- 관리자 검색 오류는 개발 서버와 jsdom에서 나타나지 않아 프로덕션 빌드로 재현했습니다. 목록 7개 중 6개에서 확인하고 업스트림 캐시 이슈를 추적했습니다. 서버가 검색 조건을 읽지 않는 화면의 같은 경로 변경은 History API로 처리해 RSC 재요청을 피했습니다. 수정 뒤 9월 28일까지 같은 증상의 재보고는 없었습니다.
- Next.js `cacheComponents` 적용 뒤 `<Activity>`로 숨겨진 폼에 이전 입력이 남는 것을 확인했습니다. 화면이 숨겨질 때도 실행되는 effect cleanup에서 공용 폼 훅이 값을 초기화하도록 했습니다.
- 리뷰 정렬·사진 필터는 URL 값을 `useState`로 복제하지 않고 URL을 기준으로 읽게 했습니다. 일부 미리보기 봇에는 늦게 생성되는 메타데이터도 `<head>`에 포함하도록 스트리밍 대상을 구분했습니다.

#### 폼·타입 설계와 코드 구조 | 2025.06 – 현재

화면마다 다른 요구사항이 거대한 공통 렌더러에 쌓여 한 화면을 고쳐도 다른 화면을 함께 확인해야 했습니다. 상태와 조회 책임을 나누고, 화면이 필요한 UI를 직접 조합하도록 바꿨습니다.

- 검색 화면 27개를 `createSearchFilter(schema)` 기반 조합으로 전환했습니다. 화면별 JSX가 일부 반복되더라도 예외를 공통 렌더러의 분기로 쌓지 않도록 했습니다. 필드명은 `z.infer`로 파생하고 URL·폼·API가 같은 계약을 사용합니다.
- Ant Design Form의 중첩 필드명이 틀려도 컴파일되는 부분은 `createTypedForm<T>`로 보완했습니다. 재귀 조건부 타입과 `infer`로 유효한 경로와 값 타입을 계산해 필드명·읽기·쓰기·구독 API가 함께 검사하도록 했습니다. 라이브러리 연결에 필요한 단언은 래퍼 내부에 한정했습니다.
- Zod 검증 실패는 출처에 따라 처리합니다. 기존 API 응답은 불일치를 기록하며 계약을 맞추고, URL은 잘못된 필드만 기본값으로 복구합니다. 결제 복귀 값은 검증에 실패하면 버립니다. dev 표본에 없는 null 응답을 운영 오류 기록에서 찾아 스키마를 교정한 경험도 있습니다.
- 예약 화면의 가족·날짜 값은 Query 캐시·Zustand·로컬 상태에 나뉘어 있었습니다. 서버 목록은 Query, 작성 중인 값은 React Hook Form, 제출 조건은 Zod가 맡도록 나눠 가족 추가 후 날짜 선택이 어긋나는 문제를 고쳤습니다. 519줄이던 예약 대상 선택 컴포넌트는 55줄로 줄이고 동기화 로직을 훅·하위 컴포넌트로 분리했습니다.
- FSD는 재사용할 것 같다는 판단만으로 `entities`에 도메인 코드를 두던 기준을 바꿨습니다. 서버 계약은 `features`, 화면 조합은 `pages`, 공용 UI는 조합 가능한 `shared`로 구분하고, 복지몰의 화면 간 직접 참조 62건을 정리한 뒤 lint error로 막았습니다.
- 인수한 정산 화면은 조회·표·선택·편집·정산 액션으로 나눴습니다. `useImperativeHandle`로 열던 모달을 대상 데이터와 `open`·`onCancel`을 props로 받게 하고, 다른 기능이 라우트 내부 모달을 직접 참조하던 의존성도 정리했습니다.
- 일부 조회 실패가 앱 전체를 내리지 않도록 Error Boundary를 독립적으로 복구할 수 있는 기능 단위로 나눴습니다. 백오피스 라우트 30개의 조회 위치와 화면 구성을 맞추고, 실패한 구획의 재시도·복구를 테스트했습니다.

- 화면을 표시할 수 없는 오류와 작업을 막는 오류, 재시도할 수 있는 실패를 구분해 레벨을 정했습니다. 의미 없는 전송을 줄이는 차단 게이트를 만들고, 같은 오류가 API 계층과 Error Boundary에서 중복 수집되지 않도록 했습니다.
- SDK 소스에서 event·breadcrumb·transaction·span에 담기는 값을 확인해 의료·인증 정보를 제거했습니다. release와 브라우저 소스맵을 연결하고 Sentry MCP를 붙였으며, LCP·FCP·TTFB 전송은 브라우저 E2E로 확인했습니다.
- Bottom Sheet 드래그 크래시를 라이브러리의 null ref 접근까지 추적했습니다. 라이브러리를 올리며 바뀐 snap point 규칙은 공통 Root에서 변환해 기존 사용처를 유지했습니다. 수정 전 누적 75건·57명 이상이던 오류 그룹은 9월 10일 배포 뒤 28일까지 18일 동안 0건이었습니다.
- 회원 조회 실패를 모두 로그아웃으로 처리하던 코드는 401일 때만 로그아웃하도록 바꿨습니다. 9월 23일 배포 뒤 28일까지 관련 CS와 Sentry 이슈가 없었습니다.

#### 테스트 체계 재구축 | 2026.07 – 현재

기존 테스트가 제출 로직을 복제하거나 잘못된 입력에도 성공하는 mock을 써서, 실제 폼과 서버의 제약을 확인하지 못했습니다. 순수 함수·스키마, UI 통합, API 계약, 브라우저 E2E로 검증 대상을 다시 나눴습니다.

- 실제 Drawer를 렌더해 제출까지 테스트합니다. 기대 payload는 제품의 변환 함수를 호출하지 않고 따로 작성해 제품 코드와 테스트가 같은 실수를 하지 않게 했습니다.
- 순수 함수·스키마는 Vitest, UI·폼은 React Testing Library, 브라우저 흐름은 Playwright로 검증합니다. dev API 서버로 먼저 확인하고 서버에서 만들기 어려운 조건은 MSW로 재현합니다.
- 새 기능은 BDD 형식의 `*.spec.{ts,tsx}`에 기대 동작을 적고 컴포넌트별로 빠진 조건을 검토합니다. 운영·QA 오류와 console warning은 `*.test.{ts,tsx}`에 재현합니다. 새 테스트 패턴은 제품 코드를 일부러 깨뜨려 실패하는지 확인한 뒤 넣습니다.
- 9월에는 병원 관리자의 프로그램 등록부터 백오피스의 검수중·반려·승인까지 두 앱을 가로지르는 E2E를 추가했습니다. 이 최종 상태를 구현 루프의 완료 조건으로 사용합니다.
- Unit·Integration 테스트는 PR 게이트에 연결했습니다. 서버 상태 준비와 실행 비용이 드는 API 계약 테스트는 PR을 막지 않는 별도 단계로 두고 E2E는 CI 밖에서 실행합니다.

#### AI 개발 workflow | 2026.04 – 현재

4월에는 생성된 코드를 모두 검토하며 의도와 다른 구현을 skills에 남겼습니다. 파일 배치와 상태 소유권이 모호하면 에이전트도 매번 다르게 해석해, Compound Engineering 방식으로 판단을 누적하고 FSD와 lint를 저장소에 맞게 바꿨습니다. 7월에는 테스트 체계를 더하고 8월부터 운영 오류를 추적했습니다. 모델 성능이 좋아지고 skills가 쌓이면서 원하는 구현이 늘어, 위임하는 범위를 점진적으로 넓혔습니다.

지금은 아래 순서로 작업하며 문제가 나오면 앞 단계로 돌아갑니다.

티켓·plan 검토 → 테스트 작성 → 에이전트 구현·에이전트 코드 리뷰 → 변경분 테스트·lint·typecheck → 제 diff 리뷰·화면을 띄워 동작 확인 → 전체 CI(테스트·knip·lint) → QA 더블 체크 요청

- Jira와 Figma·와이어프레임을 먼저 보고 빠진 동작과 UX 의견을 담당자와 맞춥니다. 티켓별로 PR까지 한 번에 맡길지, plan과 완료 결과를 확인할지 정합니다.
- 구현과 테스트 작성은 에이전트에 맡깁니다. 완성본을 제출하면 코드와 `*.spec`의 요구 동작, `*.test`의 오류 재현을 읽고 부족한 부분은 반려합니다. 에이전트 리뷰의 critical 항목은 자동 수정하고 그 결과도 검토합니다.
- 반복되는 판단은 skills에, 정적으로 확인할 수 있는 기준은 lint rule에 남깁니다. 미사용 파일·export는 Knip으로 확인합니다. 슬라이스 Public API 위반 271건은 정리한 뒤 error로 올려 새로운 위반을 막았습니다.
- 자체 규칙이 동적 import와 `as const` 쿼리 키를 놓치는 것을 확인해 보완을 지시하고 결과를 검토했습니다. 보완 전 규칙으로 새 RuleTester 테스트를 실행하면 8건이 실패해 검사 기준의 빈틈도 확인했습니다.
- 병렬 worktree마다 전체 검사를 반복하면 CPU 경합이 생겨 작업 중 lint와 테스트는 변경 파일·영향 범위를 중심으로 실행합니다. 타입 검사는 필요한 패키지·앱 단위를 유지하고 전체 검사는 CI에서 확인합니다.

#### 기술 선택과 전환 | 2025.10 – 현재

## 지원동기

중학교 때 게임 커뮤니티에서 만난 사람들과 정모로 직접 만나기도 했고, 그중 몇몇과는 지금까지 관계를 이어오고 있습니다. 같은 관심사로 온라인에서 시작한 인연이 오래 이어진 것은 제 인생에서 특별한 경험이었습니다. 당근모임에서도 이웃이 처음 만나는 부담을 덜고, 함께 시간을 보내며 관계를 이어갈 수 있도록 돕고 싶습니다.
