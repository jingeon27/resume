## 소개

제품을 만들며 불편한 사용 흐름과 복잡해진 코드를 함께 고쳐 온 프론트엔드 엔지니어입니다. React·TypeScript·Next.js로 채용 SaaS와 의료복지 서비스를 개발했습니다.

개발할 때는 기준을 먼저 세웁니다. 요구사항에서 빠진 동작은 담당자와 논의하고, 데이터를 가져오는 코드와 화면을 그리는 코드를 나눠 읽고 확인하기 쉽게 만듭니다. 새로운 기술을 도입할 때는 얻는 이점과 함께 기존 기능에 미치는 영향, 바꾸고 유지하는 데 드는 비용을 살펴봅니다.

AI 개발 workflow를 개선하며 반복해서 지적한 내용은 skills와 lint rule에 남깁니다. 에이전트가 제출한 코드와 테스트를 직접 읽고, 화면을 띄워 동작을 확인합니다. 출시 뒤에는 Sentry로 운영 오류를 추적합니다.

#### 건강검진 서비스 내재화 | 2026.09 – 현재

기존 건강검진은 아임웹에서 정보를 보고 전화로 문의하는 방식이었습니다. 제휴 병원이 세이프닥에서 검진 예약을 받기를 요청했지만, 검사항목 구성과 기업지원 코드, 예약금 결제는 기존 비급여 프로그램과 달라 별도 개발이 필요했습니다. 복지몰·병원 관리자·백오피스의 프론트엔드를 맡아 9월 9일부터 개발했고, 23일 운영 배포 후 30일 정식 오픈했습니다.

- **백오피스:** 검사항목을 등록하고 필수·선택 검사를 구성하는 기능을 만들었습니다. 기업지원 코드와 서류 확인, 결제내역 조회, 결제취소·환불 승인도 추가했습니다.
- **병원 관리자:** 검진 프로그램 조회와 예약 관리를 추가했습니다. 건강검진만 운영하는 병원에는 기존 프로그램 등록·검수 메뉴를 숨기고, 병원이 직접 처리할 수 없는 예약금 결제취소는 요청 접수로 안내했습니다.
- **복지몰:** 기존 프로그램 상세와 예약 신청·상세에 건강검진 기능을 추가했습니다. 검사 선택, 기업 검진 코드 입력, 토스페이먼츠 예약금 결제를 연결하고 사용자 부담금과 기업지원 내용을 구분해 보여줬습니다.
- **검사항목 선택:** 정해진 수만큼 고르면 다음 그룹으로 넘어가자는 요청이 있었습니다. 이미 고른 항목을 수정할 때도 화면이 넘어가는 불편을 짚고 담당자와 논의했습니다. 선택 수를 채우면 고르지 않은 chip만 비활성화해 초과 선택을 막고, 기존 선택은 수정할 수 있게 했습니다. 빠져 있던 비활성 상태의 디자인도 요청했습니다.
- **일부만 저장됐을 때의 재시도:** 일괄 등록에서 일부 항목만 저장된 뒤 같은 폼을 다시 제출하면 중복 등록될 수 있었습니다. 요청이 성공하거나 실패한 뒤 서버 목록을 다시 받아, 이미 저장된 항목의 ID를 폼에 반영했습니다.
- **결제 실패 후 입력 복원:** 전역 상태를 남기는 Zustand persist 대신 결제 시도별 `orderId`와 입력값을 `sessionStorage`에 저장했습니다. 돌아온 주문이 같은지 확인하고, 현재 Zod 스키마를 통과한 값만 한 번 복원합니다. 결제창에서 실패로 돌아왔을 때 입력이 복원되는지, 승인 요청이 실패하면 예약 목록으로 이동하는지 dev API 서버 E2E로 확인했습니다.
- 검진 구성 수정이 거절됐을 때, 조회 응답에 삭제된 검사항목이 포함된 것을 찾아 백엔드에 전달했습니다. null을 허용하는 필드와 요청값을 보내는 방식도 dev API 서버에서 확인하며 맞췄습니다.

#### 모바일 리뷰 개선과 WebView | 2025.06 – 2026.09

모바일로 리뷰를 직접 작성하다 키패드가 시술 목록을 가리고, 여러 항목을 골라야 하는데 하나만 고르면 닫히며, 선택한 항목도 잘 보이지 않는 문제를 발견했습니다. 2025년 6월 Jira에 정리해 PO에게 공유했습니다.

- 기획·디자인 담당자가 정한 복수 선택·체크·chip UI를 구현해 7월 10일 운영에 반영했습니다. 이후 디자인 시스템 시안에 맞춰 Bottom Sheet를 적용하고 8월 7일 배포했습니다. 처음 불편을 발견하고 개선한 시점은 Amplitude 도입 전입니다.
- 기존 Bottom Sheet는 `header`·`content`·`button`을 함수 인자로 받아, 본문에서 고른 값을 하단 버튼과 공유하기 어려웠습니다. Compound Components와 overlay-kit으로 바꿔 본문과 버튼이 같은 RHF 폼 안에서 동작하도록 했습니다. 시트 안에서 고른 값은 ‘확인’을 눌러야 바깥 폼에 반영되게 했습니다.
- WebView에서 동작하지 않던 `tel:` 상담 버튼은 기존 네이티브 브릿지로 외부 링크를 열도록 연결했습니다. 외부 예약 사이트 이동을 개발할 때는 뒤로 가기가 WebView 전체를 닫는 문제를 배포 전에 확인했습니다. 외부 사이트 열기는 브릿지를, 웹 내부 뒤로 가기는 웹 라우터를 사용하도록 구분했습니다.

#### A/B 테스트 환경 구축과 실험 참여 | 2025.07 – 현재

Amplitude 기반 A/B 테스트 환경을 구축했습니다. PM이 주도한 검색·병원 상세·프로그램 목록·예약신청 버튼 등의 실험에서 화면 구현과 사용자 행동 측정을 맡았습니다.

- 검색·상세·예약·쿠폰 화면의 이벤트 140개 이상을 새로 붙이거나 고쳤습니다. 상세에서 예약·상담 버튼을 눌렀는지, 예약 중 날짜·시간을 고르다 나갔는지 확인할 수 있도록 이벤트를 보내는 시점과 속성을 맞췄습니다.
- 전화상담 실험에서는 플로팅 버튼·하단 내비·말풍선으로 상담에 들어갈 수 있게 만들고, 클릭 이벤트의 `source`로 진입 위치를 구분했습니다. 고객센터 번호를 병원 번호로 오해하는 경우가 있어 상담시간을 안내했습니다. 실험 결과가 좋지 않아 전화상담이 종료된 뒤, 관련 코드를 정리하고 채팅상담으로 되돌렸습니다.
- 룰렛은 Amplitude의 페이지 방문 이벤트를 확인했습니다. 더 이상 방문하는 사용자가 없다고 판단한 뒤 관련 코드를 제거했습니다.
- 신규 가입자의 UTM이 기록되지 않아 저장 코드를 추가했다가 Amplitude 설정을 더 살펴봤습니다. unexpected로 분류된 속성을 expected로 바꾸면 해결되는 것을 확인해 PO에게 공유했습니다. 추가한 코드는 운영 배포 전에 되돌렸습니다.

#### SSR·Streaming과 데이터 조회 | 2026.04 – 현재

서버 컴포넌트에서 `ensureQuery` 결과를 render props로 전달하던 데이터 조회 전반을 TanStack Query prefetch·hydration으로 바꿨습니다. 서버는 초기 데이터를 준비하고, 클라이언트는 같은 캐시를 읽어 이후 조회·갱신·캐시 무효화를 처리하도록 했습니다.

- 이미 인증한 사용자를 로그인·본인인증 화면에서 되돌릴 때 앱이 멈추는 오류를 Next.js 라우터 소스까지 추적했습니다. 서버 컴포넌트의 `redirect()`를 처리하면서 `AppRouter`의 훅 호출 순서가 어긋나는 것을 확인했습니다. 인증 확인과 리다이렉트를 렌더 전 Next.js proxy로 옮겼습니다.
- 관리자 검색 오류는 개발 서버와 jsdom 테스트에 나타나지 않아 프로덕션 빌드로 재현했습니다. 목록 7개 중 6개에서 확인하고 Next.js의 라우터 캐시 이슈까지 찾았습니다. 클라이언트에서 목록을 조회하는 화면은 같은 경로의 검색 조건만 History API로 바꿔 RSC 재요청을 피했습니다. 수정 뒤 9월 28일까지 같은 증상의 재보고는 없었습니다.
- Next.js `cacheComponents` 적용 뒤, 뒤로·앞으로 가기로 돌아온 폼에 이전 입력이 남았습니다. `<Activity>`가 화면을 없애지 않고 숨기는 동작을 확인했습니다. 숨겨질 때도 실행되는 effect cleanup에서 폼을 초기화하도록 공용 훅을 고쳤습니다.
- 리뷰 정렬·사진 필터는 URL 값을 `useState`에도 저장하던 코드를 정리하고 URL만 읽게 했습니다. 일부 미리보기 봇에는 늦게 생성되는 메타데이터도 `<head>`에서 받도록 설정했습니다.

#### 폼·타입 설계와 코드 구조 | 2025.06 – 현재

하나의 공통 컴포넌트에 화면별 조건이 쌓여, 한 화면을 고치면 다른 화면도 함께 확인해야 했습니다. 각 화면이 필요한 UI를 직접 조합하도록 바꾸고, 데이터를 가져오는 코드와 UI를 나눴습니다.

- 검색 화면 27개를 `createSearchFilter(schema)`로 전환해 각 화면이 필요한 필터를 조합하도록 했습니다. 화면별 JSX가 일부 반복되더라도 공통 컴포넌트에 예외 조건을 계속 넣지 않기로 했습니다. URL 해석, 폼 필드, API 조회 조건은 같은 Zod 스키마를 사용하고 타입은 `z.infer`로 만듭니다.
- Ant Design Form은 중첩 필드명이 틀려도 컴파일되는 문제가 있어 `createTypedForm<T>`로 보완했습니다. 재귀 조건부 타입과 `infer`로 필드 경로에 맞는 값 타입을 계산합니다. 값을 읽고 쓰거나 구독할 때도 필드명과 값 타입을 검사하며, 필요한 타입 단언은 래퍼 내부에만 뒀습니다.
- Zod 검증이 실패했을 때는 값의 출처에 따라 다르게 처리합니다. 기존 API 응답은 불일치를 기록하고 원본을 통과시키며 스키마를 맞춥니다. URL은 잘못된 필드만 기본값으로 되돌리고, 결제 후 복원할 입력값은 검증에 실패하면 버립니다. 개발 환경에서 보지 못한 null 응답을 운영 오류 기록에서 찾아 스키마를 고치기도 했습니다.
- 예약 화면의 가족·날짜 값이 Query 캐시·Zustand·로컬 상태에 나뉘어 있어, 가족을 추가하면 날짜 선택이 어긋났습니다. 서버 목록은 Query, 작성 중인 값은 React Hook Form, 제출 전 검증은 Zod로 나눠 문제를 고쳤습니다. 동기화 로직을 훅과 하위 컴포넌트로 분리해 519줄이던 예약 대상 선택 컴포넌트를 55줄로 줄였습니다.
- FSD에서는 여러 기능에서 재사용할 것 같다는 이유로 `entities`에 코드를 두던 기준을 바꿨습니다. 서버 모델·API 코드는 `features`, 화면별 조합은 `pages`, 도메인과 무관한 공용 UI는 `shared`로 나눴습니다. 복지몰에서 화면끼리 직접 참조하던 62건을 정리하고 새 위반은 lint error로 막았습니다.
- 인수한 정산 화면은 조회·표·선택·편집·정산 처리로 나눴습니다. `useImperativeHandle`과 ref로 열던 모달은 대상 데이터와 `open`·`onCancel`을 props로 받도록 바꿨습니다. 다른 기능에서 라우트 내부의 모달을 직접 가져다 쓰던 코드도 정리했습니다.
- 조회 하나가 실패해 앱 전체가 멈추지 않도록, 따로 복구할 수 있는 기능마다 Error Boundary를 적용했습니다. 백오피스 라우트 30개에서 데이터 조회와 화면 구성을 같은 패턴으로 맞추고 재시도를 테스트했습니다.

#### Sentry 도입과 운영 오류 추적 | 2026.08 – 현재

복지몰의 브라우저·서버·Edge 오류를 한곳에서 추적하도록 Sentry를 도입했습니다. 8월 19일부터 구현해 27일 운영에 배포했습니다.

- 화면이 뜨지 않는 오류, 작업을 막는 오류, 재시도할 수 있는 실패를 구분해 레벨을 정했습니다. 의미 없는 전송을 줄이는 차단 게이트를 만들고, API 처리 코드와 Error Boundary가 같은 오류를 두 번 보내지 않게 했습니다.
- SDK 소스를 읽고 오류 기록과 breadcrumb·transaction·span에 담기는 값을 확인해 의료·인증 정보를 제거했습니다. 배포 버전별로 원본 코드를 확인할 수 있도록 release와 브라우저 소스맵을 연결하고 Sentry MCP를 붙였습니다. LCP·FCP·TTFB 전송은 브라우저 E2E로 확인했습니다.
- Bottom Sheet를 드래그할 때 앱이 멈추는 문제를 라이브러리의 null ref 접근까지 추적했습니다. 라이브러리 업데이트로 바뀐 snap point 규칙은 공통 Root에서 변환해 기존 화면을 그대로 쓸 수 있게 했습니다. 수정 전 누적 75건·57명 이상이던 오류 그룹은 9월 10일 배포 뒤 28일까지 18일 동안 0건이었습니다.
- 회원 조회 실패를 모두 로그아웃으로 처리하던 코드는 401일 때만 로그아웃하도록 바꿨습니다. 9월 23일 배포 뒤 28일까지 관련 CS와 Sentry 이슈가 없었습니다.

#### 테스트 도입 | 2026.07 – 현재

기존 테스트는 제출 로직을 따로 복제하거나 잘못된 입력도 성공으로 처리하는 mock을 사용했습니다. 실제 폼과 서버에서 생기는 문제를 놓쳐, 함수·스키마부터 UI·폼, API 요청·응답, 브라우저 흐름까지 나눠 테스트를 다시 만들었습니다.

- 실제 Drawer를 열고 제출까지 테스트합니다. 서버로 보내야 할 기대값은 제품의 변환 함수를 호출하지 않고 따로 작성해, 제품 코드와 테스트가 같은 실수를 하지 않게 했습니다.
- 순수 함수·스키마는 Vitest, UI·폼은 React Testing Library, 브라우저 흐름은 Playwright로 검증합니다. dev API 서버로 먼저 확인하고 서버에서 만들기 어려운 조건은 MSW로 재현합니다.
- 새 기능은 BDD 형식의 `*.spec.{ts,tsx}`에 기대 동작을 적고, 컴포넌트별로 필요한 조건이 빠졌는지 검토합니다. 운영·QA 오류와 console warning은 `*.test.{ts,tsx}`에 재현합니다. 새 테스트 패턴은 제품 코드를 일부러 깨뜨렸을 때 실패하는지 확인한 뒤 넣습니다.
- 9월에는 병원 관리자에서 프로그램을 등록하고 백오피스에서 검수중·반려·승인하는 과정을 두 앱에 걸쳐 확인하는 E2E를 추가했습니다. 구현을 마쳤는지는 테스트에서 기대한 최종 상태까지 도달하는지로 확인합니다.
- Unit·Integration 테스트가 성공해야 PR을 합칠 수 있도록 CI에 연결했습니다. dev API 서버의 상태를 준비해야 하는 API 계약 테스트는 별도로 실행하고, 실패해도 PR을 막지 않도록 했습니다. E2E는 CI 밖에서 실행합니다.

#### AI 개발 workflow | 2026.04 – 현재

4월에는 생성된 코드를 모두 검토하고, 의도와 다른 구현이 나오면 skills를 보완했습니다. 파일을 어디에 둘지, 상태를 어디에서 관리할지가 모호하면 에이전트의 구현도 매번 달라졌습니다. Compound Engineering 방식으로 판단을 skills에 쌓고, FSD 구조와 lint rule을 저장소에 맞게 바꿨습니다. 7월에는 테스트 체계를 더하고 8월부터 운영 오류를 추적했습니다. 모델 성능이 좋아지고 skills가 쌓이면서 만족스러운 구현이 늘어, 에이전트에 맡기는 범위를 조금씩 넓혔습니다.

지금은 아래 순서로 작업하며 문제가 나오면 앞 단계로 돌아갑니다.

티켓·plan 검토 → 테스트 작성 → 에이전트 구현·에이전트 코드 리뷰 → 변경분 테스트·lint·typecheck → 직접 diff 리뷰·화면을 띄워 동작 확인 → 전체 CI(테스트·knip·lint) → QA 더블 체크 요청

- Jira와 Figma·와이어프레임을 먼저 보고 빠진 동작과 사용성 개선 의견을 담당자와 논의합니다. 작업별로 PR까지 한 번에 맡길지, plan과 완료 결과를 직접 확인할지 정합니다.
- 구현과 테스트 작성은 에이전트에 맡깁니다. 완성본이 나오면 코드와 테스트를 읽고, `*.spec`에 필요한 동작이 모두 적혀 있는지와 `*.test`가 오류를 재현하는지 확인합니다. 부족한 부분은 반려해 다시 확인합니다. 에이전트 리뷰의 critical 항목은 자동 수정하고 그 결과도 검토합니다.
- 반복되는 판단은 skills에, 코드만으로 자동 검사할 수 있는 기준은 lint rule에 남깁니다. 미사용 파일·export는 Knip으로 확인합니다. 다른 슬라이스의 내부 파일을 직접 import하던 위반 271건을 정리하고, 이후 같은 위반은 lint error로 막았습니다.
- lint rule도 RuleTester와 `__fixture__`·mock으로 테스트 환경을 만들어 검증합니다.
- 여러 worktree에서 전체 검사를 동시에 돌리면 CPU 부하가 커져, 작업 중에는 변경 파일과 영향을 받는 범위의 lint·테스트를 실행합니다. 타입 검사는 필요한 패키지·앱 단위로 하고 전체 검사는 CI에서 확인합니다.

#### 기술 선택과 전환 | 2025.10 – 현재

- 공통 UI를 더 유연하게 조합하고 접근성 기능을 활용하기 위해 Headless UI에서 Radix UI로 옮겼습니다. Slot·`asChild`를 사용하되 기존 props·열림 상태·이벤트를 새 API에 맞춰 수정해야 했습니다. ref가 제대로 전달되는지와 포커스 동작도 확인했습니다. Bottom Sheet의 기반 라이브러리는 유지했습니다.
- Tailwind CSS v4로 바꾸기 전, 2026년 8월 27일~10월 1일 사용자 브라우저의 `color-mix()`·`@property` 지원 여부를 Amplitude로 확인했습니다. 하루 평균 약 1,000명 중 `color-mix()` 미지원 사용자는 하루 1명꼴(평균 0.94명)이었고 `@property` 미지원은 없었습니다. 업그레이드를 하지 않는 것도 검토했지만 [v4.1의 색상 fallback](https://tailwindcss.com/blog/tailwindcss-v4-1#improved-compatibility-with-older-browsers)을 확인해 전환을 진행했습니다.
- 로컬 개발 속도를 높이기 위해 Next.js 14→16·React 18→19로 전환했습니다. Turbopack 도입과 Next.js 16 자체의 개발 속도 개선을 함께 고려했습니다. 전환 과정에서는 비동기 API와 달라진 캐시 동작에 맞춰 기존 코드를 수정하고, 링크 직접 진입·뒤로가기·새로고침을 확인했습니다.
- TypeScript 7 네이티브 체커를 병행해 복지몰의 타입 검사 시간을 실측 12.5초에서 1.9초로 줄였습니다. 타입 정보까지 사용하는 lint는 검사 시간이 3.3배 늘어 도입을 보류했습니다.

#### Query key·드래그 인터랙션 공통화 | 2024.04·08

- 앱마다 따로 관리하던 TanStack Query key와 `queryFn`을 `query-key-factory` 기반 공용 패키지로 모았습니다. 상위 key를 무효화하면 필요 이상으로 데이터를 다시 가져올 수 있어, mutation마다 갱신할 대상을 명시했습니다.
- 공통 드래그 컨텍스트·핸들·정렬 컴포넌트를 만들어 채용 공고 순서, 중첩 필터 트리, 설정 테이블에 적용했습니다. 폴더를 누르는 동작과 드래그 정렬이 겹쳐 선택이 풀리는 문제 등 각 화면의 예외도 조정했습니다.

#### Electron 후보자 수집 앱 | 2024.02 – 03, 09 – 10

사이트마다 반복되던 로그인 → 수집 → 중복 확인 → 업로드를 공통 단계와 사이트별 adapter로 나누는 초기 구조를 설계했습니다. 잡플래닛·게임잡 연동도 맡았습니다. NestJS를 도입하려 했지만 CTO가 Electron main 프로세스에는 무겁다고 리뷰해 닷새 만에 걷어냈습니다. 모듈 구분과 생성자 주입은 참고하고, factory에서 직접 조립하도록 했습니다. 이후 코드의 상당 부분은 동료가 다시 작성했습니다.

## 지원동기

중학교 때 게임 커뮤니티에서 알게 된 사람들과 정모로 직접 만나기도 했고, 그중 몇몇과는 지금도 연락하며 지냅니다. 같은 관심사로 온라인에서 만난 인연이 오래 이어진 것은 제게 특별한 경험입니다. 당근모임에서도 이웃이 처음 만나는 부담을 덜고, 함께 시간을 보내며 관계를 이어갈 수 있도록 돕고 싶습니다.

제품을 성장시키는 일과 엔지니어로서 성장하는 일을 함께하고 싶습니다. 모임팀은 사용자 의견을 바탕으로 제품을 개선하면서, AI 활용과 개발 환경 개선에도 힘쓰는 팀이라고 느꼈습니다. 동료들과 기술적인 고민을 나누며 개발 역량을 넓히고, 그 역량으로 이웃이 더 편하게 모임에 참여하고 활동을 이어가는 데 기여하고 싶어 지원했습니다.
