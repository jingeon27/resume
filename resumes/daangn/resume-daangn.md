## Summary

에이전트가 일하기 좋은 저장소를 만드는 데 시간을 많이 쓰는 프론트엔드 엔지니어입니다. 매일 에이전트로 개발하면서, 생산성은 잘 시키는 데서가 아니라 **어디를 믿지 않을지 정하는 데서** 나온다는 걸 배웠습니다. 그 판단 기준을 제 머릿속이 아니라 저장소 규칙과 lint로 옮겨 왔습니다. 만든 화면은 출시 이후까지 직접 운영하고, 배포한 뒤에는 행동 데이터로 결과를 확인합니다.

- **0→1과 운영** — 사내 유일 프론트엔드로 B2C 웹·백오피스·병원 어드민 세 제품을 맡고, 글로벌 건강검진 서비스를 3주 만에 구축해 론칭했습니다.
- **에이전트 하네스** — Jira 조회부터 worktree 격리, 검증, 배포 PR 생성까지 스킬·커맨드로 묶고, "이 문제는 이 도구로 푼다"를 저장소 문서 64개와 레이어 가이드 20개로 정의했습니다. 사람이 짜든 에이전트가 짜든 비슷한 코드가 나오게 하는 것이 목적이었습니다.
- **규칙을 lint로** — FSD 레이어 역방향 의존을 막는 ESLint 플러그인을 외부 의존성 없이 직접 만들었고(두 저장소 258줄), lint 검사와 dev·stage·prod 배포, 실패 알림까지 CI 워크플로 10개를 운영합니다.
- **선언적 코드** — `ts-pattern`으로 상태·결제수단 분기를 한 곳에 모아 빠뜨린 경우가 코드 작성 단계에서 드러나게 하고, `es-toolkit`을 세 저장소 151개 파일에서 씁니다.
- **지불하는 제품과 데이터** — 쿠폰 발급·보유·최대 혜택 선택부터 결제금액 반영·정산까지의 흐름을 만들고, 제품 분석 이벤트 250개 중 140개 이상을 직접 구현해 **리뷰를 본 사용자의 예약 전환율이 15%p 높다**는 상관관계를 다음 실험의 근거로 남겼습니다.

**에이전트가 일하기 쉬운 저장소 만들기 (2026.04–현재)**

- 생성된 코드를 처음부터 끝까지 같은 깊이로 읽는 방식은 양이 늘면 먼저 무너집니다. 그래서 **어디를 깊게 볼지 신호를 먼저 정해두고 그 지점만 파고듭니다.** 규칙에서 금지한 훅이 쓰였는지(모달 열림 상태를 `useState`로 들고 있거나 다단계 화면의 step을 직접 관리하면 공용 도구를 안 썼다는 뜻입니다), 상수를 어떻게 처리했는지, 순수 함수에 있으면 안 될 의존이 섞였는지가 그 신호입니다.
- 이 기준을 사람 머릿속에 두지 않고 **스킬 문서 64개와 레이어별 가이드 20개**로 남겼습니다. 에이전트의 쓰기 권한 범위, 검증 순서, 리뷰 심각도 기준도 저장소의 단일 규칙으로 정의했습니다. **제가 다시 설명할 수 없는 코드는 반영하지 않는다**는 기준을 지키고 있습니다.

**선언적으로 쓰고, 빠뜨린 경우가 드러나게**

- 결제수단이 늘어날 때마다 예외 분기가 화면 곳곳에 퍼지는 것을 막기 위해, 쿠폰 결제를 별도 분기로 두지 않고 결제수단 타입에 포함했습니다. 노출·완료·취소·금액 집계 판단은 도메인 함수와 `ts-pattern` 분기 한 곳에 모아, 새 수단이 추가될 때 빠뜨린 경우가 코드 작성 단계에서 드러나게 했습니다.
- 상담 상태에 따른 전송 경로 라우팅도 조건문 대신 `ts-pattern`으로 표현해, 상태가 늘어날 때 분기 표가 그대로 읽히게 했습니다. `es-toolkit`은 세 저장소 151개 파일에서 쓰고 있습니다.

**아키텍처와 개발 환경**

- 운영 중인 B2C 웹을 Next.js 14→16, Node 24, Turbopack으로 단계적으로 옮기며 호환 문제를 해결했고, TypeScript 네이티브 체커를 기존 툴체인과 함께 돌려 로컬 타입 검사를 **12.5초에서 1.9초로** 줄였습니다.
- 2026년 7월부터 테스트를 순수 함수·스키마 → API 계약 → UI 통합 → 브라우저 E2E로 나눠 도입했습니다. E2E를 처음 붙였을 때 10개 시나리오의 콜드 실행이 3.5분씩 걸리고 간헐적으로 실패해서, 원인을 잘못된 내비게이션 대기 조건과 반복 삽입되는 프로모션 오버레이로 분리해 20초·3회 연속 flaky 0으로 안정화했습니다.
- 성공만 반환하던 Mock이 실서버의 필수값·enum 계약 위반을 가린다는 것을 발견해, Mock을 끄고 실제 인증과 API로 확인하는 계약 테스트 환경을 따로 만들었습니다. 400 응답만으로는 어느 필드가 문제인지 알 수 없어 서버가 준 거절 코드와 필드 단위 위반 목록을 그대로 드러내게 했습니다.
- 2026년 8월에는 Sentry를 client·server·Edge에 도입하고 Web Vitals·릴리스·소스맵·MCP를 연결했습니다. trace를 통해 `next/link` prefetch가 보호 경로의 유저 정보 조회와 권한 검증을 미리 반복하는 흐름을 찾아 제거했습니다.
- 같은 달 일부 조회 실패가 전체 화면을 내리던 구조를 page·section·overlay Error Boundary로 나눴습니다. 오류가 난 기능만 다시 시도할 수 있게 하고, 정상인 형제 영역은 계속 사용할 수 있도록 했습니다.
