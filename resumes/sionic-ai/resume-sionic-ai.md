회원 약 15만 명, 제휴 기업·대학 1,800곳, 제휴 병원 400여 곳, 등록 프로그램 5,000개 규모의 플랫폼에서 국내 B2C 웹(모바일 브라우저·앱 내 WebView)·운영 백오피스·병원 어드민을 운영합니다. 2026년 1월부터 사내 유일 프론트엔드 개발자로 국내 세 제품을 맡고 있으며, 2026년 7월에는 글로벌 서비스 구축과 글로벌 CMS 신규 런칭도 담당했습니다.

구현 전 Jira·API 스펙·Figma·운영 맥락을 확인하고 PO·디자이너·백엔드·마케팅과 선택지를 맞춥니다. 결정 이유와 남은 한계는 문서와 글로 남깁니다.

**AI 상담 — 실시간 스트리밍과 하이브리드 전송 (2026.04 – 07, 스테이징 검증 중)**

- 콜백으로 전달되는 상담 서버 SSE를 순서가 보장되는 async generator로 바꾸고, `SubscribeConnectionAdapter`를 구현해 `@tanstack/ai` 계약에 연결했습니다.
- 전송 API는 상담사 연결 구간(`connecting`/`live`/`hold`)과 AI 구간(`ai`/`done`)으로 나누되, 화면에 그리는 응답은 상담 서버 SSE 한 곳으로 일원화했습니다.
- 사용자 메시지를 낙관적으로 먼저 표시한 뒤, 서버가 같은 메시지를 내려주면 1:1로 대응시켜 치환해 같은 문장을 반복 전송해도 중복되지 않게 했습니다. 형식이 어긋난 payload는 Zod로 단계별 복구하고, 실패 시 메시지와 상태를 되돌리며 구독 종료 시 SSE를 정리했습니다.
- 스트리밍 중 마크다운의 들여쓰기·목록 개행을 렌더 전에 정규화하고, 대기 인디케이터는 AI 구간에만 노출했습니다. 변환·정합성 로직은 테스트 36개로 고정했으며, 현재 고정 3초 재구독을 백오프와 이벤트 ID 기반 재개로 개선하는 과제를 남겼습니다.

**비개발자를 위한 운영 콘솔과 폼 시스템 (운영 백오피스·병원 어드민 2025.06 – 현재 / 글로벌 CMS 2026.07)**

- 운영자가 직접 쓰는 콘솔에서, 자주 바뀌는 서버 스키마와 사용자가 입력 중인 폼 상태 사이의 경계를 설계했습니다. 서버 DTO와 폼 모델 사이에는 변환 계층(Transfer Layer)을 두고 날짜·이미지·조건부 필드를 양방향으로 옮겨, 서버 응답 형식이 바뀌어도 고칠 파일이 한 곳에 모이게 했습니다.
- 글로벌 CMS에서는 서버가 모든 엔티티를 `translations[{ languageCode, ... }]` 배열로 주고받는데 운영자는 언어 탭을 오가며 입력합니다. 이 둘을 잇는 변환을 화면이 아니라 변환 계층이 책임지게 해서, 언어가 늘어나도 폼 컴포넌트는 바뀌지 않게 했습니다.
- 프로그램 5,000개가 이 폼을 거쳐 등록되고 검수됩니다. 공통 31개 필드에 앱별 필드를 얹는 구조로 나누고, 원본·검수·임시저장처럼 생명주기가 다른 흐름은 디렉터리부터 분리했습니다(임시저장은 병원 어드민에만 해당). 필드가 많고 거쳐 가는 건수가 많은 폼일수록 잘못된 값이 늦게 발견될 때의 손해가 크다고 봤습니다.
- 중첩 필드 경로와 값, 구독(`useWatch`), render-prop까지 타입을 추론하는 폼 팩토리 `createTypedForm<T>`을 만들어 세 앱과 공통 feature의 폼 15개에 적용했습니다. 잘못된 필드 경로와 Form API 값은 컴파일 단계에서 걸립니다.
- 결제수단이 늘어날 때마다 예외 분기가 화면 곳곳에 퍼지는 것을 막기 위해, 쿠폰 결제를 별도 분기로 두지 않고 결제수단 타입에 포함했습니다. 노출·완료·취소·금액 집계 판단은 도메인 함수와 `ts-pattern` 분기 한 곳에 모아, 새 수단이 추가될 때 빠뜨린 경우가 코드 작성 단계에서 드러나게 했습니다.
- 글로벌 CMS의 파일 업로드는 업로드 요청으로 Presigned URL과 필수 헤더를 받고 → 스토리지에 직접 PUT → 폼 저장 시 확정하는 3단계로 나눴습니다. 미리보기 단계에서 파일이 확정되지 않게 해 취소하고 나가도 고아 파일이 남지 않습니다. 스토리지로 보내는 PUT은 공용 axios 인스턴스의 baseURL·인증 인터셉터를 타면 서명이 깨지므로 `fetch`로 분리했습니다. 다중 선택과 병렬 업로드, 일부 실패 시 성공한 파일 보존, 드래그 정렬, 대표 이미지 역할 매핑까지 한 화면에서 끝나게 했습니다.
- 글로벌 CMS의 폼 테스트는 `mutation`이 호출됐는지 확인하는 데서 멈추지 않고, 실제 Drawer를 사용자처럼 조작해 상태를 가진 MSW에 저장하고 API로 다시 조회했습니다. 다국어 번역·기존 ID·조건부 그룹·이미지 순서가 왕복 후에도 보존되는지, 저장에 실패한 뒤 입력이 남아 재시도가 되는지를 검증합니다.
- 성공만 반환하는 Mock이 실서버의 필수값·enum·스토리지 계약 위반을 가린다는 것을 발견하고, MSW를 끄고 실제 인증과 dev API로 확인하는 계약 테스트 환경을 따로 만들었습니다. 400만 보고는 어느 필드가 문제인지 알 수 없어서, 서버가 준 거절 코드와 필드 단위 위반 목록을 그대로 드러내도록 테스트를 짰습니다. 이렇게 찾은 계약 차이는 폼과 타입, Mock에 다시 반영했습니다.

**글로벌 서비스와 글로벌 CMS — 3주 만의 0→1 (2026.07)**

기존 세 제품의 운영과 장애 대응을 병행하면서 진행했습니다. 같은 달 B2C 웹에만 `fix` 44건·`hotfix` 11건을 처리했습니다. 3주를 이렇게 나눴습니다 — **1주차** 프로토타입에 레이어 구조를 입히고 이후 전달받은 변경분을 반영하며 위험한 코드를 걷어내기, **2주차** 확정된 API 스펙 반영과 테스트 코드 작성, **3주차** QA·추가 요청 대응과 실서버 검증 후 배포.

- PO가 만든 프로토타입을 이어받아 제품화했습니다. Vite SSG 기반에 라우트 24개·컴포넌트 88개가 2,021줄짜리 `App.jsx` 한 파일과 얽혀 있었고, 화면을 모두 반영해 Next.js 16 App Router와 `strict` TypeScript로 옮겼습니다. localStorage와 성공만 반환하는 Mock에 의존하던 데이터 흐름은 실제 API 계약과 TanStack Query 기반 서버 상태로 단계적으로 교체했습니다.
- 데이터를 조회하는 10개 라우트에 RSC 서버 prefetch와 페이지별 `HydrationBoundary`를 적용했습니다. 필터 상태는 URL을 단일 출처로 삼아 공유·새로고침·뒤로가기가 모두 같은 경로를 타게 했습니다.
- 프로토타입의 언어 레지스트리와 RTL·영문 폴백 구조를 next-intl 라우팅과 타입 안전 UI 사전으로 옮겼습니다. 영어·한국어·아랍어 3개 언어를 라우팅하고 아랍어에는 RTL 레이아웃을 적용하며, API 요청에는 `Accept-Language`를 전달합니다. 사전은 영어·한국어를 필수로 두어 번역 누락이 컴파일 단계에서 걸리게 하고, 나머지는 영어로 폴백합니다. 기존 hreflang과 sitemap도 Next.js Metadata 구조에 맞게 이전했습니다.
- 200건을 한 번에 내려받던 목록을 20건 단위 무한스크롤과 TanStack Virtual로 바꿨습니다. 화면 폭을 재기 전에는 첫 페이지를 그대로 그려 SSR HTML을 유지하고, 카드가 20개 넘게 쌓인 뒤에도 DOM에는 보이는 행만 남는 것을 E2E로 확인했습니다. URL 복원과 뒤로가기도 별도 E2E로 검증합니다.
- 서버의 `REQUIRED`/`OPTIONAL` 옵션 계약을 Zod 판별 유니온으로 모델링했습니다. 검증 오류가 나도 포커스가 옮겨가지 않던 커스텀 Select와 옵션 칩을 RHF `Controller`에 연결하고, 오류 순서에 따른 포커스 이동과 accessible name, `role="alert"`를 회귀 테스트로 고정했습니다.
- Next.js soft navigation 때문에 앞선 예약자의 개인정보 입력값과 선택 옵션이 다음 예약 화면에 남을 수 있다는 것을 확인하고, 재진입과 성공 시에는 초기화하되 제출 실패 시에는 입력을 보존하도록 상태 생명주기를 다시 나눴습니다. 실제 soft navigation E2E로 회귀를 막았습니다.
- 운영자용 글로벌 CMS는 병원·시술·블로그·FAQ의 등록·수정·발행 흐름을 12일 만에 단독으로 만들었습니다(커밋 83건). 병원별 시술 항목은 백엔드에 Excel을 넘겨 처리하는 대신 운영자가 직접 쓰는 다국어 CRUD·일괄 업로드·soft delete 화면으로 만들고, 활성 항목만 상품의 필수·선택 그룹에 연결되게 한 뒤 선택 개수 계약을 폼에서 검증했습니다. 폼 저장과 재조회 왕복은 상태를 가진 MSW로, 실서버 계약은 별도 테스트 환경으로 확인했습니다.

**아키텍처·품질·개발 환경**

- 정산 서비스는 메인과 도메인이 달라 쿠키를 공유할 수 없었습니다. 처음 구현했던 URL 토큰 전달은 서버 access log와 Referer에 토큰이 남을 위험이 있어, **form POST BFF로 바꾸고 `referrer-policy(no-referrer)`·CSP `form-action` 고정·open redirect 방어를 적용**했습니다. ([기술 글](https://blog.bambyul.com/ko/blog/정산-서비스를-별도-호스트로-분리하며-도메인-간-토큰-전달을-설계한-과정))
- 합류 시점의 B2C 웹은 6-layer FSD 골격은 있었지만 `@legacy`에 250개 파일이 남아 있었고, 앞선 담당자들이 석 달간 442개에서 여기까지 줄여온 상태였습니다. 남은 250개를 **26일 만에 0개로** 옮겼습니다(2025.05–06).
- 옮기고 나니 레이어는 있는데 무엇이 어디 속하는지가 사람마다 달랐습니다. 레이어별 책임과 재사용 카탈로그를 가이드 문서 6개로 정의하고, 역방향 의존은 외부 의존성 없이 직접 만든 ESLint 플러그인으로 lint 단계에서 막았습니다. 규칙을 문서로만 두면 지켜지지 않는다고 봤습니다.
- 그 규칙 위에서 코드베이스가 세 배 가까이 늘었습니다(`features` 49→298, `shared` 181→497, `pages` 27→91).
- 신규 글로벌 서비스는 `entities`를 빼고 `_app/_pages/widgets/features/shared` 5레이어로 줄였습니다. 반복되는 행동만 추출하되 화면별 정책은 주입하는 방식으로 지나친 공통화를 피했습니다.
- 3개 Next.js 앱과 13개 워크스페이스 패키지에서 서버 상태는 TanStack Query, 입력 중인 값은 타입이 지정된 Form, DTO 차이는 Transfer Layer, 목록 필터와 페이지는 URL이 소유하도록 경계를 정했습니다. 여러 앱에서 계약이 안정된 도메인만 공통 패키지로 올리고, 글로벌 CMS처럼 아직 계약이 독립적인 영역은 앱 안에 남겨뒀습니다.
- 테스트는 순수 함수·스키마 → API 계약·저장 왕복 → UI 통합 → 브라우저 E2E 순으로 나눴습니다. HTTP 실패와 응답 스키마 불일치, 폼 저장·재조회는 낮은 계층에서 검증하고, 브라우저에서만 증명할 수 있는 soft navigation·SSR HTML·IntersectionObserver·가상화의 결합은 Playwright로 확인합니다. 실서버 계약 테스트에서 찾은 필수값·enum 불일치는 폼과 타입에 되돌려 반영했습니다.
