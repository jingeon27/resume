[엘리스 프론트엔드팀 소개](https://elice.io/ko/resources/blog/ai-a-z-part2)에서 실시간 수업·코드 에디터와 내부 라이브러리·개발 환경을 함께 만든다는 내용이 기억에 남았습니다. 저도 여러 제품을 맡으면서 화면을 만드는 일과 공통 코드를 정리하는 일을 함께 해 왔습니다. 병원 관리자와 Back-Office의 폼은 같은 필드를 공유하되 제출 처리는 따로 두었고, 검색 필터는 화면별 예외가 많아지자 직접 조합하는 구조로 바꿨습니다. 이런 경험을 교육·평가·클라우드 서비스를 만드는 엘리스에서 이어 가고 싶습니다.

상담 기능에서는 수정할 수 없는 두 서버의 SSE를 하나의 화면에 연결했습니다. 엘리스에서는 이 경험을 실시간 기능 개발에 보태고, 연결이 끊기거나 요청이 실패하는 상황을 서버 개발자와 함께 다뤄 보고 싶습니다. 설계안과 운영 결과를 동료들과 검토하며 기술적인 피드백도 주고받고 싶습니다.

#### 코딩 에이전트 작업 방식·검사 비용 조정 | 2026.04 – 현재

에이전트가 의도와 다르게 구현한 부분의 기준을 스킬에 남기고, 정적으로 검사할 수 있는 기준은 lint 규칙으로 옮겼습니다. 현재 기능 개발·리팩터링에서는 제출된 제품 코드와 테스트를 읽고, 부족한 부분을 짚어 수정본을 다시 확인합니다.

**티켓·plan 검토 → 테스트 작성 → 에이전트 구현·에이전트 코드 리뷰 → 변경분 테스트·lint·typecheck → 제 diff 리뷰·로컬 화면 확인 → 전체 CI(테스트·knip·lint) → QA 더블 체크 요청** 순서로 진행하고, 문제가 나오면 앞 단계로 돌아갑니다.

- 새 기능의 기대 동작은 BDD 형식의 `*.spec`에 적어 컴포넌트별로 빠진 조건을 확인합니다. 운영·QA 오류는 `*.test`로 재현하고, 새 패턴의 테스트는 제품 코드를 일부러 깨뜨려 실패하는지 확인한 뒤 넣습니다.
- **lint·계약 검사(2026.08 – 09):** 복지몰의 직접 import 경고 **271건**을 정리해 9월 1일 error로 올렸습니다. 9월 29일에는 동적 import 등을 놓치는 규칙과 테스트를 보완하도록 지시하고 결과를 확인했습니다. 추가한 테스트를 수정 전 규칙에 돌렸을 때 **8건이 실패**했습니다. 글로벌 서비스도 테스트의 응답 스키마 위반을 실패로 처리하도록 바꾸고, 목 데이터를 틀리게 만들어 확인했습니다.
- worktree마다 전체 검사를 반복하니 CPU 경합이 생겼습니다. 로컬 lint·테스트는 변경 파일과 영향 범위를 중심으로 돌리고, 타입 검사는 저장소에 따라 패키지 또는 앱 단위로 유지합니다. 전체 검사는 CI에서 수행하고 결과까지 확인합니다. 타입 인지 lint는 검사 시간이 **3.3배** 늘어 도입을 보류했습니다.
