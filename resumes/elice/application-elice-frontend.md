## 소개·지원동기

React·TypeScript로 모바일 웹과 관리자 서비스를 개발하는 김진건입니다. 세이프닥에서 2026년 1월부터 사내 유일한 프론트엔드로 일하며, 4월부터 개발·운영을 단독으로 맡고 있습니다. 현재 가입 회원 약 15만 명의 복지몰과 병원 관리자, Back-Office, 글로벌 사용자 서비스·CMS를 담당합니다. 최근에는 건강검진 프로그램 관리부터 기업지원·예약·결제까지 세 제품에 추가했고, Sentry 도입과 테스트 체계 재구축도 맡았습니다.

[엘리스 프론트엔드팀 소개](https://elice.io/ko/resources/blog/ai-a-z-part2)에서 실시간 수업·코드 에디터와 내부 라이브러리·개발 환경을 함께 만든다는 내용을 읽었습니다. 제가 지금 하는 일과 연결되는 부분이 많았습니다. 여러 제품의 폼과 필터를 정리하면서 무엇을 공유하고, 어떤 처리를 각 화면에 남길지 고민해 왔습니다. 상담 화면에서는 서로 다른 두 서버의 메시지를 받아 표시하고 연결을 유지하는 방식도 다뤘습니다.

엘리스에서도 제품 기능을 개발하면서 공통 코드와 운영 문제를 함께 다루고 싶습니다. 특히 실시간 기능에서 연결이 끊기거나 요청이 실패했을 때 사용자가 작업을 이어갈 수 있도록 만드는 일에 관심이 있습니다. 지금까지 맡아 온 화면·조회·오류 대응 경험을 보태고, 서버 개발자와 협업하며 연결과 복구를 더 깊게 다뤄 보고 싶어 지원했습니다.

## 건강검진 도메인 내재화 | 2026.09 – 현재

건강검진은 아임웹과 전화 문의로 따로 운영하고 있었습니다. 한 제휴 병원이 세이프닥에서 검진 예약을 받으려 했지만, 기존 비급여 프로그램 구조로는 검사 구성, 기업지원 검진, 예약금 결제를 처리하기 어려웠습니다.

개발팀장·부팀장과 빠진 동작과 예외를 확인하며 세 제품의 프론트엔드를 맡았습니다. Back-Office에는 검사항목·필수 및 선택 검사 구성, 기업지원 코드·서류 확인, 결제내역과 결제취소·환불 승인을 구현했습니다. 병원 관리자는 검진 프로그램을 조회하고 예약을 관리하도록 하되, 검진만 운영하는 병원과 다른 진료과도 운영하는 병원의 메뉴·편집 범위를 구분했습니다. 복지몰에는 검진 상세, 검사 선택·기업 검진 코드 입력, 예약·예약금 결제와 예약 상세를 개발했습니다. 9월 9일부터 두 주 동안 순차 개발해 23일 운영에 배포했고, 30일 정식 오픈했습니다.

검사항목을 일괄 저장할 때 일부만 성공하면 재시도에서 중복 등록될 수 있었습니다. 성공·실패 모두 서버 목록을 다시 받아 발급된 id를 폼에 반영하도록 했습니다. 비급여와 검진은 같은 상세 경로를 쓰되 내부 화면과 신청 폼을 나눴습니다. 결제 복원은 이전 시도의 값이 남지 않도록 `orderId`와 현재 스키마를 확인하는 `sessionStorage` 방식으로 바꿨습니다. 같은 탭에서 입력을 한 번만 복원하고, 결제창 실패 복귀와 승인 요청 실패 경로는 dev API 서버 E2E로 확인했습니다.

## Sentry 도입과 운영 오류 추적 | 2026.08 – 09

복지몰에 Sentry를 client·server·edge별로 연결하고, 에러 레벨·중복 수집·민감 정보 전송 정책을 정했습니다. 8월 19일부터 구현해 27일 운영에 배포했습니다. 설정만으로 헤더·쿠키·URL이 모두 제외되지 않아 SDK 소스를 따라 전송 경로를 확인하고, 이벤트·breadcrumb·transaction·span을 각각 정리했습니다.

release와 브라우저 소스맵을 연결해 실제 artifact bundle이 생성되는지 확인하고, LCP·FCP·TTFB는 브라우저 envelope를 E2E로 검증했습니다. 서버 소스맵은 업로드 502 때문에 제외해 서버 스택이 minify된 채 남습니다. 이후 수집한 Bottom Sheet 크래시를 라이브러리의 null ref 접근까지 추적해 버전을 올렸습니다. 수정 전 57명 이상에게 75건 발생한 오류 그룹은 9월 10일 수정 배포 뒤 28일까지 0건이었습니다.

## 테스트 체계 재구축 | 2026.07 – 현재

7월 20일부터 관리자 서비스 모노레포와 복지몰의 테스트 체계를 다시 구성했습니다. 순수 함수·스키마, 실제 UI·폼, dev API 계약, 브라우저 흐름을 나누고 Vitest·React Testing Library·MSW·Playwright를 사용합니다. 작성은 에이전트에 맡기고, 저는 기대 동작과 누락 조건, 실제 실패를 잡는지를 확인합니다.

제품의 제출 로직을 복제하던 Harness는 실제 Drawer를 렌더하도록 바꾸고, 무엇이든 성공시키던 Mock에는 확인한 서버 제약을 반영했습니다. 등록·수정 Drawer 리팩터링에서는 기대 payload를 먼저 고정해 잠복 버그 2건을 찾았습니다. 9월에는 병원 관리자의 등록부터 Back-Office의 검수중·반려·승인까지 dev API 서버로 확인하는 E2E를 추가했습니다.

새 기능은 BDD 형식의 `*.spec`에 컴포넌트별 기대 동작을 적고 빠진 조건을 확인합니다. 운영·QA 오류는 `*.test`로 재현합니다. 새 패턴의 테스트는 제품 코드를 일부러 깨뜨려 실패하는지 확인한 뒤 넣습니다. dev API 계약 테스트는 PR을 막지 않는 별도 단계로, E2E는 CI 밖에서 실행합니다.

## 그 밖의 개발 경험

### 검색 필터 공통화 | 2026.06 – 08

여러 화면이 설정 객체를 공통 렌더러에 넘기는 구조였는데, 화면별 예외가 렌더러 안에 계속 쌓였습니다. 필터가 각자의 동작을 갖고 화면에서 필요한 필터를 조합하도록 바꿨습니다. 각 화면에 JSX를 적어야 하지만 공용 렌더러에 예외 분기를 더하는 일을 줄일 수 있었습니다. Zod 스키마로 URL·폼·API 필드를 맞추고 운영 화면 27개를 전환했습니다.

처음 바꿀 때는 선택지 조회의 수동 페이지·요청 순서 관리도 그대로 옮겼습니다. 이후 이름이 같고 코드가 다른 기업이 목록에서 사라지는 것을 찾아 조회를 도메인 쪽으로 옮겼습니다. 공용 UI에는 입력·스크롤 처리를 남기고, 목록과 선택지의 query key도 나눠 갱신 범위를 구분했습니다.

### 두 서버의 SSE를 연결한 상담 화면 | 초기 통합 2026.06

AI 답변과 상담사 메시지가 서로 다른 서버의 SSE에서 왔고, 두 서버를 수정할 수 없었습니다. 네트워크에서 상담 SSE에 두 종류의 메시지가 모두 들어오는 것을 확인해 화면 표시를 하나로 합쳤습니다. AI 생성이 끝까지 진행되도록 AI 스트림의 연결도 유지하고, 상담 상태에 따라 메시지를 보낼 대상을 나눴습니다.

이후 상담 SSE를 `@tanstack/ai`의 메시지 모델로 전달하는 어댑터를 만들었습니다. AI 생성이 브라우저 연결과 요청 시간 제한에 영향을 받는 제약은 남아 있습니다.

## 코딩 에이전트와 일하는 방식

에이전트가 의도와 다르게 구현한 부분의 기준은 스킬에 남기고, 정적으로 검사할 수 있는 기준은 lint 규칙으로 옮겼습니다. 현재 기능 개발·리팩터링은 제출된 제품 코드와 테스트를 읽고, 부족한 부분을 짚어 수정본을 다시 확인합니다.

**티켓·plan 검토 → 테스트 작성 → 에이전트 구현·에이전트 코드 리뷰 → 변경분 테스트·lint·typecheck → 제 diff 리뷰·로컬 화면 확인 → 전체 CI(테스트·knip·lint) → QA 더블 체크 요청** 순서로 진행하고, 문제가 나오면 앞 단계로 돌아갑니다.

위 테스트 기준으로 검증하고, 검사를 추가할 때 시간도 확인합니다. 타입 인지 lint는 검사 시간이 3.3배 늘어 도입을 보류했습니다.

## 합류 후 하고 싶은 일

먼저 맡을 제품의 사용 흐름과 기존 코드, 팀의 배포·운영 방식을 익히겠습니다. 기능을 개발할 때는 정상 동작과 실패 후 복구를 함께 확인하고, 공통 코드를 바꿀 때는 다른 제품의 사용처도 살피겠습니다. 제 설계안에서 놓친 조건을 동료들과 확인하고, 운영 결과를 보고 다시 고치는 경험을 더 쌓고 싶습니다.
