## 자기소개·지원동기

사용자 화면과 관리자 서비스를 개발하며, 기능이 연결되는 과정과 운영 중 실패하는 경로를 함께 확인해 온 프론트엔드 엔지니어 김진건입니다. 세이프닥에서 2026년 1월부터 사내 유일한 프론트엔드로 일하고, 4월부터 개발·운영을 단독으로 담당합니다. 현재 가입 회원 약 15만 명의 복지몰과 병원 관리자, Back-Office, 글로벌 사용자 서비스·CMS까지 다섯 제품을 맡고 있습니다.

교육·평가·클라우드 기능을 제공하는 엘리스에서는 개별 화면의 완성도와 여러 제품이 함께 사용하는 기반의 품질이 모두 중요하다고 생각합니다. [프론트엔드팀 소개](https://elice.io/ko/resources/blog/ai-a-z-part2)에서 실시간 기능뿐 아니라 내부 라이브러리와 개발 환경도 함께 만드는 업무를 보고 관심을 갖게 됐습니다. 사용자가 작업을 이어갈 수 있는 화면과 개발자가 안정적으로 기능을 바꿀 수 있는 환경을 함께 다루고 싶어 지원했습니다.

저는 병원의 프로그램 설정부터 사용자의 예약·결제까지 세 제품의 흐름을 연결했고, 서로 다른 SSE를 하나의 상담 화면에 통합했습니다. 공통 컴포넌트의 예외가 늘어났을 때는 화면이 직접 조합하는 구조로 바꾸고, 조회와 폼의 책임도 다시 나눴습니다. 이 경험을 바탕으로 엘리스에서도 기능 구현과 공통 기반 개선에 기여하고, 동료들과 설계의 근거와 비용을 검토하며 실시간 서비스 개발 경험을 넓히고 싶습니다.

## 강점과 대표 경험

### 여러 제품에 걸친 요구사항을 실제 사용 흐름으로 연결합니다

2026년 9월 건강검진 기능을 내재화했습니다. 기존에는 아임웹에서 정보를 본 뒤 전화로 문의했고, 복지몰과 병원 관리자에는 검진 구성·예약금 결제를 처리할 화면이 없었습니다. 한 제휴 병원이 세이프닥 안에서 검진 예약을 받으려면 운영팀의 설정, 병원의 관리, 사용자의 신청이 함께 바뀌어야 했습니다.

개발팀장·부팀장과 전달받은 요구사항의 빠진 동작과 예외를 확인하고, Back-Office의 검사항목·검진 구성 등록, 병원 관리자의 검진 예약 관리·예약금 결제취소 요청 접수, 복지몰의 상세·예약·결제를 개발했습니다. 9월 9일부터 두 주 동안 순차 개발해 23일 운영에 배포했고, 30일 정식 오픈했습니다.

비급여와 검진은 같은 상세 경로를 쓰지만 내부 뷰를 나눠 각자의 조회·폼을 유지하고, 상단바와 인증 후 이동은 공유했습니다. 결제 복원은 처음의 Zustand persist 방식에서 `orderId`와 현재 스키마를 확인하는 `sessionStorage` 방식으로 바꿨습니다. 같은 탭에서 결제 시도별 입력을 한 번 복원하도록 하고, 결제창 실패 복귀와 승인 요청 실패 경로는 dev API 서버 E2E로 확인했습니다.

### 공통화의 범위와 운영 중 실패를 함께 봅니다

2026년 6~8월에는 설정 객체를 받는 공통 검색 렌더러에 화면별 예외가 쌓인 문제를 다뤘습니다. 필터가 각자의 동작을 갖고 화면에서 필요한 필터를 조합하도록 바꿔 운영 화면 27개를 전환했습니다. 화면마다 JSX 조합을 적는 비용은 남지만, 공용 렌더러에 예외 분기를 계속 더하는 일을 줄일 수 있었습니다. 이후 선택지 조회도 도메인 쪽으로 옮기고 목록과 선택지의 query key를 나눠 무효화 범위를 구분했습니다.

운영에서는 Sentry의 release·브라우저 소스맵을 연결하고 의료 정보가 포함될 수 있는 전송 경로를 확인했습니다. Bottom Sheet 드래그 크래시는 라이브러리의 null ref 접근까지 추적해 버전을 올렸습니다. 수정 배포 전까지 57명 이상에게 75건 발생한 오류 그룹은 9월 10일 배포 뒤 28일까지 0건이었습니다. 실제 오류를 추적하고, 수정 뒤 같은 기록이 다시 나타나는지도 확인하는 방식으로 일합니다.

## AI를 활용하는 방식

에이전트가 구현을 맡아도 요구사항과 검증 기준은 제가 확인합니다. 현재 기능 개발·리팩터링에서는 제출된 제품 코드와 테스트를 읽고, 부족한 부분을 짚어 수정본을 다시 검토합니다. 의도와 어긋난 구현이 반복되면 판단 기준을 저장소별 스킬이나 lint 규칙에 남깁니다.

**티켓·plan 검토 → 테스트 작성 → 에이전트 구현·에이전트 코드 리뷰 → 변경분 테스트·lint·typecheck → 제 diff 리뷰·로컬 화면 확인 → 전체 CI(테스트·knip·lint) → QA 더블 체크 요청** 순서로 일하며, 문제가 나오면 앞 단계로 돌아갑니다.

새 기능의 기대 동작은 BDD 형식의 `*.spec`에 적어 컴포넌트별 누락 조건을 확인하고, 운영·QA 오류는 `*.test`에 재현합니다. 새 패턴의 테스트는 제품 코드를 일부러 깨뜨려 실제로 실패하는지 확인한 뒤 넣습니다. 검사 비용도 함께 확인해, 타입 인지 lint 규칙은 실행 비용이 3.3배 늘어나는 것을 보고 도입을 보류했습니다.

## 성장 방향과 합류 후 목표

합류하면 먼저 사용자 작업 흐름, API 계약, 공통 라이브러리의 사용 범위와 팀의 배포·운영 방식을 익히겠습니다. 맡은 기능에서는 기대 동작과 실패·복구 경로를 함께 정리하고, 기존 공통 기반을 활용할 부분과 제품에 남길 부분을 동료들과 검토하겠습니다.

지금까지는 여러 제품을 단독으로 개발·운영하며 문제를 끝까지 추적하는 경험을 쌓았습니다. 앞으로는 설계 선택과 운영 결과를 동료들과 검토하고, 실시간 연결의 수명·복구와 성능을 더 깊게 다루는 엔지니어로 성장하고 싶습니다.
