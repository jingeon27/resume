## 소개

사용자와 서비스 운영자가 함께 쓰는 제품을 개발해 온 프론트엔드 엔지니어입니다. React·TypeScript로 복지몰과 병원 관리자·백오피스를 맡으며 예약·리뷰·쿠폰·결제·정산을 다뤘습니다. 직접 써 보며 찾은 불편과 요구사항에서 빠진 동작을 담당자와 논의하고 구현에 반영합니다.

기능을 늘리면서 상태 관리·폼·공통 UI·데이터 조회 기준을 정하고 기존 코드를 리팩터링했습니다. AI 개발 workflow로 구현하며 코드와 테스트를 직접 읽고 화면을 띄워 동작을 확인합니다. 출시 뒤 오류 대응과 다음 변경까지 생각하고, 반복되는 판단은 skills와 lint rule에 남깁니다.

#### 데이터 조회 구조와 성능 개선 | 2025.05 – 현재

입사 당시 화면은 서버 컴포넌트의 `ensureQuery` 결과를 render props로 받아 그렸습니다. 일부 hydration이 있어도 화면이 Query 캐시를 구독하지 않아 클라이언트의 캐시 무효화가 반영되지 않았고, 조회 조건 변경도 서버 내비게이션에 의존했습니다. 2025년 5월부터 화면별로 prefetch·hydration·useQuery 구조로 옮겨 서버 초기 조회와 클라이언트의 갱신·무효화를 같은 캐시에서 처리하도록 했습니다.

- 글로벌 서비스의 클라이언트 번들에 목 백엔드 코드가 포함되는 것을 발견했습니다. 도메인 코드의 공개 경로를 통해 들어오는 의존을 분리해 앱 번들을 **2,564KB에서 1,880KB로 줄였습니다.**
- Sentry에서 로그인 상태의 링크 prefetch가 proxy의 권한 검증과 `member/info` 요청까지 유발하는 것을 확인했습니다. 불필요한 prefetch를 끄고 해당 요청이 사라지는 것을 확인했습니다.
- Next.js 14→16·React 18→19 전환은 Turbopack과 Next.js 16의 로컬 개발 속도 개선을 고려해 진행했습니다. 비동기 API와 달라진 캐시 동작에 맞춰 코드를 수정하고 링크 직접 진입·뒤로가기·새로고침을 확인했습니다.
- 관리자 검색 오류는 localhost에서 `dev`로 실행할 때 나타나지 않아 `build` 후 `start`로 확인했습니다. 목록 7개 중 6개에서 재현하고 업스트림 캐시 이슈까지 추적했습니다. 서버가 검색 조건을 읽지 않는 화면의 같은 경로 쿼리 변경은 History API로 처리해 불필요한 RSC 요청을 없앴습니다.
- 지역·진료과 검색의 canonical·제목·사이트맵을 구성하고, 제휴 병원이 3곳 이상인 조합만 사이트맵에 넣었습니다. 병원·시술 상세의 `h1`과 메타데이터, 검진 검사 항목의 JSON-LD도 정리했습니다.

#### 폼·검색 필터와 FSD 구조 개선 | 2025.06 – 현재

- 가족·날짜 값이 Query 캐시·Zustand·로컬 상태에 흩어져 가족 추가 시 날짜가 어긋나던 예약 폼을 정리했습니다. 서버 목록은 Query, 작성 중인 값은 React Hook Form, 제출 조건은 Zod가 맡도록 나누고 가족 선택과 목록 동기화를 분리했습니다.
- 화면별 예외가 쌓이던 공통 검색 필터를 화면별 조합으로 바꿔 운영 화면 27개를 전환했습니다. JSX 일부 반복은 감수하고, URL·폼·API의 필드 계약은 같은 Zod 스키마로 맞췄습니다.
