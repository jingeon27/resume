## 소개

사용자가 예약하는 복지몰과 병원 관리자·백오피스를 함께 개발하는 프론트엔드 엔지니어입니다. React·TypeScript·Next.js로 제품을 만들며, 사용자의 신청이 병원과 운영팀의 업무로 이어지는 흐름을 다뤄 왔습니다.

요구사항에서 빠진 동작과 예외를 확인하고 담당자와 의견을 맞춥니다. 모바일 리뷰를 직접 써 보며 발견한 선택 UI의 불편을 PO에게 공유했고, 검진 예약의 자동 이동 요청에서는 선택을 수정하는 경우를 짚어 담당자와 동작을 조정했습니다. 출시 뒤에는 Sentry로 오류를 추적해 영향을 받은 사용자와 원인을 확인합니다.

서버 데이터와 사용자 입력, 화면 상태의 책임을 나눠 사람이 읽고 검증하기 쉬운 코드를 만듭니다. 기술을 바꿀 때는 호환성과 유지보수·검증 비용도 함께 따져봅니다. AI 개발 workflow로 구현을 진행하면서 코드와 테스트를 직접 읽고 화면을 띄워 확인합니다. 반복해서 고친 내용은 skills와 lint rule에 남겨 다음 작업에 반영합니다.

건강검진은 아임웹에서 정보를 본 뒤 전화로 문의해야 했습니다. 제휴 병원이 세이프닥에서 검진 예약을 받기를 요청했지만, 기존 비급여 프로그램과 검사 구성·기업지원 코드·예약금 흐름이 달라 별도 기능이 필요했습니다. 개발팀장·부팀장과 빠진 동작과 예외를 확인하며 세 제품의 프론트엔드를 맡았습니다. 9월 9일부터 개발해 23일 운영에 배포했고, 30일 정식 오픈했습니다.

- 백오피스에는 검사항목·필수 및 선택 검사 구성, 기업지원 코드·서류 확인, 결제내역 조회와 결제취소·환불 승인 기능을 만들었습니다. 병원 관리자에는 프로그램 조회와 예약 관리를 추가하고, 병원이 직접 처리할 수 없는 예약금 결제취소는 요청 접수로 안내했습니다.
- 복지몰에는 검진 상세·검사 선택·기업 검진 코드 입력·예약금 결제·예약 상세를 구현했습니다. 기존 상세 경로는 유지하면서 비급여와 검진의 화면·신청 폼을 나누고, 상단바와 인증 후 이동은 공유했습니다.
- 일괄 저장은 일부 항목만 성공할 수 있어, 서버 목록을 다시 받아 발급된 ID를 폼에 반영했습니다. 재시도할 때 이미 저장된 항목을 신규 항목으로 중복 전송하지 않도록 했습니다.
- 모바일 토스페이먼츠 결제창에서 실패로 돌아오면 문서가 다시 로드돼 신청 내용이 사라집니다. 전역 Zustand persist 대신 `orderId`와 입력값을 `sessionStorage`에 저장하고, 같은 결제 시도이면서 현재 Zod 스키마를 통과한 값만 한 번 복원하도록 바꿨습니다.
- 결제 실패 복귀의 입력 복원과 승인 요청 실패 시 예약 목록 이동을 dev API 서버 E2E로 확인했습니다.

- 휴무 요일에도 병원이 날짜별 진료시간을 지정할 수 있도록 임시 진료일 기능을 추가했습니다. 서버가 같은 배열에 구분해 보내는 임시 휴무·진료일을 폼에서는 따로 편집하게 하고, 복지몰의 예약 가능 시간 판정에도 반영했습니다.

#### Sentry 도입과 운영 오류 대응 | 2026.08 – 현재

8월 19일부터 복지몰의 브라우저·서버·Edge에 Sentry를 적용해 27일 운영에 배포했습니다. 오류의 사용자 영향과 심각도를 나누고 release·브라우저 소스맵을 연결했습니다.

- SDK 소스를 읽고 event·breadcrumb·transaction·span에 담기는 의료·인증 정보를 제거했습니다. 같은 오류가 API 처리와 Error Boundary를 거치며 중복 수집되지 않게 하고, 차단 게이트로 의미 없는 전송을 줄였습니다.
- Bottom Sheet 드래그 크래시는 라이브러리의 null ref 접근까지 추적했습니다. 버전을 올리면서 달라진 snap point 규칙은 공통 Root에서 변환해 기존 사용처를 유지했습니다. 수정 배포 전 누적 75건·57명 이상에게 발생한 오류 그룹은 9월 10일 배포 뒤 28일까지 18일간 0건이었습니다.
- 회원 정보 조회의 모든 실패가 로그아웃으로 이어지던 정책을 확인했습니다. 인증 거절인 401과 타임아웃·서버·네트워크 오류를 나눠 일시적인 조회 실패로 로그인 상태를 잃지 않게 수정했습니다. 9월 23일 배포 뒤 28일까지 관련 CS와 Sentry 이슈가 없음을 확인했습니다.
- Sentry의 pageload 워터폴에서 배너 링크가 화면에 들어오기만 해도 여러 경로를 prefetch하는 것을 발견했습니다. 해당 링크의 prefetch를 끄고 불필요한 요청이 사라지는 것을 확인했습니다.
- 관리자 서비스에는 독립적으로 복구할 수 있는 기능 단위로 Error Boundary를 나눴습니다. 목록·상세·오버레이 일부가 실패해도 헤더와 정상 구획은 유지하고, 실패한 구획만 다시 시도하도록 했습니다.

#### SSR·라우팅과 검색 노출 개선 | 2026.04 – 현재

- 서버 조회 결과를 render props로 전달하던 상담 화면을 TanStack Query prefetch·hydration과 클라이언트 구독으로 바꿨습니다. 서버 초기 데이터와 이후 조회·무효화가 같은 캐시를 사용하게 했습니다. React 18→19·Next.js 14→16 전환도 진행했습니다.
- 인증을 마친 사용자가 화면을 이동하다 앱이 멈추는 오류를 Sentry에서 확인했습니다. Next.js 라우터 소스를 읽어 서버 컴포넌트의 `redirect()`가 하드 내비게이션으로 처리될 때 훅 호출 순서가 어긋나는 경로를 찾고, 진입 판정을 렌더 전 proxy로 옮겼습니다.
- 검색 페이지의 서버 prefetch와 클라이언트 훅이 같은 URL을 다른 스키마로 읽어 `queryKey`가 달랐습니다. HTML에 목록 대신 로딩 상태가 나가는 원인을 찾아 같은 스키마로 조건을 만들게 하고, 시술·병원 탭과 필터·통합 검색 네 조합의 첫 렌더를 테스트했습니다.
- Next.js 버전업 뒤 관리자 검색이 멈추는 오류는 개발 서버·jsdom에서 재현되지 않아 프로덕션 빌드로 확인했습니다. 목록 7개 중 6개에서 재현하고 업스트림 캐시 이슈를 추적했습니다. 서버가 검색 조건을 읽지 않는 화면은 같은 경로의 조건 변경을 History API로 처리해 RSC 요청 없이 클라이언트 목록을 갱신했습니다.
- 지역·진료과 검색은 기존 필터 URL 중 조건이 명확한 주소를 색인 대상으로 열고 canonical·제목·사이트맵을 구성했습니다. 제휴 병원이 3곳 이상인 조합만 사이트맵에 넣었습니다.
