## 소개

읽기 쉬운 코드로 제품을 만들고 운영하는 프론트엔드 엔지니어입니다. 일하면서 발견한 사용성 문제나 요구사항의 빈틈은 담당자와 논의해 보완합니다.

구현은 AI에게 맡기고 코드와 테스트는 직접 읽습니다. 빠진 조건이 없는지 확인하고, 변경한 화면은 dev 환경에 띄워 직접 동작을 확인합니다. 같은 지적이 반복되면 skills와 lint 규칙에 남깁니다.

기술을 선택할 때는 트레이드오프를 파악하고 현재 서비스에 맞는지 판단합니다. 오류를 해결할 때는 라이브러리나 프레임워크 코드도 읽어 가며 원인을 찾습니다.

왓타임에서 채용 관리 서비스 RoundHR을 만들며 채용 페이지와 지원서 설정을 개발했는데, 패스오더 채용 페이지도 RoundHR로 운영되고 있어 반가웠습니다. 페이타랩 웹 파트의 FEConf 후기에서 백오피스와 패써 웹 두 모노레포를 운영하며 공용 패키지 변경을 AI 코드 리뷰로 검증하고, 매장 검색 결과의 노출을 넓히는 SEO 작업을 한다는 내용을 읽었습니다. 저도 관리자 서비스 모노레포의 공용 패키지 경계를 lint와 리뷰 에이전트로 지키고, 복지몰에서 지역·진료과 검색 주소를 색인하는 작업을 해 왔습니다. 지금은 혼자 프론트엔드를 맡고 있어, 배운 것을 나누며 함께 성장하는 웹 파트에서 일하고 싶어 지원했습니다.

#### SSR·Streaming과 라우팅 개선 | 2026.04 – 현재

상담 화면은 서버에서 TanStack Query로 `prefetch`한 데이터를 hydration으로 전달하도록 바꿨습니다. 클라이언트의 조회와 무효화도 같은 Query 캐시를 사용합니다. 이후 Next.js `cacheComponents`를 적용하면서 동적으로 렌더할 부분과 캐시할 범위를 정리했습니다.

- 인증을 마친 회원이 화면을 이동하다 앱 전체가 멈추는 오류를 추적했습니다. 당시 프로덕션 unhandled 오류 중 영향 사용자가 가장 많았습니다(68건·53명). Next.js 라우터 코드를 읽어 서버 컴포넌트의 `redirect()`가 하드 내비게이션으로 처리되면서 훅 개수가 어긋나는 것을 확인하고, 진입 게이트를 프록시로 옮겼습니다.
- 검색 페이지에서 서버 prefetch와 화면 훅의 `queryKey`가 달라 서버에서 채운 캐시를 읽지 못했습니다. 사이트맵의 검색 URL 678개도 JS를 실행하지 않으면 목록이 나오지 않았습니다. 키를 맞춘 뒤 첫 렌더부터 서버 데이터를 읽는지 네 가지 조합으로 테스트했습니다.
- Next.js 16 전환 뒤 관리자 검색이 동작하지 않는 오류를 프로덕션 빌드에서 재현했습니다. 개발 서버와 jsdom 테스트에서는 나타나지 않았고, 목록 7개 중 6개에서 같은 증상을 확인했습니다. 업스트림 라우터 캐시 이슈를 찾은 뒤, 서버가 검색 조건을 읽지 않고 클라이언트에서 목록을 조회하는 화면은 History API로 바꿨습니다. 같은 경로의 검색 조건 변경에는 RSC 요청이 필요하지 않습니다.

#### 검색 노출(SEO) | 2026.08 – 09

- "안산 치과"처럼 지역과 진료과로 찾는 검색이 도착할 주소가 없었습니다. 새 경로를 만들지 않고 이미 노출되던 병원 필터 주소 중 지역 하나(와 진료과 하나)로 좁힌 주소만 색인 대상으로 열고, canonical·지역명 제목·사이트맵을 붙였습니다. 사이트맵에는 제휴 병원이 3곳 이상인 조합만 올렸습니다.
- 검진 기본 검사 항목 화면은 버튼의 `router.push`로만 들어가 문서에 주소가 남지 않았습니다. `<Link>`로 바꿔 크롤러가 주소를 찾게 하고, 화면에 메타·canonical과 JSON-LD(BreadcrumbList·ItemList)를 붙여 사이트맵에 실었습니다.
- 병원·시술 상세에는 `h1`이 없고 제목이 `<p>`로 되어 있었습니다. 화면 제목을 `h1`으로 세우고 헤딩 계층과 구획을 의미 태그로 바꿨습니다.
- `generateMetadata`가 메타데이터를 스트리밍하면서 기본 봇 목록에 없는 AI 인용·카카오톡·Daum 미리보기 봇은 canonical을 `<body>`에서 받았습니다. 해당 봇을 기존 목록에 추가해 `<head>`에서 받도록 바꿨습니다.

#### Sentry 도입 | 2026.08 – 09

복지몰의 브라우저·서버·Edge 환경에 Sentry를 도입했습니다. 오류의 심각도를 나누고, 배포 버전과 원본 코드를 연결해 운영 중 생긴 문제를 추적합니다.

- 화면이 뜨지 않는 오류, 작업을 막는 오류, 재시도할 수 있는 실패를 구분했습니다. 같은 오류를 API 계층과 Error Boundary에서 두 번 보내지 않도록 했습니다.
- SDK 소스를 읽고 event·breadcrumb·transaction·span에 담기는 데이터를 확인해 의료·인증 정보를 제거했습니다. 빠뜨리는 항목이 없도록 타입과 단위 테스트도 추가했습니다.
- release와 브라우저 소스맵을 연결하고 Sentry API로 artifact bundle 생성을 확인했습니다. LCP·FCP·TTFB가 실제 전송되는지는 브라우저 E2E로 확인했습니다. 사내 Sentry MCP도 연결해 에이전트가 운영 이슈를 조회할 수 있게 했습니다.
- Bottom Sheet를 드래그할 때 생긴 크래시를 라이브러리의 null ref 접근까지 추적했습니다. 라이브러리를 업데이트하면서 바뀐 snap point 규칙은 공통 Root에서 변환해 기존 사용처를 유지했습니다. 수정 전 57명 이상에게 75건 발생한 오류 그룹은 배포 후 18일 동안 0건이었습니다.

#### 건강검진 서비스 내재화 | 2026.09 – 현재

건강검진은 아임웹에서 정보를 보고 전화로 문의하던 서비스였습니다. 제휴 병원이 세이프닥에서 검진 예약을 받기를 요청했지만, 기존 비급여 프로그램으로는 검사 구성·기업지원 검진·예약금 결제를 처리하기 어려웠습니다. 개발팀장·부팀장과 빠진 동작과 예외를 맞추며 세 제품의 프론트엔드를 개발했습니다. 9월 9일부터 두 주 동안 개발해 23일 운영에 배포했고, 30일 정식 오픈했습니다.

- 백오피스에서 검사항목과 필수·선택 검사를 구성하고, 기업지원 코드와 서류를 확인하도록 했습니다. 결제내역 조회와 결제취소·환불 승인도 추가했습니다.
- 병원 관리자에는 검진 프로그램 조회와 예약 관리를 추가했습니다. 병원이 직접 처리할 수 없는 예약금 결제취소는 요청을 접수하는 방식으로 안내했습니다.
- 복지몰에는 검진 상세·검사 선택·기업 검진 코드 입력·예약금 결제·예약 상세를 만들었습니다.
- 일괄 등록 API는 일부 항목만 저장될 수 있었습니다. 요청 결과와 관계없이 서버 목록을 다시 조회해 발급된 ID를 폼에 넣고, 재시도할 때 같은 항목을 중복 등록하지 않게 했습니다.
- 결제 실패 후 입력을 복원하는 코드는 Zustand persist에서 `sessionStorage`로 바꿨습니다. 이전 결제 시도의 값을 가져오지 않도록 `orderId`와 현재 스키마가 맞는 같은 탭의 요청만 한 번 복원합니다. 새 탭이나 다른 결제 시도의 입력은 복원하지 않습니다.
- 결제창에서 실패로 돌아오면 입력이 복원되는지, 승인 요청이 실패하면 예약 목록으로 가는지를 dev API 서버 E2E로 확인했습니다.

#### 테스트 체계 재구축 | 2026.07 – 현재

기존 테스트가 실제 폼 제출과 서버의 제약을 놓쳐 관리자 서비스 모노레포와 복지몰의 테스트를 다시 정리했습니다. 에이전트가 작성한 테스트를 읽으며 컴포넌트별 동작과 빠진 조건을 확인합니다.

- 순수 함수와 스키마는 Vitest, UI와 폼은 React Testing Library, 브라우저 흐름은 Playwright로 테스트합니다.
- 관리자 화면은 dev API 서버와 통신하는 테스트를 기본으로 합니다. 이 환경으로 확인하기 어려운 경우 목을 사용합니다.
- 제출 로직을 복제한 테스트 하네스를 걷어내고 실제 Drawer를 렌더해 테스트합니다.
- 기대값은 제품의 변환 함수를 호출하지 않고 따로 작성합니다. 제품 코드와 테스트가 같은 실수를 하지 않게 하기 위해서입니다.
- 병원 관리자에서 프로그램을 등록하고 백오피스에서 검수·반려·승인하는 과정을 앱 간 E2E로 확인합니다.
- 새 테스트 패턴은 제품 코드를 일부러 깨뜨려 테스트가 실패하는지 확인한 뒤 넣습니다.
- 새 기능의 기대 동작은 BDD 형식의 `*.spec`에 적고, 운영·QA에서 발견한 오류는 `*.test`에 재현합니다. 컴포넌트별로 필요한 조건이 모두 들어 있는지 직접 읽습니다.

dev API 서버를 쓰는 테스트는 서버 상태를 준비해야 하고 실행에도 시간이 걸립니다. API 계약 테스트는 PR을 차단하지 않는 별도 단계로 두고, E2E는 CI 밖에서 실행합니다.

#### 폼과 검색 필터 리팩터링 | 2025.06 – 현재

검색·예약·프로그램 관리 화면에서 값이 어디에 저장되고 어떻게 변환되는지 정리했습니다.

- 공통 검색 필터 렌더러에 화면별 예외가 쌓여 각 화면이 필요한 필터를 직접 조합하도록 바꿨습니다. JSX 일부 중복은 감수하고 화면마다 다른 조건은 각 화면에 남겼습니다. 운영 화면 27개를 전환하고 URL·폼·API 필드를 Zod 스키마로 맞췄습니다.
- 프로그램 폼에 `createTypedForm<T>`를 적용해 잘못된 중첩 필드명을 타입 검사에서 찾도록 했습니다.
- 서버 응답을 폼 값으로, 폼 값을 제출값으로 바꾸는 코드는 순수 함수로 분리했습니다. 공통 필드를 쓰더라도 제출 정책이 다른 부분은 각 앱에 남겼습니다.
- 예약 화면의 가족·날짜 선택 값이 Query 캐시·Zustand·로컬 상태에 나뉘어 있던 것을 React Hook Form과 Zod로 모았습니다. 가족을 추가하면 날짜가 어긋나던 문제를 고쳤고, 예약 대상 선택 컴포넌트는 519줄에서 55줄로 줄었습니다.

#### AI 개발 workflow | 2026.04 – 현재

Claude Code와 Codex로 기능을 개발하고 리팩터링합니다. 에이전트가 완성본을 제출하면 코드와 테스트를 읽고, 부족한 부분은 반려한 뒤 수정본을 확인합니다. 반복되는 지적은 skills와 lint 규칙에 남깁니다.

티켓·plan 검토 → 테스트 작성 → 에이전트 구현·에이전트 코드 리뷰 → 변경분 테스트·lint·typecheck → 제 diff 리뷰·로컬 화면 확인 → 전체 CI(테스트·knip·lint) → QA 더블 체크 요청

문제가 나오면 앞 단계로 돌아가 다시 확인합니다.

- 상태를 어디에 둘지, 어떤 경로로 import할지는 skills에 정리했습니다. 자동으로 검사할 수 있는 기준은 자체 ESLint 규칙으로 옮겼습니다.
- 관리자 서비스 모노레포(앱 3개·패키지 9개)의 공용 패키지는 밖에서 실제로 쓰는 이름만 내보내도록 knip을 오류로 걸어, 앱이 쓰지 않는 공용 export와 패키지를 넘는 미사용 코드를 잡습니다.
- 직접 import 경고 271건을 정리한 뒤 오류로 승격해 같은 위반이 다시 들어오지 않도록 했습니다.
- 자체 규칙이 동적 import와 `as const` 쿼리 키를 놓치는 것을 확인해 보완을 지시하고 결과를 검토했습니다. 새 테스트를 수정 전 규칙에 실행했을 때 8건이 실패했습니다.
- 여러 worktree에서 전체 검사를 동시에 돌리니 CPU에 부하가 걸렸습니다. 로컬 lint와 테스트는 변경 파일과 영향 범위로 좁히고, 타입 검사는 패키지나 앱 단위로 유지했습니다. 전체 검사는 CI에서 돌립니다.
- 타입 인지 lint는 검사 시간이 3.3배 늘어 도입을 보류했습니다.
