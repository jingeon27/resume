#### 건강검진 서비스 내재화 | 2026.09 – 현재

건강검진은 아임웹에서 정보를 보고 전화로 문의하던 흐름이었고, 기존 복지몰과 병원 관리자에서는 검진 프로그램·예약을 처리하기 어려웠습니다. 제휴 병원의 요청으로 세 제품의 프론트엔드를 맡아 개발팀장·부팀장과 빠진 동작과 예외를 확인했습니다. 9월 9일부터 개발해 **9월 30일 정식 오픈**했습니다.

- **백오피스:** 검사 구성·검진 프로그램·기업지원 코드, 예약금 결제취소와 환불 승인.
- **병원 관리자:** 검진 예약 조회·관리, 결제취소 요청 접수.
- **복지몰:** 검사 선택·기업 검진 코드·예약신청·토스페이먼츠 예약금 결제.

모바일 결제 결과가 리다이렉트로 돌아오면 페이지가 새로 열려 신청 내용이 사라졌습니다. 입력을 결제 시도의 `orderId`와 함께 `sessionStorage`에 저장하고, 같은 주문이며 현재 Zod 스키마를 통과한 값만 한 번 복원했습니다. 결제 준비부터 결제창이 열릴 때까지는 신청 버튼을 잠가 중복 주문을 막았습니다. 결제창에서 실패로 돌아올 때의 입력 복원과 승인 요청 실패 시 예약 목록 이동을 dev API 서버 E2E로 확인했습니다.

선택 개수를 채우면 다음 검사 그룹으로 자동 이동하자는 요청에는, 기존 선택을 수정할 때도 화면이 넘어가는 점을 짚었습니다. 담당자와 논의해 미선택 chip만 비활성화하고 누락된 disabled 디자인을 요청했습니다. 검진 구성 수정이 거절된 사례에서는 삭제된 검사항목까지 조회 응답에 포함되는 것을 확인해 백엔드에 전달했습니다.

#### 모바일 리뷰 작성과 WebView | 2025.06 – 2026.09

모바일로 리뷰를 직접 써 보니 키패드가 시술 목록을 가리고, 하나를 고르면 목록이 닫혀 여러 항목을 선택하기 번거로웠으며 선택한 항목도 잘 보이지 않았습니다. 2025년 6월 Jira에 세 문제를 정리해 PO에게 공유했습니다. 기획·디자인 담당자가 정한 복수 선택·체크·chip UI를 구현해 7월 10일 배포했습니다. 이후 디자인 시스템에서 정한 Bottom Sheet를 리뷰 화면에 적용해 8월 7일 배포했습니다.

- 앱에서 열리지 않던 `tel:` 상담 버튼을 기존 네이티브 브릿지의 외부 링크 열기로 연결했습니다. 앱 재배포 없이 웹에서 수정했습니다.
- 외부 예약 사이트 이동을 붙일 때는 첫 구현의 뒤로 가기가 WebView 전체를 닫는 것을 배포 전에 확인했습니다. 외부 사이트는 브릿지로 열고 웹 내부의 이전 화면은 라우터로 이동하게 했습니다.
- 잘못 안내된 쿠폰함 주소 `/coupon`은 앱 핫픽스 대신 Load Balancer에서 `/profile/coupon`으로 리다이렉트하자고 제안해 합의했습니다.

#### 병원 관리자·백오피스와 정산 | 2025.06 – 현재

2025년 12월 말부터 병원 관리자의 프로그램 등록·검수 요청과 백오피스의 반려·승인 화면을 처음 개발했습니다. 2026년 9월 1일 운영팀이 반려 불가 오류를 제보했습니다. 반려·검수중 전환에도 폼 전체 검증이 걸려, 옛 프로그램이 새 할인율·카테고리 규칙을 통과하지 못하면 요청도 안내도 없이 끝났습니다. 승인에만 전체 검증을 남겨 당일 수정했고, 같은 달 등록→검수·반려·승인을 dev API 서버 E2E로 추가했습니다.

정산은 2026년 4월 초기 구현을 인수해 프론트엔드를 리팩터링하고 배포 전 운영 요구를 반영했습니다. 1,170줄 페이지에서 조회·표·선택·편집·정산 처리를 나눴습니다. 가격 이력을 추가하자는 요청에는 실제 정산 기준을 먼저 확인했고, 견적 금액이 기준이어서 별도 이력 구조는 만들지 않았습니다. 기업·대학의 컨택상태·활동 이력·다음 예정을 관리하는 영업관리 기능도 추가해 10월 운영에 배포했습니다.

#### 데이터 조회 전환과 네트워크 요청 | 2025.05 – 현재

입사 당시 서버 컴포넌트의 `ensureQuery` 결과를 render props로 전달하는 화면은 Query 캐시 변경을 구독하지 않았습니다. 무효화해도 화면이 갱신되지 않고, 조회 조건만 바꿀 때도 서버 렌더링 결과를 다시 받아야 했습니다. 2025년 5월 예약 화면부터 prefetch·hydration으로 전환해 서버가 초기 데이터를 준비하고 화면은 같은 캐시를 구독해 조회·갱신·무효화를 처리하게 했습니다.

관리자 검색 오류는 localhost의 `dev`에서 나타나지 않아 `build` 후 `start`로 목록 7개 중 6개에서 재현했습니다. 업스트림 이슈와 수정 PR을 확인하며 같은 경로의 라우터 캐시 문제까지 추적했습니다. 서버가 검색 조건을 읽지 않는 화면은 같은 경로의 조건 변경을 History API로 처리했습니다. 8월 13일 핫픽스와 18일 전환 후 9월 28일까지 같은 증상의 재보고는 없었습니다.

#### Sentry 도입과 운영 오류 대응 | 2026.08 – 현재

8월 19일부터 복지몰의 브라우저·서버·Edge에 Sentry를 적용해 27일 운영에 배포했습니다. 오류 레벨·중복 수집 기준을 정하고 release와 브라우저 소스맵을 연결했습니다. SDK 소스에서 event·breadcrumb·transaction·span에 실리는 값을 확인해 의료·인증 정보가 담기는 URL·본문·Cookie·인증 헤더를 제거하고 전송 payload를 확인했습니다.

- **Bottom Sheet 크래시:** 드래그 중 라이브러리가 null ref에 접근하는 원인을 추적해 버전업으로 해결했습니다. 바뀐 snap point 규칙은 공통 Root에서 변환해 26개 사용처의 API를 유지했습니다. 누적 **75건·57명 이상**이던 오류 그룹은 **9월 10일 배포 후 28일까지 18일간 0건**이었습니다.
- **로그인 해제 정책:** 회원 조회의 타임아웃·서버 오류까지 로그아웃으로 이어지는 정책을 401일 때만 끊도록 바꿨습니다. 9월 23일 배포 뒤 28일까지 관련 CS·Sentry 이슈가 없었습니다.
- **부분 실패 격리:** 관리자 서비스에서 한 조회의 실패가 앱 루트까지 전파되던 경계를 기능 단위로 나눴습니다. 실패한 구획만 재시도할 수 있게 하고 백오피스 라우트 30개의 화면 구성을 같은 패턴으로 맞췄습니다. API·렌더링 오류와 Zod 응답 스키마 불일치는 CloudWatch에서 트래킹합니다.

#### 글로벌 서비스·CMS와 웹 성능 | 2026.07 – 현재

PO가 전달한 프로토타입의 화면을 모두 반영하고 상세 상태·인터랙션을 보완해, 기존 제품 운영과 병행하며 사용자 서비스·CMS를 **3주 만에 PoC로 배포**했습니다. Next.js·strict TypeScript와 shadcn/ui·Base UI로 구현하고 영어·한국어·아랍어·RTL을 지원했습니다.

- 목 백엔드 코드가 클라이언트 번들에 들어가던 의존을 분리해 앱 번들을 **2,564KB→1,880KB**로 줄였습니다. 200건 일괄 조회는 20건 단위 무한 스크롤과 행 가상화로 바꿨습니다.
- 인증 전후의 입력 유지·실패 안내·완료 후 이동처럼 와이어프레임에 없던 동작을 보완했습니다. Select·Dialog의 ref와 폼 연결을 확인해 검증 실패 시 포커스가 이동하도록 했습니다.
- CMS의 링크 발급→사용자 서비스 파일 업로드→CMS 다운로드를 두 앱 E2E로 확인했습니다. 백엔드는 로컬에서 빌드해 연동했습니다.

복지몰은 경쟁사의 검색 결과와 상세 페이지를 비교해 검색 의도에 필요한 정보를 정리했습니다. 지역·진료과 검색의 canonical·제목과 병원·시술 상세의 구조화 데이터를 구성했습니다. 동적 사이트맵의 공개 조회가 인증 쿠키를 읽던 경계를 분리해 하루 단위로 재검증하게 하고, 제휴 병원이 3곳 이상인 지역·진료과 조합만 사이트맵에 포함했습니다.

#### 테스트 도입과 AI 개발 workflow | 2026.04 – 현재

4월부터 에이전트로 구현하고, 7월부터 테스트를 도입했습니다. 구현이 의도와 어긋나면 파일 배치·상태 소유권·공통 코드 사용 기준을 skills에 남깁니다. 의존 방향·Public API·queryKey처럼 정적으로 검사할 수 있는 기준은 lint rule로 관리합니다. 현재 기능 개발·리팩터링에서는 제출된 제품 코드와 테스트를 읽고 부족한 결과를 반려하며 수정본을 다시 확인합니다.

티켓·plan 검토 → 테스트 작성 → 에이전트 구현·에이전트 코드 리뷰 → 변경분 테스트·lint·typecheck → 직접 diff 리뷰·화면을 띄워 동작 확인 → 전체 CI(테스트·knip·lint) → QA 더블 체크 요청

- 새 기능의 기대 동작은 BDD 형식의 `*.spec`, 운영·QA 오류는 `*.test`로 작성합니다. 새 테스트 패턴은 제품 코드를 일부러 깨뜨려 실제로 실패하는지 확인합니다.
- 기대 payload는 제품의 변환 함수를 재사용하지 않고 따로 작성합니다. 실제 RHF·Ant Design 폼을 제출하며 검증하고, 만들기 어려운 조건에는 MSW를 사용합니다.
- 성공만 돌려주는 목이 서버 제약을 가려, 실제 인증으로 dev API 서버에 연결하는 계약 테스트와 병원 관리자·백오피스를 함께 사용하는 Playwright E2E를 추가했습니다.
- 자체 lint rule은 RuleTester와 `__fixture__`·mock으로 검증합니다. 위반을 정리한 규칙만 error로 올리고 미사용 코드는 Knip으로 확인합니다.

#### 공통 검색·폼·상태 설계 | 2025.06 – 현재

공통 검색 필터에 화면별 예외가 계속 쌓여, 화면이 필요한 필터를 조합하도록 바꾸고 운영 화면 **27개**를 전환했습니다. URL 파라미터·폼·API 요청의 타입을 연결하고, Ant Design Form에는 재귀 조건부 타입으로 중첩 필드명과 해당 값의 타입을 검사하는 `createTypedForm<T>`를 만들었습니다.

예약 화면의 가족·날짜 값이 Query 캐시·Zustand·로컬 상태에 나뉘어 가족 추가 시 날짜가 어긋났습니다. 서버 목록은 Query, 작성 중인 값은 React Hook Form, 제출 조건은 Zod로 나눠 고쳤습니다. 화면 간 직접 참조 **62건**을 정리하고, 공용 UI는 조합할 수 있게 열어 두면서 서버 도메인 작업과 화면 구성의 책임을 구분했습니다.

#### 사용자 행동 측정과 실험 참여 | 2025.07 – 현재

검색·병원 상세·프로그램 목록·예약신청 버튼의 변경을 비교할 수 있게 Amplitude 기반 A/B 테스트 환경을 구축했습니다. 담당자가 주도한 실험의 화면 구현과 사용자 행동 측정을 맡았고, 검색·상세·예약·쿠폰 이벤트 **140개 이상**을 새로 붙이거나 고쳤습니다.

룰렛 이벤트 종료 후에는 Amplitude의 페이지 방문 이벤트로 방문 사용자가 없다고 판단해 코드를 제거했습니다. 전화상담은 기존 상담 방식을 복지몰에서도 시도해 보자는 요청을 받아 구현했고, 실험 결과가 좋지 않아 종료된 뒤 코드를 정리하고 채팅상담으로 되돌렸습니다.

## 왓타임 | 2024.01 – 2024.11

왓타임의 채용 SaaS RoundHR이 시장성을 확인하며 기능을 확장하던 단계에 합류했습니다. 프론트엔드·백엔드 개발자, 디자이너와 pnpm·Turborepo 모노레포에서 협업했습니다.

- **제품 기능:** 채용 페이지·지원서 설정, 메일·면접 알림 템플릿, 채용 단계 자동화와 평가 템플릿·척도를 개발했습니다. 채용 담당자용 웹에는 서류·면접 평가와 온보딩 안내를 추가했습니다. 랜딩·라운지·모바일 화면과 Notion·Strapi 콘텐츠 연동도 맡았습니다.
- **입력 흐름:** 면접 템플릿을 시간 유형·장소·참여자 확인·메일 본문 네 단계로 나눠 `useFunnel`로 이동·검증하고 `sessionStorage`로 작성 내용을 복원했습니다.
- **앱 간 공통화:** Query key·조회 함수를 공용 패키지로 모으고 mutation마다 갱신 대상을 정했습니다. dnd-kit 공통 컴포넌트는 채용 공고·중첩 필터 트리·설정 테이블에 적용했습니다.
- **Electron 수집 앱:** 로그인→수집→중복 확인→업로드를 공통 단계와 사이트별 adapter로 나누는 초기 구조를 설계하고 잡플래닛·게임잡을 연동했습니다. NestJS 도입은 Electron main 프로세스에 무겁다는 CTO 피드백으로 닷새 만에 걷어냈고, 모듈 경계·생성자 주입은 참고해 factory에서 조립했습니다. 이후 동료가 상당 부분 다시 작성했으며 제 담당은 초기 구조와 사이트 연동입니다.
