## Summary

- **데이터로 확인한 사용자 행동** — 제품 분석 이벤트 250개 중 140개 이상을 직접 구현·고도화하고, **리뷰를 본 사용자의 예약 전환율이 15%p 높다**는 상관관계를 찾아 다음 실험의 근거로 남겼습니다.

- **빠른 실험과 출시** — 기간 한정 그로스 랜딩을 기획·디자인과 함께 만들고 이벤트 7개와 모바일 E2E 15개로 검증했습니다. 기존 제품 운영을 병행하면서 전달받은 프로토타입을 바탕으로 **글로벌 서비스를 3주 만에 구축·출시**했습니다.

- 예약·정산·쿠폰·병원 계약 같은 운영 화면을 검색 필터·테이블·모달·상세 폼 패턴으로 정리해 새 도메인도 같은 구조로 확장할 수 있게 했습니다. ([기술 글](https://blog.bambyul.com/ko/blog/두-관리자-앱의-프로그램-폼을-만드는-과정))

- 폼 테스트는 `mutation`이 불렸는지 확인하는 데서 멈추지 않고, 실제 화면을 사용자처럼 조작해 저장한 뒤 API로 다시 조회했습니다. 다국어 번역·기존 ID·조건부 그룹·이미지 순서가 왕복 후에도 남는지, 저장 실패 뒤 입력이 유지돼 재시도가 되는지를 검증합니다.

기존 세 제품의 운영과 장애 대응을 병행하면서 글로벌 서비스를 3주 만에 구축·출시하고, 운영자용 글로벌 CMS를 신규 런칭했습니다.

- PO가 만든 프로토타입을 이어받아 제품화했습니다. Vite SSG 기반에 라우트 24개·컴포넌트 88개가 2,021줄짜리 `App.jsx` 한 파일과 얽혀 있었고, 화면을 모두 반영해 Next.js 16 App Router와 `strict` TypeScript로 옮겼습니다. localStorage와 성공만 반환하는 Mock에 의존하던 데이터 흐름은 실제 API 계약과 TanStack Query 기반 서버 상태로 단계적으로 교체했습니다. 영어·한국어·아랍어 라우팅과 아랍어 RTL을 지원합니다.
- 운영자용 글로벌 CMS는 병원·시술·블로그·FAQ의 등록·수정·발행 흐름을 단독으로 신규 구축했습니다. 이미지 업로드는 Presigned URL 발급 → 스토리지 직접 PUT → 저장 시 확정의 세 단계로 나눠 취소하고 나가도 고아 파일이 남지 않게 했습니다.
- 성공만 반환하던 Mock이 실서버의 필수값·enum 계약 위반을 가린다는 것을 발견해, 실제 인증과 API로 확인하는 계약 테스트 환경을 따로 만들었습니다. HTTP 400 응답의 거절 코드와 필드별 위반 내용을 확인하고, 발견한 차이를 폼과 타입에 반영했습니다.
- 200건을 한 번에 내려받던 목록을 20건 단위 무한스크롤과 가상화로 바꾸면서, 첫 페이지의 SSR HTML은 그대로 유지했습니다.

**다음 변경을 빠르게 만드는 기반**

- 합류 시점의 복지몰은 6-layer FSD 골격은 있었지만 `@legacy`에 250개 파일이 남아 있었고, 남은 250개를 **26일 만에 0개로** 옮겼습니다(2025.05–06). 이후 레이어별 책임을 가이드 문서로 정의하고 역방향 의존은 자체 ESLint 플러그인으로 막아, 그 규칙 위에서 코드베이스가 세 배 가까이 늘었습니다.
- 그 FSD 경계 플러그인은 외부 의존성 없이 만들었습니다. 경로에서 레이어를 뽑아 순위를 비교하고, `import`뿐 아니라 `export * from` 재수출까지 검사해 우회 경로를 막았습니다. 검사 루트와 레이어 목록을 옵션으로 열어 복지몰(`src/modules`)과 백오피스 모노레포(`apps/*/src/modules`)가 같은 플러그인을 씁니다. 규칙은 처음부터 error로 걸지 않고 warn으로 켜 기존 위반을 먼저 정리한 뒤 승격했습니다.
- API 응답을 타입 단언으로 믿는 대신 zod 스키마로 파싱하는 계층을 두어 api 모듈 75개 파일의 호출 지점 **264곳**(2026-09-08 기준)에 적용했습니다. 서버 계약이 바뀌면 화면 깊은 곳의 `undefined` 크래시 대신 경계에서 잡히고, 불일치는 필드 경로와 함께 로그로 남습니다. 목록 50건이 같은 필드에서 어긋나도 로그는 세션당 한 번만 보내 정작 다른 사고가 묻히지 않게 했습니다.
- 페이지가 조회 상태를 들고 있으면 조회 실패가 화면 전체를 날려 에러 바운더리를 걸 자리가 없다고 보고, 12개 화면의 조회를 라우트에서 목록·통계 컴포넌트로 내렸습니다(68개 파일). 목록·상세·오버레이를 각각 `QueryErrorBoundary`로 감싸 한 구획의 실패가 나머지를 죽이지 않게 했습니다.
- 동작을 바꾸지 않는 리팩토링은 **기대 payload를 계약 파일로 먼저 고정한 뒤** 컴포넌트만 갈아끼웠습니다. 이때 기대값 계산에 프로덕션 매핑 함수를 쓰지 않았습니다 — 매핑이 깨지면 기대값도 같이 깨져 테스트가 회귀를 못 잡기 때문입니다. 432줄짜리 배너 드로어를 등록·수정으로 나누는 작업에 적용해, 잠복 버그 2개(등록 후 드로어가 닫히지 않아 URL의 새 id를 물고 상세와 겹쳐 뜨던 것, 수정 payload의 배너 타입을 열린 탭에서 읽어 URL 직접 진입 시 진료과가 어긋나던 것)를 찾았습니다.
- 테스트는 순수 함수·스키마 → API 계약 → UI 통합 → 브라우저 E2E로 나눴습니다. E2E를 처음 붙였을 때 10개 시나리오의 콜드 실행이 3.5분씩 걸리고 간헐 실패해서, 원인을 잘못된 내비게이션 대기 조건(`waitForURL`의 기본 `waitUntil: 'load'`)과 반복 삽입되는 프로모션 오버레이로 분리해 20초·3회 연속 flaky 0으로 안정화한 뒤 CI에 올렸습니다.
- 서버 상태는 TanStack Query, 입력 중인 값은 타입이 지정된 Form, DTO 차이는 변환 계층, 목록 필터와 페이지는 URL이 소유하도록 세 앱과 9개 패키지의 경계를 정했습니다.
- Next.js soft navigation 때문에 직전 예약자의 이름·연락처·병력이 다음 예약 화면에 남는 문제를 추적해, 재진입과 성공 시에는 초기화하되 제출 실패 시에는 입력을 보존하도록 상태 생명주기를 나눴습니다.
- Claude Code 스킬·커맨드로 Jira 조회부터 검증·PR 생성까지를 표준화했습니다. 생성 코드의 상태 소유권·상수 처리·의존 방향을 우선 검토하고, **제가 다시 설명할 수 없는 코드는 반영하지 않습니다.**
