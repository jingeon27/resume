## 소개

결제와 정산, 예약처럼 상태와 조건이 많은 업무를 개발해 온 프론트엔드 엔지니어입니다. 사용자가 입력한 값과 서버가 확정한 값을 구분하고, 실패한 뒤 다시 시도해도 앞선 작업과 충돌하지 않도록 설계합니다. 사용자 화면과 병원 관리자, 백오피스를 함께 맡아 운영에 필요한 동작도 살핍니다.

기술을 도입할 때는 얻는 이점과 전환 비용을 함께 따집니다. 읽고 확인하기 쉬운 코드로 정리하고, 반복되는 검토는 테스트와 lint rule에 남깁니다. AI로 구현한 코드도 직접 읽고 화면을 띄워 동작을 확인합니다.

## 지원동기

고위드처럼 고객의 금융 업무를 다루는 제품에서는 금액뿐 아니라 현재 상태와 다음에 할 수 있는 일을 정확하게 보여 주는 것이 중요하다고 생각합니다. 예약금 결제와 취소, 정산 화면을 개발하면서 여러 API와 운영 규칙을 사용자가 이해할 수 있는 흐름으로 정리해 왔습니다. 이 경험을 바탕으로 기업 고객이 안심하고 업무를 처리할 수 있는 제품을 만들고 싶습니다.

건강검진은 검사 구성, 기업지원 코드, 예약금 흐름이 일반 비급여와 달라 기존 서비스로 처리하기 어려웠습니다. 제휴 병원의 요청으로 복지몰, 병원 관리자, 백오피스의 프론트엔드를 맡았습니다. 개발팀장, 부팀장과 빠진 동작과 예외를 확인하며 9월 9일 개발을 시작해 30일 정식 오픈했습니다.

- 복지몰에는 검사 선택, 기업 검진 코드, 토스페이먼츠 예약금 결제를, 관리자 서비스에는 검사 구성과 프로그램, 예약, 결제취소 요청과 환불 승인 화면을 개발했습니다.
- 모바일 결제창을 다녀오면 신청 내용이 사라져, 입력을 `orderId`와 함께 sessionStorage에 저장했습니다. 같은 주문이며 현재 Zod 스키마를 통과한 값만 한 번 복원합니다. 이전 결제 시도의 값은 새 신청을 덮지 않게 했습니다.
- 결제 준비부터 결제창이 열릴 때까지 신청을 한 mutation으로 묶어 중복 주문을 막았습니다. 결제 실패 후 입력 복원과 승인 요청 실패 시 예약 목록 이동은 dev API 서버 E2E로 확인했습니다.
- 검사항목 일괄 저장에서 일부 요청만 성공하면 서버가 발급한 ID를 폼에 반영합니다. 재시도할 때 이미 저장된 항목을 다시 만들지 않도록 했습니다.

수기로 관리하던 정산을 내부 예약 데이터와 연결하는 프로젝트에서 초기 구현을 인수해 리팩터링과 운영 요구 반영을 맡았습니다. 1,170줄, 1,164줄이던 페이지를 조회, 표, 선택, 편집, 정산 처리로 나눴습니다. 파일 위치와 타입, 변환 로직도 함께 정리하고, ref로 열던 모달은 대상 데이터와 열림 상태를 props로 받게 바꿨습니다.

- 기업과 대학의 컨택상태, 활동 이력, 다음 일정, 담당자별 목록을 개발했습니다. 제휴 해지 시 쿠폰 회수 여부는 해당 대상의 조회가 끝난 뒤에만 판단하게 해, 이전 기업의 값이나 조회 중인 상태로 저장되지 않도록 했습니다.

#### 공통 폼과 데이터 조회 구조 | 2025.05 – 현재

서버의 `ensureQuery` 결과를 render props로 넘기던 화면은 클라이언트 캐시 변경을 구독하지 않았습니다. 2025년 5월 예약 화면부터 prefetch와 hydration으로 옮겼습니다. 초기 HTML은 서버가 준비하고, 이후 조회와 갱신은 클라이언트가 같은 Query 캐시로 처리합니다.

- 예약의 가족과 날짜 값이 Query, Zustand, 로컬 상태에 흩어진 구조를 서버 목록은 Query, 입력은 React Hook Form, 제출 조건은 Zod로 나눴습니다.
- 공통 검색 필터의 화면별 예외 분기를 없애고 화면이 필요한 필터를 조합하게 했습니다. JSX의 일부 반복은 감수하고, URL과 폼, API 요청은 같은 Zod 스키마를 쓰게 해 27개 화면을 옮겼습니다.
- Ant Design Form의 중첩 필드명과 값을 재귀 조건부 타입과 infer로 연결하는 `createTypedForm<T>`를 만들었습니다. 잘못된 경로와 값은 타입 검사에서 잡고, 라이브러리 타입을 보완하는 단언은 래퍼 안에 두었습니다.
- Headless UI에서 Radix UI로 전환해 접근성 primitive와 조합 방식을 활용했습니다. 공통 Bottom Sheet는 Compound Components와 overlay-kit으로 바꿔 본문과 하단 버튼이 같은 폼을 쓰게 했습니다.

#### 테스트와 개발 기준 | 2026.04 – 현재

AI 개발 workflow를 4월부터 다듬고, 7월부터 테스트를 도입했습니다.

티켓과 plan 검토 → 테스트 작성 → 에이전트 구현과 에이전트 코드 리뷰 → 변경분 테스트, lint, typecheck → 직접 diff 리뷰와 화면 동작 확인 → 전체 CI(테스트, knip, lint) → QA 더블 체크 요청

새 동작은 BDD 형식의 `*.spec`, 운영과 QA 오류는 `*.test`로 구분합니다. dev API 서버를 우선하고 재현하기 어려운 조건에는 MSW를 씁니다. 병원 관리자 등록부터 백오피스 검수와 승인까지 두 앱을 넘나드는 E2E를 추가했습니다. 반복되는 설계 판단은 skills에, 의존 방향과 공개 API 같은 정적 기준은 lint rule에 남기고 RuleTester와 fixture로 검증합니다.

Next.js 14→16, React 18→19는 Turbopack과 로컬 개발 속도 개선을 보고 전환했습니다. 비동기 API와 캐시 변경 대응 비용을 감수하고 이동과 새로고침을 확인했습니다. TypeScript 7 네이티브 체커는 별도로 병행해 타입 검사를 12.5초에서 1.9초로 줄였고, 검사 시간이 3.3배 늘어나는 타입 인지 lint는 보류했습니다.
