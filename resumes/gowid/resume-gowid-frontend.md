## 소개

예약금 결제와 쿠폰, 정산 화면을 개발해 온 프론트엔드 엔지니어입니다. 사용자 신청부터 병원과 운영팀의 처리까지 함께 맡았습니다. 결제창을 다녀온 뒤 입력이 사라지거나, 저장에 일부 성공한 항목이 재시도 때 중복되는 문제를 고쳤습니다.

개발하기 전에 실제 업무에서 쓰는 기준을 확인합니다. 정산에 쓰는 금액과 참고용 가격을 구분해 불필요한 이력 구조를 만들지 않았습니다. 코드는 업무 흐름을 따라 읽을 수 있도록 정리하고, AI가 만든 코드와 테스트도 직접 검토합니다.

## 지원동기

고위드가 다루는 법인카드 발급과 한도, 이용 내역은 기업의 담당자가 처리 상태와 금액을 정확히 이해해야 하는 업무입니다. RoundHR의 채용 관리와 세이프닥의 병원, 운영팀 화면을 개발하며 쌓은 경험을 이런 기업 금융 업무에 살리고 싶습니다.

결제창을 다녀온 뒤 입력을 복원하고, 일부 저장에 성공한 뒤 재시도할 때 중복을 막는 기능을 개발했습니다. 정산에서는 실제 기준 금액부터 확인해 불필요한 가격 이력 구조를 만들지 않았습니다. 고위드에서도 업무 규칙을 먼저 이해하고, 사용자가 실패한 작업을 다시 처리할 때까지 흐름을 확인하며 개발하겠습니다.

#### 건강검진 예약과 결제 | 2026.09 – 현재

건강검진은 일반 비급여 프로그램과 검사 구성이 다르고 기업지원 코드와 예약금도 필요했습니다. 제휴 병원이 기존 서비스를 이용하기 어려워 건강검진 기능을 추가했습니다. 복지몰, 병원 관리자, 백오피스의 프론트엔드를 맡아 개발팀장, 부팀장과 요구사항에서 빠진 동작과 예외를 논의했습니다. 9월 9일 개발을 시작해 30일 정식 오픈했습니다.

- 복지몰에는 검사 선택과 기업 검진 코드 입력, 토스페이먼츠 예약금 결제를 만들었습니다. 병원 관리자에는 예약 관리와 결제취소 요청을, 백오피스에는 검사 구성과 프로그램 관리, 결제취소와 환불 승인을 개발했습니다.
- 모바일에서 결제창을 다녀와도 신청 내용이 남도록 입력값과 `orderId`를 sessionStorage에 저장했습니다. 돌아온 주문의 ID가 일치하고 Zod 검증을 통과한 값만 한 번 복원합니다. 이전 결제 시도의 값으로 새 신청을 덮어쓰지 않게 했습니다.
- 결제 준비부터 결제창이 열릴 때까지 한 mutation에서 처리해 중복 주문을 막았습니다. 결제 실패 후 입력이 복원되는지, 승인 요청에 실패하면 예약 목록으로 이동하는지는 dev API 서버에 연결한 E2E로 확인했습니다.
- 검사항목 일괄 저장에서 일부 요청만 성공하면 서버가 발급한 ID를 폼에 반영합니다. 재시도할 때 이미 저장된 항목을 다시 만들지 않도록 했습니다.

#### 정산과 쿠폰 결제, 기업 관리 | 2025.06 – 현재

수기로 관리하던 정산을 내부 예약 데이터와 연결하는 프로젝트에서 코드 리팩터링과 운영 요청을 맡았습니다. 1,170줄과 1,164줄짜리 화면에 조회, 표, 편집, 정산 처리가 섞여 있었습니다. 기능별로 파일을 나누고 함께 수정되는 코드끼리 모았으며 타입과 데이터 변환도 고쳤습니다. ref로 열던 모달은 편집할 데이터와 열림 상태를 props로 받아, 코드를 읽을 때 대상과 동작을 알 수 있게 바꿨습니다.

- 프로그램 가격이 바뀌어도 정산 내역이 맞는지 논의하면서 실제 기준 금액부터 확인했습니다. 정산에는 견적 금액을 쓰고 프로그램 가격은 참고만 하므로, 별도 가격 이력 구조는 만들지 않았습니다.
- 쿠폰 결제는 결제수단과 상태에 따라 입력, 완료, 취소 동작이 달랐습니다. 관련 조건을 도메인 함수와 ts-pattern으로 모았습니다. 결제 예정 금액이 바뀌면 적용했던 쿠폰을 해제하도록 했습니다.
- 기업과 대학의 연락 상태, 활동 이력, 다음 일정, 담당자별 목록을 개발했습니다. 제휴 해지 시 쿠폰 회수 여부는 현재 선택한 대상의 조회가 끝난 뒤 판단하도록 했습니다. 조회가 끝나기 전이나 이전 기업의 값으로 저장하는 경우를 막았습니다.

#### 공통 폼과 데이터 조회 구조 | 2025.05 – 현재

기존 화면은 서버의 `ensureQuery` 결과를 render props로 받아 클라이언트에서 Query 캐시를 무효화해도 갱신되지 않았습니다. 2025년 5월 예약 화면부터 prefetch와 hydration으로 바꿨습니다. 서버가 준비한 데이터를 클라이언트도 같은 Query 캐시에서 읽어 이후 조회와 갱신을 처리하도록 했습니다.

- 예약자의 가족과 날짜 값이 Query, Zustand, 로컬 상태에 흩어져 가족을 추가하면 선택한 일시가 어긋났습니다. 서버에서 받은 목록은 Query에, 작성 중인 값은 React Hook Form에 두고 제출 조건은 Zod로 검사하도록 정리했습니다.
- 화면마다 예외가 붙던 공통 검색 필터를 각 화면에서 조합하도록 바꾸고 27개 화면에 적용했습니다. JSX가 일부 반복되지만 한 화면의 요구사항 때문에 공통 코드에 분기를 추가하지 않아도 됩니다. URL과 폼, API 요청은 같은 Zod 스키마를 사용합니다.
- Ant Design Form의 중첩 필드명과 값의 타입을 검사하는 `createTypedForm<T>`를 만들었습니다. 재귀 조건부 타입과 infer로 필드 경로에 맞는 값을 추론해, 잘못된 필드명이나 값의 타입을 컴파일 단계에서 찾습니다. 라이브러리 타입을 보완하기 위한 단언은 래퍼 안에 뒀습니다.
- Headless UI에서 Radix UI로 전환해 접근성 primitive와 조합 방식을 활용했습니다. 공통 Bottom Sheet는 Compound Components와 overlay-kit으로 바꿔 본문과 하단 버튼이 같은 폼을 쓰게 했습니다.

#### 테스트와 AI 개발 workflow | 2026.04 – 현재

2026년 4월부터 에이전트로 구현하고, 7월부터 테스트를 도입했습니다. 코드와 테스트 명세를 읽은 뒤 화면을 확인합니다. 결제 실패와 저장 재시도에서는 어떤 입력을 유지하고 버릴지도 봅니다.

티켓과 plan 검토 → 테스트 작성 → 에이전트 구현과 에이전트 코드 리뷰 → 변경분 테스트, lint, typecheck → 직접 diff 리뷰와 화면 동작 확인 → 전체 CI(테스트, knip, lint) → QA 더블 체크 요청

새 기능의 기대 동작은 BDD 형식의 `*.spec`에 적고, 운영이나 QA에서 발견한 오류는 `*.test`에 재현합니다. 새 테스트 패턴은 제품 코드를 일부러 깨뜨려 실패하는지도 확인합니다. API 연동은 dev API 서버를 우선하고 재현하기 어려운 조건에 MSW를 씁니다. 병원 관리자에서 등록하고 백오피스에서 검수와 승인하는 과정은 두 앱을 연결한 E2E로 확인합니다. 컴포넌트별 기대 동작이 명세에서 빠지지 않았는지도 검토합니다.

테스트용 QueryClient가 앱과 다르게 오류를 처리하던 문제를 고쳤습니다. 첫 조회 실패와 재조회 실패를 나눠 확인하고, 제출 payload의 기대값도 제품의 변환 함수를 가져다 쓰지 않고 따로 작성합니다.

구현이 의도와 어긋나면 수정본을 확인하고 반복되는 판단은 skills에 남깁니다. 의존 방향과 공개 API처럼 자동 검사할 수 있는 항목은 lint rule로 만들고 RuleTester와 fixture로 테스트합니다. 미사용 코드는 Knip으로 검사합니다.

Turbopack과 Next.js 16의 로컬 개발 속도 개선을 보고 Next.js 14→16, React 18→19로 전환했습니다. 비동기 API와 캐시 동작 변경에 맞춰 코드를 수정하고 이동과 새로고침을 확인했습니다. 별도로 TypeScript 7 네이티브 체커를 병행해 타입 검사 시간을 12.5초에서 1.9초로 줄였습니다. 타입 정보를 사용하는 lint는 검사 시간이 3.3배 늘어 도입을 보류했습니다.
