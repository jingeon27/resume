# 이력서와 포트폴리오 작성, 피드백

공고가 요구하는 일과 지원자가 실제로 한 일을 연결한다. 문서에 덜 드러난 역량은 코드와 기록을 확인해 보완하고, 역할이나 검증 범위를 늘려 쓰지 않는다. 현재 사용자 요청이 이 스킬의 과거 피드백보다 우선한다.

## 작업 범위와 자료 찾기

- 요청이 작성, 수정, 평가 중 무엇인지 구분한다. 평가 요청만으로 지원서를 바꾸거나 push하지 않는다. 작은 문장 수정에 전체 저장소 감사를 요구하지 않는다.
- 작업 공간의 `AGENTS.md`, 대상 저장소 지침, 현재 문서와 Git 상태를 확인한다. 저장소 이름과 원격으로 위치를 찾고 특정 Mac의 절대 경로를 전제하지 않는다.
- 김진건의 자료 위치와 반복해서 틀렸던 범위는 [지원자 맥락](references/candidate-context.md)을 참고한다. 사실관계는 현재 기록과 사용자 정정을 확인한다.
- 회사별 문서와 공고 대조 평가에는 대상 회사, 직무, 팀, 경력 단계가 같은 공고를 사용한다. 사용자가 준 공고 본문을 우선 활용하고, 링크만 있거나 최신 요건이 필요하면 공식 원문을 조회한다. 다른 팀이나 시니어 공고를 대신 평가 기준으로 삼지 않는다. 일반 포트폴리오 작성에 특정 회사 공고를 필수로 요구하지 않는다.
- 필요한 자료는 기존 파일과 연결된 도구에서 먼저 찾는다. 읽을 수 없는 코드나 지표가 있으면 확인된 범위로 진행하고 결론에 영향을 주는 정보만 질문한다. 보이지 않는 것을 경험이 없는 것으로 판정하지 않는다.

## 근거를 확인하는 방법

실질적인 작성과 평가는 [근거와 평가 기준](references/evidence-and-review.md)을 따른다. 전체 이력서 작성과 종합평가에는 공고, 실무 기록, 관련 실무와 사이드 프로젝트의 대표 구현 및 테스트를 함께 확인한다. 작은 문장 수정은 해당 주장에 필요한 근거로 범위를 좁힌다. 공고 요건, 문서의 주장, 본인 역할, 확인 자료, 결과의 범위를 연결한다. 기술 목록이나 저장소 규모만으로 실력을 판정하지 않는다.

항상 구분할 것:

- 본인, 동료, 에이전트가 각각 맡은 요구사항, 설계, 구현, 검토와 판단
- 계획, 설정, 구현, 실행한 테스트, 배포, 정식 출시와 실제 사용 결과
- 실험 환경 구축, 실험 구현, 행동 측정과 가설 수립, 분석, 종료 판단
- 제품 성장, 출시와 운영 품질, 설계와 개발 과정의 개선

이전 AI 평가와 합격률은 검증할 의견이지 사실 자료가 아니다. 같은 근거를 다시 말했거나 문구만 고쳤다는 이유로 실력과 합격 가능성을 올려 잡지 않는다.

## 작성하거나 수정할 때

[문체와 편집 기준](references/writing-feedback.md)을 읽는다. 강점을 형용사로 선언하기보다 사용자가 겪은 상황, 맡은 결정과 행동, 확인한 결과로 보여준다.

포트폴리오를 새로 만들거나 고칠 때는 [포트폴리오 작성 규칙](references/portfolio-writing.md)을 함께 읽는다. 일반/AI 문서의 역할, 목차와 상세 사례, 트레이드오프의 깊이, 화면과 코드 근거의 배치에 적용한다. 작성 규칙을 추가해 달라는 요청만으로 기존 포트폴리오 본문을 다시 쓰지는 않는다.

- **회사별 이력서:** 공고에서 중요한 경험을 먼저 배치한다. 대표 사례는 판단과 결과가 보일 만큼 쓰고, 지원 직무와 거리가 있는 작업은 비중을 줄인다. 간결하게 쓰되 역량을 기술 이름 몇 개로 축소하지 않는다.
- **지원동기:** 회사에서 맡고 싶은 구체적인 일과 이미 한 일을 연결한다. 사용자가 말하지 않은 개인 서사, 감정, 회사 비판을 만들지 않는다.
- **일반 포트폴리오와 경력기술서:** 경력별 담당 범위와 사례를 상세히 보여준다. 사례는 사용자가 정한 `문제 상황 → 해결 방법 → 트레이드오프 → 결과 및 배운 점` 순서로 쓴다.
- **AI 활용 포트폴리오:** 제품 판단, 에이전트에 준 기준, 구현 결과의 검토와 반려, 검증 과정을 상세히 쓴다. 이력서 분량으로 줄이지 않는다. 실제 workflow와 실무/개인 프로젝트의 차이는 지원자 맥락을 확인한다.

트레이드오프는 대안, 선택 이유, 받아들인 비용이나 남은 한계를 연결한다. 기록에 없는 대안 검토, 사고, 성과, 배운 점을 채우지 않는다. 소개와 담당 범위, workflow는 사례 형식으로 억지로 나누지 않는다.

## 평가할 때

문서의 전달력, 공고 적합성, 확인한 기술 역량을 구분해 판단한다. 코드에서 강점이 확인되지만 문서에 드러나지 않는다면 해당 사례와 넣을 위치를 제안한다. 반대로 문서가 주장하는 수준을 코드가 뒷받침하지 못하면 근거와 수정 범위를 짚는다.

결론을 먼저 말하고, 중요한 강점과 보완점에 자료 위치와 이유를 붙인다. 포괄적인 칭찬이나 일반적인 준비 목록 대신 채용 판단에 영향을 줄 내용을 우선한다. 여러 회사 비교는 같은 기준을 적용하고 자료의 차이도 표시한다. 작은 평가에 고정 점수표나 긴 근거표를 강요하지 않는다.

서류 합격 확률과 `3년 차에 준하는 경험`은 [별도 판단 기준](references/evidence-and-review.md#경력-요건과-합격-가능성)을 따른다. 적합도 점수를 합격률로 바꾸거나, 실제 재직 기간을 늘려 적지 않는다.

## 파일 작업 마무리

기존 Markdown 저장소 작업은 그 위치와 형식을 유지한다. 현재 사용자 지시 없이 PDF를 갱신하거나 별도 문서 서비스를 만들지 않는다. 제출했거나 탈락한 과거 지원서는 새 초안과 구분해 보존한다.

수정한 사실, 기간, 수치, 역할, 상대 링크와 파일 차이를 확인한다. 지침이 요구하는 커밋과 이미 허용된 push는 반복 승인 질문 없이 진행하되 저장, 커밋, 원격 반영을 구분해 실제 상태를 확인한다. 다른 미커밋 변경을 섞지 않는다. 이 스킬 자체가 다른 저장소의 수정과 공개를 포괄적으로 허가하지는 않는다.

새 피드백을 누적할 때는 반복된 선호와 한 번의 문장 수정을 구분한다. 출처와 적용 범위를 [피드백 출처](references/feedback-sources.md)에 짧게 남기고 원시 대화나 비공개 업무 자료를 복사하지 않는다.
