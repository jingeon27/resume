# 근거와 평가 기준

## 주장과 근거 연결

전체 이력서나 역량을 평가할 때는 다음 연결을 작업 메모로 만든다. 필요한 항목만 사용자에게 보여준다.

| 공고의 요구 | 확인할 것 |
| --- | --- |
| 필수/우대 요건의 정확한 문구 | 대상 팀, 직무와 경력 단계가 같은가 |
| 연결할 사례와 현재 문구 | 지원자가 실제로 맡은 결정과 행동은 무엇인가 |
| 근거 | 현재 코드, 커밋/PR, 실행 결과, 운영 자료, 사용자 확인 중 무엇인가 |
| 결과 | 구현, 검증, 배포, 운영 중 어디까지 확인했는가 |
| 평가 | 직접 충족, 관련 경험, 아직 확인 필요 중 어디에 해당하는가 |

증거 종류를 섞지 않는다. `사용자 확인`, `코드로 확인`, `테스트 실행`, `운영 자료`, `추정`을 내부적으로 구별한다. 같은 문장을 이력서와 블로그가 반복한다고 독립 근거가 늘어나지는 않는다.

최근 사용자 정정은 과거 초안과 AI 요약보다 우선한다. 사용자 설명과 현재 코드가 다르면 시점, 브랜치, squash, 후속 변경을 확인한다. 설명 없이 한쪽을 폐기하지 않는다. 대화나 업무 논의로 처리해 Git에 남지 않은 일도 있을 수 있다. 현재 코드만으로 최초 설계자와 당시 구현자를 단정하지 않는다.

## 코드로 역량을 볼 때

공고의 중요한 요구를 설명할 수 있는 경로를 골라 구현과 테스트를 함께 읽는다. 검토한 저장소, 브랜치/커밋과 파일 범위를 남기고 표본 검토를 전체 코드 감사로 표현하지 않는다. 저장소 전체를 반드시 실행하거나 감사할 필요는 없다. 결론을 바꿀 수 있는 쟁점에 깊이를 쓴다.

- **사용자 흐름:** 진입부터 완료, 실패와 재시도까지 따라간다. 입력 유지, 중복 제출, 로딩, 오류, 키보드, 포커스, 스크롤과 화면 크기 변화가 해당 기능에서 어떻게 처리되는지 본다.
- **언어와 설계:** 타입이 실제 오류를 막는 경계, 런타임 검증, 서버/클라이언트 책임, 비동기 상태와 데이터 일관성을 본다. 유명 라이브러리 사용 자체를 깊이의 근거로 삼지 않는다.
- **API와 DB:** 계약, 권한, 트랜잭션, 동시 요청, 실패 후 재시도, 캐시 무효화가 실제 코드에서 이어지는지 확인한다. 관련 없는 체크 항목을 모두 결함으로 나열하지 않는다.
- **테스트와 배포:** assertion이 무엇을 확인하는지, mock이 실제 계약과 맞는지, 실패를 재현하는지 확인한다. 설정 파일의 존재, 테스트 파일 수, 성공 표시만으로 운영 안정성과 복구 능력을 확정하지 않는다.

직접 실행한 명령과 신뢰할 수 있는 기존 실행 기록을 구분한다. 코드를 읽었으면 `구현과 테스트를 확인했다`, 실행했으면 해당 실행 결과를 말한다. 실행하지 않은 테스트를 통과했다고 하지 않는다. 검증이 필요하면 변경과 쟁점에 맞는 테스트만 실행하고 기존 작업을 건드리지 않는다.

AI 활용은 사람이 정한 기준과 선택, 에이전트의 구현, 사람이 검토한 결과를 나누어 본다. 모든 줄을 직접 타이핑했다고 쓰지 않고, AI가 구현했다는 이유로 설계와 검증 역량을 지우지도 않는다. 빠른 제작은 범위와 기간의 근거이며 출시 후 제품 성공을 대신 증명하지는 않는다.

## 결과와 KPI

성과를 공고와 담당 범위에 맞게 해석한다.

- **출시와 전달:** 실제 공개한 기능, 연결한 제품/업무 흐름, 담당 범위와 완료 조건
- **운영 품질:** 특정 오류의 재발, 영향을 받은 사용자, 실패 복구와 업무 중단 여부
- **설계와 개발 과정:** 반복 작업 제거, 상태/타입 경계, 검증 가능성, 측정된 작업 시간과 성능
- **제품 지표:** 전환, 재방문, 사용, 매출 등 실제 측정한 변화와 개인의 기여

회사 성장에는 공급, 영업, 마케팅과 제품 방향도 영향을 준다. 성장 지표가 약하다는 이유로 프론트엔드의 정식 출시, 운영, 설계 성과까지 없다고 평가하지 않는다. 제품 성공을 주도한 경험을 요구하는 공고라면 그 요건의 근거가 별도로 필요한 것은 분명히 한다.

수치를 쓰기 전에는 원자료, 기간, 단위, 분모, 집계 방식, 비교 조건과 귀속을 확인한다. 가입 회원과 활성 사용자, 일/주 활성, 오류 이벤트와 영향받은 사람, 상대 변화율과 %p를 구분한다. 전후 비교를 무작위 A/B 테스트로, 상관관계를 인과효과로 바꾸지 않는다. 실험 환경 구축이나 구현 참여를 가설과 분석 주도로 늘리지 않는다.

Amplitude나 Sentry 확인을 요청받으면 사용 가능한 기존 연결에서 해당 프로젝트, 기간, 이벤트/오류 그룹과 필터를 확인한다. 연결이 없으면 기존 확인 자료의 범위를 밝히고 진행한다. 도구가 없는 상태에서 조회했다고 하거나 인증정보를 요청 문서에 저장하지 않는다.

KPI를 넣어 달라는 요청은 문맥에 따라 나눈다.

- **이미 달성한 성과:** 확인한 수치만 문장에 넣고 원자료를 추적할 수 있게 한다.
- **앞으로 측정할 지표:** 의사결정 목적과 측정 정의를 제안하고 `제안`으로 표시한다. 목표값과 달성값을 만들지 않는다.
- **수치가 없는 사례:** 실제 출시, 확인한 실패 처리와 운영 결과로 쓴다. 주장하지 않은 성장 효과에 매번 면책 문장을 붙이지 않는다.

코드 줄 수 감소나 테스트 개수는 맥락을 설명하는 보조 자료다. 유지보수성, 안정성, 생산성 향상률과 동일시하지 않는다. `0건`은 확인한 그룹과 기간에 한정한다. 발생 기록이 없던 과거와 비교해 예방 건수를 계산하지 않는다.

## 경력 요건과 합격 가능성

`3년 이상 또는 그에 준하는 경험`은 경과 연수와 수행 범위를 함께 본다. 요구사항, 사용자 흐름, API와 DB, 테스트, 배포 구성, 출시와 운영에서 어느 결정을 독립적으로 책임졌는지 연결한다. 개인 프로젝트의 넓은 범위와 실무 운영을 함께 평가하되 실제 재직 기간과 프로젝트 날짜는 그대로 쓴다. 회사가 동등 경험을 인정할지는 확정하지 않는다.

전직 가능처럼 사용자가 확인한 지원 조건을 매번 미확인 위험으로 되살리지 않는다. 전직 가능, 경력 요건, 서류 경쟁력은 별개의 판단이다.

기본 출력은 직무 적합성과 제출 준비 상태, 강한 근거와 남은 공백이다. 점수를 원하면 평가 기준과 점수의 의미를 밝히고 합격률과 구별한다.

합격 확률을 명시적으로 물으면 공개된 선발 비율과 지원자 분포가 있는지 먼저 구별한다. 없다면 객관적 확률로 계산할 수 없다고 말한다. 숫자가 유용하고 사용자가 요구한다면 조건을 밝힌 폭넓은 주관적 추정으로만 제시하고 정밀한 백분율을 만들어내지 않는다. 근거가 부족하면 숫자를 산출하지 않는 것이 더 정확하다. 서류에서 면접으로 가는 가능성과 최종 합격은 구분한다.

같은 성과를 반복 강조하거나 `더 높지 않냐`고 물었다는 이유로 수치를 올리지 않는다. 새 자료가 기존 평가의 누락을 드러냈다면 무엇을 누락했는지 밝히고 판단을 고친다. 이전에 근거 없이 제시한 비율을 새 평가의 기준값으로 쓰지 않는다.

코드를 실제 검토했는지와 채용 담당자가 링크를 열어 볼지는 다르다. 코드 검토를 전제로 한 역량 판단을 제출된 문서만 보는 심사의 확률로 곧바로 옮기지 않는다. 핵심 근거를 문서에서 바로 찾게 만드는 개선안을 제시한다.
