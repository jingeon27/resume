# 문체와 편집 기준

이력서 저장소 지침과 기존 `blog-writing`의 사용자 피드백에서 이력서에도 맞는 부분을 가져왔다. 특정 표현으로 AI 작성 여부를 판정하거나 탐지기 회피를 목표로 하지 않는다. 사실, 판단과 읽기 쉬운 문장이 목적이다.

## 구체적으로 쓰기

`생산성이 높은 제너럴리스트`, `사용자 중심의 개발자`, `높은 안정성을 확보` 같은 평가를 먼저 선언하지 않는다. 맡은 범위와 실제 선택이 그 역량을 보여주게 쓴다. 추상 명사를 연결한 문장은 주어, 행동과 대상이 보이게 푼다.

예시의 사실도 대상 사례에서 확인됐을 때만 쓴다.

| 모호한 문장 | 구체화 방향 |
| --- | --- |
| 사용자 중심의 UX 고도화를 주도했습니다. | 직접 사용하며 발견한 불편, 누구와 논의했는지, 바꾼 동작을 적는다. |
| AI를 활용해 압도적인 생산성을 확보했습니다. | 정해진 기간에 만든 범위, 본인이 정한 기준과 검토, 에이전트 구현을 구분한다. |
| 캐시 안정성을 강화했습니다. | DB 변경과 캐시 삭제가 어긋나는 조건, 고친 경로와 확인한 실패 테스트를 적는다. |
| 출시를 넘어 제품 성공까지 책임지고 싶습니다. | 맡고 싶은 제품 업무와 이미 해 본 구현/측정 경험을 연결한다. |

사용자가 `사용자 입장에서 생각한다`는 표현을 원하면 그 의도를 유지하고 근거 사례를 붙인다. 추상어를 금지한다는 이유로 요청한 메시지 자체를 삭제하지 않는다.

## 반복되는 문장 습관 줄이기

- `~가 아니라 ~다`, `~를 넘어 ~까지` 같은 대비와 비슷한 결론을 반복하지 않는다.
- 세 가지 강점, 모든 문단의 교훈, 질문 체크리스트나 포부로 끝나는 결론을 자동으로 만들지 않는다.
- `중요하다고 생각했습니다`, `이를 통해 역량을 길렀습니다` 대신 실제로 바뀐 동작과 다음 판단에 영향을 준 내용을 쓴다. 배운 점이 기록에 없으면 만들어 넣지 않는다.
- 자료 확인 날짜를 도입과 끝에 관성적으로 붙이지 않는다. 재직 기간, 작업/배포 시점과 측정 기간처럼 판단에 필요한 날짜는 유지한다.
- 자연스럽게 보이려고 감정, 사고, 사용자 반응, 동료의 칭찬을 창작하지 않는다. 불리한 회사 상황을 지원동기에 임의로 옮기지 않는다.

## 표현과 형식

- 이력서는 간결한 `합니다/했습니다`체로, 기존 문서의 어조와 사용자의 요청을 따른다. 블로그의 해요체와 장문의 회고 형식을 그대로 옮기지 않는다.
- 사용자 선호에 따라 낱말을 가운데 점으로 잇지 않는다. 쉼표와 조사를 쓰고 링크/머리글 구분에는 ` | `를 쓴다. 제목의 em dash와 습관적인 순번을 피한다. 코드, URL, 인용과 제품 이름은 구두점 교정 때문에 훼손하지 않는다.
- 지원 문서에서 `계측/관측`은 문맥에 따라 `사용자 행동 측정`, `운영 오류 수집과 추적`으로 쓴다. `AI 개발 workflow`, skills, lint rule 등 사용자가 선택한 표현과 정확한 기술 용어는 유지한다.
- 화면 검증은 `화면을 띄워 동작을 확인`처럼 쓴다. 백엔드 검증 환경인 `dev API 서버` 등 기술적으로 필요한 구분은 유지한다.
- 본문에서 역할을 설명하지 않은 기술을 목록에 추가해 키워드만 늘리지 않는다. 기술 분류와 기존 형식은 저장소 지침을 따른다.

## 분량과 트레이드오프

이력서는 공고와 관련된 대표 사례가 빠르게 보이게 쓴다. 모든 작업을 같은 비중으로 나열하거나, 간결함 때문에 요구사항 정의와 설계, 검증을 모두 삭제하지 않는다. 일반 포트폴리오와 AI 활용 포트폴리오는 상세해도 된다. 긴 문서에는 실제 제목에 맞는 목차와 읽을 경로를 둔다.

포트폴리오의 사례 구성과 트레이드오프, 화면과 코드 근거 배치는 [포트폴리오 작성 규칙](portfolio-writing.md)을 따른다. 이력서에서는 그중 지원 직무에 중요한 판단과 결과를 추려 쓴다.

블로그에서 작업 집계가 어색하다는 피드백을 이력서의 모든 수치 금지로 확대하지 않는다. 규모, 결과와 기술적 판단을 설명하는 숫자는 근거와 함께 쓴다.

하지 않은 일을 매 문단에서 해명하지 않는다. 한계가 결론을 바꾸면 해당 주장 옆에 짧게 적는다. 확인한 로컬 동작을 운영 성과처럼 보이게 만드는 문구는 유지할 수 없다.

스크린샷을 갱신할 때는 최신 실제 UI를 촬영하고 소스 상태와 테스트 데이터 여부를 기록한다. 옛 이미지의 텍스트나 픽셀을 바꿔 현재 화면처럼 만들지 않는다. 접근할 수 없으면 기존 이미지를 유지하고 무엇이 필요한지 설명한다.
