# 김진건의 자료 위치와 주의할 범위

2026-10-31에 모은 출처 안내와 정정 요약이다. 당시 배포 상태와 경력 기간을 영구적인 현재 사실로 쓰지 않는다. 현재 사용자 설명과 저장소 기록을 확인한다. 전체 이력을 이 파일에 복제하지 않고 원자료를 읽는다.

## 자료 찾기

작업 공간 지침의 경로와 Git 원격을 먼저 확인한다. 로컬에 없으면 기존 GitHub 연결을 사용한다. 다른 Mac에서 같은 절대 경로를 요구하지 않는다.

| 원격/위치 | 사용할 자료 |
| --- | --- |
| `jingeon27/resume` | `AGENTS.md`의 사실 정정과 작성 기준, `resumes/README.md`의 문서 목록 |
| resume 저장소 | `portfolio.md`는 일반 포트폴리오 겸 경력기술서, `resumes/doers/portfolio-doers-ai-experience.md`는 상세 AI 활용 포트폴리오 |
| resume 저장소 | 회사별 `resumes/<회사>/README.md`, 현재 이력서, `경력기술서.md`, `development-process.md`, 관련 코드 감사와 변경 이력 |
| `jingeon27/side-project` | 제품 코드와 테스트, Git 이력. 블로그는 `projects/blog/apps/web` |
| 실무 코드 | 작업 공간의 `safedoc-react`, `safedoc-usermall`, `safedoc-global`, `when-front` 등 실제 존재하는 저장소와 브랜치를 확인 |
| 개인 스킬 경로 | `.agents/skills/blog-writing/references/writing-feedback.md`에 누적 문체 피드백 |

resume의 `HANDOFF.md`, 예전 버전과 감사 문서는 당시 상태를 설명한다. 현재 `AGENTS.md`와 사용자 정정을 덮어쓰는 근거로 삼지 않는다. 코드 증거 링크에 커밋이 고정돼 있으면 해당 시점과 현재 변경을 구분한다. `side-project-blog`는 side-project의 worktree일 수 있으므로 이름만으로 별도 저장소라 판단하지 않는다.

블로그는 `https://blog.bambyul.com/ko/blog`를 사용한다. Tistory는 더 이상 현재 블로그가 아니다. 개별 글은 배포된 같은 글의 canonical 주소를 확인한다.

## 반복된 사실 정정

다음은 자주 혼동된 범위다. 해당 사례를 쓸 때 원자료와 후속 변경을 다시 확인한다.

- **실무와 개인 프로젝트:** 건강검진은 세 제품을 잇는 실무 정식 출시/운영 경험이다. 개인 서비스의 미출시 상태를 전체 경력의 출시 경험 부족으로 일반화하지 않는다.
- **개인 프로젝트 담당:** 두 서비스와 블로그를 2주 만에 만든 것은 사용자 설명이다. 요구사항 정의, 화면 설계, API와 DB, 테스트 기준, 배포 구성을 맡았고 구현과 테스트 작성은 에이전트가 했다. `5명이 두 달 걸릴 규모`라는 추산 문구는 이후 삭제 요청을 받았으므로 되살리지 않는다.
- **배포 구성:** 당시 두 서비스는 공개 전, 블로그는 배포된 상태였다. Terraform과 백업/롤백 설정, mock provider 테스트를 실제 EC2 적용이나 운영 복구 실적으로 바꾸지 않는다. 새 배포 증거가 있으면 상태를 갱신한다.
- **Game Mate:** 출발점은 친추 판매와 게임 코칭이다. 모집 글에서 가격과 조건을 보고 1:1 채팅으로 문의하는 흐름이다. 최초 목적을 피드백 커뮤니티로 되돌리거나 결제, 정산, 실제 매칭 성공을 덧붙이지 않는다.
- **세이프닥 담당:** 프론트엔드와 QA, 병원 관리자/백오피스의 화면 디자인을 맡았다. 복지몰 화면 디자인, 영업, 제휴와 마케팅까지 맡았다고 쓰지 않는다. 건강검진 요구사항은 병원 요청을 전달받아 개발 리더/백엔드 등과 누락 동작과 예외를 논의한 범위다.
- **규모:** 가입 회원 약 15만 명과 주간 활성 약 1만 명은 서로 다른 수치다. 측정 기간별 하루 숫자와 혼합하거나 가입 회원을 활성 사용자로 바꾸지 않는다.
- **UX 개선:** 직접 모바일로 발견해 PO에게 공유한 리뷰 불편, 담당자가 정한 복수 선택/체크/chip 개선 구현, 후속 디자인 시스템 Bottom Sheet 적용은 구분한다. Bottom Sheet를 최초 제안했거나 사용성 KPI가 개선됐다고 만들지 않는다.
- **실험:** Amplitude A/B 환경 구축, 제품 실험 구현과 사용자 행동 측정은 경험으로 드러낸다. 월간 랜딩 전후 비교를 무작위 A/B, 본인 분석 주도나 전환 개선으로 바꾸지 않는다. 전화상담 실험의 요청자를 임의 확정하지 않는다.
- **오류 성과:** Bottom Sheet의 배포 전 75건/57명 이상과 이후 0건은 당시 특정 오류 그룹과 확인 기간의 값이다. 전역 무오류와 현재까지 무재발로 확대하지 않는다.
- **건강검진 검증:** 결제 복귀 입력 복원과 승인 실패 후 이동을 확인한 E2E를 백엔드 환불 처리 전체 검증으로 확대하지 않는다. 병원 관리자의 결제 취소 요청과 실제 결제 취소 실행도 구분한다.
- **왓타임:** 로컬 코드가 없다는 이유로 사용자 확인 경험을 `근거 없음`으로 지우지 않는다. Electron의 초기 구조 설계, CTO가 반려해 제거한 NestJS 도입, 이후 동료가 다시 쓴 코드를 구분한다.

## AI workflow

실무 AI 경험을 작성할 때 사용자가 중요하다고 한 순서와 검증 기준을 보존한다.

티켓과 plan 검토 → 테스트 작성 → 에이전트 구현과 에이전트 코드 리뷰 → 변경분 테스트, lint, typecheck → 본인 diff 리뷰와 화면 동작 확인 → 전체 CI(테스트, knip, lint) → QA 더블 체크 요청

문제가 나오면 앞 단계로 돌아간다. 새 기능의 기대 동작은 BDD 형식의 `*.spec`, 운영/QA 오류는 `*.test`로 다루고, 새 패턴의 테스트는 코드를 일부러 깨뜨려 실제 실패하는지 확인한다. 반복해서 의도와 어긋나는 구현은 기준을 skills나 lint 규칙으로 남긴다.

QA 더블 체크 요청은 실무 경험이다. 개인 프로젝트에 붙이지 않는다. 현재는 에이전트가 완성본으로 낸 기능/리팩터링의 제품 코드와 테스트를 읽고 반려/재검토한다. 과거 모든 작업을 예외 없이 읽었다고 쓰지 않는다. 작은 작업을 직접 고치지 않는 것과 읽지 않는 것도 다르다.

## 회사별 강조점과 지원 조건

아래는 사용자가 요청한 방향이며 새 공고를 확인하는 일을 대신하지 않는다.

- **당근 캠페인:** 실제 사용자와 운영, 사용자 관점과 인터랙션 품질, JS/TS와 웹 원리, 스스로 발견한 문제, SSR/WebView, AI를 활용한 구현/검증과 협업. 지원동기에서 게임 커뮤니티 정모 서사는 삭제했다.
- **두어스:** 생산성, 넓은 제품 개발 범위, 사용자 관점과 AI 활용. 판단력과 통찰은 실제 제품 기여와 앞으로 기르고 싶은 방향을 연결한다.
- **고위드:** 테스트와 검증, 안정성, 왓타임 B2B와 의료 도메인에서 여러 업무 주체를 잇는 경험.
- **엘리스/페이타랩:** 해당 지원 공고와 문서에서 기준을 확인한다. 엘리스 일반 FE를 시니어 공고로 바꿔 평가하지 않는다.

이 대화에서 사용자는 다섯 곳의 산업기능요원 전직 지원 가능을 확인했다. 이를 반복해서 미확인 위험으로 제시하지 않는다. 두어스/고위드의 `3년 또는 동등 경험`은 실제 공고 표현과 수행 범위로 판단하며 연차를 바꾸지 않는다.

최신 작업 선호는 PDF 갱신 제외다. Markdown 수정이나 push 요청에 PDF 재생성을 포함하지 않는다. 공개 자료에는 필요한 최소한의 사례만 쓰고 고객 이름, 의료/결제 자료와 원시 대화는 옮기지 않는다.
