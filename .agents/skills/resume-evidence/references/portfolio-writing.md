# 포트폴리오 작성 규칙

일반 포트폴리오와 AI 활용 포트폴리오를 만들거나 수정할 때 적용한다. 현재 사용자 요청과 저장소의 사실 정정을 우선한다. 수치와 역할의 검증은 [근거와 평가 기준](evidence-and-review.md), 문장은 [문체와 편집 기준](writing-feedback.md)을 따른다.

## 문서의 역할과 읽는 순서

- **일반 포트폴리오:** 경력기술서 역할을 겸한다. 제품과 사용자, 경력별 담당 범위, 대표 프로젝트의 판단과 구현, 검증 및 운영 결과를 보여준다. 회사별 이력서는 여기서 직무에 맞는 핵심 경험을 요약해 연결한다.
- **AI 활용 포트폴리오:** AI를 쓰며 제품을 만드는 과정과 사람이 책임진 판단을 보여준다. 요구사항과 완료 기준, 기술 선택, 에이전트 작업, 결과 검토와 반려, 테스트와 화면 확인을 실제 사례에 연결한다. 일반 포트폴리오의 전체 경력을 그대로 복제하지 않는다.
- 기존 `portfolio.md`와 AI 문서의 위치를 유지한다. 특정 회사용 재구성이 아니라면 한 공고에만 맞춰 전체 경력을 좁히지 않는다. 대상 독자가 정해지면 사례 순서와 읽을 경로를 조정한다.

처음에는 제품과 담당 범위, 대표 사례와 결과를 짧게 파악할 수 있게 하고, 뒤에서 선택과 구현을 상세히 읽게 한다. 긴 문서에는 실제 제목과 일치하는 목차를 둔다. 대표 경험에서 상세 사례로, 관련 사례에서 코드나 검증 자료로 이동할 수 있게 연결한다. 전체 분량과 사례 수를 고정하지 않는다.

## 사례를 고르고 범위를 정하기

파일별 변경 기록 대신 사용자의 불편, 업무 흐름, 중요한 기술적 제약을 중심으로 묶는다. 관련 작업을 너무 잘게 나누거나 모든 작은 수정에 같은 비중을 주지 않는다. 반대로 건강검진처럼 여러 제품의 흐름을 잇는 프로젝트를 결제 화면 하나로 축소하지 않는다.

사례 앞에는 이해에 필요한 기간, 제품, 사용자와 본인 담당 범위를 간단히 둔다. 개발 시작, 후속 개선, 배포와 정식 출시의 시점이 다르면 구분한다. 동료가 만든 부분과 인수한 기능은 본인 기여가 정확히 읽히게 설명한다. 같은 정보를 문단마다 반복할 필요는 없다.

목록에 넣을 후보는 공고와의 관련성, 본인이 내린 결정, 문제의 난도, 실제 검증 근거로 고른다. 도입한 기술 이름과 코드량만 많은 사례를 앞세우지 않는다. 기록이 적은 경험은 사용자 확인 범위를 보존하고 불필요한 질문으로 작성을 멈추지 않는다.

## 프로젝트별 기여와 판단의 흐름

사례 앞에서 본인이 어느 부분을 어느 정도 맡았는지 읽히게 한다. 전담한 제품/계층, 함께 구현한 부분, 최초 설계, 인수 후 리팩터링과 검증 등 실제 책임으로 설명한다. 에이전트 구현과 사람의 설계/검토, 담당자가 정한 요구사항과 본인이 제안한 개선을 구분한다. 기여율을 측정한 자료가 없으면 임의의 퍼센트를 만들지 않는다.

문제를 직접 사용하며 발견했는지, 운영 제보나 요구사항으로 전달받았는지 밝히고 어떤 불편이나 반복 작업을 바꾸려 했는지 연결한다. 이어서 확인한 원인, 선택 이유, 구현한 범위와 실제 결과를 설명한다. 작업 목록에 사후 설명을 덧붙이거나 기록에 없는 고민을 창작하지 않는다.

기술과 아키텍처의 비판적 검토는 도입 사례에만 한정하지 않는다. 기존 구조 유지, 점진 전환, 도입 철회와 보류도 당시 제약과 근거가 있으면 담는다. 라이브러리 이름보다 해결할 문제와 받아들인 비용이 먼저 보이게 하고, 제안과 최종 의사결정의 주체도 실제 역할에 맞춘다.

## 사례의 기본 구조

사례는 `문제 상황 → 해결 방법 → 트레이드오프 → 결과 및 배운 점` 순서로 쓴다. 소개, 경력별 담당 범위와 workflow에까지 네 항목을 강제하지 않는다. 하위 항목의 제목과 분량은 실제 내용에 맞춘다.

| 항목 | 설명할 내용 |
| --- | --- |
| 문제 상황 | 누가 어떤 일을 하려 했는지, 기존 흐름에서 무엇이 막혔는지, 왜 해결해야 했는지와 제약 |
| 해결 방법 | 본인이 맡은 판단과 행동, 협업한 상대와 역할, 실제 코드와 사용자 흐름에서 바뀐 부분 |
| 트레이드오프 | 검토한 대안과 선택 이유, 받아들인 비용, 남은 한계와 보완 방법 |
| 결과 및 배운 점 | 확인한 동작과 측정 결과, 출시/운영 범위, 이후 판단이나 검증 기준에 실제로 반영한 내용 |

문제는 `관리가 어려웠다`로 끝내지 않는다. 어느 입력이 사라졌는지, 누가 다시 작업했는지, 어느 캐시가 갱신을 구독하지 않았는지처럼 실제 조건을 적는다. 아직 발생하지 않은 위험과 실제 운영 사고도 구분한다.

해결 방법은 기술 목록으로 대신하지 않는다. 데이터와 상태가 어디를 거치는지, 어떤 경계에서 검증하는지, 왜 이 선택이 문제에 맞는지 설명한다. 라이브러리의 일반적인 장점을 해당 프로젝트에서 검증한 결과처럼 옮기지 않는다.

배운 점은 다음 작업에서 바꾼 기준이나 재발 방지 방법으로 드러낸다. `사용자 관점이 중요함을 배웠다` 같은 총평을 반복하지 않는다. 기록에 없는 깨달음을 지어내거나 모든 사례에 같은 다짐을 덧붙이지 않는다.

## 트레이드오프의 설명 깊이

`복잡성이 늘었지만 안정성을 택했다`만으로 마무리하지 않는다. 비용이 구현 분기, 추가 저장, 운영 작업, 지연, 장애 범위 중 무엇인지 구체화한다. 대안의 장단점은 당시 제약과 연결하고, 선택한 방법의 단점도 실제로 감당하는 범위까지 쓴다.

실제로 비교한 대안만 당시 검토한 선택지로 쓴다. 뒤늦게 떠올린 대안은 지금의 평가나 향후 제안으로 구분한다. 검토 기록이 없으면 확인한 선택의 비용과 한계를 먼저 적고, 평가를 바꿀 만큼 중요한 정보만 확인한다. 그럴듯한 선택 서사를 채우지 않는다.

제품 방향, 사용자 흐름과 기술 선택에서 판단의 성격을 구분한다. 요구사항을 그대로 구현한 부분과 동작을 제안하거나 조정한 부분을 분명히 한다. 기능을 뺀 이유, 점진적으로 전환한 이유와 실패 시 유지할 상태도 근거가 있으면 유효한 판단 사례다.

## 일반 포트폴리오에서 드러낼 것

경력별로 서비스의 목적과 실제 사용자, 담당한 제품과 협업 범위를 먼저 설명한다. 대표 프로젝트에서는 사용자 흐름, 구조 설계, 출시와 운영, 오류 대응이 어떻게 이어졌는지 보여준다. 한 사례에 모든 역량을 억지로 넣을 필요는 없다.

건강검진, Sentry 도입, 테스트 도입처럼 담당 범위와 판단이 다른 큰 경험은 서로 묻히지 않게 배치한다. 이전 회사 경험을 공통 유틸리티 몇 개로 축소하지 않는다. 현재 상태와 최초 설계, 인수 후 개선을 구분한다. 지원자별 실제 범위는 [지원자 맥락](candidate-context.md)과 최신 기록을 확인한다.

수치가 없더라도 정식 출시, 운영팀 업무 변화와 검증된 실패 처리는 결과로 쓸 수 있다. 성장, 안정성이나 생산성의 개선율은 측정했을 때만 쓴다. 미출시 개인 프로젝트의 설계와 검증도 상세히 보여주되 출시한 실무 경험과 상태를 섞지 않는다.

## AI 활용 포트폴리오에서 드러낼 것

도구 이름과 프롬프트 목록을 나열하기보다 실제 작업에서 다음 내용이 어떻게 이어졌는지 보여준다. 모든 사례에 항목을 별도 소제목으로 만들 필요는 없다.

- 사용자가 정한 문제와 요구사항, 화면 흐름, 기술 선택 및 완료 기준
- 에이전트에 맡긴 구현과 테스트 범위, 사람이 결정하거나 검토한 범위
- 제출된 결과에서 실제로 발견한 누락, 잘못된 가정이나 검증의 허점
- 반려와 수정, 테스트 및 화면 확인으로 무엇을 확인했는지
- 반복된 문제를 skills, AGENTS.md, lint 규칙이나 테스트에 반영한 경우의 구체적인 기준

검토에서 놓친 사례도 실제로 확인한 원인과 바꾼 검증 방식이 있으면 담는다. 에이전트가 시킨 일을 모두 맞게 했다고 꾸미거나, 에이전트가 쓴 구현을 전부 수작업으로 작성했다고 적지 않는다. 작업 중 던진 질문과 대안 검토도 본인이 이해하고 결정한 내용과 연결한다.

실무 workflow와 테스트 기준은 지원자 맥락의 순서를 보존한다. 실무의 QA 요청을 개인 프로젝트에 추가하지 않는다. 제작 기간은 작업 범위와 함께 적고, 다른 인원/기간을 가정한 생산성 배수나 검증하지 않은 품질 수치로 환산하지 않는다. 원시 대화와 전체 프롬프트를 붙일 필요는 없다.

## 화면, 코드와 검증 자료

스크린샷은 설명하려는 사용자 흐름과 판단 가까이에 둔다. 캡션에는 어떤 화면/상태이며 무엇을 볼 수 있는지 쓴다. 정상 화면만으로 설명되지 않는 사례는 필요한 실패, 재시도나 입력 복원 상태를 실제로 보여준다. 이미지 수를 늘리는 것이 목적은 아니다.

화면은 최신 실제 UI를 다시 촬영하고 촬영한 소스 상태와 테스트 데이터 여부를 편집 기록이나 캡션에 남긴다. 고객 이름과 의료/결제 정보는 테스트 데이터로 대체한다. 기존 캡처의 픽셀과 문구를 고쳐 최신 화면처럼 만들지 않는다. 화면에서 확인할 수 없는 DB 원자성이나 운영 복구를 캡처가 증명한다고 쓰지 않는다.

설계 설명에는 필요할 때 짧은 코드, 전후 비교, 흐름도나 표를 쓴다. 전체 파일을 덤프하거나 기술을 장식으로 나열하지 않는다. 코드 링크는 가능하면 해당 시점의 커밋과 파일을 가리키고, 독자가 읽을 수 있는 접근 범위를 확인한다. 비공개 코드를 허락 없이 공개하지 않는다.

테스트는 개수보다 재현 조건, 기대 결과와 실제 확인 범위를 적는다. 단위 테스트, dev API 서버 연동, 로컬 백엔드 E2E, 실제 운영 자료를 구분한다. 구현만 읽은 테스트는 실행 성공으로, 배포 설정은 실제 인프라 적용과 복구 경험으로 바꾸지 않는다.

## 편집 완료 기준

목차와 사례 링크, 상대 이미지 경로, 실제 파일과 커밋 링크가 맞는지 확인한다. 소개의 담당 범위, 본문 사례, 기술 목록과 연결된 이력서 사이에서 기간, 역할, 수치와 출시 상태가 어긋나는지도 점검한다. 설명을 고쳤다고 측정값이나 원자료를 바꾸지 않는다.

새로 쓴 판단과 결과의 근거를 추적할 수 있어야 한다. 자료가 없어 결론이 달라지는 한계는 해당 문장 가까이 짧게 남긴다. 나머지는 확인한 내용으로 자연스럽게 마무리한다. 문서가 길어도 중복된 소개, 똑같은 교훈과 자기평가는 정리한다. PDF와 미리보기 갱신은 현재 사용자 요청 범위를 따른다.
