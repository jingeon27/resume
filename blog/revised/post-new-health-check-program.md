# 기존 프로그램 구조에 건강검진을 들이며 화면을 나눈 기준

<div class="note note-summary">
  <strong>이 글에서 다루는 것</strong>
  <p>외부 사이트와 전화 문의로 따로 돌던 건강검진을 세이프닥의 프로그램 흐름 안으로 들인 과정을 다뤄요. 비급여 프로그램은 파트너가 올리고 운영팀이 검수하지만, 검진 프로그램은 내부 운영팀이 Back-Office에서 직접 올리고 검수 단계가 없어요. 파트너는 병원 관리자에서 조회만 해요. 보여 줄 정보와 신청 뒤에 일어나는 일도 비급여 프로그램과 달랐어요. 그래서 검진 구성은 한 벌로 저장해 네 화면이 같은 모양으로 읽게 하고, 복지몰의 상세와 신청 폼은 조건을 얹는 대신 화면째 나눴어요. 선택 검사 시트의 동작은 담당자와 논의해 바꿨고, 결제는 실패하고 돌아오는 경로부터 정했어요. 사례는 관리자 서비스 모노레포(Back-Office·병원 관리자)와 복지몰 두 저장소에 걸쳐 있어요. 이 글은 건강검진 예약 흐름을 정식 오픈한 2026년 9월 30일에 정리했어요. 그림은 9월 28일 stage 테스트 데이터로 진행한 화면을 바탕으로 다시 그린 것이고, 코드는 설명을 위해 줄였어요.</p>
</div>

세이프닥의 비급여 프로그램은 흐름이 정해져 있어요. 파트너가 병원 관리자에서 프로그램을 올리고 검수를 요청하면, 운영팀이 Back-Office에서 관련 법규와 서비스 정책에 맞는지 보고 승인해요. 승인된 프로그램은 복지몰의 상세 화면에 노출되고, 사용자는 거기서 방문예약을 신청하죠. 병원 관리자의 등록·검수 요청 화면과 Back-Office의 검수 화면은 제가 처음 만든 화면이기도 해요.

세이프닥은 제휴 병원과 제휴기업을 함께 늘려야 하는 서비스예요. 사용자의 대부분은 제휴기업을 통해 들어오고, 예약할 수 있는 병원이 부족하면 원하는 지역이나 검진을 찾기 어려워요. 반대로 병원 입장에서는 예약이 적으면 입점할 이유가 약해져요. 화면을 개선하는 것만으로 이 문제를 해결했다고 말할 수는 없어요. 제가 맡은 건강검진 작업은 이미 제휴한 병원의 검진을 복지몰 안에서 살펴보고 신청할 수 있게 만든 일이에요.

건강검진은 이 흐름 밖에 있었어요. 사용자는 외부 사이트에서 검진 정보를 본 뒤 전화로 문의했어요. 기업 계약에 따른 검진 코드를 쓰기도 하고, 예약금을 먼저 결제하기도 하고, 프로그램 구성도 "기본 검사 몇 가지에 선택 검사를 그룹마다 몇 개"처럼 비급여와 모양이 달라서 기존 프로그램에 그대로 넣기 어려웠죠. 한 제휴 파트너가 검진 예약을 세이프닥 안에서 받고 싶다고 요청하면서 이 흐름을 들이게 됐어요. 전달받은 스펙에서 빠진 동작과 예외는 개발팀장·부팀장과 확인해 가며 채웠어요.

## 검진 프로그램은 파트너가 올리지 않아요

비급여 프로그램의 검수는 상태로 움직여요. 파트너가 신규등록·수정·삭제 중 하나로 검수를 요청하면 병원 관리자에는 '검수중'으로 보여요. 운영팀이 Back-Office에서 검수중 스위치를 켜고 내용을 본 뒤 반려하면 사유가 파트너의 검수 내역 상세에 남고, 승인하면 프로그램이 생기고 노출 일시가 정해져요.

검진 프로그램은 스펙상 이 검수를 거치지 않아요. 운영팀이 Back-Office에서 검진 구성까지 직접 등록하고, 파트너는 병원 관리자에서 그 결과를 조회만 해요. 그래서 병원 관리자에서는 검진 프로그램으로 검수 요청이 이어지는 입구를 모두 막아야 했어요. 검수요청 메뉴, 목록의 신규 등록·삭제 버튼, 상세의 검수요청·삭제요청 버튼이요. 상세 폼은 그대로 두되 모든 입력을 잠갔어요.

처음에는 이 판정을 파트너 단위로 했어요. 파트너의 진료과에 건강검진이 하나라도 있으면 막는 식이었죠. 그런데 검진과 피부과를 함께 운영하는 파트너가 있었어요. 이 파트너는 피부과 프로그램까지 조회 전용이 되고 검수요청 메뉴도 사라졌어요. 막아야 하는 건 "검진 파트너의 검수 요청"이 아니라 "검진 프로그램의 검수 요청"이었던 거예요. 그래서 판정 단위를 둘로 나눴어요.

- 프로그램 상세는 조회한 프로그램의 진료과로 가려요. 파트너 조회에 기대지 않아요.
- 메뉴와 목록의 읽기 전용 모드는 진료과가 건강검진뿐인 파트너에게만 켜요. 이런 파트너는 검수를 요청할 프로그램이 아예 없으니까요.
- 검진과 다른 진료과를 함께 가진 파트너에게는 신규 등록과 예전 임시저장 불러오기, 반려 건 재요청이 모두 같은 폼을 거쳐요. 그래서 폼의 카테고리 검증이 건강검진 진료과 제출을 거절하게 했어요. 공용 캐스케이더에 한 곳만 쓰는 prop을 늘리지 않으면서, 이미 저장된 임시저장·반려 건에 실린 건강검진 진료과까지 한 자리에서 잡으려는 선택이었어요.

건강검진인지를 가르는 기준도 한 곳으로 모았어요. 판별이 진료과 이름에서 진료과 id로 바뀌면서 `===` 비교가 여섯 곳에 흩어져 있었거든요. 공용 패키지에 `isHealthCheckDepartment` 하나를 두고, 그 id가 dev·stage·운영에서 같은지는 세 환경의 진료과 목록 API로 확인해 상수 옆에 적어 뒀어요.

## 검진 구성은 한 벌로 저장하고 네 화면이 읽어요

검진 구성은 필수 항목 목록과 선택 그룹 목록이에요. 선택 그룹은 이름과 "몇 개를 고르는지(`pickCount`)", 그리고 고를 수 있는 항목으로 이뤄져요. Back-Office가 이 한 벌을 저장하고, 네 화면이 같은 값을 읽어요.

<figure class="figure-wide">
  <img src="../assets/figures/health-check/02-composition.png" alt="필수 항목과 선택 그룹으로 이뤄진 검진 구성 하나를 Back-Office 등록 폼, 병원 관리자 조회 전용 폼, 복지몰 검진 상세의 검사 구성, 복지몰 선택 검사 시트가 각각 편집, 잠금, 요약, 선택 형태로 그리는 모습" />
  <figcaption>같은 검진 구성을 Back-Office는 편집하고, 병원 관리자는 잠근 채 보여 주고, 복지몰은 요약과 선택 화면으로 그려요</figcaption>
</figure>

Back-Office 등록 폼에서 지킨 규칙은 하나예요. 한 검사 항목은 한 곳에만 들어가요. 한 예약에 같은 항목이 두 번 들어가면 안 되니까, 다른 그룹이 이미 가져간 항목은 선택지에서 잠가요.

```ts
/** owner 를 뺀 나머지 그룹이 이미 가져간 검사항목 id. 다른 그룹의 선택지는 잠근다. */
export function getItemIdsTakenByOtherGroups(values: CompositionValues, owner: 'included' | number): number[] {
  const fromIncluded = owner === 'included' ? [] : (values.includedItemIds ?? []);
  const fromGroups = (values.selectableGroups ?? []).flatMap((group, index) =>
    index === owner ? [] : (group?.itemIds ?? []),
  );
  return uniq([...fromIncluded, ...fromGroups]);
}
```

운영팀이 입력 결과를 가늠하는 미리보기도 바꿨어요. 처음 미리보기는 그룹명과 항목명을 한 줄로 늘어놓는 표라서, 복지몰의 실제 검사 구성과 모양이 달랐어요. 복지몰 상세의 검사 구성 섹션을 그대로 옮겨 와서, 기본 검사는 개수만 보여 주고 선택 검사는 그룹별로 카테고리와 항목 칩을 그리게 했어요. 미리보기라 "항목 보기"는 모양만 두고, 선택 그룹은 펼친 채로 고정했어요.

진료과를 검진에서 다른 과로 옮기는 수정에서는 저장 순서가 문제가 됐어요. 프로그램 저장은 성공하고 구성을 비우는 요청만 실패하면, 다시 불러온 상세는 이미 검진이 아니라서 구성 조회가 꺼지고, 재시도해도 남은 구성을 비우지 않은 채 닫혔어요. 실패한 비우기를 기억하는 저장 훅 하나로 등록·수정 모달과 프로그램 상세가 같은 순서를 쓰게 하고, 재시도하는 흐름을 테스트로 남겼어요.

기록에 남지 않은 일도 하나 있었어요. 검진 구성 수정이 `HEALTH_CHECK_ITEM_UNAVAILABLE`로 거절돼서 원인을 따라가 보니, 이미 삭제된 검사 항목이 조회 응답에 섞여 있었어요. 화면에서 그 항목을 걸러 내 덮지 않고, 응답을 그대로 백엔드 담당자에게 전달했어요.

## 상세 화면은 조건을 얹지 않고 둘로 나눴어요

복지몰의 비급여 프로그램 상세는 동료가 주로 만든 화면이에요. 여기에 검진을 얹을 방법은 두 가지였어요. 한 화면에 `healthCheck` 조건을 여기저기 붙이거나, 화면을 둘로 나누거나요.

검진 상세는 비급여 상세와 세 곳이 달랐어요. 쿠폰을 쓰지 않아서 쿠폰 조회와 쿠폰 적용가가 없고, 검사 구성을 보여 줘야 하고, 전화상담이 없어요. 한 화면에 조건을 얹으면 갈래마다 조건이 붙어서, 비급여 화면을 고치는 사람도 검진 화면을 고치는 사람도 어느 쪽이 그려지는지 매번 따져야 해요.

<figure class="figure-wide">
  <img src="../assets/figures/health-check/03-detail-split.png" alt="프로그램 상세 페이지가 programInfo.healthCheck 값으로 비급여 상세 View와 검진 상세 View 중 하나를 고르고, 두 View가 상단바와 가격 같은 기존 구획은 함께 쓰되 쿠폰 적용가, 검사 구성, 전화상담 버튼은 한쪽에만 두는 구조" />
  <figcaption>상세 페이지는 조회와 화면 선택만 하고, 두 View가 각자 자기 구조를 조립해요</figcaption>
</figure>

그래서 `programInfo.healthCheck`로 화면을 나눴어요. 예약 화면이 신청 폼을 나누는 기준과 같은 값이에요.

```tsx
// 설명을 위해 줄인 코드예요. 페이지는 조회·최근 본 시술 저장·화면 선택만 해요.
function ProgramPage({ programId }: Props) {
  const { data: program } = useSuspenseQuery(programDetailOptions(programId));
  useSaveRecentProgram(program);

  return program.programInfo.healthCheck ? (
    <HealthCheckProgramDetailView program={program} />
  ) : (
    <ProgramDetailView program={program} />
  );
}
```

두 View는 각자 전체 구조를 선언적으로 조립해요. 함께 쓰는 건 이미 있던 구획들과 상단바, 비로그인 버튼, 방문예약 버튼, 인증 뒤 이동 훅, 이벤트 헬퍼뿐이에요. 가격 구획은 쿠폰 아코디언을 직접 그리지 않고 가격 아래 슬롯으로 받게 바꿨어요. 비급여 View는 그 자리에 쿠폰 적용가를 넣고, 검진 View는 비워 둬요. 조회 이벤트의 모양은 같게 유지했어요. 검진은 쿠폰이 없으니 쿠폰 칸을 적용 전 가격으로 채워서, 분석 쪽에서 두 화면의 이벤트를 따로 해석하지 않아도 되게 했어요.

<div class="note note-decision">
  <strong>최종 결정</strong>
  <p>검진은 조건 하나가 다른 게 아니라 보여 줄 정보와 버튼, 조회할 데이터가 함께 달랐어요. 이럴 때 한 화면에 조건을 얹으면 두 화면을 한 파일에서 동시에 읽어야 해요. 페이지는 어느 화면을 그릴지만 정하고, 두 View가 각자 구조를 조립하게 했어요. 신청 폼도 같은 이유로 폼째 나눴어요. 검진에만 있는 검사 선택·공단 검진 여부·주소·기업 검진 코드·청약철회 안내와, 비급여에만 있는 쿠폰·추가 문의가 한 폼에서 갈리지 않게요.</p>
</div>

파트너 상세의 프로그램 카드에서는 이 값을 쓸 수 없었어요. 파트너 응답의 프로그램 목록에는 검진 여부가 없거든요. 그래서 카드는 진료과로 검진인지 가르고, 검진 카드에서 전화상담을 뺐어요.

## 택 N을 채우면 남은 칩을 잠갔어요

선택 검사는 그룹마다 정해진 개수를 골라야 해요. "정밀 영상검사 중 2개"처럼요. 처음 요청은 한 그룹을 다 고르면 다음 그룹을 자동으로 열어 달라는 거였어요.

그렇게 하면 이미 고른 그룹의 선택을 고칠 때가 문제였어요. 한 칩을 빼고 다른 칩을 넣으려고 누르는 순간에도 개수가 차니까, 시트가 사용자의 의도와 상관없이 다음 그룹으로 넘어가요. 게다가 당시 구현은 택 N을 넘기면 먼저 고른 칩을 조용히 밀어내고 있었어요. 사용자는 고른 줄 알았던 검사가 빠진 걸 모르고 지나갈 수 있었죠. 강제로 넘어가는 문제를 담당자에게 짚고 동작을 다시 논의했어요.

<figure class="figure-wide">
  <img src="../assets/figures/health-check/04-pick-lock.png" alt="선택 검사 시트의 세 상태. 그룹을 채우는 중에는 모든 칩을 고를 수 있고, 한 그룹을 채우면 고르지 않은 칩이 비활성이 되며, 모든 그룹을 채워야 선택 완료 버튼이 켜진다. 아래에는 처음 요청인 자동 다음 그룹 열기와 논의 뒤의 칩 잠금을 비교한다" />
  <figcaption>그룹을 채우면 남은 칩이 잠기고, 모든 그룹을 채워야 선택 완료가 켜져요</figcaption>
</figure>

결론은 넘치는 선택을 화면이 막는 쪽이었어요. 다 채운 그룹은 고르지 않은 칩이 비활성이 되고, 바꾸려면 고른 칩을 먼저 해제해요. 시트는 스스로 다음 그룹을 열지 않아요. 선택 로직은 배열에 넣고 빼기만 하게 줄였어요.

```ts
// 선택 로직은 넣고 빼기만 해요. 밀어내기와 pickCount 인자를 걷어냈어요.
export const toggleHealthCheckItem = (selected: number[], itemId: number) =>
  selected.includes(itemId) ? selected.filter((id) => id !== itemId) : [...selected, itemId];

// 넘치는 선택은 화면이 막아요(설명을 위해 줄인 코드예요).
const isFull = selected.length >= group.pickCount;
<Chip pressed={isSelected} disabled={isFull && !isSelected} onClick={() => onToggle(item.id)} />;
```

디자인에는 비활성 칩 모양이 없었어요. 공용 Chip에 비활성 모양을 요청해서 받았고, 지금 그 모양을 쓰는 곳은 이 시트뿐이에요. 밀어내기를 검증하던 테스트는 잠금 테스트로 바꿨어요. 채우면 잠기고, 덜 채우면 누를 수 있고, 해제하면 다시 고를 수 있는지를 봐요. 잠금 코드를 빼면 이 테스트가 실패하는 것도 확인했어요.

## 신청부터 접수까지는 실패하고 돌아오는 길부터 정했어요

신청 폼을 채우고 확인 시트에서 금액을 확인하면 결제로 넘어가요. 이 구간은 작업 중에 백엔드 계약이 한 번 바뀌었어요. 예전에는 예약을 먼저 만들고 결제 화면에서 주문을 따로 만들었는데, 바뀐 계약에서는 checkout 호출 하나가 결제가 필요한지를 정해요. 프론트엔드는 9월 16일에 이 계약으로 옮겼어요. 기업 지원이나 0원 예약은 그 호출로 접수가 끝나고, 예약금이 있는 예약만 주문을 받아 결제창을 열어요. 결제하지 않은 예약이 남지 않는 계약이라, 옛 결제 라우트와 목, E2E를 통째로 걷어내고 새 흐름에 맞췄어요.

<figure class="figure-wide">
  <img src="../assets/figures/health-check/05-checkout-states.png" alt="검진 신청 폼에서 확인 시트, checkout으로 이어지고, 기업 지원·0원이면 바로 접수, 예약금이 있으면 토스 결제창을 거쳐 승인, 실패·승인 거절·승인 직후 환불, 결과 불명의 세 갈래로 나뉘는 상태도" />
  <figcaption>결제창을 다녀온 결과마다 사용자가 돌아갈 자리를 먼저 정했어요</figcaption>
</figure>

토스 결제창은 모바일에서 결과를 리다이렉트로만 돌려줘요. 결제창을 다녀오면 페이지가 새로 열리고 메모리 상태는 남지 않아요. 그래서 폼 값을 결제 시도의 `orderId`와 함께 `sessionStorage`에 맡기고, 돌아왔을 때 같은 시도이면서 현재 폼 스키마를 통과한 값만 한 번 되살려요. 꺼내면 맞든 틀리든 지워서, 성공한 신청의 주소와 검사 선택이 다음 신청에 남지 않게 했어요.

stage에서 끝까지 결제해 보다가 예상하지 못한 결과도 만났어요. 결제 승인 응답이 성공인데 상태가 `REFUNDED`였어요. 이 결제에서 허용하는 수단은 카드와 간편결제뿐인데, 결제창에는 퀵계좌이체가 기본으로 선택돼 있었어요. 그 수단으로 내면 서버가 승인 직후 전액 환불하고 예약을 만들지 않았죠. 결제창에 어떤 수단을 보여 줄지는 SDK 옵션이 아니라 결제사 관리 화면의 위젯 설정이 정해서, 프론트엔드에서 고칠 수 있는 건 그 결과를 받는 화면이었어요. 예약도 청구도 남지 않았는데 "예약 목록에서 확인"으로 보내던 것을, 결제 실패와 같게 신청 화면으로 돌려보내 입력을 되살리고 사유를 안내하게 바꿨어요. 결과를 알 수 없는 경우만 예약 목록으로 보내요.

중복 신청도 막았어요. checkout이 끝난 뒤에도 결제 SDK를 기다리는 동안(최대 10초) 신청 버튼이 다시 열려서, 한 번 더 누르면 주문이 하나 더 생겼거든요. 주문 생성부터 결제창이 뜨기까지를 한 mutation으로 묶고 그동안 버튼을 잠갔어요. 확인 시트가 뜨기 전 연타로 시트가 둘 열리는 경우는 따로 플래그를 만들지 않고, 그동안 켜져 있는 폼 제출 상태로 막았어요.

## 확인한 것

- 복지몰: 선택 검사 잠금, 신청 폼 스키마(필수 약관 셋이 모두 켜져야 통과), 결제창 인계 값의 저장·복원·삭제를 Vitest로 고정했어요. 검진 예약금 결제 흐름은 dev API 서버에 붙는 E2E로 토스 테스트 결제창 이동과, 결제창에서 돌아오는 실패·승인 거절 경로를 확인해요. 기업 검진 코드 입력도 이 E2E에 들어가 있어요.
- 관리자 서비스: 파트너 단위 판정이면 실패하도록 혼합 진료과 파트너 케이스를 명세 테스트에 더했고, 진료과를 옮길 때 빈 구성을 보내는 흐름은 실제 폼 조작으로 테스트해요. 건강검진 파트너 흐름은 dev API 서버를 쓰는 E2E와 계약 테스트로 돌리고, CI의 dev API 서버 테스트는 일반 파트너와 건강검진 파트너 갈래로 나눠 실행해요.
- 9월 28일에는 stage 테스트 데이터로 비급여 프로그램의 등록 → 검수 요청 → 승인, 복지몰 비급여 예약 신청, 검진 프로그램 등록과 복지몰 검진 신청 → 결제창까지를 직접 진행하며 화면을 확인했어요. 이 글의 그림이 그 화면을 바탕으로 한 거예요.

위 테스트와 그림은 오픈 전에 진행한 검증 기록이에요. 글을 정리한 날이 정식 오픈 당일이라, 예약 건수나 전환 성과는 아직 다루지 않았어요.
