### 문체

`article-template.md`대로 `~했어요`·`~였어요`·`~인데요`를 기본으로 쓴다. 모든 문장을 같은 어미로 맞추지 않고 짧은 단정과 질문을 섞는다. 코드 블록·인용문·표 셀은 예외다. 23·32·33·34·35·36번을 이 기준으로 맞췄고(32·33은 2026-09-23), 아직 평서체(`~했다`)나 합쇼체(`~습니다`)로 남은 글은 순차 전환한다.

제목과 소제목에는 em dash(`—`)나 `0.`, `1.` 같은 순번을 붙이지 않는다. 자연스러운 문장으로 쓰고, 구분이 필요하면 콜론을 사용한다. 기술 버전(예: FSD 2.1)과 본문의 절차 번호는 유지한다.

### 사실 표기

- 수치에는 산출 기준을 붙인다. 예: "핵심 이동 커밋 한 건 기준 853개 파일". 시점·날짜는 본문에 쓰지 않는다(아래 날짜 규칙).
- 브랜치에만 있는 작업은 완료형으로 쓰지 않고 진행 상태를 적는다. 관리자 서비스 모노레포의 FSD 재편은 2026-09-08, 복지몰은 2026-09-09 develop에 합쳐졌다.
- 가명을 쓴 식별자는 그 자리에서 가명임을 한 번 밝힌다(패키지 스코프, 공용 훅 이름 등).
- 확인하지 못한 것은 "재현하지 못했어요"로 낮추고, 추정은 추정으로 쓴다.
- 저장소마다 구현이 다르면 어느 저장소 사례인지 밝힌다.
- 이미 공개된 글의 개정본은 티스토리 공개 시점에 쓴 글처럼 쓴다. 코드·수치·그림은 공개 시각 직전 develop 기준이고, 그 뒤의 커밋·변경·링크·참고 문서와 나중에 고쳐진 문제를 미리 아는 듯한 서술은 넣지 않는다(2026-10-01, 11·15·22번 적용). 34번(AI 작업 흐름)은 예외로 지금 일하는 방식을 쓴다(2026-10-02 사용자 결정 "AI 작업 흐름은 지금이 베스트"). 18번(프로그램 폼)도 현재 구현 기준으로 쓴다(2026-10-03 사용자 결정). typed form·업로드 응답 타입·변환 테스트와 그림을 함께 갱신하고, 코드에 남아 있는 구현을 이미 제거했다고 쓰지 않는다. 두 글을 다시 공개일 기준으로 되돌리지 않는다.
- 본문·그림·각주에 날짜를 쓰지 않는다(2026-10-02 사용자 지시 "굳이 날짜 언급은 하지마"). '이 글의 코드는 ○○ develop 기준(버전)' 같은 기준일 문장, 사건 날짜, '8월 말' 같은 시기, 월별 수치가 모두 대상이고, 순서는 '처음에는·그 뒤·이제는'으로 잇는다. 공개 전 글(건강검진)도 오픈일·작업일 같은 날짜에 묶지 않는다. 이 지시 전에 고친 다른 글에 남은 사건 날짜는 사용자 확인 뒤 한꺼번에 뺀다.

## 이번 판단에서 바로잡은 부분

- 11번 글은 서비스명과 내부 코드 식별자를 역할 중심의 가명으로 바꿨다. 예약 대상 선택 컴포넌트가 리팩터링 당시 519줄에서 55줄로 줄었다는 범위로 수치를 바로잡고, 가족 선택 기능 전체가 줄어든 것처럼 표현하지 않았다. 현재 구현에 없는 `mode: 'onChange'`와 `setValue`의 `shouldDirty`·`shouldValidate`가 적용된 것처럼 쓴 설명은 제거하고, 이를 남은 부채로 명시했다.
- 15번 글은 회사·서비스 이름을 생략하고 내부 코드 식별자를 역할 중심의 가명으로 바꿨다. 개선안 예시를 현재 구현인 것처럼 서술한 부분도 바로잡았다. 값과 단계를 관리하던 두 Zustand 스토어를 없애고 `@use-funnel/core` 기반 퍼널, 단계별 폼, `reset + history.replace`, 서버 prefetch 뒤 `useQueries`로 캐시를 읽는 구조는 유지했다. `_def` 의존과 최종 전체 검증 부재, 불리언 값의 의미가 불분명한 문제는 완료된 개선이 아니라 남은 기술 부채로 구분했다.
- 19번 글은 서로 다른 호스트 사이에서 인증 정보를 한 번 넘겨야 했던 제약을 다룬다. 회사 실명·실제 도메인·내부 경로와 사용자 정의 식별자를 익명화했다. 현재 코드의 `no-referrer`·`unsafe-inline` 설정과 Origin 검증 부재를 그대로 적고, Origin 검증과 nonce 기반 CSP는 적용된 코드가 아니라 검토 중인 보강안으로 구분했다. URL 방식에서 줄어든 노출 범위와 리프레시 토큰 복제, 갱신 충돌, 로그아웃 동기화, 브라우저 자바스크립트에 토큰이 다시 노출되는 위험도 함께 적었다.
- 20번 글은 번호를 따라가는 개발 일지 형식을 걷어내고, 서로 다른 두 SSE를 하나의 화면에 연결한 제약과 판단 중심으로 다시 썼다. 응답을 읽고 버리는 연결, 인증 헤더, 상태 전이, `@tanstack/ai` 어댑터와 남은 한계를 필요한 코드와 함께 설명한다.
- 12번 낙관적 업데이트 글도 수정 대상에 포함했다. 자동으로 롤백된다는 잘못된 설명을 제거하고, 목록·상세 캐시의 스냅샷을 `onMutate`에서 반환해 `onError`에서 직접 복구하는 흐름으로 다시 작성했다.
- 21번 글은 서비스명과 내부 코드 식별자를 일반화하고, 현재 구현에 맞춰 인증 정책을 "서버에서는 토큰을 읽지 않는다"가 아니라 "공개 조회는 기본적으로 쿠키를 읽지 않고, 회원별 서버 렌더링(SSR) 조회만 명시적으로 허용한다"로 표현했다. 배포 환경에 따라 런타임 캐시가 인스턴스별로 나뉠 수 있다는 조건과 실제 비용 절감 수치를 측정하지 않았다는 한계도 추가했다. 생성 시각 `lastModified`, `priority`, 전체 개수를 그대로 페이지 크기로 보내는 조회, 오류를 `[]`로 바꾸는 처리와 수동 XML 이스케이프는 제거된 개선이 아니라 현재 코드에 남은 부채로 바로잡았다.
- 25번 글은 앱 이름과 내부 식별자를 일반화하고, 최초 구축과 8월 11일 시점의 테스트 파일 수를 구분했다. 가입 우회 시나리오 26행 중 25행에 대표 E2E가 생긴 현재 범위와 함께, 일부 상태만 검증한 테스트·잘못된 현재 동작을 기록한 테스트·자동 실행되지 않는 범위도 한계로 표시했다. 응답 스키마의 관측형 경계와 사이트맵 테스트의 잘못된 성공 판정도 반영했다.

- 32번 글은 타입 접두사 이탈을 규칙 도입 커밋 직전 트리에서 다시 쟀다(`.d.ts` 제외 TS/TSX 1,838개, interface 145/639, type 262/661, 합계 407/1,300 = 31%). 테스트·mock을 빼면 388/1,264으로 비율은 같다. 이력서 문서들이 적은 400/1,285(31%)은 같은 커밋을 다른 필터로 센 값이라 비율은 일치하고 절대값만 1~2% 다르다. 현재 트리(2026-09-18)는 4/1,372.
- 33번 글은 시리즈 기준(해요체·note 블록·참고 절)에 맞춰 다시 썼다. 논지는 그대로다.
