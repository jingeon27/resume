# 문서에만 있는 규칙은 20~38% 어긋나 있었습니다

프로젝트에는 컨벤션 문서가 잘 갖춰져 있었습니다. 아키텍처 경계, queryKey 관리, 배럴 작성, 파일 네이밍까지 영역별로 정리돼 있었고, 저도 그걸 쓰면서 지키고 있다고 생각했는데요.

같은 리뷰 코멘트가 계속 반복됐습니다. 문서에 적혀 있는 내용인데도요. 문서를 더 자세히 쓰는 게 답인지 확신이 없어서, 먼저 저장소를 통째로 계측해 봤습니다.

## 숫자가 보여준 것

소스 파일 1,600여 개를 놓고 규칙별 위반 건수를 셌는데요.

| 규칙 | 문서화 | lint | 위반 |
| --- | --- | --- | --- |
| 레이어 경계 (FSD) | O | O | 0건 |
| queryKey는 options 함수에서만 | O | O | 0건 |
| 배럴에 `export *` 금지 | O | O | 0건 |
| `let` 대신 `const` | O | O (warning) | 16건 |
| interface `I` 접두사 | X | X | 627건 중 140건 (22%) |
| type `T` 접두사 | X | X | 627건 중 239건 (38%) |
| 컴포넌트 named export | X | X | 1,063건 중 340건 (32%) |

패턴이 선명했습니다. **lint로 옮긴 규칙은 위반이 0건이고, 문서에만 있는 규칙은 어긋난 게 수백 건이었습니다.** 타입 선언만 합쳐도 1,254건 중 379건(30%)입니다. 유일하게 위반이 남은 lint 규칙은 warning이라 빌드를 세우지 않는 `let` 하나였고요.

이탈이 언제 쌓였는지도 시점별로 재봤는데요. 특정 시기의 문제가 아니었습니다.

| 시점 | 파일 수 | interface 이탈 | type 이탈 |
| --- | --- | --- | --- |
| 2025-05 (합류) | 294 | 17/138 (12%) | 5/93 (5%) |
| 2025-11 | 557 | 61/265 (23%) | 18/199 (9%) |
| 2026-05 | 999 | 70/414 (17%) | 81/330 (25%) |
| 2026-08 (정리 직전) | 1,657 | 140/627 (22%) | 239/627 (38%) |

코드가 294개 파일에서 1,657개로 다섯 배 넘게 커지는 15개월 동안 이탈이 함께 쌓였습니다. 특히 type 접두사는 코드가 빠르게 늘던 후반부에 5%에서 38%까지 가속했는데요. 규칙 없이 코드만 늘면 이탈은 비율째 커진다는 뜻입니다.

미리 말해두면, 어긋난 코드의 상당수는 제가 쓴 것이었습니다. 커밋 내역을 열어보면 규칙을 세우기 전의 저는 이 문서의 성실한 위반자였는데요. `any`를 쓰고, queryKey를 손으로 적고, 접두사 없는 타입을 만들었습니다. 문서를 알고 있는 것과 매 순간 지키는 것은 다른 일이었고, 그건 의지의 문제라기보다 **사람의 주의력이 규칙 개수만큼 늘어나지 않는다**는 문제였습니다.

규율이 느슨한 게 아니었습니다. **적어놓고 기계에 넘긴 것만 지켜지고 있었던 건데요.** 문서는 규칙의 출발점이지 도착점이 아니었던 겁니다.

그래서 문서를 더 자세히 쓰는 대신, 문법만 봐도 판정할 수 있는 규칙부터 lint로 옮기기로 했습니다.

## 0건은 규율이 아니라 청소의 결과입니다

표의 "위반 0건"은 사람들이 규칙을 잘 지켜서 나온 숫자가 아닌데요. **규칙을 켜기 전에 쌓여 있던 위반을 전부 걷어내고, 다시 생기지 않게 잠근 결과**입니다.

lint 규칙은 위반이 남아 있는 채로는 켤 수 없습니다. 켜는 순간 빌드가 깨지거나, warning 수백 개 속에서 새 경고가 묻히거나 둘 중 하나거든요. 그래서 규칙 하나를 올릴 때마다 청소가 먼저였습니다.

- 앱에서 꺼져 있던 `no-explicit-any`를 켜면서 `any` **82곳**을 걷어냈습니다 (50개 파일)
- 무효화 자리의 raw-string queryKey를 options 함수로 옮겼습니다 (15개 파일)
- 저장소에 남아 있던 `let`을 걷어냈습니다 (25개 파일)
- 타입 접두사 통일은 이탈 379건을 **한 커밋에 431개 파일**로 정리했습니다. 정리 후 이탈은 interface 4건(1%), type 0건입니다

여기에 더 근본적인 문제가 하나 있었는데요. 규칙이 없어서가 아니라, **모든 규칙을 warning으로 낮추는 설정이 전체에 걸려 있었습니다.** 규칙은 존재했지만 아무것도 빌드를 세우지 못했고, 저를 포함해 아무도 경고 목록을 읽지 않았습니다. 그 설정을 걷어내자 가려져 있던 미사용 import 같은 것들이 바로 드러났고요.

warning이 수백 개면 0개와 같습니다. 규칙의 값어치는 개수가 아니라 **위반이 생긴 그 자리에서 보이는가**에 있었습니다.

## 셀렉터로 끝나는 규칙부터

가장 싼 방법은 `no-restricted-syntax` 셀렉터인데요. queryKey 상수 선언 금지가 그렇습니다.

```ts
{
  selector: "VariableDeclarator > Identifier[name=/_QUERY_KEYS?$/]",
  message: 'queryKey 상수를 따로 선언하지 않습니다 — 키 문자열은 options 함수 안에 인라인으로 둡니다.',
},
```

셀렉터로 안 되는 규칙은 파일을 따로 만들었습니다. 라우트에서 조회 금지, 슬라이스 Public API 강제, 미사용 재수출 검출 같은 것들인데요. 이쪽은 파일 시스템을 읽고 import 그래프를 따라가는 작은 정적 분석기가 됩니다. 규칙 자체를 어떻게 테스트하고 fixture를 관리했는지는 별도의 글에서 다뤘습니다.

## error는 하나뿐입니다

규칙을 옮기면서 심각도 기준을 하나로 잡았는데요. **틀렸을 때 조용히 실패하는가.**

`let`을 쓰면 코드가 읽기 나빠질 뿐 동작은 합니다. 그런데 무효화 자리에 queryKey를 손으로 적으면 이야기가 다른데요.

```ts
// options 의 키가 바뀌어도 이쪽은 조용히 남는다 — 아무것도 무효화하지 않는 코드
queryClient.invalidateQueries({ queryKey: ['fetchProgramList'] });
```

options의 키가 바뀌는 순간 이 무효화는 아무 일도 하지 않으면서 아무 에러도 내지 않습니다. 화면에는 옛 데이터가 남고, 문자열이 맞는지 확인할 방법은 사람 눈밖에 없거든요. 그래서 이 규칙 하나만 error이고 나머지는 전부 warning입니다.

warning에서 error로 올릴 때는 저장소 위반이 0건인지 먼저 확인하는데요. 남아 있는 채로 올리면 그 순간부터 lint가 깨지고, 급한 PR을 막는 규칙은 결국 꺼집니다. 규칙이 죽는 경로는 대개 이쪽입니다.

## 밟은 함정들

**규칙을 재선언하면 통째로 덮입니다.** `no-restricted-syntax`를 하위 설정에서 다시 선언하면, 상위에서 걸어둔 셀렉터가 그 파일들에서만 전부 사라지는데요. 배럴에만 `export *` 금지를 얹으려다 그 파일들에서 `let` 검사와 queryKey 검사가 꺼져 있던 걸 나중에 발견했습니다. 지금은 얹을 때 항상 기존 배열을 깔고 시작합니다.

```ts
'no-restricted-syntax': ['warn', ...restrictedSyntax, noExportStar],
//                               ^^^^^^^^^^^^^^^^^^^ 빼먹으면 조용히 꺼진다
```

**`tsconfigRootDir`는 명시해야 합니다.** typescript-eslint 8.46+는 이 값을 안 주면 호출 스택의 설정 파일 위치로 추론하는데요. 에디터의 ESLint 확장처럼 한 프로세스가 모노레포의 여러 패키지 설정을 로드하면 후보가 둘 이상이 되어 파싱 에러로 죽습니다. CI는 멀쩡한데 에디터에서만 빨간 줄이 뜨는 상태였습니다.

**빌드 산출물은 직접 막아야 합니다.** ESLint의 기본 ignore는 `node_modules`뿐인데요. 게다가 설정을 `.map`으로 감싸며 모든 항목에 `files`를 붙이는 곳에서는 global ignores가 무력화되므로, 그쪽에서 ignore 항목을 다시 걸어야 했습니다.

## 20~38%는 규칙이 없어서 어긋난 것이었습니다

계측에서 이탈률이 높았던 항목들을 다시 보면 공통점이 있는데요. 전부 **문서에 규칙 자체가 없던 것들**입니다. 타입 접두사, export 방식, 훅 파일 이름.

순서가 이렇게 정리됩니다.

1. 암묵적 합의 → 문서에 적는다
2. 문서에 적힌 것 중 문법으로 판정 가능한 것 → lint로 옮긴다
3. 조용히 실패하는 것 → error로 올린다

계측 시점에는 2단계까지 와 있었고 1단계에서 빠진 게 남아 있었는데요. 이후 타입 접두사부터 실제로 옮겼습니다. 앞에서 적은 431개 파일짜리 커밋이 그것입니다. `interface`는 `I`, `type`은 `T`로 통일하는 정리와 lint 고정을 한 커밋에 담았는데요. 규칙 없이 정리만 하면 새 코드가 다시 갈라지고, 정리 없이 규칙만 켜면 그 순간부터 경고 수백 개가 쏟아져 아무도 읽지 않는 목록이 되기 때문입니다.

## 규칙 개수가 아니라 실제로 지켜지는지를 봅니다

이 작업이 잘 됐는지를 무엇으로 판정할지도 정해 뒀는데요. 규칙을 몇 개 만들었는지는 기준이 될 수 없습니다. 규칙은 늘리는 것 자체가 쉽고, 늘어난 규칙이 부담만 주고 있을 수도 있으니까요.

기준은 세 가지로 잡았습니다.

- **같은 리뷰 코멘트가 다시 나오지 않는가.** 이 작업의 출발점이 반복되는 리뷰 코멘트였으니, 성공 판정도 거기서 해야 하는데요. 규칙으로 옮긴 항목이 리뷰에 다시 등장하면 규칙이 구멍을 놓치고 있다는 뜻입니다.
- **warning이 0 근처를 유지하는가.** 앞에서 적었듯 warning 수백 개는 0개와 같은데요. warning 수가 다시 쌓이기 시작하면 규칙이 죽어가고 있다는 신호라, 개수 자체를 지표로 봅니다. 쌓이는 규칙은 error로 올리거나, 오탐이면 규칙을 고치거나, 안 맞는 규칙이면 빼는 결정을 해야 합니다.
- **몇 주 뒤 같은 계측에서 이탈률이 유지되는가.** 20~38%였던 항목을 lint로 옮겼으니, 시간이 지난 뒤 다시 재서 0 근처면 성공이고 다시 벌어져 있으면 규칙이 실효가 없는 겁니다. 처음 계측에 쓴 방법을 그대로 다시 돌리면 되니 비용도 크지 않고요.

그리고 이 기준에는 전제가 하나 있는데요. **규칙이 실제로 강제되는 자리에서 돌아야 한다**는 것입니다. 에디터에서만 보이는 경고는 사람에 따라 무시되고, 로컬 검증은 건너뛸 수 있습니다. PR을 막는 게이트에서 도는 것까지가 규칙 도입의 마지막 단계이고, 솔직히 말하면 규칙을 만드는 일보다 이 배선이 뒤로 밀리기 쉬웠습니다. 만드는 쪽이 더 재미있거든요.

## 한계

lint가 지켜주는 건 문법 층위까지입니다. "이 추상화가 적절한가", "이 분기가 요구사항과 맞는가"는 여전히 사람이 봐야 하는데요. 무엇을 규칙으로 적을지 고르는 단계도 여전히 사람의 인지에 달려 있습니다. 20~38%가 어긋나 있던 것도 결국 아무도 그걸 규칙이라고 적지 않았기 때문이니까요.

그래서 이 작업의 결론은 "lint를 늘리자"가 아닙니다. **반복되는 리뷰 코멘트를 발견하면, 그걸 사람에게 다시 말하는 대신 적어서 기계에 넘길 수 있는지 먼저 묻는 것**인데요. 넘긴 만큼 리뷰는 문법이 아니라 설계에 쓸 수 있게 됩니다.
