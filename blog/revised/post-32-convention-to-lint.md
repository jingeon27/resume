# 문서에만 있는 규칙은 셋 중 하나가 어긋나 있었어요

<div class="note note-summary">
  <strong>이 글에서 다루는 것</strong>
  <p>컨벤션 문서가 잘 갖춰진 관리자 서비스 모노레포에서 같은 리뷰 코멘트가 반복되던 이유를 저장소 계측으로 확인한 과정이에요. lint로 옮긴 규칙은 위반 0건, 문서에만 있던 타입 접두사 규칙은 31%가 어긋나 있었어요. 어떤 규칙부터 lint로 옮겼는지, 심각도를 어떻게 정했는지, 밟은 함정과 현재 설정까지 적어요. 타입 접두사 수치는 이 글을 고치며 같은 스크립트로 다시 잰 값이에요.</p>
</div>

프로젝트에는 컨벤션 문서가 잘 갖춰져 있었어요. 아키텍처 경계, queryKey 관리, 배럴 작성, 파일 네이밍까지 영역별로 정리돼 있었고, 저도 그걸 쓰면서 지키고 있다고 생각했는데요.

같은 리뷰 코멘트가 계속 반복됐어요. 문서에 적혀 있는 내용인데도요. 문서를 더 자세히 쓰는 게 답인지 확신이 없어서, 먼저 저장소를 통째로 계측해 봤어요.

## 숫자가 보여준 것

규칙별로 위반 건수를 셌어요. 아래 표에서 타입 접두사 두 줄은 이 글을 고치며 다시 잰 값이에요. 규칙 도입 커밋 `675eb2ce0` 직전 트리에서 `.d.ts`만 제외한 TS/TSX 1,838개를 놓고 `interface X`와 `type X =` 선언을 정규식으로 셌어요. 나머지 줄은 처음 계측한 값 그대로예요.

| 규칙 | 문서화 | lint | 위반 |
| --- | --- | --- | --- |
| 레이어 경계 (FSD) | O | O | 0건 |
| queryKey는 options 함수에서만 | O | O | 0건 |
| 배럴에 `export *` 금지 | O | O | 0건 |
| `let` 대신 `const` | O | O (warning) | 16건 |
| interface `I` 접두사 | X | X | 639건 중 145건 (23%) |
| type `T` 접두사 | X | X | 661건 중 262건 (40%) |
| 컴포넌트 named export | X | X | 1,063건 중 340건 (32%) |

패턴이 선명했어요. **lint로 옮긴 규칙은 위반이 0건이고, 문서에만 있는 규칙은 어긋난 게 수백 건이었어요.** 타입 선언만 합쳐도 1,300건 중 407건(31%)이에요. 테스트, mock 파일을 빼고 세면 1,264건 중 388건으로 비율은 같아요. 유일하게 위반이 남은 lint 규칙은 warning이라 빌드를 세우지 않는 `let` 하나였고요.

이탈이 언제 쌓였는지도 시점별로 재봤는데요. 특정 시기의 문제가 아니었어요.

| 시점 (각 시점 develop의 마지막 커밋) | 파일 수 | interface 이탈 | type 이탈 |
| --- | --- | --- | --- |
| 합류 시점 트리 (마지막 커밋은 합류 두 달쯤 전) | 294 | 18/139 (13%) | 9/97 (9%) |
| 합류 6개월 뒤 | 586 | 69/283 (24%) | 23/217 (11%) |
| 합류 1년 뒤 | 1,066 | 104/495 (21%) | 101/372 (27%) |
| 규칙 도입 직전 | 1,838 | 145/639 (23%) | 262/661 (40%) |

코드가 294개 파일에서 1,838개로 여섯 배 넘게 커지는 사이 이탈이 함께 쌓였어요. 특히 type 접두사는 코드가 빠르게 늘던 후반부에 9%에서 40%까지 가속했는데요. 규칙 없이 코드만 늘면 이탈은 비율째 커진다는 뜻이에요.

미리 말해두면, 어긋난 코드의 상당수는 제가 쓴 것이었어요. 커밋 내역을 열어보면 규칙을 세우기 전의 저는 이 문서의 성실한 위반자였는데요. `any`를 쓰고, queryKey를 손으로 적고, 접두사 없는 타입을 만들었어요. 문서를 알고 있는 것과 매 순간 지키는 것은 다른 일이었고, 그건 의지의 문제라기보다 **사람의 주의력이 규칙 개수만큼 늘어나지 않는다**는 문제였어요.

규율이 느슨한 게 아니었어요. **적어놓고 기계에 넘긴 것만 지켜지고 있었던 건데요.** 문서는 규칙의 출발점이지 도착점이 아니었던 거예요.

그래서 문서를 더 자세히 쓰는 대신, 문법만 봐도 판정할 수 있는 규칙부터 lint로 옮기기로 했어요.

## 0건은 규율이 아니라 청소의 결과예요

표의 "위반 0건"은 사람들이 규칙을 잘 지켜서 나온 숫자가 아닌데요. **규칙을 켜기 전에 쌓여 있던 위반을 전부 걷어내고, 다시 생기지 않게 잠근 결과**예요.

lint 규칙은 위반이 남아 있는 채로는 켤 수 없어요. 켜는 순간 빌드가 깨지거나, warning 수백 개 속에서 새 경고가 묻히거나 둘 중 하나거든요. 그래서 규칙 하나를 올릴 때마다 청소가 먼저였어요.

- 앱에서 꺼져 있던 `no-explicit-any`를 켜면서 `any` **82곳**을 걷어냈어요 (50개 파일)
- 무효화 자리의 raw-string queryKey를 options 함수로 옮겼어요 (15개 파일)
- 저장소에 남아 있던 `let`을 걷어냈어요 (25개 파일)
- 타입 접두사 통일은 **한 커밋에 431개 파일**(+1,852 / -1,808)로 정리하고 같은 커밋에서 규칙을 켰어요. 이 글을 고칠 때의 트리에서 같은 스크립트로 다시 재면 남은 이탈은 interface 3건, type 1건이고, 선언 병합이나 제네릭 지역 별칭이라 그 줄에서만 규칙을 껐어요

여기에 더 근본적인 문제가 하나 있었는데요. 규칙이 없어서가 아니라, **모든 규칙을 warning으로 낮추는 설정이 전체에 걸려 있었어요.** 규칙은 존재했지만 아무것도 빌드를 세우지 못했고, 저를 포함해 아무도 경고 목록을 읽지 않았어요. 그 설정을 걷어내자 가려져 있던 미사용 import 같은 것들이 바로 드러났고요.

warning이 수백 개면 0개와 같아요. 규칙의 값어치는 개수가 아니라 **위반이 생긴 그 자리에서 보이는가**에 있었어요.

## 셀렉터로 끝나는 규칙부터

가장 싼 방법은 `no-restricted-syntax` 셀렉터인데요. queryKey 상수 선언 금지가 그래요.

```ts
{
  selector: "VariableDeclarator > Identifier[name=/_QUERY_KEYS?$/]",
  message: 'queryKey 상수를 따로 선언하지 않습니다 — 키 문자열은 options 함수 안에 인라인으로 둡니다.',
},
```

셀렉터로 안 되는 규칙은 파일을 따로 만들었어요. 라우트에서 조회 금지, 슬라이스 Public API 강제, 미사용 재수출 검출 같은 것들인데요. 이쪽은 파일 시스템을 읽고 import 그래프를 따라가는 작은 정적 분석기가 돼요.

## 처음에는 error가 하나뿐이었어요

규칙을 옮기면서 심각도 기준을 하나로 잡았는데요. **틀렸을 때 조용히 실패하는가.**

<div class="note note-decision">
  <strong>핵심 결정</strong>
  <p>심각도는 코드가 얼마나 지저분해지는가가 아니라 틀렸을 때 조용히 실패하는가로 정해요. 조용히 실패하는 규칙만 error로 올리고, 저장소 위반이 0건이 된 뒤에만 올려요.</p>
</div>

`let`을 쓰면 코드가 읽기 나빠질 뿐 동작은 해요. 그런데 무효화 자리에 queryKey를 손으로 적으면 이야기가 다른데요.

```ts
// options 의 키가 바뀌어도 이쪽은 조용히 남는다 — 아무것도 무효화하지 않는 코드
queryClient.invalidateQueries({ queryKey: ['fetchProgramList'] });
```

options의 키가 바뀌는 순간 이 무효화는 아무 일도 하지 않으면서 아무 에러도 내지 않아요. 화면에는 옛 데이터가 남고, 문자열이 맞는지 확인할 방법은 사람 눈밖에 없거든요. 그래서 처음에는 이 규칙 하나만 error였고 나머지는 전부 warning이었어요.

warning에서 error로 올릴 때는 저장소 위반이 0건인지 먼저 확인하는데요. 남아 있는 채로 올리면 그 순간부터 lint가 깨지고, 급한 PR을 막는 규칙은 결국 꺼져요. 규칙이 죽는 경로는 대개 이쪽이에요.

그 뒤로 error가 늘었어요. 이 글을 고치는 시점의 설정 기준으로 관리자 서비스에서 error인 자체 규칙은 `query/no-raw-key`, `query/no-passthrough-hook`, `query/no-enabled-in-options`, `form/no-key-reset`, `antd/no-deprecated-prop` 다섯이에요. 전부 저장소 위반 0건에서 켰고, 뒤의 넷은 새로 생기는 것만 막는 회귀 가드예요. `app/no-query`, `slice/structure`, `slice/public-api`, `boundary/explicit-variant`와 타입 접두사, `let`, queryKey 상수 셀렉터는 아직 warning이에요. 같은 시기 복지몰은 반대로 레이어, Public API, page 간 참조, raw key, `any`, non-null 단언을 전부 error로 잠갔고, "lint 규칙은 warn으로 켜지 않는다"가 원칙이 됐어요. 저장소마다 진도가 달라서 이 상태를 일반화하지는 않아요.

## 밟은 함정들

**규칙을 재선언하면 통째로 덮여요.** `no-restricted-syntax`를 하위 설정에서 다시 선언하면, 상위에서 걸어둔 셀렉터가 그 파일들에서만 전부 사라지는데요. 배럴에만 `export *` 금지를 얹으려다 그 파일들에서 `let` 검사와 queryKey 검사가 꺼져 있던 걸 나중에 발견했어요. 지금은 얹을 때 항상 기존 배열을 깔고 시작해요.

```ts
'no-restricted-syntax': ['warn', ...restrictedSyntax, noExportStar],
//                               ^^^^^^^^^^^^^^^^^^^ 빼먹으면 조용히 꺼진다
```

**`tsconfigRootDir`는 명시해야 해요.** typescript-eslint 8.46+는 이 값을 안 주면 호출 스택의 설정 파일 위치로 추론하는데요. 에디터의 ESLint 확장처럼 한 프로세스가 모노레포의 여러 패키지 설정을 로드하면 후보가 둘 이상이 되어 파싱 에러로 죽어요. CI는 멀쩡한데 에디터에서만 빨간 줄이 뜨는 상태였어요.

**빌드 산출물은 직접 막아야 해요.** ESLint의 기본 ignore는 `node_modules`뿐인데요. 게다가 설정을 `.map`으로 감싸며 모든 항목에 `files`를 붙이는 곳에서는 global ignores가 무력화되므로, 그쪽에서 ignore 항목을 다시 걸어야 했어요.

## 어긋난 건 규칙이 없던 자리였어요

계측에서 이탈률이 높았던 항목들을 다시 보면 공통점이 있는데요. 전부 **문서에 규칙 자체가 없던 것들**이에요. 타입 접두사, export 방식, 훅 파일 이름.

순서가 이렇게 정리돼요.

1. 암묵적 합의 → 문서에 적는다
2. 문서에 적힌 것 중 문법으로 판정 가능한 것 → lint로 옮긴다
3. 조용히 실패하는 것 → error로 올린다

계측 시점에는 2단계까지 와 있었고 1단계에서 빠진 게 남아 있었는데요. 이후 타입 접두사부터 실제로 옮겼어요. 앞에서 적은 431개 파일짜리 커밋이 그거예요. `interface`는 `I`, `type`은 `T`로 통일하는 정리와 lint 고정을 한 커밋에 담았는데요. 규칙 없이 정리만 하면 새 코드가 다시 갈라지고, 정리 없이 규칙만 켜면 그 순간부터 경고 수백 개가 쏟아져 아무도 읽지 않는 목록이 되기 때문이에요.

## 규칙 개수가 아니라 실제로 지켜지는지를 봐요

이 작업이 잘 됐는지를 무엇으로 판정할지도 정해 뒀는데요. 규칙을 몇 개 만들었는지는 기준이 될 수 없어요. 규칙은 늘리는 것 자체가 쉽고, 늘어난 규칙이 부담만 주고 있을 수도 있으니까요.

기준은 세 가지로 잡았어요.

- **같은 리뷰 코멘트가 다시 나오지 않는가.** 이 작업의 출발점이 반복되는 리뷰 코멘트였으니 성공 판정도 거기서 해야 하는데요. 규칙으로 옮긴 항목이 리뷰에 다시 등장하면 규칙이 구멍을 놓치고 있다는 뜻이에요.
- **warning이 0 근처를 유지하는가.** 앞에서 적었듯 warning 수백 개는 0개와 같은데요. warning 수가 다시 쌓이기 시작하면 규칙이 죽어가고 있다는 신호라 개수 자체를 지표로 봐요. 쌓이는 규칙은 error로 올리거나, 오탐이면 규칙을 고치거나, 안 맞는 규칙이면 빼는 결정을 해야 해요.
- **몇 주 뒤 같은 계측에서 이탈률이 유지되는가.** 31%였던 타입 접두사를 lint로 옮겼으니 시간이 지난 뒤 다시 재서 0 근처면 성공이고 다시 벌어져 있으면 규칙이 실효가 없는 거예요. 이 글을 고치며 실제로 다시 쟀고, 1,372건 중 4건이었어요.

그리고 이 기준에는 전제가 하나 있는데요. **규칙이 실제로 강제되는 자리에서 돌아야 한다**는 거예요. 에디터에서만 보이는 경고는 사람에 따라 무시되고, 로컬 검증은 건너뛸 수 있어요. PR을 막는 게이트에서 도는 것까지가 규칙 도입의 마지막 단계이고, 솔직히 말하면 규칙을 만드는 일보다 이 배선이 뒤로 밀리기 쉬웠어요. 만드는 쪽이 더 재미있거든요.

## 다음 작업에 남긴 기준

lint가 지켜주는 건 문법 층위까지예요. "이 추상화가 적절한가", "이 분기가 요구사항과 맞는가"는 여전히 사람이 봐야 하는데요. 무엇을 규칙으로 적을지 고르는 단계도 여전히 사람의 인지에 달려 있어요. 31%가 어긋나 있던 것도 결국 아무도 그걸 규칙이라고 적지 않았기 때문이니까요.

그래서 이 작업의 결론은 "lint를 늘리자"가 아니에요. **반복되는 리뷰 코멘트를 발견하면, 그걸 사람에게 다시 말하는 대신 적어서 기계에 넘길 수 있는지 먼저 묻는 것**인데요. 넘긴 만큼 리뷰는 문법이 아니라 설계에 쓸 수 있게 돼요.
