# Sentry에서 발견한 Bottom Sheet 드래그 크래시의 원인 경로를 제거하기까지

<div class="note note-summary">
  <strong>이 글에서 다루는 것</strong>
  <p>Sentry의 관련 오류 그룹 두 개에서 23건이 발생해 사용자 17명에게 영향을 준 Bottom Sheet 크래시를 라이브러리 소스까지 추적하고, 제품 코드 26개 사용처의 인터페이스를 유지한 채 원인 코드 경로를 제거한 과정을 다룹니다.</p>
</div>

운영 Sentry에 Bottom Sheet를 드래그하다 놓는 순간 화면이 멈추는 오류가 잡혔습니다. 확인 당시 같은 원인으로 판단한 오류 그룹 두 개에서 총 23건이 발생했고, 영향을 받은 사용자는 17명이었는데요. 개발 중에는 만나지 못했던 오류였지만, Sentry의 스택 추적에서 예외가 발생한 위치는 모두 `react-modal-sheet`의 드래그 종료 처리로 이어졌습니다.

처음에는 앱의 닫기 로직을 의심했습니다. 하지만 실제 원인은 앱 코드보다 한 단계 아래에 있었습니다. 드래그 종료 콜백이 post-render 단계에 예약된 사이 닫힘 상태 전환이 먼저 일어나면서, 이미 사라진 DOM을 라이브러리가 다시 읽고 있었습니다.

이번 작업의 목표는 예외 한 줄을 막는 데 그치지 않았습니다.

- 어떤 동작에서 사용자 흐름이 중단되는지 확인할 것
- 앱에서 막을 수 있는 오류인지 라이브러리 경계의 오류인지 구분할 것
- 26개 사용처의 동작을 유지하면서 원인이 된 코드 경로를 제거할 것
- 메이저 버전 변경으로 달라진 의미를 테스트로 고정할 것
- 배포 후에는 같은 Sentry 이슈의 재발 여부로 해결을 판정할 것

## Sentry에서 오류의 크기와 공통 경로를 먼저 확인했습니다

브라우저 콘솔에서 한 번 본 오류였다면 우선순위를 정하기 어려웠을 겁니다. Sentry에서는 같은 스택의 오류가 반복됐고, 단순 이벤트 수뿐 아니라 영향을 받은 사용자 수도 확인할 수 있었는데요. 간헐적으로 발생하는 제스처 오류가 개인 환경의 문제가 아니라 실제 사용자 흐름을 끊고 있다는 근거가 됐습니다.

스택 추적에서 예외가 발생한 위치는 애플리케이션의 Bottom Sheet 호출부가 아니라 `react-modal-sheet` 2.x의 `onDragEnd`였습니다. 해당 버전의 동작을 단순화하면 다음과 같습니다.

```ts
function onDragEnd() {
  const sheet = sheetRef.current!;
  const height = sheet.getBoundingClientRect().height;

  // 드래그 위치에 맞는 snap point 계산
}
```

`sheetRef.current`가 반드시 존재한다고 단언한 뒤 곧바로 DOM 크기를 읽고 있었습니다. 같은 파일의 `snapTo`에는 null 검사가 있었지만, 드래그 종료 경로에는 없었는데요. 이 콜백은 라이브러리 내부에 있어서 애플리케이션의 `onClose`에서 ref 상태를 확인하는 방식으로는 막을 수 없었습니다.

## 닫힘 상태 전환과 드래그 종료 콜백이 경합했습니다

시트 내용은 `AnimatePresence` 안에서 렌더링되고 있었습니다. 시트가 닫히면 컴포넌트가 언마운트되고 ref가 비워지는데요. 반면 Motion은 드래그 종료 콜백을 post-render 단계에 예약했습니다. 예약된 콜백이 실행되기 전에 다른 닫힘 상태 전환이 먼저 일어나면, 콜백은 이미 정리된 ref를 읽을 수 있었습니다.

```text
포인터 입력 종료
  → Motion이 onDragEnd를 post-render 단계에 예약
  → 그 사이 시트 닫힘 처리
  → 시트 DOM 언마운트, ref = null
  → 예약된 onDragEnd 실행
  → null에서 getBoundingClientRect 호출
  → 화면 크래시
```

항상 발생하지 않았던 이유도 이 실행 순서 때문이었습니다. 닫힘 상태 전환과 예약된 콜백의 타이밍이 겹치는 경우에만 문제가 드러났고, 콜백이 실행될 때 시트가 남아 있으면 정상으로 보였습니다.

`react-modal-sheet` 5.x에서는 드래그가 끝날 때 ref를 다시 읽지 않고 앞에서 측정해 둔 `sheetHeight`를 사용하고 있었습니다. null 검사만 추가한 것이 아니라 문제가 생기던 DOM 접근 경로 자체가 사라진 셈이었습니다.

선택지는 세 가지였습니다.

| 선택 | 장점 | 한계 |
| --- | --- | --- |
| 호출부에서 닫힘 지연 | 변경 범위가 작음 | 라이브러리 내부 콜백을 확실히 막지 못하고 타이밍 의존성이 남음 |
| 패키지에 null guard 패치 | 원인 지점을 직접 막음 | 설치 때마다 사설 패치를 유지해야 함 |
| 5.x로 업그레이드 | ref 접근 경로 자체가 사라짐 | `snapPoints`·`detent`·Motion API 마이그레이션 필요 |

공통 Root가 메이저 변경을 한곳에서 흡수할 수 있었기 때문에 세 번째 방법을 선택했습니다.

## 각 호출부를 고치지 않고 공통 경계에서 호환성을 유지했습니다

메이저 버전을 올리면 크래시는 사라지지만 `snapPoints`의 의미가 달라집니다.

| 구분 | 2.x | 5.x |
| --- | --- | --- |
| 프로젝트에서 사용한 0~1 비율의 기준 | 뷰포트 높이 | 시트 높이 |
| 순서 | 내림차순 | 오름차순 |
| 시작 인덱스 | `0`이 가장 높게 열린 위치 | `0`이 닫힘, 마지막이 완전히 열린 위치 |
| 비율 배열의 경계 | `0`·`1` 강제 없음 | `0`에서 시작해 `1`로 끝남 |

공통 `BottomSheet.Root`는 제품 코드 26곳에서 사용되고 있었습니다. 이 가운데 3곳이 뷰포트 기준 `snapPoints`를 직접 전달했는데요. 세 호출부를 새 좌표계에 직접 맞추면 라이브러리 규칙이 기능 코드로 새어 나옵니다. 그래서 Root의 외부 인터페이스는 유지하고 내부에서만 새 규칙으로 변환했습니다.

```ts
function toSheetSnapConfig(points: number[], initialSnap: number) {
  const [tallest] = points;
  const ascending = [...points]
    .reverse()
    .map((point) => point / tallest);

  const needsClosedSnap = ascending[0] !== 0;
  const snapPoints = needsClosedSnap ? [0, ...ascending] : ascending;
  const closedSnapOffset = needsClosedSnap ? 1 : 0;
  const height = Number((tallest * 100).toFixed(2));

  return {
    snapPoints,
    initialSnap: points.length - 1 - initialSnap + closedSnapOffset,
    contentHeight: `calc(${height}dvh - ${BOTTOM_SHEET_HEADER_HEIGHT}px)`,
  };
}
```

예를 들어 기존의 `[0.8, 0.5, 0.3, 0]`은 뷰포트의 80%·50%·30%·닫힘을 뜻합니다. 새 라이브러리에는 시트의 최대 높이인 `0.8`을 기준으로 나눠 `[0, 0.375, 0.625, 1]`을 전달했습니다. 호출부는 같은 값을 계속 사용하지만 라이브러리는 자신이 요구하는 좌표계로 값을 받습니다.

시트의 실제 높이도 변환 계층에서 함께 계산했습니다. 5.x에서는 `detent`가 컨테이너의 `height`를 나중에 결정하기 때문에 컨테이너 스타일만으로는 기존 높이를 보존할 수 없었는데요. 컨테이너 높이를 콘텐츠가 결정하도록 하는 `content` 모드를 사용하고 `Sheet.Content`에 계산된 높이를 전달했습니다. 헤더 높이 40px은 계산과 마크업이 어긋나지 않도록 하나의 상수로 묶었습니다.

명시적 `snapPoints`가 없는 나머지 사용처도 이름만 보고 기계적으로 옮기지 않았습니다. 기존 `content-height`는 5.x의 `content`로, 기존 `full-height`는 이전 높이 동작과 가까운 `default`로 매핑했습니다. 5.x에 `full`이라는 이름이 있더라도 이름보다 실제 렌더링 결과를 보존하는 쪽을 택했습니다.

## 업그레이드의 주변 변화도 함께 정리했습니다

문제가 된 함수만 보고 의존성을 올리면 빌드는 되더라도 다른 동작이 달라질 수 있었습니다. 실제로 5.x에서는 다음 API도 함께 바뀌었습니다.

- `Sheet`가 기본 export에서 named export로 변경됐습니다.
- `Sheet.Scroller`가 사라지고 `Sheet.Content`가 스크롤 영역을 맡았습니다.
- `detent` 값과 높이 계산 방식이 달라졌습니다.
- peer dependency가 `framer-motion`에서 `motion`으로 바뀌었습니다.

특히 `motion@11`이 사용하는 런타임과 애플리케이션이 직접 import하던 `framer-motion`이 함께 남으면 애니메이션 런타임이 두 벌 들어갈 수 있었는데요. 직접 import하던 30곳을 `motion/react`로 옮겨 실행 경로를 하나로 맞췄습니다. 타입 진입점에 필요한 기존 패키지는 의존성에 남겼지만, 런타임 import는 한쪽으로 통일했습니다.

후속 diff 검토에서는 세 가지를 더 정리했습니다. `snapPoints`가 있는 3개 시트에 남아 있던 `detent` prop은 실제 동작에 영향을 주지 않아 제거했고, 부동소수점 계산이 `55.00000000000001dvh` 같은 CSS를 만들지 않도록 소수 둘째 자리에서 정리했습니다. 같은 판단이 다음 Bottom Sheet 작업에서도 유지되도록 사용 규칙 문서도 현재 API에 맞췄습니다.

## 변환 규칙은 순수 함수 테스트로 고정했습니다

드래그 크래시 자체는 의존성 내부의 생명주기 문제라 단위 테스트로 그대로 재현하기 어렵습니다. 대신 업그레이드하면서 애플리케이션이 새로 책임지게 된 변환 규칙은 순수 함수로 분리해 테스트했습니다.

```ts
it('두 번째로 높은 위치의 의미를 유지한다', () => {
  const { snapPoints, initialSnap } = toSheetSnapConfig(
    [0.8, 0.5, 0.3, 0],
    1,
  );

  expect(snapPoints[initialSnap] * 0.8).toBe(0.5);
});

it('닫힌 위치가 없으면 0을 추가하고 인덱스도 옮긴다', () => {
  const result = toSheetSnapConfig([0.8], 0);

  expect(result.snapPoints).toEqual([0, 1]);
  expect(result.snapPoints[result.initialSnap]).toBe(1);
});
```

배열 순서, 기준 높이, 초기 인덱스, 닫힌 위치 보정, 콘텐츠 높이를 각각 검증했습니다. 테스트를 작성한 뒤 인덱스 계산을 일부러 틀리게 바꿔 실패하는지도 확인했는데요. 구현과 똑같은 계산을 반복해 항상 성공하는 테스트가 아니라, 사용자가 보게 될 위치의 의미를 검증하는 테스트인지 확인하기 위해서였습니다.

## 코드 경로 제거와 운영상 해결은 구분했습니다

이번 변경으로 null ref를 읽던 2.x의 코드 경로는 제거됐고, 기존 26개 사용처의 공개 인터페이스와 명시적 스냅 3개의 위치 의미는 유지했습니다. 다만 라이브러리를 올리고 테스트가 성공했다고 해서 운영 크래시가 사라졌다고 바로 단정할 수는 없는데요.

배포 뒤에는 다음을 확인해야 합니다.

- 기존 Sentry 오류 그룹 두 개가 새 release에서 다시 발생하는지
- Bottom Sheet 관련 새로운 오류 그룹이 생기지 않는지
- 모바일에서 드래그·스크롤·닫기 제스처가 기존과 같은지
- `snapPoints`별 초기 위치와 최대 높이가 유지되는지

따라서 이 작업의 완료 조건은 “5.x로 업그레이드했다”가 아니라, **새 release에서 기존 크래시가 재발하지 않고 주요 시트의 동작이 유지되는 것**으로 잡았습니다. 현재 글에 적은 23건·17명은 수정 전 Sentry에서 확인한 수치이며, 수정 후 감소율은 충분한 운영 기간이 쌓인 뒤 별도로 판단할 값입니다.

  <p>단위 테스트는 좌표 변환의 회귀를 막지만 브라우저의 실제 드래그 타이밍까지 검증하지는 않습니다. 제스처 회귀는 실제 모바일 환경 확인과 Sentry의 release별 재발 여부를 함께 봐야 합니다.</p>
</div>

## 이번 작업에서 남긴 기준

이번 문제를 해결하면서 다음 기준을 남겼습니다.

1. 간헐적인 UI 오류는 재현 여부만으로 우선순위를 정하지 않고, Sentry의 발생 수와 영향 사용자 수를 함께 봅니다.
2. 스택이 의존성 내부에서 끝나면 앱의 우회부터 만들기보다 해당 버전의 소스와 이후 변경을 먼저 확인합니다.
3. 메이저 업그레이드에서 의미가 달라진 값은 호출부마다 고치지 않고 공통 경계의 어댑터에서 변환합니다.
4. 라이브러리 내부 오류를 직접 테스트하기 어렵다면, 업그레이드로 애플리케이션이 새로 책임지는 규칙을 테스트합니다.
5. 해결 여부는 코드 변경이 아니라 새 release의 동일 오류 재발 여부로 판정합니다.

Sentry가 없었다면 이 문제는 “가끔 시트가 이상하다”는 제보로 남았을 가능성이 큽니다. 관측 도구가 오류를 대신 해결해 주는 것은 아니지만, 누가 얼마나 겪었는지와 어느 경계부터 읽어야 하는지를 알려줬는데요. 이번에는 그 신호를 라이브러리 소스, 생명주기, 호환 계층, 테스트까지 연결하면서 실제로 닫을 수 있는 문제로 바꿨습니다.
