8월 말, 에이전트가 성공했다고 보고한 E2E를 열어 봤어요. 배너 등록 드로어에서 '업로드 중...' 문구가 사라지길 기다리는 줄이 있었는데, 그 문구는 저장소 어디에도 없었어요. 없는 요소는 바로 '사라진' 것으로 판정되니 이미지가 폼에 실리기 전에 다음 단계로 넘어가도 테스트는 성공으로 끝났어요. 성공했다는 말을 그대로 믿었다면 그냥 지나갔을 일이에요.

저장소에 Claude 설정 파일을 처음 넣은 건 2월이었는데(첫 커밋 기준) 그때는 설정만 있고 흐름은 없었어요. push 명령에 리뷰어를 붙인 건 4월이고(복지몰 4월 8일, 관리자 서비스 4월 20일), 티켓 브랜치 스킬이 plan을 제시하고 멈추는 흐름은 관리자 서비스가 4월 말, 복지몰이 5월 중순에 세웠어요. 그때는 코드가 나오는 속도만 빨라졌어요. 폼을 어디에 두는지, Query Options를 어떻게 만드는지 같은 기준이 코드와 제 머릿속에 흩어져 있어서 결과물은 제가 처음부터 끝까지 읽고 고쳤어요. 모델이 틀리는 문제보다 저장소에 제 기준이 적혀 있지 않은 문제가 더 컸어요.

지금은 모든 코드를 같은 방식으로 읽지 않아요. 작업할 때마다 불편했던 부분을 하나씩 고친 결과라서 그 순서대로 적어 볼게요.

## 티켓부터 AI에 넘기지는 않았어요

티켓을 받으면 내용을 읽고 코드 수준에서 해결할 수 있는 문제인지, 기존 구현보다 나은 방법이 있는지 먼저 생각해요. 티켓 이전의 요구사항 논의에 참여한 경우도 있지만, 모든 티켓의 스펙을 제가 정하거나 전부 확인한 것은 아니에요. plan을 검토하면서 모호한 요구사항이나 백엔드 작업이 필요한 부분을 발견하면 관련 담당자에게 확인해요.

복지몰은 디자이너의 시안을 바탕으로 작업하고, 그 외 제품은 주로 와이어프레임을 분석해 구현해요. 시안이 있는 작업에는 Figma MCP를 활용해요. 와이어프레임 기반 작업은 에이전트 구현과 테스트를 마친 뒤 자체검증에서 UI를 검토하기도 해요. 글로벌 서비스의 파일 업로드 화면에서는 OTP 입력값을 어디까지 유지할지, 업로드 실패 시 무엇을 보여줄지를 와이어프레임 밖에서 정해야 했어요.

그다음 에이전트가 관련 코드와 기존 패턴을 조사해요. 저는 세션에서 작업을 세 종류로 나눠 지시했어요. 기존 패턴이 명확해 바로 PR까지 가는 작업, 구현 전에 요구사항 확인이 필요한 작업, 구현 뒤 사람이 화면이나 데이터를 봐야 하는 작업이에요. 아직 스킬로 옮기지 않은 세션 관행이고, 바로 PR까지 가는 작업도 plan 승인은 거쳐요.

## 코드를 보기 전에 plan부터 봤어요

예전에는 구현이 끝난 뒤 diff에서 방향이 틀린 것을 발견했고, 그 시점에는 코드와 테스트를 같이 버려야 했어요. 그래서 티켓으로 브랜치를 만드는 스킬이 plan을 제시한 뒤 멈추게 했어요. auto mode여도 제 입력을 기다리고, 승인 전에는 구현하지 않아요.

스킬 템플릿에는 티켓 요약, 영향 범위, 작업 순서, 검토 필요 항목 넷만 적게 했어요. 저는 그중 전제와 검토 필요 항목을 봐요. 티켓을 어떤 동작으로 이해했는지가 틀리면 파일 목록이 정확해도 소용이 없거든요. 상태와 데이터를 누가 소유하는지, 무엇이 성공하면 끝낼지는 템플릿 항목이 아니라 제가 승인하면서 되묻는 것들이에요. 빠진 상태나 잘못 이해한 API가 보이면 다시 조사하게 했고, 수정된 plan을 본 뒤 구현을 시작했어요. 이 단계에는 코드가 없어서 방향을 바꿔도 버리는 건 plan 문서뿐이에요.

## 같은 지적을 두 번 하지 않게 만들었어요

초기에는 작업마다 주의사항을 프롬프트에 덧붙였어요. 내용이 길어지면서 폼, Query, FSD, 디자인 시스템처럼 작업 종류별 skill로 나눴고(에러 처리는 관리자 서비스의 정책 문서로, 디자인 시스템 skill은 복지몰에만 있어요), 새 반례가 나오면 현재 파일과 함께 해당 skill도 고쳤어요. 9월 초 기준 관리자 서비스에 33개, 복지몰에 30개가 있고 규칙의 정본은 `AGENTS.md`예요.

코드만 보고 판단할 수 있는 기준은 lint로 옮겼어요. 레이어를 거꾸로 참조하는 import, 다른 슬라이스 내부로 들어가는 import, raw query key 같은 항목이에요. 다만 두 저장소의 진도가 달라요. 복지몰은 Public API 규칙을 271건에서 44건, 17건, 0건까지 걷어낸 뒤 error로 잠갔고, 지금은 "lint 규칙은 warn으로 켜지 않는다"가 원칙이에요. warning만 있으면 eslint가 exit 0으로 끝나 아무것도 막지 못하거든요. 이 글의 9월 초 점검 시점에는 관리자 서비스 세 앱의 레이어·Public API 규칙이 warning이었고, raw query key 규칙은 error였어요. 저장소별 적용 시점이 달라 이 상태를 현재 설정으로 일반화하지는 않아요.

맥락이 필요한 것까지 lint에 넣지는 않았어요. 어떤 컴포넌트가 한 화면의 조각인지 도메인 UI인지는 사용처를 봐야 해서 문서와 리뷰에 남겼어요.

[Compound Engineering](https://every.to/guides/compound-engineering) 방식을 참고하며 작업에서 얻은 판단을 다음 작업의 규칙으로 남겼어요. 처음부터 지금의 흐름을 한 번에 만든 것은 아니에요. 반복해서 고치는 부분을 스킬에 보강했고, 모델 성능도 좋아지면서 제 코드 스타일에 맞는 결과가 늘었어요. 그 과정에서 제가 직접 검토하는 범위를 조금씩 조정했어요.

## 실제 화면부터 봤어요

Figma 작업은 에이전트가 `claude-in-chrome` MCP나 Chrome CDP 스크립트로 dev 화면을 열고 스크린샷을 찍게 했어요. 간격, 글꼴, 색상, 아이콘, 반응형 배치와 열림·오류 상태가 시안과 다르면 차이 목록을 만들고, 고친 뒤 같은 viewport와 상태에서 다시 찍었어요. 이미지 유사도 점수는 쓰지 않았고, 남은 차이 목록이 비면 끝냈어요.

기능도 화면과 E2E는 dev 서버로 확인했어요. 통합 테스트의 Mock은 서버 제약을 그대로 검사해 거절하도록 만들었어요. 무엇이든 받아 주는 목이 400을 숨긴 일이 있었거든요. dev 서버에서 다른 제약이 나오면 실서버 테스트를 새로 만드는 대신 스키마와 Mock, 기존 테스트를 서버에 맞춰 고쳤어요.

## 테스트가 성공했다는 말도 그대로 믿을 수 없었어요

테스트는 7월부터 들어왔어요. 관리자 서비스의 첫 테스트 커밋이 7월 20일이었고, 새 테스트가 7월 31개, 8월 71개 추가됐어요(커밋 기준). 기본은 화면 통합 테스트(렌더 + MSW)이고, 도메인별 MSW 핸들러는 관리자 서비스 27개, 복지몰 14개예요(9월 첫째 주 기준이고, 복지몰 쪽은 vitest가 아니라 dev·E2E 목킹에 써요). 실서버에 붙는 `*.live.test.ts`는 마지막 수단이에요.

처음에는 AI가 만든 테스트도 전부 읽었어요. 글머리의 '업로드 중...' E2E는 8월 28일에 이렇게 고쳤어요.

```ts
// before: 저장소에 없는 문구라 대기가 즉시 끝난다
await expect(drawer.getByText('업로드 중...')).toBeHidden();

// after: 진행 중인 업로드 항목이 0개인지 본다
await expect(drawer.locator('.ant-upload-list-item-uploading')).toHaveCount(0);
```

이 대기문만으로 업로드 성공을 판단할 수는 없어요. 업로드가 시작되지 않았거나 실패해도 진행 중인 항목은 0개일 수 있으니까요. 이 코드는 잘못된 대기 대상을 바꾼 예시이고, 완료 여부는 이번 실행에서 올린 파일과 저장 결과까지 확인해야 해요.

그 뒤 테스트는 입력과 행동, 기대 결과가 본문에 보이도록 규칙을 정했어요. 동작을 유지하는 리팩터링은 기존 계약을 테스트로 먼저 고정하고, 제품 코드를 일부러 틀리게 바꿔 그 테스트만 실패하는지 보는 뮤테이션 체크를 `AGENTS.md` 원칙으로 적었어요. 이 패턴이 자리 잡은 뒤부터는 테스트의 모든 줄보다 plan의 성공 조건과 실행 결과를 중심으로 봐요.

한 앱에서 끝나지 않는 기능은 두 서비스를 횡단하는 E2E로 봤어요(9월 1일). 파트너용 관리자에서 프로그램을 등록해 검수 요청을 만들고 내부 CMS에서 반려하는 흐름이라 한쪽 앱의 렌더 테스트로는 덮이지 않았어요. 별도 Playwright 설정에서 두 dev 서버(3000·3002)를 함께 띄우고 실제 dev API를 호출했고, 쿠키 도메인이 같은 localhost라 파트너용 세션은 별도 브라우저 context에 뒀어요. 반려 성공은 화면에 원래 있던 '반려' 글자가 아니라 테스트에서 입력한 반려 사유가 상세에 다시 나타나는지로 확인했어요. 드로어에 반려 버튼이 있어서 글자만 찾으면 상태가 안 바뀌어도 통과하거든요.

## 병렬로 맡길 일과 함께 편집할 일을 나눴어요

독립적인 티켓은 Orca에서 여러 세션으로 진행해요. Orca 자체를 제가 만든 것은 아니고, 세션별 작업 범위와 검토 흐름을 정해 사용하는 방식이에요. 리팩터링처럼 코드를 계속 보며 결정해야 하는 작업은 VS Code에서 제가 직접 편집하고 단일 에이전트 세션과 변경 맥락을 공유해요. 작업 수보다 판단을 얼마나 연속해서 함께해야 하는지가 구분 기준이에요.

plan에서는 영향 범위와 바꾸지 않을 동작, 예외 조건, 검토할 부분을 먼저 맞춰요. 구현 후 리뷰는 그때 정한 기준을 실제 diff가 지키는지 확인하는 단계예요. 에이전트의 지적도 코드 근거와 재현 조건을 확인한 뒤 반영해요. 도구의 리뷰를 동료와 설계에 합의한 경험으로 보지는 않아요.

## 여러 세션이 CPU를 같이 잡아먹기 시작했어요

서로 겹치지 않는 티켓은 별도 Git worktree에서 진행했어요. 한 세션이 브랜치나 의존성을 건드려도 다른 세션에 영향을 주지 않게 하려는 목적이었는데, 세션을 여러 개 돌리자 이번에는 검증이 병목이 됐어요.

각 세션이 전체 lint와 테스트를 동시에 돌리면 turbo가 전 패키지를 콜드로 실행해 CPU를 통째로 먹었어요. 여러 검사가 겹친 실행에서는 exit 143으로 종료되기도 했어요. 이 종료 코드만으로 CPU 경합이 직접 원인이라고 단정할 수는 없지만, 검사가 끝나지 않아 코드 문제인지 판단할 결과도 얻지 못했어요. 처음 push 명령(4월)은 전 패키지 `pnpm run lint` 하나가 게이트였는데요. 8월 말에 push 직전 검증을 변경 파일의 eslint, 그 파일이 속한 패키지의 타입체크, `vitest --changed`로 좁히면서 관련 테스트도 같이 넣었고, 관리자 서비스 CI의 PR 게이트에는 9월 초에 Vitest를 붙였어요. 복지몰의 PR 게이트는 lint·타입 검사·Knip까지이고, 실서버 테스트와 브라우저 E2E는 별도로 실행해요.

구현이 끝나면 변경 내용과 실행한 검증을 보고받아요. 이 보고는 plan 문구가 아니라 처음 확인한 요구사항과 대조해요. plan도 에이전트가 만든 결과물이라 plan대로 했다는 것만으로 완료 처리하지 않았어요.

현재 흐름은 테스트 작성 → 구현 → 에이전트 리뷰 → 변경 영향에 맞춘 로컬 검증 → push 후 CI 전체 검증이에요. 리뷰나 로컬 검증이 실패하면 원인에 따라 plan·구현·테스트 수정으로 돌아가요. CI가 실패한 작업도 완료로 처리하지 않아요. 캐시를 쓰려고 메인 worktree에 임시로 합치는 대신 각 작업의 worktree를 유지해요.

여기서 변경 영향 검증이 모든 도구에 파일 목록만 넘긴다는 뜻은 아니에요. 복지몰은 ESLint를 변경 파일에, Vitest를 영향 범위에 적용하지만 타입 검사와 Knip은 전체 앱·참조 그래프를 봐요. 관리자 서비스는 영향받는 패키지의 타입 검사와 관련 테스트를 실행하고, 공용 API가 바뀌면 소비하는 패키지도 포함해요. 전체 lint·타입 검사·일반 테스트는 CI에서 확인하되, live와 브라우저 검증은 별도 실행 경로와 조건을 구분해요.

## 리뷰 지적과 검증 실패를 구분해서 처리했어요

push를 지시하면 별도 리뷰어가 `origin/develop...HEAD` diff를 읽고 항목마다 Critical·Warning·Nit과 확신도를 붙여 전부 보고해요. 리뷰어는 eslint·타입체크·테스트보다 먼저 돌아요. 리뷰가 더 싸서 Critical로 멈출 변경이면 비싼 검증을 아예 돌리지 않게 하려는 순서예요.

Critical 수정까지 에이전트에 맡기는 작업도 있지만, 수정되지 않은 Critical을 남긴 채 push하는 것과는 구분해요. 현재 확인한 두 저장소의 push 스킬에는 Critical이 있으면 제 확인을 받도록 적혀 있어요. Warning·Nit은 보고만 하고 그 자체로 멈추지는 않아요. 리뷰와 별개로 lint·타입 검사·테스트가 실패해도 다음 단계로 진행하지 않아요.

반복되는 오탐은 리뷰어 정의에 예외로 적었어요. 두 앱의 `src/app/api` route가 구조는 비슷하고 엔드포인트·서비스명만 달라서 공통 팩토리로 뽑으라는 지적이 반복됐는데요. 각 앱의 백엔드와 응답 타입에 묶여 있어 분리가 맞다고 보고, 공통 핸들러 팩토리로 추출하라고 권고하지 않는다는 문장을 남겼어요.

## 마지막에는 합쳐진 코드를 읽어요

Stage 배포 전에는 develop에 합쳐진 diff 전체를 다시 봐요. 이 검토가 들어가는 건 쌓인 PR을 `/stage-deploy`로 따로 배포 PR로 만드는 경로예요. `/full-deploy`는 PR 머지부터 stage 배포 PR 머지까지 확인 없이 이어져서 이 검토가 들어갈 자리가 없어요. PR 하나만 볼 때는 자연스러웠던 코드도 함께 놓으면 중복된 추상화나 어긋난 이름, 갈라진 FSD 경계가 보여서 전체 규칙에 맞게 다시 리팩터링했어요.

배포 뒤에도 마음에 걸리는 패턴이 있으면 그 파일만 고치지 않고 프로젝트 전체에서 찾아 skill이나 lint, 공용 구현을 바꿨어요. 복지몰에서 `entities`를 없애고 page 간 직접 참조를 막는 규칙(정리 전 62건에서 0건)까지 넣은 작업도 여기서 시작됐는데요. 이 작업의 브랜치 검토와 develop 반영은 구분해서 봐야 해요. 당시 초안에는 미머지 상태로 기록했지만 복지몰의 FSD 개편은 9월 9일 develop에 반영됐어요. 두 저장소의 구조와 규칙이 모두 같아졌다는 뜻은 아니에요. 과정은 [FSD 레이어를 다시 나눈 글](https://jingeon27.tistory.com/23)에 적었어요.

  <strong>최종 결정</strong>
  <p>검토 시점은 방향을 바꾸는 비용이 가장 싼 곳에 뒀어요. 요구사항과 구조는 코드가 없는 plan 단계에서, 개별 동작은 dev 화면과 테스트에서, 여러 작업의 일관성은 Stage 배포 전 합쳐진 diff에서 봐요. 기계가 판단할 수 있는 규칙은 lint로, 맥락이 필요한 판단은 문서와 리뷰에 남겼어요.</p>
