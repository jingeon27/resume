# AI가 코드를 잘 짜기 시작했는데 제가 덜 바빠지지는 않았어요

AI 에이전트를 본격적으로 쓰기 시작한 것은 4월이었어요. 처음에는 코드를 만드는 속도만 빨라졌어요. 결과물은 제가 다시 처음부터 끝까지 읽었고, 프로젝트에서 쓰는 방식과 다르면 직접 고쳤어요. 생성은 빠른데 제가 뒤에서 다시 손보니 전체 작업 시간은 생각만큼 줄지 않았어요.

당시에는 지금 같은 테스트 체계도 없었어요. 폼을 어디에 두는지, Query Options를 어떻게 만드는지, 공용 UI를 어디까지 올리는지 같은 기준도 코드와 제 머릿속에 흩어져 있었어요. 모델이 틀리는 문제도 있었지만 저장소에 제 기준이 제대로 적혀 있지 않은 문제도 컸어요.

지금은 모든 코드를 같은 방식으로 읽지 않아요. 티켓을 보고 요구사항을 맞추는 일, 구현 전에 plan을 확인하는 일, 실제 화면과 테스트로 완료 여부를 확인하는 일, Stage 배포 전에 합쳐진 diff를 읽는 일로 검토 시점을 나눴어요. 여기까지 한 번에 설계한 것은 아니고, 작업할 때마다 불편했던 부분을 하나씩 고친 결과예요.

## 티켓부터 AI에 넘기지는 않았어요

Jira 티켓과 Figma는 제가 먼저 봐요. 요구사항이 모호하면 기획자나 디자이너, 백엔드 개발자와 얘기한 뒤 작업을 시작했어요. 사용자가 마지막에 무엇을 완료해야 하는지, 모바일과 오류 상태가 빠지지는 않았는지, API 준비가 먼저 필요한지를 확인했어요. 시안보다 나은 UX가 보이면 코드에서 임의로 바꾸지 않고 먼저 의견을 맞췄어요.

글로벌 파일 업로드 화면을 만들 때도 와이어프레임만 그대로 옮기지는 않았어요. OTP 과정에서 입력값을 어디까지 유지할지, 업로드가 실패하면 무엇을 보여줄지, 완료 뒤 이전 화면으로 가는 버튼은 어떻게 동작할지, 모바일 규격은 어떻게 적용할지를 추가로 정했어요. 화면을 그리는 것보다 먼저 끝나야 했던 일이에요.

그다음 에이전트가 관련 코드와 기존 패턴을 조사해요. 이때 티켓도 세 종류로 나눠요. 기존 패턴이 명확해 바로 PR까지 만들 수 있는 작업, 구현 전에 요구사항 확인이 필요한 작업, 구현이 끝난 뒤 사람이 화면이나 데이터를 봐야 하는 작업이에요. 분류와 검토 지점은 에이전트가 먼저 제안하고, 저는 빠진 조건과 판단이 맞는지 봐요.

## 코드를 보기 전에 plan부터 봤어요

예전에는 구현이 끝난 뒤 diff에서 방향이 틀린 것을 발견했어요. 그 시점에는 코드와 테스트를 같이 버려야 했어요. 그래서 에이전트가 plan을 만든 뒤 멈추게 했어요. 제가 승인하기 전에는 구현하지 않아요.

plan에는 바꿀 파일만 적지 않아요. 티켓을 어떤 동작으로 이해했는지, 상태와 데이터는 누가 소유하는지, 어떤 순서로 고칠지, 무엇이 성공하면 끝낼지를 적어요. 기존 패턴으로 정할 수 없는 부분도 표시하게 했어요. 계획이 길어도 사용자 행동을 잘못 이해하면 소용이 없어서 파일 목록보다 전제를 더 오래 봤어요.

승인도 한 번에 끝나지 않을 때가 많았어요. 빠진 상태나 잘못 이해한 API가 보이면 다시 조사하게 했고, 수정된 plan을 보고 나서 구현을 시작했어요. 코드를 다 만든 뒤 고치는 것보다 이 단계에서 방향을 바꾸는 편이 훨씬 쌌어요.

## 같은 지적을 두 번 하지 않게 만들었어요

초기에는 작업을 시킬 때마다 주의사항을 프롬프트에 덧붙였어요. 내용이 길어지면서 폼, Query, FSD, 에러 처리, 디자인 시스템처럼 작업 종류별 skill로 나눴어요. 새 반례가 나오면 현재 파일만 고치는 대신 해당 skill도 함께 수정했어요.

코드만 보고 판단할 수 있는 기준은 lint로 옮겼어요. FSD 레이어를 거꾸로 참조하는 import, 다른 슬라이스 내부로 바로 들어가는 import, page 간 직접 참조, raw query key 같은 항목이에요. 기존 코드에 위반이 많으면 warning으로 시작했고, 모두 고친 다음 error로 올렸어요.

반대로 맥락이 필요한 것까지 lint에 넣지는 않았어요. 어떤 컴포넌트가 한 화면의 조각인지 도메인 UI인지는 사용처를 봐야 해요. 이런 판단은 문서와 리뷰에 남겼어요. 기계가 잘 판단하는 부분과 사람이 계속 봐야 하는 부분을 나누는 데 시간이 꽤 걸렸어요.

나중에 [Compound Engineering](https://every.to/guides/compound-engineering)이라는 표현을 알게 됐는데요. 한 작업에서 얻은 판단을 다음 작업의 시작점으로 돌려보낸다는 점에서 제가 만든 방식과 비슷했어요. 방법론을 먼저 가져와 적용한 것은 아니었어요. 같은 리뷰를 두 번 하고 싶지 않아 쌓아 온 규칙에 가까웠어요.

## 테스트가 성공했다는 말도 그대로 믿을 수 없었어요

Figma 작업은 Playwright MCP로 실제 개발 화면을 열고 스크린샷을 찍게 했어요. 간격이나 글꼴, 색상, 아이콘, 반응형 배치와 열림·오류 상태가 시안과 다르면 다시 수정했어요. 여기서 일치율 100%는 이미지 유사도 점수가 아니에요. 확인하기로 한 viewport와 상태에서 남은 차이가 없어야 한다는 뜻이에요.

기능 검증은 실제 dev 서버를 우선했어요. 실제 API와 데이터로 확인하기 어려운 오류 응답이나 로그인 상태만 Mock으로 만들었어요. Mock이 받아 준 요청을 실제 서버도 받아 줄 것이라고 가정하지 않았어요. dev 서버에서 다른 제약이 나오면 스키마와 Mock, 테스트를 다시 맞췄어요.

테스트는 7월부터 본격적으로 도입했어요. 처음에는 AI가 만든 테스트도 전부 읽었어요. 실제로 화면에 없는 “업로드 중...” 문구를 기다리게 만든 E2E가 있었는데요. 없는 요소를 찾으니 대기 코드가 즉시 끝났고 테스트는 성공했어요. 이후 실제 업로드 항목의 상태가 사라지는지를 보도록 고쳤어요. 테스트가 성공했다는 결과만 봤다면 발견하기 어려운 문제였어요.

그 뒤 테스트는 입력과 행동, 기대 결과가 본문에 보이도록 작성 규칙을 정했어요. 중요한 테스트는 제품 코드를 일부러 틀리게 바꿔 정말 실패하는지도 확인했어요. 이 패턴이 자리 잡은 뒤부터는 생성된 테스트의 모든 줄보다 plan의 성공 조건과 실행 결과를 중심으로 보게 됐어요.

한 앱에서 끝나지 않는 기능은 서비스 전체 흐름을 테스트했어요. 파트너용 관리자에서 프로그램을 등록해 검수 요청을 만들고, 내부 CMS에서 그 요청을 찾아 반려하는 작업이 있었어요. 한쪽 앱의 컴포넌트 테스트만으로는 실제 상태 변화를 확인할 수 없었어요.

Playwright가 두 dev 서버를 함께 띄우고 실제 dev API를 호출하도록 별도 설정을 만들었어요. 두 앱이 같은 localhost를 사용해서 로그인 쿠키가 섞이지 않도록 브라우저 context도 나눴어요. 마지막에는 화면에 원래 있던 “반려”라는 글자가 아니라 테스트에서 입력한 반려 사유가 상세에 다시 나타나는지 확인했어요. 두 서비스를 오가는 작업은 이 지점까지 와야 끝난 것으로 봤어요.

## 여러 세션이 CPU를 같이 잡아먹기 시작했어요

작업은 별도 Git worktree에서 진행했어요. 한 세션이 브랜치를 바꾸거나 의존성을 건드려도 다른 세션에 영향을 주지 않게 하려는 목적이었어요. 세션을 여러 개 돌리기 시작하자 이번에는 검증이 병목이 됐어요.

각 세션이 저장소 전체 lint와 typecheck를 동시에 실행하면 CPU 사용량이 치솟았어요. 개발 서버까지 느려지고 다른 작업의 검증이 종료되기도 했어요. 그래서 push 직전에 변경 파일의 ESLint, 변경이 속한 패키지의 typecheck, 관련 테스트만 한 번 실행하도록 바꿨어요. 테스트를 도입하기 전에는 정적 검사와 직접 리뷰를 사용했고, 7월 이후 관련 테스트가 이 단계에 들어왔어요.

구현이 끝나면 변경 내용과 실행한 검증을 보고받아요. 저는 이 보고를 plan 문구가 아니라 처음 확인한 요구사항과 대조해요. plan도 에이전트가 만든 결과물이기 때문에 plan대로 했다는 것만으로 완료 처리하지 않았어요.

push를 지시하면 별도 리뷰어가 기준 브랜치와의 diff를 읽어요. Critical은 같은 흐름에서 자동으로 수정하고 검증을 다시 실행한 뒤 push해요. Warning은 실제 영향과 요구사항을 보고 반영 여부를 정했어요. 반복되는 오탐은 다음 리뷰에서도 같은 말을 하지 않도록 규칙에 예외를 추가했어요.

## 마지막에는 합쳐진 코드를 읽어요

개별 작업의 모든 줄을 읽는 비중은 줄었지만 Stage 배포 전에는 develop에 합쳐진 diff 전체를 다시 봐요. PR 하나만 볼 때는 자연스러웠던 코드도 여러 작업과 함께 놓으면 중복된 추상화나 어긋난 이름, 이상하게 갈라진 FSD 경계가 보여요. 이때 프로젝트 전체의 규칙에 맞게 다시 리팩터링했어요.

배포 뒤에도 마음에 걸리는 코드 스타일이 있으면 그 파일만 고치지 않았어요. 같은 패턴을 프로젝트 전체에서 찾고 skill이나 lint, 공용 구현을 바꿨어요. 최근 `entities`를 없애고 FSD 레이어를 다시 정리한 일도 여기서 시작됐어요. 문서에 적힌 구분이 실제 코드에서는 반복되지 않았고, 구조를 바꾼 뒤 page 간 참조와 Public API 규칙까지 lint로 잠갔어요.

4월에는 AI가 작성한 코드를 전부 읽어야 안심할 수 있었어요. 지금은 구현 전에 요구사항과 plan을 보고, 구현 중에는 실제 화면과 테스트를 보고, 배포 전에는 합쳐진 구조를 봐요. 모델 성능이 좋아진 영향도 있지만 그것만으로는 부족했어요. 이전 작업에서 내린 판단이 skill과 lint, 테스트로 저장소에 남기 시작하면서 비슷한 코드를 다시 검토하는 시간이 줄었어요.

제가 보는 코드의 양은 줄었어요. 대신 어떤 동작을 만들지, 어디까지 확인해야 끝난 것인지, 프로젝트 전체에서 같은 기준을 유지하고 있는지는 계속 제가 판단해요. 지금의 자동화는 그 판단을 대신하기보다 반복되는 실행을 가져가는 쪽에 가까워요.
