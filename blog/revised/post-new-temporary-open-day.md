# 임시 진료일을 세 제품의 예약 달력에 반영하기

<div class="note note-summary">
  <strong>이 글에서 다루는 것</strong>
  <p>평소 쉬는 날에도 병원이 임시로 진료할 수 있도록 기능을 추가했어요. 두 관리자 서비스의 입력과 복지몰의 예약 달력을 함께 바꾸면서, 날짜 판정과 진료시간 계산, 기존 휴무 데이터의 호환성을 맞춘 과정을 적었어요.</p>
</div>

병원은 관리자 서비스에서 진료일을 정하고, 사용자는 복지몰의 달력에서 그날을 골라요. 임시 진료일을 추가하려면 입력을 저장하는 화면과 예약 가능일을 읽는 화면을 함께 바꿔야 했어요. 먼저 같은 응답을 읽는 곳부터 찾아봤어요.

## 서버는 한 배열에 담았고 프론트는 전부 휴무로 읽는 구조였어요

백엔드는 이미 있던 임시 휴무 배열에 `type`을 붙여 두 종류를 함께 싣기 시작했어요. 임시 진료 항목에는 그날의 진료 시간도 함께 실리고요.

```ts
// 서버 응답의 한 항목(식별자는 공개용 가명이에요)
type ScheduleException = {
  type?: 'CLOSED' | 'OPEN' | null; // 임시 진료가 생기기 전에 저장된 항목에는 없어요
  startDate: string; // YYYY-MM-DD
  endDate: string;
  hours?: { start: string; end: string } | null; // 임시 진료에만 있어요
};
```

프론트엔드에서 이 배열을 읽어 예약 가능일을 판정하는 곳은 세 군데였어요. 복지몰의 예약 달력, Back-Office에서 CS 담당자가 전화로 받은 예약을 넣는 화면, 병원 관리자의 예약 등록 화면이에요. 세 곳 모두 응답 스키마에는 시작일과 종료일만 있었고, 판정은 "요일 휴무면 막고, 배열의 어느 구간에 들어가도 막는다"였어요. `type`을 모르니 임시 진료 항목도 휴무 구간으로 읽혀요.

그래서 운영 화면에 입력만 먼저 붙이면 이상한 일이 생겨요. 파트너가 일요일을 임시 진료일로 저장해도 복지몰은 그 항목을 휴무로 읽고 일요일을 계속 막아요. 입력은 관리자 서비스 모노레포에, 판정은 복지몰 저장소에 있으니 한쪽만 배포돼도 이렇게 어긋날 수 있었어요. 입력 화면과 세 곳의 판정을 같은 날 함께 바꾼 이유예요.

## 화면은 두 목록으로 두고 서버와는 변환 함수에서만 합쳤어요

운영 화면의 요구는 임시 휴무와 임시 진료를 서로 독립된 목록으로 편집하는 것이었어요. 서버는 한 배열이고요. 어느 한쪽 모양에 맞추면 비용이 생겨요. 서버 배열을 그대로 폼에 두면 화면 곳곳에서 `type`으로 거르는 코드가 필요하고, 화면의 두 목록을 그대로 보내면 서버 계약이 깨져요.

그래서 폼은 `closedDays`와 `openDays`를 따로 들고, 서버와 오갈 때만 변환 함수가 가르고 합치게 했어요. 서버에서 폼으로 올 때는 `type`이 `OPEN`인 항목만 임시 진료 목록으로 보내고 나머지는 모두 임시 휴무 목록으로 보내요. 폼에서 서버로 갈 때는 반대예요.

```ts
// 폼 → 서버. 두 목록에 type 을 붙여 한 배열로 합쳐요. 날짜·시간이 덜 채워진 행은 아직 안 쓴 행이라 빼요.
export function mergeExceptions({ closedDays = [], openDays = [] }: ExceptionFormValues): ScheduleException[] {
  return [
    ...closedDays.flatMap((row) => {
      const [startDate, endDate] = closedRowSchema.parse(row);
      return isDate(startDate) && isDate(endDate) ? [{ type: 'CLOSED', startDate, endDate }] : [];
    }),
    ...openDays.flatMap((row) => {
      const { dates: [startDate, endDate], hours: [start, end] } = openRowSchema.parse(row);
      return isDate(startDate) && isDate(endDate) && isTime(start) && isTime(end)
        ? [{ type: 'OPEN', startDate, endDate, hours: { start, end } }]
        : [];
    }),
  ];
}
```

이 변환을 한 번만 쓸 수 있었던 건 3주쯤 앞선 작업 덕분이었어요. Back-Office와 병원 관리자에 따로 있던 임시 휴무 UI를 공용 패키지로 합쳐 뒀거든요. 이번에는 그 공용 슬라이스에 타입과 판정 함수, 변환, 입력 UI를 함께 두고, 두 운영 앱은 가져다 쓰기만 해요.

겹침 검증은 같은 목록 안에서만 해요. 임시 휴무끼리, 임시 진료끼리 겹치면 막고, 임시 휴무와 임시 진료가 겹치는 건 허용해요. 겹친 날은 진료일이 이긴다는 규칙을 판정 쪽에서 따로 맡으니까요.

폼 값을 스키마로 받는 부분은 머지 전에 한 번 고쳤어요. 처음에는 행을 타입 주석대로 구조분해했는데, 행이 통째로 비어 있거나 피커를 비워 칸이 `null`인 값이 섞이면 저장이 `undefined is not iterable`로 죽었어요. 폼 값은 사용자가 채우는 중인 데이터라 타입이 약속하는 모양이 아니에요. 어긋난 행은 Zod의 `.catch`로 빈 쌍으로 떨어뜨려 저장에서 빼고, 덜 채운 행은 기존처럼 안내 문구로 막게 했어요.

<div class="note note-decision">
  <strong>최종 결정</strong>
  <p>폼은 임시 휴무와 임시 진료를 따로 편집하고, 서버와 오갈 때 변환 함수가 한 배열로 합치거나 나눠요. 두 관리자 화면이 같은 변환을 쓰도록 공용 슬라이스에 뒀어요.</p>
</div>

## 예약 가능일은 네 단계 순서로 판정해요

판정 순서는 오늘 이전 → 임시 진료 → 요일 휴무 → 임시 휴무예요. 임시 진료가 요일 휴무와 임시 휴무보다 앞에 있어야 겹친 날이 열려요. 다음은 복지몰의 판정이에요.

```ts
export const isDateAvailable = (day: Date, partner?: PartnerDTO): boolean => {
  const date = dayjs(day).startOf('day');

  if (dayjs().startOf('day').isAfter(date)) return false; // 오늘 이전
  if (!partner) return true;

  if (findOpening(partner.scheduleExceptions, date)) return true; // 임시 진료
  if (partner.weeklyHours?.[getDayKey(date)]?.isClosed) return false; // 요일 휴무
  return !isClosedByException(partner.scheduleExceptions, date); // 임시 휴무
};

export const findOpening = (exceptions: Exceptions, date: dayjs.Dayjs) =>
  exceptions?.find((e) => e.type === 'OPEN' && isWithinRange(date, e));

// 'CLOSED' 로 좁히지 않아요. 임시 진료가 생기기 전에 저장된 항목은 type 없이 오고, 그것도 휴무예요.
export const isClosedByException = (exceptions: Exceptions, date: dayjs.Dayjs) =>
  !!exceptions?.some((e) => e.type !== 'OPEN' && isWithinRange(date, e));
```

휴무 판정은 `type === 'CLOSED'`로 쓰는 편이 더 명확해 보여요. 그런데 그러면 `type`이 생기기 전에 저장된 휴무가 휴무에서 빠져요. 쉬기로 한 날이 예약 가능일로 열리는 거죠. 새 규칙을 넣으면서 옛 데이터의 뜻까지 바뀌면 안 되니까 "OPEN이 아니면 휴무"로 썼어요.

스키마에서 빈 `type`을 `'CLOSED'`로 채우면 되지 않을까요? 여기서는 통하지 않아요. 두 저장소의 응답 파서는 스키마로 검증만 하고 원본을 그대로 돌려주기 때문에, 스키마의 기본값이 런타임 값에 반영되지 않아요([32번 글](https://blog.bambyul.com/ko/blog/타입-단언을-걷어내며-zod를-경계마다-다르게-배치한-기준)에 이 경계를 적었어요). 그래서 스키마에서는 `type`을 `nullish`로 열어 두고, 값이 없을 때의 뜻은 판정 함수가 정해요.

같은 순서를 세 곳에 넣었어요. Back-Office 예약 등록은 공용 판정 함수를 그대로 쓰고, 병원 관리자 예약 등록은 이미 두 목록으로 갈라 둔 폼 값을 같은 순서로 읽어요. 복지몰은 저장소가 달라 공용 패키지를 쓸 수 없어서, 같은 판정 함수를 따로 두고 순서를 테스트로 고정했어요.

## 임시 진료일의 시간은 요일 진료시간을 통째로 대신해요

날짜가 열려도 시간대가 틀리면 예약할 수 없어요. 임시 진료일에는 그날의 진료 시간이 요일 진료시간을 대신하고, 점심시간과 접수 시작, 마감 offset은 그 위에 그대로 적용해요.

가장 먼저 떠오르는 코드는 `opening?.hours ?? weeklyHours[day].hours`예요. 복지몰에서는 이렇게 쓰지 않았어요. dev API 서버 응답을 보니 휴무 요일의 진료시간이 파트너마다 다르게 남아 있었거든요. `00:00~00:00`, `09:00~18:00`, `00:00~23:00`이 다 있었어요. 휴무 요일이라 화면에 쓰이지 않던 잔여값인데, 폴백으로 이어 두면 임시 진료 항목에 시간이 빠지는 순간 이 값이 그대로 예약 시간대가 돼요.

```ts
// 임시 진료일이면 요일 값은 아예 보지 않아요.
const opening = findOpening(partner.scheduleExceptions, selected);
const hours = opening ? opening.hours : partner.weeklyHours?.[getDayKey(selected)]?.hours;
```

임시 진료일인데 시간이 없으면 요일 잔여값 대신 기본 범위로 떨어지고, 테스트도 그 경우를 따로 확인해요.

같은 응답에서 하나 더 나왔어요. 점심시간을 쓰지 않는 파트너에게 `14:00~14:00`이 내려오고 있었어요. 기존 계산은 점심이 정각에 시작하면 그 시간대를 통째로 빼기 때문에, 임시 진료 시간이 14시에 걸리면 그 시간의 슬롯이 사라져요. 시작과 끝이 같으면 점심시간이 없는 것으로 보게 했어요. 파트너 상세의 진료시간 표는 이미 같은 규칙을 쓰고 있었어요.

## 복지몰에서는 임시 진료일을 펼쳐 뒀어요

티켓에는 파트너 상세에서 임시 진료일을 휴무보다 우선해 보여 달라는 요구까지만 있었어요. 어디에 어떻게 둘지는 제가 정했어요.

파트너 상세의 진료시간은 아코디언이에요. 접혀 있을 때는 첫 요일 한 줄만 보이고, 나머지 요일과 점심시간, 추가 설명은 펼쳐야 보여요. 두 정보는 성격이 달랐어요.

- 임시 진료일은 평소 쉬는 날에도 예약할 수 있다는 안내예요. 추가로 열린 날짜를 빠르게 찾을 수 있도록 아코디언 밖에 뒀어요.
- 임시 휴무일은 기존 진료시간 안내와 함께 확인할 수 있도록 아코디언 안에 뒀어요.
- 이미 끝난 기간은 둘 다 그리지 않아요.

다음 날 순서를 한 번 더 고쳤어요. 추가 설명은 요일 표의 부연이라 표 바로 뒤로 보내고, 임시 휴무는 아코디언의 맨 끝으로 옮겨 펼쳤을 때 바로 아래의 임시 진료와 붙게 했어요. 라벨이 있는지만 보는 단언은 순서가 뒤집혀도 통과해서, 행 순서를 배열 값으로 비교하는 테스트로 바꿨고요.

<div class="note note-decision">
  <strong>핵심 결정</strong>
  <p>병원이 추가로 연 날짜는 달력에서 선택할 수 있게 하는 것과 함께 상세 화면에서도 눈에 띄게 보여 줬어요. 기존 진료시간 안내를 유지하면서 임시 진료일은 펼친 상태로 뒀어요.</p>
</div>

## 규칙은 Vitest로, 서버 계약은 dev API 서버로 확인했어요

테스트는 무엇을 증명하려는지에 따라 나눴어요.

판정 순서와 옛 데이터 처리, 변환, 입력 UI는 Vitest로 고정했어요. 관리자 서비스에서는 공용 슬라이스의 판정 함수, 변환, 입력 UI를, 복지몰에서는 판정 함수와 예약 달력의 날짜 및 시간 계산, 파트너 상세 표시를 테스트해요. 테스트가 고정한 조건은 이런 것들이에요.

- 임시 휴무 구간과 겹쳐도 임시 진료일만 선택돼요.
- 임시 진료일이어도 오늘 이전 날짜는 막혀요.
- `type`이 없는 옛 항목도 임시 휴무로 봐요.
- 휴무 요일의 진료시간이 `00:00~00:00`이어도 하루 전체가 열리지 않아요.
- 임시 휴무 한가운데 임시 진료일이 있으면 가장 가까운 예약일은 그날이에요.
- 임시 진료일은 아코디언을 펼치지 않아도 보여요.

목 픽스처도 고쳤어요. 기존 픽스처는 휴무 요일에도 평일과 같은 `09:00~18:00`을 넣고 있었어요. 휴무 요일에 이런 정상값이 들어 있으면, 요일 값이 새어 들어와도 그럴듯한 시간대가 나와요. 정작 dev API 서버에 실제로 있던 `00:00~00:00`은 테스트가 한 번도 만나지 못했고요. 이 값은 끝 시각에서 접수 마감 offset을 빼는 순간 전날 23시대로 넘어가서, 0시부터 23시까지가 전부 예약 시간대가 돼요. 휴무 요일의 기본값을 dev API 서버 응답처럼 `00:00~00:00`으로 바꾸고, offset을 건 경우도 따로 확인하게 했어요.

서버 계약은 목으로 확인할 수 없어요. 목은 우리가 정한 모양이라, 서버가 `type`이나 진료 시간을 싣지 않게 바뀌어도 계속 통과하고 화면만 조용히 옛 동작으로 돌아가요. 그래서 dev API 서버를 대상으로 하는 테스트를 저장소마다 따로 뒀어요. 관리자 서비스는 앱마다 Vitest 프로젝트를 mock, live로 나눠 계정이 있는 환경에서만 live 프로젝트가 생기게 했고, 복지몰은 별도 설정 파일로 따로 실행해요.

- 병원 관리자: 임시 휴무와 하루 겹치는 임시 진료일을 저장하고 다시 조회해, 임시 진료 항목이 `type`과 진료 시간까지 그대로 돌아오고 겹친 임시 휴무도 휴무로 남는지 봐요. 실제 데이터와 겹치지 않게 2099년 날짜를 쓰고, 끝나면 원래 값으로 되돌려요.
- Back-Office: 고정한 파트너의 실제 응답에 임시 진료일 한 건을 얹어 예약 가능일과 시간대, 접수 offset이 반영되는지 보고, 점심시간은 값을 고정해 빠지는지 봐요. 데이터는 읽기만 해요.
- 복지몰: 서버의 OpenAPI 명세에 `type` enum과 진료 시간 칸이 있는지, 고정 파트너의 응답이 프론트 스키마를 통과하는지, 날짜가 `YYYY-MM-DD`로 오는지, 임시 진료 항목에 진료 시간이 빠짐없이 오는지 봐요. 저장은 관리자 서비스의 몫이라 복지몰은 읽기만 해요.

이 중 가장 중요한 건 첫 번째였어요. 프론트엔드는 같은 종류끼리만 겹침을 막고 "겹치면 진료일이 이긴다"를 전제하는데, 서버가 겹친 요청을 거절하면 이 전제가 통째로 무너져요. 저장하고 다시 읽는 테스트로, 서버가 겹친 두 항목을 받아 그대로 돌려준다는 걸 확인했어요.

PR이 합쳐지고 이틀 뒤에는 테스트 기준을 저장소의 스킬에 정리하면서, 관리자 서비스의 dev API 서버 테스트를 API 함수 호출에서 화면 테스트로 옮겼어요. 병원 관리자는 화면에서 입력하고 저장한 값을 조회 화면에서 확인하고, Back-Office는 파트너 상세를 읽기 전용으로 확인해요.

## 바뀐 것과 확인한 것

세 제품 모두 오늘 이전 → 임시 진료 → 요일 휴무 → 임시 휴무 순서로 예약 가능일을 판정하도록 바꿨어요. 두 관리자 화면은 같은 변환 함수로 서버 배열과 오가고, `type`이 없는 옛 항목은 계속 휴무로 처리해요. 함께 발견한 시간대 예외 두 가지는 복지몰에 반영했어요. Back-Office 예약 등록의 시간대 계산은 이번 변경에 포함하지 않았어요.

돌아보면 입력 화면을 만드는 일보다 그 값을 읽는 쪽을 모두 찾는 일이 더 중요했어요. 파트너의 설정은 한 저장소에서 저장되고, 다른 저장소의 달력에서 읽히고, 그 사이의 모양은 서버가 정해요. 세 지점 중 하나라도 옛 계약을 믿고 있으면 설정은 사용자에게 도착하지 않아요.
