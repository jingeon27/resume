# Amplitude에서 이벤트를 붙이는 일과 읽는 일

<div class="note note-summary">
  <strong>이 글에서 다루는 것</strong>
  <p>복지몰에서 UTM이 남지 않거나 클릭이 겹쳐 기록되는 문제를 고쳤어요. 계측을 바로잡은 경험과 퍼널을 직접 열어 본 경험에서 출발해, Amplitude 생성 메뉴의 차트·대시보드·코호트·기능 플래그·실험이 각각 어디에 쓰이는지 정리했어요. 제품 실험의 가설과 판단은 디자인팀·PM·PO가 맡았고, 저는 구현과 계측에 참여했어요. 뒤의 메뉴 설명과 실험 예시는 공식 문서를 바탕으로 정리한 내용이며, 모두 직접 운영했다는 뜻은 아니에요. 코드의 컴포넌트·쿠키·클릭 이벤트 이름은 공개용 가명이에요.</p>
</div>

행동 이벤트를 붙이는 코드는 대개 한 줄이에요. 클릭 핸들러 옆에서 전송 함수를 하나 더 부르면 되니까요. 그래서 이벤트가 틀리게 찍혀도 코드만 봐서는 잘 드러나지 않았어요.

복지몰에서 겪은 세 문제는 증상이 제각각이었어요. 새로 가입한 사용자의 UTM이 비어 있었고, 버튼을 누르면 카드 클릭까지 찍혔고, 소셜 로그인 완료는 SDK가 준비되기 전에 보내지는 구조였어요. 원인은 셋 다 전송하는 한 줄 바깥에 있었어요.

이벤트를 고치는 것만으로 끝나지는 않아요. 제대로 남은 이벤트로 무엇을 볼 것인지도 알아야 하니까요. Amplitude의 생성 메뉴에는 차트뿐 아니라 대시보드, 실험, 기능 플래그, 코호트가 있어요. 이름만 보면 비슷한 분석 기능 같지만, 실제로는 서로 다른 일을 해요. 먼저 제가 겪은 계측 문제를 적고, 그다음 이 메뉴들을 사용자 흐름과 연결해 볼게요.

## 신규 가입자의 UTM이 비던 원인은 코드에 없었어요

3월에 유입 경로 사용자 속성에 `utm_source` 값도 함께 담아 달라는 요청을 받았어요. PO는 문제 하나를 더 알려 줬는데요. UTM을 달고 들어와 새로 가입한 사용자는 가입 뒤 UTM 값이 남지 않는다는 것이었어요. 기존 사용자는 정상이었고, 손대기 어렵다면 새 속성으로 따로 만들어도 된다는 대안도 함께 왔어요.

저는 원인을 확인하기 전에 코드부터 넣었어요. 3월 23일 오전에는 처음 들어온 `utm_source`를 브라우저 저장소에 남겨 두고, 서버가 준 유입 경로가 비어 있으면 그 값으로 사용자 속성을 채웠어요. 같은 날 오후에는 그 코드를 지우고, 기존 유입 경로 쿠키가 비어 있을 때 `utm_source`를 그 쿠키에 쓰는 방식으로 바꿨어요. 두 변경 모두 그날 스테이지까지 올라갔어요.

그사이 마케팅 외주사에서 의견이 왔어요. 소셜 로그인으로 밖에 나갔다 돌아오면 Amplitude가 로그인 전후를 다른 사용자로 볼 수 있으니, 로그인 직후 `setUserId`를 부르라는 것이었어요. 확인해 보니 코드는 이미 회원 정보를 받으면 서버의 회원 id로 `setUserId`를 부르고 있었고, 대시보드에서도 로그인 전후 활동이 같은 사용자로 이어져 있었어요. 식별자 문제는 아니었어요.

원인은 분석 도구 쪽에 있었어요. Amplitude Data의 사용자 속성 목록에서 `initial_utm_source`가 `unexpected` 상태로 분류돼 있었어요. 추적 계획에 없이 들어온 속성에 붙는 상태예요. 이 속성을 추적 계획에 추가해 `live` 상태로 바꾸자 새로 가입한 테스트 사용자에게 `initial_utm_source`가 기록됐어요. 다른 UTM으로 다시 들어와도 처음 값이 유지됐고, `utm_source`도 함께 남았어요.

원인이 설정이었으니 제가 넣은 저장 코드는 필요 없었어요. 4월 2일에 쿠키 저장 코드를 걷어냈고, 이 코드가 들어간 뒤 운영 브랜치에 처음 합쳐진 4월 3일 배포에는 이미 빠져 있었어요. 그 사이 운영에 들어간 핫픽스 세 건에도 이 코드는 없었어요.

<div class="note note-decision">
  <strong>최종 결정</strong>
  <p>프론트 저장 코드는 운영에 내보내지 않고 걷어냈어요. 설정을 바꾸자 사라지던 값이 돌아왔으니, 코드를 남기면 같은 유입 정보를 채우는 경로만 하나 늘어요. 처음 요청받은 `utm_source`도 SDK가 남기는 `utm_source` 사용자 속성으로 볼 수 있어서, 유입 경로 속성에 따로 담지 않았어요. 대안으로 받은 새 속성도 만들지 않았어요. 원인을 모른 채 만든 새 속성 역시 추적 계획 밖에서 들어와 같은 상태로 분류될 수 있었거든요. 이 일에서 배운 건, 해결책 모양으로 온 요청이라도 값이 어느 단계에서 사라지는지를 먼저 확인해야 한다는 것이었어요.</p>
</div>

## 버튼을 되살리다 카드 클릭까지 함께 찍었어요

1월에 만들어 2월 26일 운영에 나간 상세 개편에서, 파트너 상세 화면의 프로그램 카드에 있던 예약·상담 버튼이 빠졌어요. 4월에 PO 결정으로 이 버튼을 다시 넣었는데요. 카드에는 이미 카드 클릭 이벤트가 붙어 있었어요.

이 카드의 클릭 계측 래퍼는 Radix `Slot`으로 만든 컴포넌트예요. 감싸는 요소를 새로 만들지 않고, 자식 요소의 `onClick`에 전송 핸들러를 병합해요. 그러니 카드 안 버튼의 클릭이 카드 요소까지 버블링되면 카드 클릭 이벤트도 찍혀요.

되살린 첫 커밋의 버튼 핸들러에는 전파를 막는 `stopPropagation`이 있었어요. 그런데 같은 날 버튼 이동 앞에 인증 확인을 끼우며 핸들러를 새로 쓰다가 이 줄을 빠뜨렸어요. 상담 버튼을 누르면 상담 화면으로 이동하면서 카드 클릭도 한 번 기록됐고, 이 상태로 4월 10일 스테이지에 올라갔어요.

스테이지 QA 기간인 4월 13일, QA 반영 PR에서 버튼 핸들러에 전파 차단을 되돌리고, 카드 본문에는 프로그램 상세로 가는 이동을 따로 줬어요. 다음 날 버튼마다 클릭 이벤트를 붙일 때는 같은 래퍼로 버튼 요소 자체에 병합했어요. 이동 핸들러와 전송 핸들러가 같은 요소에 있으니, 전파를 막아도 버튼 이벤트는 찍히고 카드로는 올라가지 않아요.

```tsx
// ClickTracker 와 이벤트 이름은 공개용 가명이에요. Slot 이라 onClick 을 자식 요소에 직접 병합해요.
<ClickTracker event="click_program_card">
  <div onClick={goToProgramDetail}>
    {/* 썸네일·이름·가격 */}
    <ClickTracker event="click_consultation">
      <Button
        onClick={(event) => {
          event.stopPropagation(); // 카드 요소에 병합된 이동·전송까지 올라가지 않게 해요
          goToConsultation();
        }}
      >
        상담
      </Button>
    </ClickTracker>
  </div>
</ClickTracker>
```

수정은 4월 14일 운영 브랜치에 함께 합쳐졌어요. 중복을 만든 코드는 그 전에 운영에 나간 적이 없어요(4월 13일 운영 핫픽스에도 없었어요). 코드대로라면 버튼을 한 번 누르면 버튼 이벤트만 한 번 남아요. 다만 수정 뒤 스테이지에서 이벤트 건수를 잰 기록은 남아 있지 않아요.

### 같은 `stopPropagation`이 8월에는 기록을 끊을 뻔했어요

8월 31일에는 검색엔진이 따라갈 수 있게 상세 페이지 사이를 링크로 잇는 작업을 했어요. 카드의 프로그램 이름을 상세 페이지로 가는 앵커로 바꾸고, 앵커 클릭이 카드의 이동 핸들러까지 올라가 히스토리가 두 번 쌓이지 않게 앵커에 `stopPropagation`을 걸었는데요. 이번에는 이름을 누르면 카드 클릭 이벤트가 나가지 않게 됐어요. 전송 핸들러가 카드 요소에 병합돼 있으니, 전파를 끊으면 이동과 함께 계측도 끊기는 거예요.

그래서 앵커에서는 전파를 막지 않고, 카드 핸들러가 클릭 출처를 보고 이동만 건너뛰게 했어요. 앵커를 넣은 커밋 6분 뒤 같은 브랜치에서 고쳐 두 커밋이 한 PR로 함께 합쳐졌으니, 기록이 끊기는 코드는 스테이지에도 운영에도 나가지 않았어요.

```tsx
const goToProgramDetail = (event: MouseEvent) => {
  // 앵커를 눌렀으면 이동은 앵커가 해요. 전파는 그대로 두어 카드 요소에 병합된 전송이 돌게 해요.
  if ((event.target as HTMLElement).closest('a')) return;
  router.push(programDetailPath);
};
```

4월에는 전파를 막아서 중복을 없앴고, 8월에는 전파를 막았다가 기록을 끊을 뻔했어요. 둘 다 전송 핸들러가 카드 요소에 병합돼 있다는 같은 구조에서 나온 결과였어요. 전파를 막을지는 이동이 아니라 전송 핸들러가 어느 요소에 붙어 있는지를 보고 정해야 했어요.

## 소셜 로그인 완료가 SDK 초기화 전에 보내지는 구조였어요

로그인 완료 이벤트는 2025년 7월부터 있던 기존 구현이었어요. 레이아웃의 한 컴포넌트가 회원 정보를 받으면 토큰의 회원 id를 이전 값과 비교해, 달라졌을 때 한 번 보내고 그 id를 ref에 적어 두는 방식이었어요.

9월에 이 코드를 따라가 보니 소셜 로그인의 복귀는 전부 전체 페이지 로드였어요. 콜백이 `location.replace`로 이동시키거나, 팝업이 닫힌 뒤 새로고침하거나, 인앱 브라우저에서 리다이렉트해요. 코드대로라면 새로 뜬 앱에서는 이 컴포넌트의 effect가 SDK 초기화보다 먼저 돌아요. 이 컴포넌트가 초기화를 맡은 Provider 안쪽에 있고, React는 한 번 반영할 때 자식의 effect를 부모보다 먼저 돌리거든요. 전송 함수는 초기화 전이면 아무것도 보내지 않고 끝나는데, ref에는 보냈다고 적혀서 다시 시도하지도 않았어요. 로그인 직후의 문서에서는 이 이벤트가 나갈 길이 없는 구조였던 거예요. 운영 건수로 확인한 결론은 아니에요.

초기화 순서만 맞추는 것으로는 부족했어요. ref는 문서가 새로 뜰 때마다 비니, 이 구조는 새 문서에서 회원 정보를 처음 받을 때마다 보내요. 순서만 고쳤다면 로그인한 회원이 페이지를 새로 열 때마다 로그인 완료가 찍혔을 거예요. 로그인이 일어났다는 사실을 아는 곳은 로그인 콜백뿐이었어요.

## 사건을 아는 곳이 표식을 남기고 보낼 시점을 아는 곳이 소비해요

소셜 콜백 라우트가 토큰 쿠키를 구울 때 일회성 쿠키를 하나 더 굽게 했어요. 그리고 SDK 초기화 시점을 아는 분석 훅이, 초기화와 회원 정보 조회를 마친 뒤 그 쿠키를 한 번 보고 지운 다음 이벤트를 보내요.

```ts
// 콜백 라우트: 토큰 쿠키와 함께 일회성 표식을 구워요(쿠키 이름은 공개용 가명이에요)
response.cookies.set(LOGIN_DONE_COOKIE, 'true', { path: '/', maxAge: 60 * 5 });

// 분석 훅: 초기화와 회원 정보가 갖춰진 뒤에만 표식을 소비해요
useEffect(() => {
  if (!isInitialized || !userInfo || !loginDoneCookie) return;

  // 지우는 순간 쿠키 상태가 비어서, 회원 정보가 다시 조회돼 effect 가 또 돌아도 두 번 보내지 않아요
  deleteLoginDoneCookie();
  decodeToken().then((token) => {
    if (token) track('login_complete', { type: token.loginType });
  });
}, [isInitialized, userInfo, loginDoneCookie]);
```

순서에는 이유가 있어요. 초기화 전에 쿠키를 지우면 이벤트는 나가지 못하고 표식만 사라져요. 회원 정보까지 기다리는 건 이벤트에 회원 id를 싣기 위해서예요. 쿠키는 클라이언트가 읽고 지워야 해서 httpOnly를 붙이지 않았고, SDK를 켜지 않는 로컬·개발 환경에서는 아무도 지우지 않으니 5분 뒤 저절로 사라지게 했어요.

<div class="note note-decision">
  <strong>최종 결정</strong>
  <p>로그인 복귀 경로를 로그인 완료 전용 페이지로 모으는 안도 검토했어요. 한 곳에서 보내면 되니 단순해 보였지만, 로그인마다 전체 로드가 한 번 늘고 보내자마자 페이지를 떠나 전송이 끝나기를 기다려야 했어요. 이벤트 하나 때문에 가입 흐름의 이동을 바꿀 이유는 없다고 봤어요. 로그인이 일어났다는 사실은 콜백이 표식으로 남기고, 보낼 수 있는 시점은 분석 훅이 판단하게 나눴어요.</p>
</div>

## 한 번만인지는 전송 큐가 빈 뒤에 셌어요

쿠키를 굽는 콜백과 쿠키를 소비하는 훅은 각자 단위 테스트로 고정했어요. 훅 테스트 8건은 초기화 전, 회원 정보 전, 쿠키가 없을 때, 토큰을 읽지 못할 때 보내지 않는지와 회원 id가 먼저 설정되는지, 회원 정보가 다시 조회돼도 한 번만 보내는지를 봐요. 콜백 테스트는 소셜 계정 연동에는 표식을 굽지 않는지와, 계정 병합만 실패한 응답에는 굽는지를 봐요. 연동은 로그인이 아니고, 병합이 실패해도 소셜 토큰은 구워져 회원은 로그인된 채로 돌아가거든요.

그래도 두 쪽은 서로 다른 문서에서 돌아요. 단위 테스트는 이음매 양쪽만 볼 뿐 둘이 이어지는지는 못 봐요. 그래서 목 서버로 팝업 로그인을 실제로 태우는 E2E 2건을 붙였어요. 하나는 로그인하고 돌아오면 한 번만 보내고 새로고침해도 다시 보내지 않는지, 다른 하나는 이미 로그인된 채로 들어온 회원에게는 보내지 않는지를 봐요. 두 번째가 앞에서 적은 "새로 열 때마다 찍히는" 동작이 생기지 않게 막는 테스트예요.

"한 번"을 세는 시점도 정해야 했어요. SDK는 보낸 이벤트를 응답이 올 때까지 브라우저 저장소의 미전송 큐에 둬요. 큐가 비기 전에 문서를 다시 띄우면 다음 초기화가 같은 배치를 또 보내서, 요청을 가로채 세는 E2E에서는 한 번 보낸 이벤트가 두 번 잡혀요. Amplitude 서버는 SDK가 붙인 같은 `insert_id`를 한 번으로 거르니 운영 집계가 두 배가 되는 건 아니지만, 테스트는 요청에 실린 이벤트를 세니까요. 그래서 개수는 큐가 빈 뒤에 셌어요.

테스트가 성공했다는 결과도 따로 확인했어요. 약관 동의 여부로 갈리는 콜백 테스트 두 건은 응답이 실제로 어느 목적지로 보내는지부터 확인하게 했어요. 목이 어긋나 두 건이 같은 갈래를 타도 통과하던 걸 막으려고요. E2E는 목 토큰의 로그인 방식을 기본값이 아닌 카카오로 줘서, 전송값이 기본값이 아니라 토큰 클레임에서 온다는 걸 확인했어요.

수정은 9월 16일 운영 브랜치에 반영했어요. 목 서버 E2E에서는 로그인 한 번에 이벤트 한 번, 새로고침과 이미 로그인된 회원에게는 0번인 걸 확인했지만, 운영에서 수정 전후 건수는 대조하지 않았어요. 9월 21일에는 SDK 초기화를 하이드레이션 전으로 옮겨서, 지금은 초기화를 state로 기다리지 않고 그 자리에서 초기화 여부를 확인해요.

## 퍼널을 열어 보고 배운 것

이벤트가 일어난 일만 기록하게 된 뒤에도 남는 질문이 있었어요. 그 이벤트로 무엇을 비교할지예요. 4월 버튼 복원을 배포한 뒤, 비즈니스 맥락을 파악하려고 상세 개편 구간(2026.02.27~04.01, 기존 사용자 기준)의 퍼널을 직접 열어 봤어요. 개편의 가설과 판단은 디자인팀·PM·PO의 몫이었고, 저는 그 화면에 이벤트를 붙인 사람으로서 흐름을 이해하고 싶었어요.

같은 배포에 메인 화면 개편이 섞여 있었고, 트래픽도 A/B 비교를 할 만큼 충분하지 않았어요. 그 수치만으로는 상세 개편의 효과를 읽을 수 없었어요.

이벤트를 정확하게 만드는 일과 그 이벤트로 효과를 읽는 일은 별개였어요. 클릭 한 번이 이벤트 한 번으로 남아도, 비교 구간에 다른 변경이 섞이면 어느 변경의 결과인지 가를 수 없어요. 이벤트가 빠지거나 겹치면 비교 이전에 숫자 자체를 믿을 수 없고요. 그래서 비교 구간과 성공 기준은 배포 전에 정해 둬야 한다는 걸 배웠어요. 다음에 계측을 맡으면 이벤트를 붙이기 전에 무엇과 비교하고 무엇을 성공으로 볼지부터 담당자와 맞추고 싶어요.

## 생성 메뉴는 무엇을 알고 싶은지에 따라 달라져요

아래는 실제 성과가 아니라, 복지몰의 흐름을 놓고 각 기능을 어떻게 쓸 수 있을지 정리한 예시예요. 메뉴 이름이나 사용할 수 있는 기능은 계정의 권한과 플랜에 따라 다를 수 있어요.

| 만드는 것 | 무엇을 하나요 | 복지몰에 대입하면 |
| --- | --- | --- |
| 차트(Chart) | 이벤트와 속성으로 한 가지 질문을 살펴봐요 | 프로그램 상세를 본 사람이 예약을 시작하는 비율 |
| 대시보드(Dashboard) | 관련 차트를 한곳에 모아 계속 확인해요 | 유입, 인증, 예약 시작, 접수를 같은 화면에서 확인 |
| 코호트(Cohort) | 같은 조건에 해당하는 사용자 집단을 저장해요 | 최근 상세를 봤지만 예약을 접수하지 않은 사용자 |
| 기능 플래그(Feature Flag) | 누구에게 어떤 기능을 보여 줄지 제어해요 | 새 예약 버튼을 일부 사용자에게만 표시 |
| 실험(Experiment) | 나눠 제공한 경험의 결과를 비교해요 | 기존 버튼과 새 버튼 중 어느 쪽이 예약 시작에 도움이 되는지 |

차트는 질문 하나를 보는 도구이고, 대시보드는 그 질문들을 모아 보는 자리예요. 코호트는 분석할 사람을 묶는 조건이고요. 기능 플래그와 실험은 변경을 누구에게 제공하고 어떻게 비교할지에 가깝다고 보면 이해하기 쉬워요.

### 차트는 먼저 질문을 하나 고르는 일이에요

`생성 → 차트`에서는 이벤트, 속성, 사용자 집단을 골라 분석해요. 이벤트는 '무엇을 했는지'이고, 속성은 '어떤 조건에서 했는지'예요. 프로그램 상세 조회가 이벤트라면, 프로그램 식별자나 진입 경로는 그 이벤트를 나눠 볼 수 있는 속성이에요. [Amplitude의 차트 생성 안내](https://amplitude.com/docs/get-started/create-a-chart)

화면에서는 `차트 종류 선택 → 이벤트 선택 → 대상·속성 조건 설정 → 기간·집계 방식 확인 → 저장` 순서로 볼 수 있어요. '예약 버튼 클릭 수'처럼 이름만 붙이기보다 사용자 수를 세는지 전체 클릭을 세는지까지 맞춰 두는 편이 좋아요.

같은 이벤트를 골라도 차트 종류에 따라 질문은 달라져요.

- **Event Segmentation**은 얼마나 일어났는지 봐요. 예약 버튼을 누른 횟수와 누른 사람 수는 다른 값이에요. 한 사람이 다섯 번 눌렀다면 `Event Totals`는 5건, 해당 집계 구간의 `Uniques`는 1명이에요. 유입 경로나 기기별로 나누면 어느 집단에서 행동이 많았는지도 볼 수 있어요. [집계 방식 설명](https://amplitude.com/docs/analytics/charts/event-segmentation/event-segmentation-choose-measurement)
- **Funnel Analysis**는 정한 단계를 거쳐 어디까지 갔는지 봐요. `상세 조회 → 예약 시작 → 예약 접수`처럼 이벤트를 놓고, 순서와 전환을 인정할 시간을 정해요. 기본 집계는 고유 사용자 기준이며, 여러 시도를 따로 세려면 집계 설정을 바꿔야 해요. [퍼널 집계 설명](https://amplitude.com/docs/analytics/charts/funnel-analysis/faq)
- **Retention Analysis**는 어떤 행동 이후 다시 돌아와 정한 행동을 했는지 봐요. 시작 이벤트와 복귀 이벤트를 따로 고를 수 있어요. 다만 의료 예약처럼 이용 주기가 긴 제품에서 7일 재방문율을 그대로 목표로 삼으면, 당장 다시 예약할 필요가 없는 사람까지 이탈로 읽을 수 있어요. 어떤 복귀가 의미 있는지부터 정해야 해요. [리텐션 차트 안내](https://amplitude.com/docs/analytics/charts/retention-analysis/retention-analysis-build)

정해 둔 경로가 아니라 실제 이동 경로를 살펴보려면 Journeys 같은 차트도 있어요. 퍼널은 제가 먼저 정한 단계를 기준으로 보고, 경로 탐색은 그 사이에 어떤 행동이 있었는지 찾는 데 쓸 수 있어요. 차트 종류를 전부 외우기보다는 지금 궁금한 게 횟수인지, 단계별 전환인지, 다시 사용하는지부터 구분하는 편이 낫겠어요. [차트 종류 안내](https://amplitude.com/docs/analytics/charts)

퍼널에서는 분모가 특히 중요해요. 가령 상세를 본 100명 중 20명이 예약을 시작하고 10명이 접수했다면, 상세 기준 접수율은 10%이고 예약 시작 기준 접수율은 50%예요. 둘 다 맞는 숫자지만, 답하는 질문이 달라요. 신청 버튼을 누른 것을 접수로 기록하면 이 구분부터 틀어지고요.

같은 프로그램을 끝까지 예약했는지도 확인해야 해요. A 프로그램 상세를 본 뒤 B 프로그램을 예약한 사람을 A의 전환으로 세면 곤란하니까요. Amplitude의 `Holding Property Constant`를 쓰면 모든 단계에서 같은 `programId`를 가진 경로로 좁힐 수 있어요. 이때 그 속성을 모든 단계의 이벤트에 보내야 하고, 집계도 단순한 사용자 수가 아니라 사용자와 속성 값의 조합 기준으로 달라져요. 아래 식별자 이름은 설명용이에요. [같은 속성을 유지하는 퍼널 설정](https://amplitude.com/docs/analytics/charts/funnel-analysis/funnel-analysis-hold-properties-constant)

```text
질문: 같은 프로그램의 상세를 본 뒤 예약을 접수했는가?
단계: 상세 조회 → 예약 시작 → 예약 접수
연결: 모든 단계에서 같은 programId 유지
기간: 첫 단계부터 얼마 안에 완료한 것을 인정할지 합의
완료: 신청 버튼 클릭이 아니라 서버가 접수를 확정한 상태
```

이런 정의를 먼저 정리해야 어떤 이벤트가 빠졌는지도 알 수 있어요. 마지막 접수 이벤트가 없다면 차트 설정만으로 접수율을 만들 수는 없으니까요.

### 대시보드는 같은 흐름을 함께 보는 자리예요

차트 하나에서 질문에 답했다면, 대시보드에는 계속 같이 확인할 차트들을 모아요. `생성 → 대시보드`로 만들거나 저장한 차트에서 대시보드에 추가할 수 있어요. 대시보드 자체가 새로운 계측을 하는 것은 아니에요. [대시보드 생성 안내](https://amplitude.com/docs/analytics/dashboard-create)

예약 흐름을 본다면 유입 사용자, 인증 단계별 전환, 상세에서 예약으로 가는 퍼널, 실제 접수 추이를 함께 두겠어요. 예약이 줄었을 때 상세 화면부터 의심하기보다, 들어온 사람이 줄었는지 인증에서 멈췄는지부터 나눠 볼 수 있으니까요.

다만 차트를 한곳에 붙인다고 비교 조건까지 같아지지는 않아요. 차트마다 기간, 집계 단위, 유입 집단, 전환 시간이 다르면 서로 다른 숫자를 나란히 놓은 셈이에요. '예약 전환율'이라는 제목만 붙이지 않고 무엇을 분모로 삼았는지도 적어 두고 싶어요.

오류나 결제 실패도 함께 볼 수 있지만, 그 정보를 이벤트로 수집하거나 별도 데이터로 연결했다는 전제가 있어요. 대시보드를 만들었다는 이유로 아직 보내지 않은 데이터가 생기지는 않아요.

### 코호트는 함께 볼 사람을 저장해 두는 것이에요

코호트는 특정 속성이나 행동 조건에 해당하는 사용자 집단이에요. 예를 들어 '최근 7일 동안 프로그램 상세를 봤지만 같은 기간 예약을 접수하지 않은 사용자'처럼 조건을 저장하고, 여러 차트에서 같은 집단을 볼 때 다시 쓸 수 있어요. 매번 차트마다 같은 필터를 만드는 것과 달리 집단의 정의를 함께 관리할 수 있는 셈이에요. [코호트 생성 안내](https://amplitude.com/docs/quick-guides/build-your-first-cohort)

이 집단에서 인증을 마치지 못한 사람이 많은지, 검색 결과가 없었던 사람이 많은지 살펴볼 수 있겠어요. 그래도 상세만 보고 끝난 이유가 화면 때문이라는 결론이 바로 나오지는 않아요. 원하는 지역에 예약 가능한 병원이 없었을 수도 있으니까요.

코호트의 조건과 기준 기간도 남겨야 해요. '최근 7일' 조건의 동적 코호트는 시간이 지나면 포함된 사람이 달라질 수 있어요. 반면 특정 시점의 명단을 고정한 정적 코호트는 그때의 집단을 유지해요. 같은 이름의 코호트를 골랐다고 항상 같은 사람들을 비교하는 것은 아니에요. [동적·정적 코호트의 차이](https://amplitude.com/docs/analytics/track-cohort-changes)

그리고 **코호트를 둘로 나누는 것과 A/B 실험군을 나누는 것은 달라요.** 쿠폰을 쓴 사람과 안 쓴 사람은 구매 의향부터 다를 수 있어요. 두 집단의 예약률 차이는 관찰할 수 있지만, 그 차이를 쿠폰의 효과라고 바로 말할 수는 없어요. 코호트는 살펴볼 집단을 정하는 데 쓰고, 변경의 효과를 비교하려면 실험 대상과 배정 방식을 별도로 정해야 해요.

### 기능 플래그는 기능을 배포하는 것과 켜는 것을 나눠요

기능 플래그는 새 기능을 누구에게 켤지 정하는 장치예요. 새 예약 버튼 코드를 배포해 두고, 내부 확인을 마친 뒤 일부 사용자에게만 켜거나 문제가 생기면 다시 끄는 식으로 쓸 수 있어요. 사용자 조건과 제공 비율도 설정할 수 있어요. [기능 플래그 설정 안내](https://amplitude.com/docs/feature-experiment/experiment-quick-start)

중요한 건 Amplitude 화면에서 플래그만 만들면 제품이 바뀌는 게 아니라는 점이에요. Feature Flag를 사용하는 방식에서는 애플리케이션이 Experiment SDK나 API로 값을 받아 그에 맞는 UI나 동작을 선택하도록 구현돼 있어야 해요. 분석 SDK로 클릭 이벤트를 보내는 것만으로는 이 분기가 생기지 않아요.

프론트엔드에서는 플래그 값을 못 받았을 때 어떤 화면을 보여 줄지도 정해야 해요. 기존 예약 버튼을 기본값으로 둘지, 값을 기다릴지, SSR로 보낸 화면과 클라이언트에서 받은 값이 달라지면 어떻게 처리할지요. 플래그를 끄는 것도 새 기능의 사용을 막는 것이지, 이미 만들어진 예약이나 결제 데이터를 되돌리는 일은 아니에요.

기능 플래그를 켜서 일부 사용자에게 배포했다고 해서 A/B 실험이 된 것은 아니에요. 비교할 가설과 지표 없이 안전하게 출시 범위를 조절하는 데만 쓸 수도 있어요. 반대로 기능 플래그에 비교할 버전과 지표를 붙여 실험으로 이어 갈 수도 있고요. [Feature Experiment와 Web Experiment 설명](https://amplitude.com/docs/feature-experiment/overview)

### 실험은 바꾼 화면의 효과를 비교할 조건이 필요해요

실험을 만들 때는 기존 경험과 변경한 경험을 나누고, 어떤 결과가 달라져야 하는지 정해요. Amplitude에는 코드와 기능 플래그를 연동하는 Feature Experiment와 시각적 편집기를 사용하는 Web Experiment가 있어요. 화면이나 동작 변경의 범위에 따라 선택이 달라질 수 있어요.

가상의 예로 예약 버튼의 위치를 바꾼다면, 다음 정도는 구현 전에 맞춰야겠어요.

```text
가설: 예약 버튼이 더 잘 보이면 상세를 본 사용자가 예약을 시작하는 비율이 높아진다.
대상: 예약 가능한 프로그램의 상세 화면을 보는 사용자
비교: 기존 버튼 위치 / 바꾼 버튼 위치
배정: 대상 사용자를 무작위로 나누되 같은 사용자의 버전이 유지되도록 식별자와 배정 단위 확인
노출: 해당 화면에서 어떤 버전이 제공됐는지 기록
주 지표: 노출된 사용자 중 정한 시간 안에 예약을 시작한 비율
보조 지표: 실제 예약 접수까지 이어진 비율
가드레일: 예약 실패율이나 중복 접수가 늘지 않는지
판단: 필요한 표본과 관찰 기간, 중단·확대 조건을 시작 전에 합의
```

실험 대상의 조건을 정하는 것과 그 안에서 비교 버전을 배정하는 것도 구분해야 해요. 먼저 예약 가능한 프로그램을 보는 사람을 대상으로 정하고, 그 안에서 무작위로 기존·새 버전을 나누는 식이에요. 서로 다른 유입 집단을 그대로 기존·새 버전으로 삼으면 화면의 차이와 사용자의 차이가 섞여요. [Amplitude의 무작위 배정 방식](https://amplitude.com/docs/feature-experiment/under-the-hood/experiment-randomization)

주 지표는 바꾼 부분과 연결이 가까워야 해요. 버튼 위치를 바꾸는데 매출만 보면 영향이 여러 단계 뒤에 있어 원인을 읽기 어려워요. 그렇다고 버튼 클릭만 늘면 성공이라고 보기도 어려우니, 접수까지 이어지는지와 실패가 늘지 않는지도 함께 봐야겠어요. Amplitude도 성공 지표와 나빠지면 안 되는 가드레일을 구분하고, 표본과 기간을 추정할 수 있는 기능을 제공해요. [실험 지표 설정 안내](https://amplitude.com/docs/feature-experiment/workflow/define-goals)

계측을 맡는 입장에서는 노출 기록도 신경 써야 해요. 새 버전으로 배정된 것과 실제 해당 화면을 본 것은 같지 않을 수 있어요. 전체 앱이 시작할 때 화면과 상관없이 노출을 기록하면, 버튼을 볼 기회가 없던 사람까지 결과에 섞여요. SDK의 자동 노출도 어떤 시점에 발생하는지 확인해야 하고요. Amplitude의 클라이언트 Experiment SDK는 variant에 접근할 때 자동으로 노출을 기록할 수 있으므로, 값을 미리 읽는 위치와 기능이 실제 제공되는 위치가 맞는지 살펴봐야 해요. [실험 노출 기록 안내](https://amplitude.com/docs/feature-experiment/track-exposure)

실험 결과를 볼 때도 전환율이 조금 높은 버전을 바로 고르는 것은 아니에요. 대상이 비교 가능했는지, 노출과 접수가 제대로 연결됐는지, 필요한 표본이 모였는지, 불확실성이 얼마나 남았는지를 같이 봐야 해요. 사용자가 적으면 확인할 수 있는 효과의 크기나 필요한 기간도 달라지고요. 트래픽이 부족하다고 단순 전후 비교를 A/B 테스트라고 부를 수는 없어요.

## 다음 계측에서는 무엇을 볼지부터 묻고 싶어요

모든 기능을 쓰는 게 목표는 아니에요. 이벤트 횟수가 궁금하면 차트 하나로 충분하고, 그 흐름을 계속 살펴봐야 할 때 대시보드를 만들면 돼요. 특정 집단을 반복해서 볼 때는 코호트가 필요하고, 변경을 나눠 제공할 때는 기능 플래그와 실험을 검토할 수 있어요.

복지몰에서는 병원과 기업 제휴, 마케팅 유입도 예약에 영향을 줘요. 프로그램 정보가 좋아져도 원하는 지역에 예약 가능한 병원이 없으면 예약으로 이어지기 어렵고요. 그래서 전체 예약 건수 하나만 보기보다, 그 화면을 이용할 조건이 갖춰진 사용자가 어디서 멈추는지부터 보고 싶어요. 기능별로 생각한 지표는 [별도 메모](post-new-product-metrics.md)에 정리했어요.

지금까지 제가 주로 맡은 것은 이벤트를 붙이고 누락·중복을 고치는 일이었어요. 그 경험으로 분명해진 건, 계측을 구현할 때도 숫자를 어떻게 읽을지 알아야 한다는 점이에요. 앞으로는 이벤트 요청을 받으면 '어디서 보내야 하나'와 함께 '누구를 분모로 무엇을 확인하려 하나'를 묻고 싶어요. 그 질문이 정해져야 클릭과 접수를 구분하고, 필요한 속성과 노출 시점도 맞출 수 있으니까요.

<div class="note note-limit">
  <strong>아직 확인하지 못한 것</strong>
  <p>계측 수정은 스테이지 QA, 분석 도구의 테스트 가입자, 목 서버 E2E와 단위 테스트로 확인했어요. 운영 이벤트 건수를 전후 대조하지는 않았고, 로그인 완료의 기존 누락 여부도 코드 흐름을 따라 내린 판단이에요. `unexpected` 상태가 신규 가입자에게만 영향을 준 상세 설정과 카드 클릭 수정 뒤의 건수는 확인하지 못했어요. 버튼·카드 전파는 테스트로 고정하지 않았으며, 로그인 E2E는 목 서버의 팝업 경로만 확인하는 수동 실행 레인이에요. 메뉴 설명에 든 코호트·플래그·실험과 성과 지표는 사용 예시이지 실제 운영 결과가 아니에요.</p>
