# Sentry 도입기 — 붙이는 건 하루, 다듬는 데 닷새

프런트엔드 에러와 Web Vitals를 보려고 Sentry를 붙였습니다. SDK를 깔고 세 런타임 초기화를 채우는 데는 하루면 충분했는데요. 그 뒤로 닷새 동안 수집 정책을 여섯 번 고쳤습니다.

이 글은 그 닷새 동안 확인한 것들입니다. 개인정보가 새는 경로를 막고, 잡음을 표본으로 줄이고, Web Vitals를 확인하다가 메인 화면의 프리페치를 끄게 된 이야기까지 담았는데요. 대부분은 "옵션 하나 켜고 끄기"로 끝나지 않았습니다.

## 붙이는 것 자체는 어렵지 않습니다

`@sentry/nextjs`를 설치하고 client·server·edge 세 런타임 초기화를 채우면 이벤트가 올라옵니다. 레벨을 나누고 그룹핑과 필터링으로 잡음을 관리하는 큰 틀은 우아한형제들 기술블로그의 [선제적 장애 대응을 위한 Sentry 최적화 적용기](https://techblog.woowahan.com/21604/)를 참고했습니다.

- `fatal` — 화면이 뜨지 못한 경우 (에러 바운더리 진입)
- `error` — 화면은 떴지만 하려던 일이 막힌 경우 (기본값)
- `warning` — 예상 가능하고 서비스 이용에 지장이 없는 경우 (위치 조회 실패, 응답 스키마 불일치)

Web Vitals는 pageload 트랜잭션에 실려 오기 때문에 트레이스 샘플링도 함께 켰는데요. 프로덕션은 트래픽이 많아 일부 표본만 뜨도록 잡아 두고, 나머지 환경은 전부 뜨게 했습니다.

DSN이 비어 있으면 SDK가 통째로 꺼지도록 게이트도 하나 뒀습니다. 토큰 갱신으로 복구되는 401과 사용자 네트워크 사정인 타임아웃·중단은 처음부터 보내지 않기로 했고요.

프로덕션에 바로 열지는 않았습니다. 정책이 다듬어질 때까지는 스테이징까지만 붙여 두기로 했는데요. 결과적으로 잘한 선택이었습니다. 문제가 그 첫 배포 직후부터 나왔거든요. 의료 서비스라 개인정보에는 처음부터 신경을 썼는데도, 이슈를 열어보니 요청 헤더에 액세스 토큰이 그대로 들어 있었습니다. 옵션은 분명히 껐다고 생각한 상태였습니다.

## `sendDefaultPii: false`는 쿠키와 헤더를 빼주지 않습니다

이름만 보면 개인식별정보를 보내지 않는다는 뜻인데요. 실제로는 이슈의 `event.request`에 헤더 딕셔너리와 파싱된 쿠키가 통째로 들어 있었습니다. `accessToken`과 `refreshToken`까지 포함해서요.

SDK 구현을 따라가 보니 이유가 있었는데요.

`sendDefaultPii: false`를 주면 SDK는 그 값을 `false`로 두지 않습니다. 내부에서 "무엇을 수집하지 않을지"를 담은 **객체**로 변환하는데요. 이벤트 경로를 담당하는 `requestDataIntegration`은 그 값을 `!== false`로 판정합니다.

```text
sendDefaultPii: false
  → { cookies: false, httpHeaders: false, ... } 형태의 객체로 변환
  → requestDataIntegration: "false가 아니다 → 수집 설정이 있다"
  → deny 목록을 적용하지 않은 채 헤더와 쿠키를 event.request 에 싣는다
```

deny 필터는 span 경로에는 구현돼 있었지만 이벤트 경로에는 없었습니다. 트레이싱 쪽은 잘 걸러지고, 정작 에러 이슈에는 전부 실려 나가고 있었던 셈이죠.

해결은 `dataCollection`으로 끌 항목을 직접 적는 것이었습니다.

```ts
export const SENTRY_DATA_COLLECTION = {
  userInfo: false,
  cookies: false,
  httpHeaders: { request: false, response: false },
  httpBodies: [],
  urlQueryParams: false,
  // ...
};
```

## `dataCollection`을 넘기는 순간 기준값이 뒤집힙니다

객체를 넘기고 안심했는데요. 이 옵션에는 조건이 하나 더 있었습니다.

**이 객체를 전달하면 적지 않은 키의 기준값이 "전부 수집"으로 바뀝니다.** 안 적으면 기본값이 유지되는 게 아니라 열리는 건데요. 그래서 세 항목이 빠져 있었습니다.

그중 `stackFrameVariables`가 문제였는데요. Node 기본 통합인 `localVariablesIntegration`이 이 값을 읽어 **예외 프레임의 지역 변수를 이슈에 붙입니다.** 에러가 난 함수 안에 토큰이나 회원 정보가 변수로 들어 있으면 그대로 올라가는 거죠.

같은 사고가 반복되지 않도록 SDK의 옵션 타입을 걸어 키 오타를 빌드에서 잡도록 했습니다.

```ts
type TSentryDataCollection = NonNullable<
  NonNullable<Parameters<typeof init>[0]>['dataCollection']
>;

export const SENTRY_DATA_COLLECTION: TSentryDataCollection = {
  /* ... */
};
```

`frameContextLines`는 반대로 기본값을 **명시적으로 유지**했습니다. 개인정보가 아니라 소스 노출의 문제인데요. 어차피 소스맵을 같은 Sentry 인스턴스로 올리고 있어서 원본은 이미 그쪽에 있고, 원인 파악에 쓰는 값이 더 크다고 봤습니다.

`graphQL`은 지금 쓰지 않지만 닫아 뒀습니다. 나중에 통합이 추가돼도 닫힌 상태에서 시작하도록요.

## breadcrumb은 `dataCollection`이 걸러주지 않습니다

또 토큰이 나왔습니다. 이번에는 이벤트가 아니라 breadcrumb이었는데요.

`dataCollection`은 SDK가 자동 수집하는 request data에만 적용됩니다. breadcrumb은 그 바깥이고요. 그리고 console breadcrumb에는 인자에 실린 값이 무엇이든 들어가는데요. 코드베이스에 axios 에러 객체를 그대로 `console.error`에 넘기는 자리가 있었고, 그 객체의 요청 설정에 토큰이 있었습니다.

console breadcrumb은 통째로 버리기로 했습니다. 같은 에러는 이벤트로 따로 올라오거든요.

```ts
export function sanitizeBreadcrumb(breadcrumb: Breadcrumb): Breadcrumb | null {
  if (breadcrumb.category === 'console') return null;
  if (!breadcrumb.data) return breadcrumb;

  const data = { ...breadcrumb.data };
  // fetch·xhr 은 url, history 이동은 from·to 에 URL 이 실린다
  ['url', 'from', 'to'].forEach((key) => {
    const value = data[key];
    if (typeof value === 'string') data[key] = stripUrlParams(value);
  });

  return { ...breadcrumb, data };
}
```

여기서 한 가지가 더 보였는데요. **우리가 직접 context에 넣는 값도 자동 수집 차단 대상이 아닙니다.**

- 화면 경로를 전체 URL로 넣던 자리는 pathname만 남겼습니다.
- 이슈에 싣는 API URL에서 쿼리를 뗐습니다. 호출부가 요청 URL을 그대로 넘기는 자리가 있었는데요. OAuth 콜백이면 그 쿼리에 인증 코드와 state가 들어 있습니다.
- 조회 조건 스키마 불일치 로그에는 현재 주소가 통째로 실리고 있었습니다.

id 세그먼트도 접었습니다. 이건 개인정보보다는 그룹핑 문제인데요. 경로를 그대로 키로 쓰면 대상 id마다 다른 이슈가 생겨 목록이 계속 늘어납니다.

```ts
export function normalizePathname(pathname: string): string {
  return pathname
    .split('/')
    .map((segment) => (ID_SEGMENT_PATTERN.test(segment) ? ':id' : segment))
    .join('/');
}
```

## 이슈 목록이 고칠 수 없는 에러로 덮였습니다

개인정보 경로를 막고 나니 다른 문제가 보였는데요. 이슈 목록 상위가 전부 위치 조회 실패였습니다.

권한 거부는 원래 제외하고 있었는데, "위치 소스 없음"과 "시간 초과"가 계속 올라왔습니다. 기기나 주변 환경 사정이라 코드로 고칠 게 없는데요. 그렇다고 완전히 끄면 급증을 알아챌 방법도 사라집니다.

그래서 10%만 남기기로 했습니다. 다만 오류 코드가 없는 실패는 전부 남기는데요. 앱 브리지 reject나 `navigator.geolocation` 부재처럼 **브라우저가 아니라 우리 쪽이 깨졌다는 신호**라, 표본으로 줄이면 정작 봐야 할 것이 묻히기 때문입니다.

여기서 하마터면 크게 잘못할 뻔했습니다. 처음에는 `ignoreErrors`에 넣으려고 했는데요. `GeolocationPositionError`는 `Error`도 `Event`도 아니라서 SDK가 이런 공통 문구로 바꿔 보냅니다.

```text
Object captured as exception with keys: code, message
```

이 문구를 무시 목록에 넣으면 **`Error`가 아닌 모든 예외가 함께 사라집니다.** 무시 목록은 메시지 문자열을 보기 때문에, 그 문자열이 특정 에러의 것인지 SDK의 공통 폴백인지 구분하지 않거든요. 그래서 거르는 위치를 `beforeSend` 쪽으로 옮기고, 왜 `ignoreErrors`가 아닌지를 주석으로 남겼습니다.

레벨 정책도 이때 다시 잡았는데요. API 에러는 HTTP 메서드로 가르는 편이 맞다고 봤습니다.

| | 5xx | 4xx |
| --- | --- | --- |
| GET (화면을 채우는 호출) | `fatal` | `error` |
| 그 외 (재시도로 넘어갈 수 있음) | `error` | `warning` |

GET이 실패하면 그 자리에서 내용이 뜨지 않습니다. 쓰기 요청이 실패하면 사용자가 다시 시도할 수 있고요. 같은 상태 코드라도 사용자가 겪는 일이 다릅니다.

404도 `fatal`에서 `error`로 내리고 유입을 갈랐습니다. 고칠 수 있는 건 앱 안에서 끊긴 링크뿐이라 그쪽만 경로별로 이슈를 나누고, 외부나 봇 유입은 경로가 무한히 다양해서 한 이슈로 모아 일부만 남깁니다.

## Web Vitals를 확인하다가 프리페치를 껐습니다

수집이 돌기 시작한 뒤 Web Vitals를 확인해 봤는데요. 메인 화면의 **JS 로드 구간이 유난히 길었습니다.** pageload 트랜잭션에는 로딩 동안 나간 요청이 스팬으로 남기 때문에 워터폴을 열어 그 구간을 따라가 봤습니다.

첫 화면을 그리는 데 필요 없는 라우트 요청이 줄지어 있었는데요. 프리페치였습니다. 메인 배너 스와이퍼와 배너 전체보기 리스트, 공용 배너 컴포넌트의 링크가 **뷰포트에 들어오기만 해도 대상 라우트를 프리페치**하고 있었습니다. 배너는 화면 상단이라 진입하자마자 전부 뷰포트에 들어오고, 스와이퍼가 돌 때마다 다음 배너의 요청이 또 나가고요. 첫 화면의 JS를 받는 시간과 이 프리페치들이 같은 네트워크를 두고 겹치고 있었습니다.

프리페치 자체는 눌렀을 때 빠르게 열리라고 있는 기능인데요. 배너는 홍보 영역이라 대부분의 방문자가 누르지 않습니다. **소수가 누를 때 빠르자고 모든 방문자가 첫 로딩 대역폭을 내고, 서버는 아무도 안 볼 라우트를 렌더하고 있었던 셈이죠.** 해당 링크들에 `prefetch={false}`를 명시해서 껐습니다.

요청이 사라진 것은 워터폴에서 확인했지만, Web Vitals 수치가 얼마나 좋아졌는지까지 주장할 만큼 측정하지는 않았습니다. 다만 이 발견 자체가 도구 값을 했다고 보는데요. 에러를 모으려고 붙인 수집이 첫 화면의 낭비를 먼저 보여줬으니까요.

솔직히 말하면 이번 수정은 워터폴을 보다가 눈에 띈 것을 고친 **기회적 개선**입니다. 수집은 도는데 판정 기준이 아직 없거든요. 그래서 다음 과제는 기준을 정하는 것입니다.

- **어떤 백분위를 보는가** — Core Web Vitals의 관례적 판정선은 p75입니다(LCP 2.5초). 평균은 빠른 다수에 묻히는데요. p75는 "사용자 4명 중 1명이 이보다 나쁘다"는 뜻이라 판정선으로 쓸 수 있습니다. 꼬리의 저사양 구간을 따로 보려면 p90도 함께 봐야 하고요.
- **몇 초를 넘으면 나쁜가** — 지표별 임계값을 정해야 "느려졌다"가 감상이 아니라 판정이 됩니다.
- **어떤 구간에서의 저하를 막을 것인가** — 이 서비스는 모바일 브라우저와 앱 안 WebView로 열리는데요. 같은 화면이라도 WebView 콜드 스타트와 저사양 기기의 수치는 따로 갈라 봐야 하고, 전체 p75가 좋아도 특정 구간만 무너지는 걸 잡으려면 세그먼트별 기준이 필요합니다.
- **넘으면 누가 움직이는가** — 기준을 넘었을 때 알림이 가고 대응이 시작되는 배선까지가 기준의 일부입니다. 에러 쪽은 레벨 정책이 그 역할을 하는데요. 성능 쪽에는 아직 그게 없습니다.

기준이 없는 수치는 관측이지 운영이 아닙니다. 이번 프리페치 제거가 우연한 발견이었다면, 다음번에는 기준을 넘은 수치가 대응을 시작하게 만드는 것이 목표입니다.

## 로컬에서 도는 앱은 아무것도 보내지 않게 했습니다

다음은 비용이었는데요. Sentry를 self-hosted로 운영하고 있어서 이벤트 하나하나가 곧 우리 서버의 수집·저장 비용입니다. 그런데 개발하는 동안 로컬에서 난 에러까지 전부 올라가고 있었습니다.

로컬 에러는 터미널과 콘솔에 그대로 보이니 이슈로 만들 값어치가 없는데요. 서버 자원만 쓰는 트래픽인 데다, 실환경 이슈 사이에 섞이면 무엇이 진짜 사용자 문제인지 가리기도 어려워집니다. 그래서 로컬에서 도는 앱은 아예 아무것도 보내지 않게 막기로 했습니다.

환경 변수 하나만 보면 될 줄 알았는데 아니었습니다. 결국 셋을 함께 보는데요.

```ts
const isLocalRuntime = () => {
  if (PUBLIC_MODE === 'local' || process.env.NODE_ENV === 'development') return true;

  return typeof window !== 'undefined' && isLocalHostname(window.location.hostname);
};
```

모드만으로 부족한 이유는 모드를 덮어써서 띄우는 경우가 있어서인데요. E2E 스펙 하나가 분석 도구를 켜려고 모드를 스테이징으로 지정한 채 개발 서버를 띄웁니다. 그래서 개발 서버 여부를 `NODE_ENV`로 함께 보고, 배포 빌드를 로컬에서 띄운 경우는 브라우저가 보고 있는 호스트로 가립니다.

호스트 판정은 처음에 목록으로 짰다가 패턴으로 바꿨는데요. 실기기 확인을 할 때 개발 서버를 사설 IP로 여는 경우가 많은데, 목록 방식으로는 그때 난 이슈가 그대로 올라갔습니다.

```ts
const LOCAL_HOSTNAME_PATTERN =
  /^(localhost|0\.0\.0\.0|::1|127\.\d+\.\d+\.\d+|10\.\d+\.\d+\.\d+|192\.168\.\d+\.\d+|172\.(1[6-9]|2\d|3[01])\.\d+\.\d+)$/i;
```

그런데 **서버는 기동 시점에 자기가 어디서 도는지 알 수 없습니다.** 호스트 판정은 브라우저 전용이라 배포 빌드를 로컬에서 띄우면 서버 이벤트만 게이트를 통과했는데요. 그래서 요청 URL의 호스트를 보는 필터를 `beforeSend`에 따로 걸었습니다.

```ts
export function dropLocalRequestEvent(event: ErrorEvent): ErrorEvent | null {
  const url = event.request?.url;
  if (isNil(url)) return event;

  try {
    return isLocalHostname(new URL(url).hostname) ? null : event;
  } catch {
    // 상대 경로 등 URL 로 파싱되지 않는 값은 판정할 근거가 없으므로 그대로 보낸다
    return event;
  }
}
```

요청 밖에서 난 서버 에러는 URL이 없어 여전히 통과합니다. 판정할 근거가 없어서 그런데요. 이것도 주석으로 남겼습니다.

## 회원 id는 붙이고, 나머지는 붙이지 않았습니다

이슈마다 영향받은 사용자 수가 잡혀야 한 명만 겪는 문제와 다수가 겪는 문제를 갈라 우선순위를 정할 수 있는데요. 싣는 값은 회원 id 하나뿐입니다. 의료 서비스라 이름·이메일·전화번호는 넣지 않고, IP는 `dataCollection.userInfo`가 SDK 쪽에서 막습니다.

브라우저 이슈에만 붙입니다. 서버는 요청마다 스코프가 갈리는데요. 그 경계가 레이아웃 렌더와 맞지 않고, 캐시된 렌더에서 넣으면 **다른 요청의 이슈에 다른 사용자의 id가 실릴 수 있습니다.**

처음에는 컴포넌트가 SDK의 `setUser`를 직접 호출했는데요. 그러면 앞에서 만든 전송 게이트를 지나쳐 버립니다. capture 헬퍼와 같은 자리에 `setSentryUser`를 두고, 무엇을 싣는지도 거기서 정하도록 모았습니다.

## 남은 한계

- **프로덕션에는 아직 적용하지 않았습니다.** 지금까지의 정책은 전부 스테이징에서 다듬은 것인데요. 프로덕션은 트래픽 규모가 달라서, 여는 시점에 표본 비율과 잡음 목록을 다시 조정해야 할 가능성이 큽니다. self-hosted라 수집량이 곧 서버 비용이니, 열기 전에 예상 이벤트 양부터 가늠해 볼 생각입니다.
- 사용자 정의 context에 개인정보가 실리는 걸 막는 건 지금은 규칙과 리뷰에 의존합니다. 새 로그를 추가할 때 URL을 그대로 넘기면 다시 같은 문제가 생길 수 있는데요. 이걸 lint로 잡을 수 있을지는 아직 검토 단계입니다.
- 요청 밖에서 발생한 서버 에러의 로컬 판정은 여전히 못 합니다.
- 표본 비율은 이슈 목록을 보고 정한 값이고, 급증 감지에 충분한 비율인지는 아직 검증하지 않았습니다.
- SDK 버전이 올라가면 `dataCollection`의 키가 늘어날 수 있습니다. 타입을 걸어 오타는 잡히지만, **새로 생긴 키의 기준값이 열려 있는 상황은 타입으로 잡히지 않는데요.** 버전 업그레이드 때 옵션 목록을 다시 확인해야 합니다.

## 정리

돌아보면 세 가지가 남았는데요.

**옵션 이름을 믿지 않는 것.** `sendDefaultPii: false`는 이름이 약속하는 걸 하지 않았습니다. 민감한 데이터를 다룰 때는 옵션을 켜고 끄는 것으로 끝내지 말고, 실제로 나간 이벤트를 열어서 확인해야 하는데요. 저는 배포하고 나서야 열어봤습니다.

**기본값이 안전한 쪽인지 확인하는 것.** `dataCollection`처럼 객체를 넘기는 순간 기준값이 뒤집히는 API가 있습니다. 명시적 옵트인처럼 생겼는데 실제로는 명시적 옵트아웃이었던 거죠.

**수집 정책은 붙이기 전에 정할 수 없다는 것.** 레벨을 어떻게 가를지, 무엇을 잡음으로 볼지는 이슈 목록을 며칠 들여다보고 나서야 판단이 섰습니다. 정책은 한 번에 세우는 게 아니라 며칠에 걸쳐 좁혀졌습니다.

그리고 왜 그렇게 하지 **않았는지**를 주석에 남기는 게 생각보다 중요했는데요. 위치 조회 실패를 `ignoreErrors`가 아니라 `beforeSend`에서 거른 이유 같은 건, 적어두지 않으면 나중에 누군가 "이건 무시 목록에 넣으면 되는데" 하고 옮깁니다. 그러면 `Error`가 아닌 모든 예외가 조용히 사라지고요.
