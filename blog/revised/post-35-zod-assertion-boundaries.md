# 타입 단언을 걷어내다 정산 월별표를 깨뜨리고 다시 세운 기준

9월 3일, 운영 도구 모노레포에서 타입 단언을 걷어내는 중이었어요. 표 셀 콜백이 첫 인자를 넓은 타입으로 주길래 두 번째 인자인 행 전체를 읽도록 바꿨는데요. 그러면서 `d || 'INACTIVE'` 같은 폴백 한 줄이 필요 없어 보여 같이 지웠어요. 정산 월별표의 입금상태 칸이 죽었어요. 서버가 모르는 값을 하나 내려주면 `config`가 `undefined`가 되는데, 바로 다음 줄에서 `config.next`를 읽고 있었거든요.

그날 되돌리는 커밋에 이렇게 적었어요.

> 응답 파서(parseApiResponse)는 스키마 불일치를 로그만 남기고 원본을 통과시키므로, 타입이 좁다고 런타임 값까지 좁은 건 아니다.

<div class="note note-summary">
  <strong>이 글에서 다루는 것</strong>
  <p>타입 단언을 Zod로 일괄 치환하지 않고 값의 출처로 갈라 처리한 기준을 다뤄요. 폴백을 지웠다가 낸 회귀에서 시작해, 같은 날 `.parse`를 넣었다 되돌린 일과 `consistent-type-assertions`를 켰다 뺀 일, 그리고 응답 관측 로그가 실제 스키마 수정으로 돌아온 흐름까지 적었어요. 운영 도구 모노레포와 소비자용 앱 두 저장소 사례를 섞어 쓰고, 나올 때마다 어느 쪽인지 밝혀요. 코드 블록은 운영 도구 `zod ^4.4.3`, 소비자용 앱 `zod ^3.24.4` 기준이에요.</p>
</div>

## 타입이 좁다고 런타임 값까지 좁지는 않았어요

작업을 시작할 때 세운 규칙은 단순했어요. `as`가 필요해지는 자리에 Zod 스키마를 두자는 것이었는데요. 코드를 바꾸기 시작하자 절반만 맞는 규칙이었어요.

컴포넌트 안에서 이미 타입이 정해진 값을 라이브러리의 느슨한 콜백 타입 때문에 다시 단언하는 자리가 있었고, API 응답이나 URL처럼 런타임에 무엇이 들어올지 모르는 자리가 있었어요. 앞쪽은 타입의 출처를 바로잡을 문제였고, 뒤쪽은 런타임 검증이 필요한 문제였어요. 둘을 다 Zod로 감싸면 검증만 늘어요.

```tsx
// 느슨한 셀 값을 다시 단언하는 대신, 행 전체가 이미 들고 있는 타입을 읽어요.
render: (_, record) => STATUS_LABEL[record.status] ?? '-'
```

문제는 여기서 `record.status`의 타입이 좁아 보이는 근거였어요. 운영 도구의 응답 파서는 스키마가 어긋나도 로그만 남기고 원본을 그대로 통과시켜요. 그러니 화면까지 도달하는 값은 스키마가 말하는 enum 바깥일 수 있어요. 타입 흐름을 고치는 작업과 방어 폴백을 지우는 작업은 별개였는데 한 커밋에서 같이 해버린 셈이에요.

전체 diff를 다시 훑어 "제거된 줄 중 폴백을 담은 것"을 대조했더니 두 곳이 나왔어요. 하나는 위의 정산 월별표, 다른 하나는 전체 시술내역의 상태 칸에서 `?? '-'`가 빠져 모르는 값이면 빈 칸이 되던 자리였고요.

<div class="note note-decision">
  <strong>최종 결정</strong>
  <p>단언이 보이면 값의 출처부터 찾아요. 코드 안에서 이미 검증된 값이면 타입 흐름을 고치고, 애플리케이션 밖에서 들어온 값이면 런타임 경계를 세워요. 다만 응답 경계가 관측형인 동안에는 타입 흐름을 고치더라도 렌더에 있던 런타임 폴백은 지우지 않아요. 파서가 원본을 통과시키는 이상, 좁은 타입은 약속이지 보장이 아니니까요.</p>
</div>

## 단언 216건 중 138건을 걷어내다 버그 4건이 나왔어요

9월 3일 운영 도구의 단언 정리 커밋 한 건 기준으로 프로덕션 non-null 단언 27건을 전부, 타입 단언 216건 중 138건을 없앴어요. 바꾼 방식은 네 갈래였어요. 라이브러리 제네릭을 제대로 쓰기(`UploadFile<T>`, `axios.get<Blob>`, `querySelector<HTMLElement>`), 느슨한 문자열을 enum 목록으로 좁히기, 폼에서 서버 payload로 가는 변환에 제출 스키마 두기, 배열은 `flatMap`과 조건부 spread로 추론시키기예요. 명시적 `any`도 0이 됐는데, 에디터 래퍼 8건은 라이브러리가 이미 내보내던 타입으로 대체했어요.

단언을 걷는 동안 그 단언이 가리고 있던 버그 4건도 같이 나왔어요.

- 검색 필터의 배타 체크박스가 동작하지 않았어요. 위젯이 `onChange` 안에서 쓴 값을 폼 아이템이 곧바로 덮고 있었어요.
- 주간 휴무를 해제하면 그날 항목이 payload 안으로 한 겹 더 들어갔어요. `Object.entries`의 값이 항목 전체인 걸 놓친 자리였고요.
- 썸네일을 지울 때 보내는 `null`이 타입에서 보이지 않았어요. 업로드 타입의 `any` 때문이었어요.
- 이미지 업로드 API 라우트가 `type`과 `file`을 검증 없이 받고 있었어요. enum과 `instanceof File`로 걸러 400을 주도록 바꿨어요.

같은 날 뒤이은 커밋에서 35건을 더 걷어 107건에서 72건이 됐는데요. 이 수치는 앞의 216건과 집계 범위가 달라요(뒤쪽은 그 시점에 남아 있던 `as` 단언만 센 값이에요). 두 숫자를 이어 붙이면 안 되는 이유를 커밋에도 적어 뒀어요.

## `.parse`를 넣었다가 같은 날 되돌렸어요

폼에서 서버 payload로 가는 변환에 제출 스키마를 두는 건 잘 맞았어요. 그래서 같은 방식을 몇 군데 더 밀어 넣었는데, 리뷰에서 두 자리가 걸렸어요.

첫째는 검사 요청의 라벨 제출 스키마였어요. 요청 DTO는 `type`이 필수인데 라벨 선택 UI는 `type` 없이도 값을 만들 수 있었어요. 스키마를 넣자 기존 테스트가 깨졌고요. 검사 상태 쪽은 두 호출부가 이미 좁힌 값을 들고 있어서, 파라미터로 받도록 바꿔 파싱 자체를 없앴어요.

둘째가 더 중요했어요. FAQ와 검색 키워드 화면에서는 `.parse`가 던지는 예외를 받을 곳이 없었어요. 그 자리를 감싸는 Drawer의 `catch {}`가 예외를 삼켜서, 검증 실패가 사용자에게는 "아무 일도 안 일어남"으로 보였어요. 무음 실패는 단언보다 나쁘죠. 캐스트로 되돌렸어요.

여기서 배운 건 `parse`와 `safeParse`의 선택이 스키마의 문제가 아니라는 거예요.

> 던져도 되는 자리는 실패 경로가 이미 정의된 자리예요. 그걸 확인하지 않고 `parse`를 넣으면 검증을 추가한 게 아니라 실패를 숨긴 거예요.

## 같은 토큰인데 한쪽은 `parse`, 한쪽은 `safeParse`였어요

`jwtDecode<Claims>(token)`의 `Claims`는 검증이 아니라 단언이에요. 디코딩 결과를 그대로 돌려주니 클레임이 그 모양인지는 아무도 확인하지 않아요. 두 저장소 다 이 자리를 고쳤는데 결론이 갈렸어요.

운영 도구에서는 `parse`를 `try/catch`로 감쌌어요. 실패하면 권한 없음으로 떨어뜨리면 되는, 실패 경로가 이미 있는 자리였거든요.

```ts
const claimsSchema = z.object({ role: z.enum(ROLES) });

try {
  const { role } = claimsSchema.parse(jwtDecode(token));
  return ALLOWED_ROLES.includes(role);
} catch {
  return false;
}
```

`z.enum(ROLES)`에 enum 객체를 그대로 넣는 건 zod 4에서만 되는 표기예요. zod 3을 쓰는 소비자용 앱에서는 `z.nativeEnum(ROLES)`이 필요해요.

소비자용 앱은 반대로 갔어요. 형태가 깨진 토큰에서 던지면 그 예외가 프록시 바깥 `catch`로 가는데, 거기가 사용자를 즉시 로그아웃시키는 자리였어요. 그래서 함수마다 자기가 읽는 클레임만 담은 좁은 스키마로 `safeParse`하고, 실패는 `false`나 `null`로 돌려줬어요. 스키마를 하나로 합치지 않은 이유도 같아요. 어느 한 함수에만 필요한 클레임이 빠진 토큰까지 인증 판정에서 탈락하면 그건 곧 쿠키 삭제니까요.

순서도 이 작업의 핵심이었어요. 먼저 앞 커밋에서 현재 판정을 계약 테스트 25건으로 고정하고, 그다음 구현을 `safeParse`로 바꿔 25건이 그대로 통과하는지 봤어요. 스키마를 관대하게 잡아야 했던 자리도 그 과정에서 드러났어요. `exp`는 기존 코드의 `exp * 1000`이 하던 JS 강제변환을 그대로 옮기려고 `z.coerce.number()`로 뒀고, 로그인 종류는 타입에 적힌 멤버가 4개인데 실제 종류는 8개여서 `z.string().optional()`로 열어 뒀어요. enum으로 잠갔다면 빠져 있던 4종으로 로그인한 사용자가 전부 판정에서 탈락할 뻔했어요.

남긴 버그도 그때 적어 뒀어요. `exp`를 숫자로 읽지 못하는 토큰이 "만료 아님"으로 남는 문제였는데, 실토큰 payload를 확인하기 전에는 그 인구 규모를 알 수 없어 미뤘어요. 이후 커밋에서 판정을 뒤집었고, 옛 정의로 되돌려 새 테스트가 실제로 실패하는지도 확인했어요. "`parse`로 강하게 막는다"가 항상 옳지는 않다는 사례로 남았어요.

## `consistent-type-assertions`도 켰다가 뺐어요

단언을 걷어냈으니 다시 들어오는 것도 막고 싶었어요. 그래서 lint에 `consistent-type-assertions`를 `assertionStyle: 'as'`로 켰는데, 같은 날 뺐어요. 이 규칙은 꺾쇠 문법을 막을 뿐 `as` 재유입은 전혀 못 막아요. 게다가 꺾쇠 단언은 `.tsx`에서 문법상 쓸 수도 없어서 실효가 거의 없었어요.

재유입을 실제로 막으려면 타입 정보를 읽는 규칙이 필요한데, 그건 별도 판단으로 남겼어요. 규칙을 켜는 일과 규칙이 목표를 달성하는 일은 다르다는 걸, 규칙 이름만 보고 켰다가 확인한 셈이에요.

## 응답 경계는 아직 막지 않고 관측만 해요

API 응답에 스키마를 씌우는 작업은 이 정리보다 3주쯤 앞선 8월에 했고, 화면 장애 범위를 줄이는 이야기와 함께 [별도 글](https://jingeon27.tistory.com/27)에 적었어요. 여기서는 그 경계가 이번 판단에 어떤 제약을 걸었는지만 짚을게요. 이미 돌아가는 화면에 뒤늦게 스키마를 씌우는 마이그레이션이라, 파싱 결과로 갈아끼우면 스키마에 아직 적지 않은 필드가 조용히 사라져요(zod는 3·4 모두 객체의 미선언 키를 기본으로 버려요). 그래서 검증만 하고 원본을 돌려줘요.

2026-09-07 develop 기준으로 운영 도구는 `*.api.ts` 75개 파일에서 `parseApiResponse(`를 264곳, 소비자용 앱은 32개 파일에서 86곳 호출해요(테스트·목·정의 파일은 뺀 수치예요).

```ts
/** schema 는 TData 와 정확히 일치할 필요가 없어요 — 선택 필드를 열어 둔 "검증용 근사치"예요. */
export function parseApiResponse<TData>(schema: z.ZodType, response: AxiosResponse<TData>): TData {
  const result = schema.safeParse(response.data);

  if (!result.success) {
    reportOnce({
      code: 'RESPONSE_SCHEMA_MISMATCH',
      url: describeRequest(response), // axios config 의 메서드 + 경로
      path: getCurrentPath(),
      issues: toSchemaIssues(result.error).slice(0, MAX_LOGGED_ISSUES), // 앞쪽 20개
    });
  }

  return response.data;
}
```

호출부가 요청 이름을 문자열로 다시 적지 않아요. 손으로 적으면 엔드포인트가 바뀔 때 로그만 옛 값으로 남거든요. 이슈는 앞쪽 20개까지만 실어요. 목록 하나가 통째로 어긋나면 이슈가 수백 개 나오는데, 로그 한 건이 그만큼 커질 이유는 없었어요.

중복 억제는 두 저장소가 달라요. 운영 도구는 같은 불일치를 브라우저 세션당 한 번만 보내요(모듈 스코프의 `Set`). 서버 렌더링이 도는 소비자용 앱에서는 이 방식이 처음에 문제였어요. Node 프로세스가 다음 배포까지 살아 있으니 불일치가 배포 직후 첫 요청에만 찍히고, 그 뒤로는 고쳤는지조차 알 수 없었거든요. 8월 12일에 영구 `Set`을 한 시간 간격으로 바꿔 다시 열어 뒀어요.

## 로그에서 실제로 찾은 건 세 가지였어요

관측형 검증은 로그를 보는 사람이 없으면 단언과 크게 다르지 않아요. 그래서 불일치 로그를 수정 절차의 입력으로 연결했어요.

```text
SCHEMA_MISMATCH 로그
  → 요청 경로와 앱으로 호출부·스키마 특정
  → OpenAPI 계약과 실제 응답 대조
  → 프론트 스키마 오류 / 서버 스펙 위반 / 판단 불가로 분류
  → 프론트 오류만 스키마와 파생 타입 수정
  → 계약 테스트와 뮤테이션 체크
  → 리뷰·검증 후 PR 반영
```

중단 조건을 먼저 정했어요. 로그를 없애는 게 목표가 아니에요. 실제 응답이 OpenAPI와 다르면 프론트 스키마에 `.nullish()`를 붙여 조용히 통과시키지 않고, 서버 스펙 위반으로 분류한 뒤 프론트 수정은 멈춰요.

이 흐름으로 8월 19일부터 9월 7일까지 세 종류를 찾았어요.

- 페이징 봉투가 없는 목록 응답. 기존 단일 봉투 스키마가 이걸 불일치로 잘못 판정하고 있었어요. 8월 31일에는 가족 목록 49건이 같은 이유로 찍혔고요.
- 취소 응답이 배열이 아니라 한 건. 목록으로 알고 있던 자리였어요.
- 검색 제안 항목이 두 형태. dev 표본 2,292건을 대조해 `discriminatedUnion`으로 모델링했어요.

응답 수준에서 `anyOf`로 갈리는 사례는 아직 만나지 못했어요. 그런 응답을 만나면 한쪽만 알고 있는 상태로 두지 않고 유니언으로 모델링한 뒤 양쪽 계약 테스트를 붙인다는 규칙만 절차에 적어 뒀어요.

## URL은 필드마다 따로 복구해요

URL은 실패 조건이 응답과 달라요. 사용자가 직접 고칠 수 있고 예전에 공유한 링크로도 들어와요. 검색 조건 하나가 잘못됐다고 화면 전체를 오류로 보내면 사용자는 이유를 알 수 없죠. 처음에는 객체 전체를 한 번 `safeParse`하고 실패하면 기본 조회 조건으로 떨어뜨렸는데, `status` 하나 때문에 정상적인 검색어와 페이지, 상세 드로어의 `id`까지 같이 사라졌어요.

그래서 독립적으로 복구할 수 있는 필드는 필드마다 fallback을 갖게 했어요. 다음은 운영 도구의 조회 조건 스키마예요.

```ts
const searchParamsSchema = z.object({
  pageNumber: z.coerce.number().int().positive().catch(1),
  status: z.enum(STATUSES).optional().catch(undefined),
  keyword: z.string().optional().catch(undefined),
  id: z.coerce.number().optional().catch(undefined),
});

const params = useTypedQueryParams({ schema: searchParamsSchema });
```

관측상의 비용이 하나 붙어요. 객체 전체의 `safeParse`가 실패하면 불일치 로그가 남지만, 필드에 붙인 `.catch`가 값을 복구하면 객체 파싱은 성공으로 끝나서 로그가 남지 않아요. 오래된 링크로 오류를 계속 쌓지 않는 대신 잘못된 값의 유입 빈도를 알 수 없어요. 반드시 추적해야 하는 파라미터에는 `.catch`를 쓰지 않고 객체 경계에서 실패를 기록해야 해요.

현재 URL을 다시 조립해 공유 링크나 필터 이동에 쓰는 화면은 저장소마다 다르게 풀었어요. 소비자용 앱은 `.passthrough()`를 명시해 그 화면의 스키마가 소유하지 않는 파라미터를 지우지 않도록 했고, 2026-09-07 develop 기준 `src`에 10곳 있어요(zod 3 기준 표기고, zod 4에서는 `z.looseObject`예요). 운영 도구에는 `.passthrough()`가 0건인데, 대신 URL을 재조립만 하는 자리에서는 스키마를 거치지 않고 `useSearchParams()` 문자열을 그대로 병합해요. 조립에 스키마가 필요 없다면 통과 옵션도 필요 없으니까요.

## 폼은 제출을 막고, 검색 폼은 필드명을 막아요

폼은 사용자가 값을 직접 고칠 수 있는 자리예요. 그러니 원본을 통과시키거나 기본값으로 바꾸지 않고, 해당 필드에 이유를 보여주며 제출을 막아요. 소비자용 앱의 입력 폼은 React Hook Form과 `zodResolver`를 공용 훅으로 묶었어요.

```ts
function useSchemaForm<T extends ZodRawShape>({ schema, ...options }: Options<T>) {
  return useForm<z.infer<ZodObject<T>>>({
    ...options,
    resolver: zodResolver(schema),
  });
}
```

실제 시그니처는 `ZodObject<T> | ZodEffects<ZodObject<T>>`만 받아요. 객체 스키마 한정이라는 제약이 붙어 있고, 위 코드는 그 부분을 줄여 쓴 거예요. 단계가 이어지는 폼은 단계별 스키마로 나눴어요. 아직 입력하지 않은 다음 단계의 필드 때문에 현재 단계가 막히지 않게 하려고요.

운영 도구의 검색 폼은 성격이 달라요. 제출 검증 전체를 Zod로 바꾼 게 아니라 `createSearchFilter(schema)`가 `z.infer`로 필드명을 좁히고, URL을 읽을 때 같은 스키마를 써요. 잘못된 필드명은 컴파일 단계에서 막고 외부에서 들어온 값은 런타임에서 복구하는 구조인데요. 같은 "폼"이라도 실제 경계가 사용자 입력인지 URL인지에 따라 Zod의 자리가 달랐어요.

## `x is T` 술어는 검증한 쪽에서 받아왔어요

8월 27일에는 사용자 정의 타입 가드를 정리했어요. `x is T`는 컴파일러가 확인하지 않는 단언이라, 본문이 무엇을 하든 TS는 술어를 그대로 믿어요.

```ts
function isCompletedPayment(value: unknown): value is CompletedPayment {
  return value != null;
}
```

호출부가 `boolean`만 쓰던 결제 헬퍼 넷은 반환 타입을 `boolean`으로 내리고, 조건은 스키마로 옮겼어요. 상태와 수단의 조합이 한자리에 모이니 조건식을 읽기도 편해졌고요.

```ts
const completedPaymentSchema = z.object({
  method: z.literal('NORMAL'),
  status: z.literal('COMPLETED'),
});

const isCompletedPayment = (value: unknown): boolean => completedPaymentSchema.safeParse(value).success;
```

좁히기가 실제로 필요했던 자리는 술어를 다시 선언하는 대신 검증 결과를 그대로 썼어요. 상담과 예약을 함께 그리는 Select가 그랬어요.

```tsx
const consultation = consultationOnlyStatusSchema.safeParse(status);

// safeParse 는 성공 브랜치만 좁혀요. 예약 쪽은 갈라진 뒤라 parse 로 받아요.
return consultation.success ? (
  <ConsultationStatusSelect status={consultation.data} />
) : (
  <ReservationStatusSelect status={reservationStatusSchema.parse(status)} />
);
```

유니언 판별 두 곳은 오히려 네이티브 `in`으로 되돌렸어요. TS 5.5부터는 술어를 추론해 줘서 캐스트 없이도 `filter` 결과 타입이 갈리거든요. UI 라이브러리가 문자열로 돌려주는 탭·정렬 키처럼 모르는 값은 무시해도 되는 자리에는 `z.enum(...).optional().catch(undefined)`를 썼고요.

술어를 전부 없애지는 못했어요. 소비자용 앱에는 `isHumanTicket`·`isStarRating`·`isValidInflowChannel` 세 건이 남아 있고, 운영 도구에도 몇 곳 남았어요. 목 쪽은 방향을 조금 바꿨어요. 목 핸들러는 `Partial<T>`를 반환 타입으로 적어 부분 목이라는 사실을 타입에 남기고, 서비스 스텁에는 `satisfies Pick`을 붙였어요.

## 같은 Zod인데 실패 처리는 다섯 갈래였어요

| 경계 | 검증 결과 사용 | 실패 시 처리 | 이유 |
| --- | --- | --- | --- |
| 기존 API 응답 | 원본 유지 | 기록 후 통과 | 검증 도입이 돌아가던 화면을 먼저 깨뜨리지 않게 함 |
| 신규 API·스트림 이벤트 | 파싱 결과 사용 | 요청·이벤트 단위 실패 | 실패 범위를 경계에서 닫을 수 있음 |
| 인증 토큰 | 파싱 결과 사용 | 운영 도구는 throw 후 권한 없음, 소비자용 앱은 `false`/`null` | 던진 예외를 받는 자리가 강제 로그아웃이면 던지면 안 됨 |
| URL 조회 조건 | 파싱 결과 사용 | 필드별 fallback, 마지막에 객체 fallback + 기록 | 오래된 링크 때문에 정상 조건까지 잃지 않게 함 |
| 사용자 입력 폼 | 파싱 결과 사용 | 제출 차단 + 필드 안내 | 사용자가 직접 고칠 수 있음 |

검증 도구를 통일했다고 실패 동작까지 통일하지는 않았어요. "스키마가 어긋났다"는 사실과 "화면을 멈춰야 한다"는 결정은 서로 다른 문제였으니까요.

## 테스트는 성공 경로가 아니라 실패 정책을 고정했어요

스키마가 정상 값을 받는 테스트만으로는 이 구조의 목적을 확인할 수 없어요. 그래서 각 경계가 실패했을 때 무엇을 해야 하는지에 테스트를 붙였어요.

- 응답이 어긋나도 원본 객체와 미선언 필드가 유지되는가
- 로그가 호출부의 문자열이 아니라 실제 요청 메서드·경로를 담는가
- 서버가 모르는 enum을 추가하면 정확한 필드 경로가 기록되는가
- 페이징 봉투가 없는 목록과 본문 없는 응답을 정상 계약으로 구분하는가
- URL의 enum 하나가 잘못돼도 검색어·페이지·상세 `id`는 유지되는가
- 형태가 깨진 토큰에서 던지지 않고 `false`/`null`을 돌려주는가
- 폼의 잘못된 값은 제출되지 않고 사용자가 고칠 수 있는 오류로 보이는가

테스트를 새로 붙일 때는 스키마를 옛 정의로 잠시 되돌려 그 테스트가 실제로 실패하는지도 봤어요. 토큰 판정을 뒤집은 커밋을 포함해 세 건에서 이 확인을 했어요. 목 픽스처가 스키마와 함께 잘못 바뀌면 테스트는 계속 통과하니까요.

## 다음 작업에 남긴 기준

lint에는 `no-explicit-any`와 `no-non-null-assertion`을 error로 올렸어요(테스트 파일은 off). 반면 `consistent-type-assertions`는 앞서 적은 이유로 뺐고, `as` 재유입을 실제로 잡는 `no-unnecessary-type-assertion` 계열은 아직 켜지 않았어요. 타입 정보를 읽는 lint를 켜 보니 게이트 시간이 3.3배, 피크 메모리가 1.4GB까지 올라가서, 이 비용을 감당할 방법을 정하기 전에는 규칙을 켜지 않기로 했어요.

절차에는 세 가지를 남겼어요. 첫째, 단언을 걷는 커밋에서는 diff의 삭제된 줄 중 폴백을 담은 것을 따로 훑어요. 이번 회귀가 거기서 나왔거든요. 둘째, `.parse`를 넣기 전에 그 예외를 받는 자리가 어디인지 먼저 확인해요. 셋째, 스키마를 바꾸는 PR은 계약 테스트를 먼저 고정하고 구현을 바꿔요.

결국 이 작업의 기준은 "타입 단언을 Zod로 바꾼다"가 아니었어요. 값이 어디에서 왔고, 검증 실패가 누구에게 어떤 피해를 주며, 그 실패를 어느 단위에서 복구할 수 있는지를 먼저 정하는 일이었어요. 스키마는 그 결정을 실행하는 도구였고요.
