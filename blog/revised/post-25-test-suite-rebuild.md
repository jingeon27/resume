입사 초기에 두 저장소의 Vitest 테스트 파일 23개를 모두 지웠습니다. 테스트가 싫어서가 아니었는데요. 사라진 화면을 계속 가리키는 테스트, 실제 서버와 다른 Mock, 기능을 검증하지 않는 예제가 섞여 있어 테스트 성공 결과를 신뢰하기 어려웠습니다.

몇 달 뒤에는 반대로 테스트를 다시 도입했습니다. 관리자 모노레포에서는 첫 19일 동안 102개 테스트 파일을 만들었고, 이후 기능 개발과 회귀 대응 과정에서 계속 늘렸습니다. 2026년 8월 30일 기준으로는 다음과 같이 운영하고 있습니다.

- 관리자 모노레포: 일반 단위·통합 테스트 181개, 실서버 `live` 테스트 23개, Playwright E2E 7개
- 사용자몰: Vitest 단위·컴포넌트 테스트 69개, Playwright E2E 9개

테스트 파일 수만 보면 처음의 선택과 모순돼 보입니다. 달라진 것은 테스트에 대한 태도가 아니라 “테스트 성공이 무엇을 보장하는가”를 구분하는 기준이었습니다.

먼저 선을 그을 부분도 있습니다. 이 테스트가 모두 PR 병합을 자동으로 막는 것은 아닙니다. 현재 PR의 기본 게이트는 lint와 typecheck이고, 테스트는 변경 범위와 위험에 따라 별도로 실행하고 있는데요. 테스트의 개수, 실행 환경, 자동화 범위를 같은 성과처럼 묶지 않으려고 합니다.

## 테스트를 소스 옆에 뒀습니다

지웠던 테스트는 별도 디렉터리에 모여 있었습니다.

```text
src/
__tests__/
  pages/
  hooks/
  mocks/
```

도메인 코드를 옮겨도 테스트는 따라오지 않았습니다. 오래된 화면의 테스트는 남고 새 화면에는 테스트가 없었는데요. 다시 도입할 때는 대상 파일 옆에 두는 것을 기본 규칙으로 정했습니다.

```text
program-form.tsx
program-form.test.tsx
```

파일을 이동하거나 삭제하면 테스트도 같은 diff에서 눈에 띕니다. 책임을 다른 컴포넌트나 라우트로 옮겼다면 테스트도 그 자리로 함께 옮겼는데요. 실제로 목록 View의 책임을 `page.tsx`로 옮긴 뒤 기존 테스트가 옛 컴포넌트에 남아 깨진 경험을 이 규칙으로 반영했습니다.

## 테스트 계층마다 확인할 범위를 나눴습니다

처음에는 테스트 종류가 많을수록 안전해진다고 생각하기 쉬웠습니다. 하지만 같은 동작을 여러 계층에서 반복하면 실행 비용만 커지고, 반대로 각 계층의 한계를 모르면 성공 결과를 과신하게 됩니다.

현재는 다음처럼 역할을 나눕니다.

- 단위 테스트는 순수 함수, Zod 스키마, 상태 전이와 경곗값을 확인합니다.
- 컴포넌트·통합 테스트는 실제 UI와 Query, 폼, MSW 계약이 연결되는지를 확인합니다.
- `*.live.test.ts(x)`는 관리자 서비스에서 Mock과 실제 개발 서버의 계약이 어긋났는지 확인하는 마지막 수단으로 사용합니다.
- Playwright E2E는 직접 URL 진입, 새로고침, 뒤로 가기, 쿠키와 서버 게이트처럼 브라우저에서만 드러나는 흐름을 맡습니다.

서버 컴포넌트나 Provider가 많이 필요한 화면을 억지로 jsdom에 올리지는 않습니다. 컴포넌트 안의 계산을 순수 함수로 분리해 단위 테스트하거나, 실제 브라우저가 필요한 문제라면 E2E로 옮겼습니다.

## 첫 통합 테스트는 제품 코드를 검증하지 않았습니다

초기 통합 테스트에서는 폼을 감싼 `FormHarness`가 제출 순서를 대신 실행했습니다.

```tsx
function FormHarness() {
  const form = useForm();

  const submit = () => {
    const values = form.getValues();
    return api.create(toRequest(values));
  };

  return <ProgramForm form={form} onSubmit={submit} />;
}
```

보기에는 편했지만 테스트가 프로덕션의 제출 로직을 복제하고 있었습니다. 실제 컴포넌트의 `onSubmit`이 깨져도 Harness만 맞으면 테스트가 통과했는데요. 만든 다음 날 이런 Harness 네 개를 모두 지우고 실제 컨테이너를 렌더하도록 바꿨습니다.

테스트 코드의 중복보다 더 위험한 것은 테스트가 제품의 결정을 대신하는 경우였습니다. Provider나 라우터처럼 화면을 준비하는 코드는 공통화할 수 있지만, 무엇을 언제 서버로 보낼지는 실제 제품 코드만 소유하게 했습니다.

## 무엇이든 받아주는 Mock을 서버 계약으로 착각했습니다

통합 테스트는 통과하는데 실제 개발 서버에서는 등록이 400으로 실패하는 일이 반복됐습니다. MSW handler가 요청 본문을 검증하지 않고 그대로 저장했기 때문인데요. Mock 시드의 분류·언어·지역 코드도 실제 서버의 초기 데이터와 달라, Mock에만 존재하는 탭을 E2E가 정상 기능으로 단언하기도 했습니다.

그래서 백엔드 DTO와 validation에서 확인한 규칙만 Mock에 옮겼습니다.

```ts
const createProgramRequestSchema = z.object({
  name: z.string().trim().min(1),
  locale: z.enum(['ko', 'en', 'ar']),
  hospitalId: z.number().int().positive(),
});

http.post('/programs', async ({ request }) => {
  const result = createProgramRequestSchema.safeParse(await request.json());

  if (!result.success) {
    return HttpResponse.json(toValidationError(result.error), { status: 400 });
  }

  return HttpResponse.json(programStore.create(result.data));
});
```

등록되지 않은 요청은 `onUnhandledRequest: 'error'`로 실패하게 했습니다. 화면을 열었을 때 자식 컴포넌트가 새 API를 호출해도 handler가 없으면 테스트가 멈추는데요. Mock을 편의를 위한 가짜 백엔드가 아니라, 프론트엔드가 현재 이해한 서버 계약을 명시하는 계층으로 사용했습니다.

그래도 Mock이 실제 계약의 정본은 아닙니다. 실제 개발 서버에서 새로운 제약을 발견하면 Zod 스키마와 Mock handler, 통합 테스트에 다시 반영해 다음 작업부터 로컬에서 먼저 실패하게 했습니다.

## 실제 개발 서버를 우선하고 Mock은 만들기 어려운 상태에 사용했습니다

기능을 실제 개발 서버에서 확인할 수 있다면 그 환경을 먼저 사용합니다. API 계약과 데이터가 실제로 연결된 상태에서 확인할 수 있기 때문인데요. Mock은 로그인 단계, 특정 오류 응답, 빈 목록처럼 실서버에서 안전하고 반복적으로 만들기 어려운 조건을 고정할 때 사용했습니다.

사용자몰의 회원가입 E2E도 모든 요청을 Mock으로 바꾸지 않았습니다. 사용자 상태와 인증 흐름처럼 테스트가 직접 제어해야 하는 요청만 MSW가 처리하고, 나머지 요청은 개발 서버로 보냈습니다.

관리자 모노레포에서는 실서버 검증이 필요한 테스트를 일반 Vitest 실행과 분리해 `*.live.test.ts(x)`와 별도 설정으로 운영합니다. 일반 테스트에서 MSW가 켜진 채로 live 테스트가 실행되면 실제 서버를 검증했다고 착각할 수 있기 때문인데요. 실서버는 계정과 데이터를 공유하므로 파일을 직렬로 실행하고, 다른 사람의 데이터를 임의로 수정하는 흐름은 자동화하지 않았습니다.

live 테스트에서 계약 차이를 발견했다고 live 테스트만 늘리지도 않습니다. 확인한 제약은 다시 로컬 Mock과 기존 테스트로 되돌립니다. 실서버 테스트는 계약 차이를 발견하는 보조 장치이지, 가장 많은 시나리오를 실행하는 계층이 아닙니다.

## 새 테스트가 실제로 실패하는지 확인했습니다

테스트를 다시 도입한 초기에는 새로 보호한 경로의 제품 코드를 일부러 잘못 바꿔 봤습니다.

```ts
// 정상
const finalAmount = paymentAmount - couponDiscount;

// 테스트 확인을 위해 잠시 변경
const finalAmount = paymentAmount + couponDiscount;
```

새 테스트가 실패하는지 확인한 뒤 제품 코드를 되돌렸습니다. 자동 mutation testing을 구축한 것은 아니고 모든 테스트에 적용했다고 말할 수도 없는데요. 적어도 새로운 패턴을 만들 때는 “테스트를 추가했다”와 “그 테스트가 회귀를 잡는 것을 확인했다”를 구분했습니다.

리팩터링에서는 순서도 중요했습니다. 먼저 현재 동작을 테스트로 고정하고 구조를 바꿨습니다. 구현을 바꾼 뒤 테스트를 작성하면 새 동작을 그대로 정답으로 만들 수 있기 때문입니다.

## E2E는 브라우저에서만 보이는 경계에 뒀습니다

회원가입 퍼널은 URL 직접 진입, 새로고침, 뒤로 가기와 인증 상태가 함께 움직였습니다. 함수 테스트만으로는 이 조합을 확인하기 어려웠는데요. 순서대로 가입하는 흐름뿐 아니라 중간 URL로 바로 들어가거나, 로그아웃한 뒤 다시 접근하거나, 팝업이 차단된 조건을 Playwright로 확인했습니다.

URL만 맞다고 성공으로 보지도 않았습니다.

```ts
await page.goto('/terms');

await expect(page).toHaveURL(/\/sign$/);
await expect(page.getByRole('button', { name: '카카오로 계속하기' })).toBeVisible();
```

리다이렉트 목적지와 실제 화면을 함께 확인해야 가드가 사라졌을 때 테스트가 실패합니다. E2E의 가치는 브라우저를 띄웠다는 데 있지 않고, 사용자가 실제로 보게 되는 결과를 단언하는 데 있었습니다.

실행 환경도 하나로 고정하지 않았습니다. 사용자몰 E2E는 기본적으로 Next 개발 서버를 띄우고, 테스트가 제어해야 하는 요청은 MSW로 고정하며 나머지는 개발 API로 보냅니다. Next.js Router Cache처럼 프로덕션 빌드에서만 발생하는 문제는 별도의 빌드 실행 경로로 확인했는데요. 개발 서버의 온디맨드 컴파일과 실제 API CORS 조건도 제품 환경의 일부이므로, 빠르다는 이유만으로 모든 E2E를 프로덕션 빌드로 바꾸지는 않았습니다.

## 테스트에서는 핵심 행동이 보이도록 반복을 남겼습니다

제품 코드에서는 공통화를 자주 검토하지만 테스트에서는 시나리오를 한눈에 읽는 쪽을 우선합니다.

```ts
it('쿠폰 필터를 누르면 URL에 couponDiscount=true가 남아야 한다', async () => {
  renderSearchPage();

  await user.click(screen.getByRole('button', { name: '쿠폰 추가 할인' }));

  expect(window.location.search).toContain('couponDiscount=true');
});
```

클릭과 URL 검증이 다른 테스트에도 반복되더라도 핵심 행동을 `expectFilterScenario()` 같은 범용 헬퍼 안에 숨기지 않았습니다. 로그인이나 Provider처럼 이 테스트의 관심사가 아닌 준비만 감췄는데요. 테스트 이름과 본문에서 입력, 행동과 기대 결과를 바로 읽을 수 있어야 AI가 보고한 `성공`의 의미도 빠르게 확인할 수 있었습니다.

테스트 도입 초기에는 AI가 작성한 테스트 코드도 모두 읽었습니다. 제품 코드를 복제한 Harness, 항상 통과하는 단언, 실서버와 다른 Mock이 섞이면 테스트 성공이 오히려 잘못된 확신을 만들기 때문인데요. 작성 방식과 계층이 안정된 뒤에는 plan의 성공 조건, 실행한 테스트와 실패 원인을 중심으로 검토 범위를 바꿨습니다.

## 병렬 작업에서는 전체 테스트를 매번 실행하지 않았습니다

여러 worktree에서 전체 lint, typecheck와 테스트를 동시에 실행하면 CPU 경합이 크게 발생했습니다. 관리자 모노레포에서는 한 번의 전체 lint가 여러 패키지를 함께 검사하고, linked worktree마다 Turbo와 TypeScript 캐시가 다시 만들어지는데요. 실제로 여러 검증이 겹치면서 프로세스가 강제 종료돼 통과와 실패조차 판정할 수 없는 상황이 있었습니다.

그래서 개별 작업에서는 변경한 파일과 관련된 테스트를 먼저 실행했습니다. 관리자 모노레포에서 전체 검증이 필요하면 캐시가 유지되는 메인 워킹트리에 작업 브랜치를 임시로 합쳐 실행한 뒤 되돌렸고, 전체 테스트는 패키지 간 동시 실행을 제한했습니다.

검증 범위를 줄인 이유는 AI 코드를 신뢰해서가 아니라 같은 검사를 여러 세션이 중복 실행하지 않기 위해서였습니다. 이 실행 전략과 테스트가 보장하는 범위는 별개의 문제로 관리했습니다.

## 지금 테스트가 통과한다는 말의 범위

- 단위 테스트 통과는 변환, 상태 전이와 도메인 경곗값이 유지됐다는 뜻입니다.
- MSW 통합 테스트 통과는 실제 컴포넌트와 프론트가 현재 이해한 계약이 연결됐다는 뜻입니다.
- live 테스트 통과는 자동으로 만들고 정리할 수 있는 범위에서 실제 개발 서버와 계약이 맞았다는 뜻입니다.
- E2E 통과는 선택한 브라우저 흐름에서 사용자에게 보이는 결과가 유지됐다는 뜻입니다.

이 네 종류가 있다고 제품 전체가 검증되는 것은 아닙니다. 사용자 데이터가 필요한 흐름, 브라우저에서 직접 확인해야 하는 UI, 운영에서만 발생하는 조건은 여전히 남는데요. 테스트가 없는 범위는 없는 그대로 말하고 직접 확인합니다.

AI에게 작업을 맡길 때도 같은 기준을 사용합니다. 성공 조건이 코드로 적힌 구간은 병렬로 맡길 수 있지만, 그 조건 자체가 실제 서버 계약인지 테스트가 복제한 가짜 계약인지는 별도로 확인해야 합니다.

처음 테스트를 지운 이유도, 다시 만든 이유도 같았습니다. 성공하는 테스트의 개수를 늘리는 것보다 그 성공이 무엇을 보장하고 무엇은 보장하지 않는지 설명할 수 있어야 했습니다.
