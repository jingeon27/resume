# 테스트 도입기 — AI 작업의 성공 조건을 코드로 관리하기

> 두 저장소에서 인수한 Vitest 파일 가운데 실제 기능을 검증하던 22개와 기능 검증이 없는 예제 파일 1개를 모두 지웠다. 석 달 뒤에는 19일에 걸쳐 다섯 개의 테스트 계층과 100개가 넘는 파일로 테스트 체계를 다시 세웠다.
> 목표는 커버리지가 아니라 AI에게 맡긴 작업의 성공 조건과 완료 판정을 같은 코드에 두는 것이었다.
> 다만 제출 로직을 테스트가 복제하거나 목 서버가 모든 요청을 받아주면 테스트가 성공해도 실제 동작을 보증하지 않는다.
> 이 글은 콘텐츠 CMS·운영자 앱·고객용 앱과 다국어 서비스의 고객용 프런트엔드·CMS에서 그 구멍을 찾아 막은 기록이다.
> 회사·제품·저장소·계정·도메인은 생략하거나 역할 중심의 가명으로 바꿨다. 내부 경로·API·환경 변수·테스트 전용 식별자도 필요한 범위에서 일반화했으며, 테스트 수와 버전은 실제 값이다.

---

## 0. 배경 — 지웠다가 다시 세운 이유

처음에는 기존 테스트 모음을 유지할 근거를 찾지 못했다. 파일은 별도 테스트 디렉터리(가명 `src/legacy-tests/`)에 모여 있었고, 목 서버의 동작은 실제 서버 계약과 달랐다. 테스트 파일뿐 아니라 의존성, `turbo` 파이프라인, ESLint 예외까지 걷어냈다. 같은 날 고객용 앱 저장소에서도 같은 일을 했다.

석 달 뒤 작업 방식이 바뀌었다. 화면 수정을 문장으로 지시하고 결과를 눈으로 확인하는 대신, 통과해야 할 단언을 먼저 적고 AI에게 구현을 맡겼다. 실행 가능한 성공 조건이 있으면 작업 지시와 완료 판정이 같은 파일에 남고, 여러 작업의 결과를 같은 기준으로 확인할 수 있었다.

다시 세울 때는 테스트 성공이 무엇을 뜻해야 하는지부터 정했다. 실제 컴포넌트가 서버 계약을 지켰다는 뜻이어야 했다. 테스트를 소스 옆으로 옮기고, 제출 절차를 복제한 하네스를 지웠으며, 목 서버는 백엔드 DTO만큼 엄격하게 만들었다. 실서버와의 차이는 별도 실서버 테스트에서 찾았다. 새 단언은 프로덕션 코드를 일부러 깨뜨려 확인했다. 이후의 시행착오는 이 기준을 여러 프런트엔드에 적용한 과정이다.

## 1. 배치 — 테스트를 소스와 함께 움직이게 했다

기존 테스트는 별도 테스트 디렉터리 한 곳에 모여 있었다. 그 안에 목 모듈 디렉터리와 공용 렌더러가 있었고, 테스트는 페이지와 훅 단위였다.

소스와 테스트가 다른 트리에 있어 도메인을 재배치할 때 함께 움직이지 않았다. 남은 테스트는 없어진 화면을 가리키고 새 화면은 검증에서 빠졌다. 다시 세울 때는 경로부터 바꿨다.

```text
gen-1  src/legacy-tests/app/example/ExampleModalForm.spec.tsx
gen-2  src/features/example/ui/ExampleModal.test.tsx
```

별도 테스트 디렉토리를 만들지 않고 소스 파일 옆에 뒀다. 파일 이동과 삭제가 같은 커밋에 드러나게 해 검증 대상을 최신으로 유지했다.

---

## 2. 단위 테스트 — 통합 테스트를 받치는 계약

다시 시작한 첫 커밋은 순수 함수만 다뤘다. 포맷·계산·상태 판별 헬퍼 128개를 테스트했다. 시간에 의존하는 로직은 `TZ=Asia/Seoul`과 `vi.setSystemTime`으로 고정했다.

나흘 뒤에는 다른 관리자 앱까지 MSW와 RTL 통합 테스트 범위를 넓혔다. 이 가운데 세 관리자 앱과 공용 패키지를 둔 모노레포의 파일 분포는 다국어 CMS 43개, 콘텐츠 CMS 19개, 운영자 앱 14개, 공용 패키지 26개다. 파일이 가장 많은 다국어 CMS는 처음부터 통합 테스트 중심으로 구축했다.

헬퍼 테스트는 jsdom이 재현하지 못하는 동작의 계약을 한 단계 아래에서 고정할 때 쓴다. dnd-kit 드래그는 jsdom에 레이아웃이 없어 재현할 수 없다. 대신 "화면 순서 = 페이로드 순서"를 변환 함수에서 검증한다.

## 3. 하네스 — 테스트가 제출 로직을 다시 구현하면 생기는 문제

첫 통합 테스트에는 `FormHarness`라는 가명으로 적은 래퍼를 뒀다. 폼 컴포넌트를 감싸 제출 순서를 재현하고, 목 서버에 도달한 페이로드를 검증하는 구조였다.

다음 날 하네스 네 개를 모두 지웠다. 복제한 제출 로직이 맞으면 프로덕션 컴포넌트의 제출 경로가 깨져도 테스트가 통과했기 때문이다.

```tsx
// 지운 쪽: 제출 순서를 테스트가 다시 구현한다
const FormHarness = () => {
  const [form] = Form.useForm();
  const submitValues = async () => mutate(mapFormToRequest(form.getFieldsValue()));
  return <EntityForm form={form} onFinish={submitValues} />;
};

// 남긴 쪽: 실제로 배포되는 컴포넌트를 그대로 렌더한다
renderAppComponent(<CreateEntityDrawerView open />);
```

판단 기준은 코드 중복보다 테스트가 프로덕션의 결정을 대신하는지였다. 화면을 띄우거나 결과를 조회하는 헬퍼는 준비와 관찰을 맡으므로 묶을 수 있다. 무엇을 언제 보낼지 정하는 코드는 실제 컴포넌트에 남겼다. 준비 코드가 조금 반복돼도 테스트의 흐름을 위에서 아래로 읽을 수 있게 뒀다.

## 4. 목 서버 — 느슨한 응답도 버그를 만든다

초기 목 서버는 요청을 확인하지 않고 무엇이든 200으로 받아줬다.

이 구멍은 실서버를 확인하다가 드러났다. 두 핵심 등록 요청이 실서버에서 계속 400을 받고 있었고, 그동안 통합 테스트는 모두 성공했다. 화면이 서버 계약을 어긴 상태로 검증을 통과하고 있었다.

목 데이터도 서버와 따로 바뀌고 있었다. 목 데이터에 쓰인 분류·카테고리·언어·지역 코드를 실서버의 마이그레이션과 초기 데이터에 맞춰보니 교집합이 0이었다. 실서버에서는 통하지 않는 값인데도 테스트가 통과하고 있었다.

```ts
// 이전: 요청을 보기만 하고 통과시킨다
http.post('/entities', () => HttpResponse.json({ id: 101 }));

// 이후: 백엔드 DTO의 검증 규칙을 옮겨 적는다
http.post('/entities', async ({ request }) => {
  const body = await request.json();
  if (!body.translations?.some((t) => t.language === 'PRIMARY')) {
    return HttpResponse.json({ code: 'REQUIRED_PRIMARY_TRANSLATION' }, { status: 400 });
  }
  return HttpResponse.json({ id: 101 });
});
```

제약은 백엔드 저장소의 DTO와 검증 애노테이션을 읽고 옮겼다. 추측한 제약은 목 서버와 실서버를 다시 갈라놓으므로 넣지 않았다. 이후 목 서버 변경은 테스트 편의가 아니라 서버 계약 변경으로 다뤘다.

## 5. 프로토타입 백엔드 — 서버가 없을 때 목 서버로 흐름을 만든다

다국어 서비스는 프론트엔드와 백엔드 개발을 동시에 시작했다. API 완성을 기다릴 수 없어 실서버에 붙기 전 보름 동안 목 서버를 프로토타입 백엔드로 썼다.

처음 열하루는 API 주소가 없으면 공통 요청 함수(가명 `requestApi()`)가 고정된 성공 응답을 돌려주는 스텁이었다. 실제 응답 스키마와 관계없이 요청이 성공으로 처리됐다. 스펙을 합의한 뒤 이 분기를 걷어내고 시드와 메모리 DB를 넣었다. 예약 생성 후 예약번호로 다시 조회하려면 상태가 필요했다.

앱 코드에는 목 모드 여부를 확인하는 조건문을 두지 않고 네트워크 계층에서만 가로챘다. 앱이 목 서버 사용 여부를 몰랐기 때문에 실서버 연동 때 API 주소만 채우면 됐고, 두 응답은 같은 Zod 검증을 통과했다.

백엔드가 공통 응답 형식을 통일한 날에는 오십 분 뒤 스키마·목 핸들러·쿼리를 같은 계약으로 바꿨다. 아래에서는 이 응답 래퍼를 가명 `ResultEnvelope<T>`로 부른다.

### 5-1. 시드는 데이터로 두고 코드로 조립하지 않는다

시드 JSON은 서버 응답 모양 그대로 두고, 도메인별 목 저장소 파일(가명 `*.mock-store.ts`)은 언어 선택·조회·필터만 맡겼다. 응답 조립 코드를 없애자 세 파일은 각각 103→33줄, 150→63줄, 75→31줄로 줄었고 당시 네 언어의 응답은 유지됐다. 실서버 연결 뒤 버릴 코드가 데이터 내용을 가리지 않게 하려는 선택이었다.

다국어 필드는 언어 코드를 키로 둔 맵을 그대로 들고 있다. 서버 DB의 번역 테이블 모양이 그렇기 때문이다.

### 5-2. 목 코드를 프로덕션 번들에서 분리하기

핸들러와 목 DB는 도메인 슬라이스가 소유하고 MSW 기반 코드는 `shared`에 뒀다. `shared`가 `features`를 참조하지 않도록 팩토리만 제공하고 호출부에서 조립했다.

목 코드를 도메인에 함께 둔 구조가 번들 경계를 흐렸다. 슬라이스 루트가 목 코드까지 내보내고 있어 화면이 컴포넌트 하나를 가져오면 시드 JSON과 MSW도 따라왔다. 프로덕션 클라이언트 청크에는 시드 280KB와 MSW 88KB가 실제로 실려 있었다.

목 코드는 슬라이스 루트와 분리한 공개 진입점으로만 내보내고, 프로덕션 코드가 해당 경로를 가져오지 못하도록 ESLint로 막았다. 각 진입 파일은 환경 변수를 직접 읽게 했다. 다른 모듈의 상수를 거치면 번들러가 사용하지 않는 분기를 제거하지 못해 시드와 MSW가 남았다.

### 5-3. 워커가 붙기 전에 나간 요청

서비스 워커가 등록되기 전에 나간 요청은 목 서버를 거치지 않고 실제 서버로 간다. 렌더링을 막으면 하이드레이션 불일치가 생기므로, 대신 요청이 등록 완료를 기다리게 했다. `requestApi()`는 매 요청마다 등록 작업을 나타내는 Promise를 기다리고, 목 서버를 쓰지 않는 모드에서는 이미 완료된 Promise를 받는다.

서버 렌더링 경로에는 같은 방식을 쓸 수 없었다. 전역 `fetch`를 가로채면 Next.js의 HMR이 인터셉터를 걷어낼 수 있다. 대신 같은 핸들러 배열을 직접 실행하는 리졸버를 등록했다.

## 6. 실서버 연결에서 드러난 목 서버의 네 가지 오류

나흘 뒤 실서버에 연결하자 목 서버와 어긋난 지점이 열 곳 남짓 드러났다.

먼저 요청 검증이 없었다. 목 서버는 데이터를 그대로 저장해 로컬과 CI에서는 통과했고 실서버에서만 400이 났다. 서버도 어느 필드가 문제인지 알려주지 않아 사용자가 고칠 수 없었다. 서버 규칙을 폼과 목 서버에 옮기자 픽스처 열두 개가 계약 위반으로 드러났다.

목 서버가 실제보다 많은 데이터를 주기도 했다. 목록의 "전체" 탭은 목 시드의 카테고리 행 하나 때문에만 존재했고 실서버에서는 사라졌다. 그 라벨이 서버에서 와야 한다고 단언한 E2E도 이 시드 위에서 통과하고 있었다.

목 시드에만 있던 필드도 있었다. 아무도 쓰지 않는 필드를 스키마에서 필수로 잡아둔 탓에 실서버에 붙자 목록과 상세가 Zod 파싱 단계에서 모두 멈췄다.

반대로 데이터가 부족한 경우도 있었다. 시드의 시설 스물여덟 곳은 운영시간이 모두 빈 객체였다. 목 데이터에서는 해당 섹션이 한 번도 그려지지 않았고 검증도 비어 있었다.

예약 조회의 오류 처리도 달랐다. 프론트는 예약번호와 이메일 오류를 구분했지만, 서버는 열거 공격을 막기 위해 둘 다 같은 404를 반환했다. 목 서버가 실서버에서 의도적으로 감춘 구분을 만들어낸 셈이다.

목 서버가 느슨하면 계약 위반이 통과하고, 실제보다 풍부하면 없는 기능이 화면에 생긴다.

## 7. 경계 — 목 서버 검증과 실서버 검증은 다르다

상태를 가진 목 DB도 도메인별로 테스트했다. 목 DB의 출력이 프로덕션 응답 스키마를 만족하는지 단언했다.

```ts
// 화면이 실제로 쓰는 스키마로 목 서버의 출력을 파싱한다
it('모든 언어의 응답이 responseSchema를 만족해야 한다', ...);
```

도메인 API 테스트도 실제 `requestApi()`를 통해 목 서버를 호출해 공통 응답 형식과 페이지 구조를 같은 경로로 검증한다.

다만 스키마와 실서버의 일치는 실제 연결 전에는 알 수 없었다. 가장 큰 차이는 응답 모양이 아니라 엔드포인트 자체였다.

> 프론트엔드가 호출하던 예약 상세 조회·취소 요청·수정 요청 API는 백엔드에 없다. API 명세가 예약 관리·변경 기능을 범위 밖으로 두고 있어 앞으로도 생기지 않는다. 목 서버가 받아주고 있어 드러나지 않았을 뿐이다.

존재하지도, 앞으로 생기지도 않을 API를 전제로 세 화면을 만든 상태였다. 이후에는 문서와 백엔드 컨트롤러를 함께 대조했고, 필수 파라미터 하나를 실서버 연결 이틀 전에 찾았다.

## 8. 실서버 테스트 — 실제 계약과의 차이를 찾는 계층

목 서버는 우리가 정한 응답을 돌려준다. 필드 이름이나 에러 코드 접두사가 실제와 달라도 스스로 알아낼 수 없다.

개발 실서버에 연결하는 테스트 계층을 따로 만들었다. `*.remote.test.ts`만 찾는 두 번째 Vitest 설정과 `RUN_REMOTE_TESTS` 스위치를 두고, 로그인은 `globalSetup`에서 한 번만 실행해 토큰을 주입한다.

자격 증명 처리는 두 앱이 아직 다르다. 콘텐츠 CMS는 `REMOTE_TEST_EMAIL`과 `REMOTE_TEST_PASSWORD`가 없으면 실행을 중단한다. 다국어 CMS는 같은 환경 변수로 덮어쓸 수 있지만 개발 공용 계정 기본값이 저장소에 남아 있다. 자격 증명을 환경 변수로 분리하는 작업은 콘텐츠 CMS에만 끝났고, 다국어 CMS의 기본값 제거는 남은 과제다.

```ts
// 기본 실행에서는 제외되며, 명시적으로 켜야 실행된다.
// package.json: "test:remote": "vitest run --config vitest.remote.config.mts"
include: ['src/**/*.remote.test.{ts,tsx}'],
```

실서버에 데이터를 쓰는 테스트는 앱 안에서 생성과 정리까지 마칠 수 있는 리소스에만 붙였다. 콘텐츠·FAQ·시설·상품·파일 업로드처럼 테스트가 만든 데이터를 다시 조회하고 정리할 수 있는 경우다. 현재 실서버 테스트 파일 13개에는 이런 CRUD 왕복 외에도 로그인·에러 응답·기존 데이터 조회처럼 서버 상태를 바꾸지 않는 계약 확인이 들어 있다.

예약은 예외였다. 전화·현장 예약은 운영자 앱에서 만들 수 있지만, 검증할 혜택 적용 예약 상태는 고객용 앱에서만 생성된다. 운영자 앱의 실서버 테스트만으로 초기 상태를 만들 수 없어 해당 예약은 목 응답으로 검증했다.

실서버 테스트에서 계약 차이를 찾으면 파일 수를 늘리기보다 목 서버와 통합 테스트를 실서버에 맞춰 고친다. 실서버 테스트는 느리고 데이터와 배포 상태에 의존하므로, 반복해서 돌리는 회귀 검증은 수정된 목 서버가 맡는다.

개발 데이터는 운영과 다르고, 쓰기 테스트는 다른 사람의 작업 데이터를 건드릴 수 있다. 외부 연동은 환경마다 달라 테스트를 끝까지 실행하기 어렵다. 그래서 테스트 계층을 고를 때는 실제 환경과의 거리보다 검증할 상태를 앱 안에서 만들고 정리할 수 있는지를 먼저 봤다.

## 9. 고의 변경 — 새 테스트가 실패하는지 확인한다

새 테스트마다 프로덕션 코드를 일부러 깨뜨렸다. 해당 테스트가 실패하는지 확인한 뒤 원복했다. 실패하지 않으면 단언이 실제 경로를 지키지 않는다는 뜻이다.

테스트를 통과시키려고 단언을 지우거나 약화시키는 것도 금지했다. 실패가 프로덕션 버그를 가리키면 구현을 고치거나 발견 사실을 보고한다.

동작을 바꾸는 리팩토링은 변경 전 계약을 먼저 테스트로 고정했다. 나중에 쓰면 새 동작만 박제하기 때문이다.

이 규칙은 곧 제값을 했다. 동의 모달 회귀 테스트를 쓰다가 앞서 머지된 리팩토링 두 개의 결함을 발견했고, 그때 내가 규칙 문서에 적어둔 권장 사항 자체가 틀렸다는 것도 같이 드러났다.

## 10. E2E — 브라우저 경계에서 퍼널 검증하기

고객용 앱의 E2E는 회원가입 퍼널의 상태와 서버 진입 제어 사이의 전이를 검증한다. 서버 레이아웃·히스토리·서비스 워커·팝업·쿠키가 함께 움직여 컴포넌트 렌더링만으로는 확인할 수 없는 구간이다.

실서버에서는 소셜 로그인, 본인인증 대행, 이메일 수신, 환경별 콜백 주소 때문에 퍼널을 완주할 수 없었다. 실계정도 "약관 동의 직전" 상태를 실행마다 만들거나 되돌릴 수 없다. 개발 서버를 목 서버 모드로 띄워 인증과 회원 정보 조회만 서버·브라우저 양쪽의 MSW로 가로채고, 나머지 API는 개발 서버로 보냈다.

원하는 단계의 사용자로 진입하려고 토큰을 만들어 쿠키에 심었다. 이 토큰은 실제 API에 닿으면 403을 받으므로 인증 목 핸들러가 응답하는 구간에서만 쓸 수 있다.

```ts
// 단계를 지정해 토큰을 만들고 쿠키로 심는다. 개발 서버는 HTTP를 쓰므로 secure 옵션을 끈다.
const state = buildTestUserState({ sessionKey, acceptedTerms: true });
await context.addCookies(
  ['sessionToken', 'renewalToken'].map((name) => ({
    name,
    value: encodeTestToken(state),
    domain: cookieHost,
    path: '/',
    httpOnly: true,
    secure: false,
  })),
);
```

브라우저 MSW 워커는 하이드레이션 직전에 실행되지만 Next.js는 등록 완료를 기다리지 않는다. 첫 요청이 테스트용 토큰을 들고 실제 API로 새어 403을 받지 않도록, 전체 페이지를 불러올 때마다 워커가 현재 문서를 제어하는지 확인했다. 재시작 없이 여러 실행을 처리하는 개발 서버의 목 저장소는 세션 ID로 격리했다.

화면이 보여도 React 핸들러가 붙기 전의 클릭은 무시되고 Playwright는 이를 성공으로 본다. DOM 노드에 Fiber 속성이 생길 때까지 기다린 뒤 클릭하고, 이동을 확인할 때까지 재시도했다.

### 10-1. 퍼널 상태와 진입 제어

로그인·약관 동의·본인인증·소속인증 방식 선택을 지나면 인증 경로가 코드 입력·이메일 링크·메신저 카드·건강보험 네 갈래로 나뉜다. 여기에 수동 심사 대기와 완료 화면이 붙는다.

완료를 알리는 방식도 경로마다 다르다. 코드와 건강보험은 응답을 받은 자리에서 토큰을 바꾸고 다음 단계로 넘긴다. 메신저 카드는 폴링 화면을 거친 뒤 페이지 전체를 새로 불러오며 이동한다. 이메일 링크는 앱이 아니라 콜백 라우트로 들어가 "창을 닫으라"는 정적 페이지만 그린다. 앱은 다음 회원 정보 조회에서야 완료 사실을 알 수 있다.

상태는 회원 정보, JWT 권한 클레임, 쿠키 세 개에 나뉘어 있다. 쿠키에는 가입 후 돌아갈 목적지, 혜택 안내 트리거, 대기 중인 소속코드를 담는다. 단계가 끝날 때마다 토큰이 새로 발급되므로 권한이 화면에 반영되는 경로도 회원 정보와 토큰으로 갈린다.

진입 제어의 실행 순서도 정해져 있다. `proxy`가 토큰을 버리거나 갱신하고 현재 URL을 헤더로 넘긴다. 보호 그룹 레이아웃은 본인인증을 먼저 보고 약관을 확인하지만, 본인인증 화면의 레이아웃은 약관부터 확인한다. 이 순서 차이가 일반 페이지와 본인인증 화면의 전이를 결정한다.

### 10-2. 정상 경로보다 우회 경로가 많았다

퍼널을 통과하는 길은 하나인데 그 화면에 도달하는 길은 여러 개다. 세어보니 스물여섯 갈래였다.

| 우회 상황 | 어떻게 도달하나 | 무엇이 막는가 | 테스트 |
| --- | --- | --- | --- |
| 미인증 회원이 보호 경로 진입 | 로그인만 한 상태로 프로필 URL 진입 | 보호 그룹 레이아웃이 본인인증으로 보내며 목적지를 쿼리에 싣는다 | 있음 |
| 가입 끝난 회원이 본인인증 재진입 | 히스토리나 오래된 링크 | 페이지가 목적지로 바로 보낸다 | 있음 |
| 가입 끝난 회원이 로그인 화면 재진입 | 로그인 링크나 북마크 | 페이지가 목적지로 보낸다. 다만 여기만 목적지 해석기를 거치지 않는다 | 있음 |
| 외부 주소를 목적지로 주입 | `?destination=//evil.example` | 내부 경로만 통과시키는 해석기. 자기 자신을 가리켜 무한 루프가 되는 경우도 같이 막는다 | 있음 |
| 인증 팝업 종료 | 팝업이 스스로 닫히며 부모 창을 이동시킨다 | 팝업 쪽 스크립트 | 있음 |
| 인증 실패 | 팝업이 실패로 닫힌다 | 본인인증 화면에 그대로 머문다 | 있음 |
| 심사 중 회원이 소속인증 진입 | 이메일·보험 신청 뒤 다시 진입 | 페이지가 심사 대기 화면으로 보낸다 | 있음 |
| 완료 직후 뒤로 가기 | 나가기 버튼을 누른 뒤 브라우저 뒤로 | 각 단계에서 `replace`를 사용해 이전 퍼널 화면이 히스토리에 남지 않는다 | 있음 |
| 회원 정보 조회 실패 | 토큰은 있는데 조회가 깨진다 | 강제 로그아웃 뒤 로그인 화면 | 있음 |
| 혜택 안내 트리거 노출 | 콜백에서 소속인증이 끝나 완료 화면을 거치지 않는다 | 트리거 쿠키를 여덟 가지 상태와 교차해 노출 조건을 고정했다 | 있음 |
| 목적지 쿠키로 복귀 | 가입 전 보려던 화면이 쿠키에 남아 있다 | 완료 화면 나가기 버튼이 쿠키를 읽고 지운다 | 있음 |
| 완료 화면 직접 진입 | 소속인증이 없는 상태로 완료 URL 진입 | 막는 것이 없다. 소속인증을 하지 않은 회원이 환영 문구와 나가기 버튼을 그대로 본다 | 없음 |
| 심사 대기 화면 직접 진입 | 심사 상태가 아닌데 대기 URL 진입 | 레이아웃이 메인으로 보낸다 | 없음 |
| 잘못된 인증 경로 세그먼트 | URL 조각을 손으로 고친다 | 알려진 값이 아니면 404 | 없음 |
| 약관 끝낸 회원이 약관 재진입 | 히스토리나 북마크 | 세 갈래로 갈라 보낸다. 대기 중인 소속코드가 있으면 그쪽으로, 정회원이면 목적지로, 아니면 본인인증으로 | 없음 |
| 약관 미동의 상태로 본인인증 딥링크 | 본인인증 URL 직접 진입 | 본인인증 화면의 레이아웃이 약관으로 되돌린다 | 없음 |
| 소속코드 딥링크로 진입 | 초대 링크를 받아 코드가 붙은 URL로 들어온다 | 로그인 여부와 유입 채널에 따라 세 갈래로 갈린다 | 없음 |
| 약관에서 소속코드로 인계 | 대기 중인 소속코드 쿠키를 들고 약관을 마친다 | 약관 페이지가 코드 화면으로 넘긴다 | 없음 |

| 미승인 회원이 소속 전용 경로 진입 | 혜택·예약·이벤트 상세 URL 진입 | 경로별 레이아웃이 소속인증으로 보낸다. 거절 상태면 프로필로, 심사 중이면 대기 화면으로 | 없음 |
| 약관 화면에서 뒤로 가기 | 브라우저 뒤로 | 히스토리에 심어둔 표식을 읽어 로그아웃 라우트로 보낸다 | 없음 |
| 퍼널 중간 로그아웃 | 약관·본인인증 단계에서 로그아웃 | 로그인 화면으로 되돌아간다 | 없음 |
| 단계 중간에 새로고침 | 페이지 전체 새로고침 | 히스토리 표식과 목적지 쿠키를 다시 쓴다 | 없음 |
| 팝업이 막히거나 웹뷰인 경우 | 브라우저가 팝업을 차단한다. 앱 안 웹뷰로 들어온다 | 앱 브리지 경로와 부모 창 없는 경우의 대체 이동 | 없음 |
| 목적지 쿠키가 진입 제어 화면을 가리킴 | 쿠키에 약관이나 소속인증 경로가 담긴다 | 본인인증 자기 참조만 막혀 있다. 쿠키를 사용하는 쪽이 값을 지우지 않아 한 시간 동안 반복해서 작동한다 | 없음 |
| 권한과 토큰 클레임 불일치 | 소속 승인 직후 보호 경로로 이동한다 | `proxy`가 토큰을 갱신해 클레임을 맞춘다 | 없음 |

### 10-3. 이 구간이 테스트로만 고정되는 이유

첫째, 진입 제어가 서버 레이아웃에 있어 화면 하나만 렌더링해서는 전이가 일어나지 않는다. 검증 대상은 컴포넌트 출력이 아니라 "어떤 상태에서 어디로 보내는가"다. 단위 테스트로 확인하기 어렵다.

둘째, 히스토리 스택·서비스 워커·팝업과 부모 창의 관계는 브라우저에만 있고 jsdom에는 없다.

셋째, 뒤로 가기는 한 사례만으로 고정할 수 없다. 완료 화면에서 나온 직후에는 퍼널로 돌아가지 않고 메인으로 나가야 한다. 목적지에서 두 단계 더 이동한 뒤에는 바로 앞 페이지로 돌아가야 한다. 두 경우를 함께 검증하지 않으면 한쪽만 맞는 구현도 통과한다. 첫 구현은 `document.referrer`를 읽었지만 이 값은 문서가 로드될 때 고정돼 두 경우를 구분하지 못했다.

넷째, 진입 제어가 없어도 화면은 정상으로 보인다. 소속인증을 하지 않은 회원이 완료 화면에 들어가도 환영 문구와 나가기 버튼이 그려진다. 빠진 진입 제어는 변경 내역에 나타나지 않아 코드 리뷰만으로 찾기 어렵다.

스물여섯 갈래 중 열한 개에만 테스트가 있다. 정상 경로와 인접한 상태는 다뤘지만 딥링크와 새로고침처럼 사용자가 우연히 만드는 상태는 비어 있다. 그중 두 곳은 막는 장치도 없다. 그래서 "회원가입 테스트가 있다"는 표현 대신 `11/26`으로 범위를 기록했다.

## 11. 검증 가능한 구간을 병렬로 맡기기

단언이 지키는 범위를 좁힌 뒤 그 조건을 AI 작업에 넘겼다. 각 작업은 성공 조건을 들고 병렬로 진행했다. 리뷰에서는 변경 전체보다 새로 추가된 단언과 고정한 동작을 먼저 확인했다. 속도 변화는 측정하지 않아 수치로 적지 않는다.

시행착오는 스킬 문서의 금지 규칙 두 줄로 남겼다. 테스트를 통과시키려고 단언을 삭제하거나 약화시키지 않는다. 검증하지 못한 범위를 검증했다고 보고하지 않는다. 작업을 시작할 때 반드시 읽도록 코드 옆이 아니라 작업 지시에 뒀다.

병렬로 맡길 수 있는 범위는 성공 조건이 코드로 적힌 구간까지다. `proxy`나 라우트 핸들러처럼 테스트가 없는 곳은 사람이 직접 읽고 순서대로 확인한다.

## 정리

| 테스트 계층 | 무엇에 붙는가 | 고른 이유 |
| --- | --- | --- |
| 순수 단위 | 함수 | 통합 테스트의 기반. jsdom이 재현하지 못하는 동작의 계약도 한 단계 아래에서 고정한다 |
| 컴포넌트 단위 | jsdom 렌더링 | 목 서버와 라우터가 필요 없는 표시 로직 |
| MSW 통합 | 프로덕션 컴포넌트 + 목 서버 | 기본 계층. 검증할 상태를 앱 안에서 만들 수 있다 |
| 실서버 테스트 | 개발 실서버 | 쓰기와 읽기를 앱 안에서 마칠 수 있을 때만 |
| E2E | 실제 브라우저 | 브라우저에서만 확인할 수 있는 동작 |

19일 동안 다섯 개의 테스트 계층, 100개가 넘는 파일을 만들었다. 새 테스트마다 프로덕션 코드를 손으로 바꿔 실제 경로의 실패를 잡는지 확인했다. 자동 뮤테이션 테스트를 구축한 것은 아니다. 테스트별로 코드를 바꾸고 실패를 확인한 뒤 원복하는 절차여서 이 과정을 빠뜨려도 테스트는 그대로 성공한다. 파일 수와 별개로 작업 지시에 이 절차를 남긴 이유다.

E2E는 서버 액션이 쿠키를 심고 클라이언트 캐시가 관리자 정보를 읽는 로그인 흐름, 겹친 드로어의 `elementFromPoint` 히트 테스트, 정산 화면 진입을 실제 브라우저에서 확인한다. 로그인 흐름은 jsdom에서 서버와 브라우저 상태를 함께 재현할 수 없다. z축 순서는 DOM 구조만으로 실제 클릭 대상을 알 수 없어 브라우저 테스트 계층에 남겼다.

테스트가 보장하지 못하는 범위도 기록했다. `proxy`는 로컬 모드에서 바로 통과하고 Playwright는 localhost의 `pnpm dev`에 붙으므로 호스트 강제 분기가 실행되지 않는다. 다른 도메인으로 브라우저를 띄우기 전에 로컬 개발용 분기가 검증 경로를 끊는다. 따라서 E2E가 통과해도 호스트 간 토큰 핸드오프를 검증했다고 볼 수 없다. 해당 라우트 핸들러는 테스트가 0건이고, `proxy`도 경로 계산 헬퍼 하나만 단위 테스트가 있다.

가장 큰 변화는 테스트 수보다 테스트 성공을 해석하는 기준이다. 서버 계약을 반영한 목 서버로 실제 컴포넌트를 렌더링하고, 고의 변경 확인까지 마친 구간만 검증됐다고 본다. 성공 조건을 코드로 두면 AI 작업을 병렬로 맡길 수 있지만, 그 코드가 실제 계약인지 테스트 안에서 만든 복제본인지는 자동으로 판정되지 않는다. 백엔드 DTO·컨트롤러 대조, 실서버 연결, 고의 변경 확인을 함께 둔 이유다. 남은 범위는 위의 `11/26`과 테스트 0건처럼 따로 드러내 사람이 검토할 대상으로 남긴다.
