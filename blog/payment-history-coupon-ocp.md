# 케이스가 계속 늘어나는 UI를 확장 가능하게 짜기: 결제내역에 쿠폰결제를 더하며

어떤 화면은 처음부터 케이스가 여러 개고 앞으로 더 늘어날 게 정해져 있다. 결제내역이 그랬다. 결제 한 건은 수단(일반/취소/쿠폰…) × 상태(완료/대기/처리중…) × 저장 유무로 갈리고, 그 조합마다 화면에 다르게 그려야 한다. 이런 화면은 케이스가 늘 때마다 기존 코드를 뜯어고치지 않아도 되게 짜는 게 가장 중요하다.

이번에 결제내역에 쿠폰결제를 새 케이스로 더했다. 기능 자체는 복잡하지 않았고, 끝내고 보니 기존 코드를 거의 고치지 않았다. 처음부터 케이스가 늘어난다고 보고 확장할 수 있게 짜 둔 덕분이다. 그 설계가 무엇이었는지, 새 케이스를 넣으면서 어디서 헤맸는지 정리해 둔다. 코드는 회사 코드 대신 핵심만 단순화하고 마스킹한 예시다.

## 케이스는 곱셈으로 늘어난다

우리 서비스는 병원과 의원 시술을 예약하고 결제까지 가는 플랫폼이고, 나는 병원이 쓰는 어드민을 맡고 있다. 환자가 예약하면 담당자가 시술을 확정하고, 그 뒤로 결제내역이 시간순으로 쌓인다.

결제 한 건은 수단(`method`), 금액(`amount`), 상태(`status`), 저장 여부(`id`)로 이뤄진다. 문제는 화면에 보여야 할 표시 케이스가 이 축들의 곱이라는 점이다. 결제완료(일반 × 완료), 결제취소(취소 × 완료), 결제대기(일반 × 대기), 편집 중(일반 × 미저장)처럼, 같은 상태값이라도 어떤 수단, 저장 상태와 만나느냐에 따라 다른 케이스가 된다. 도메인 규칙도 얽혀 있다. 결제일이 들어가면 "받은 돈"이 되어 정산에 잡히고, 잔액이 0이면 더 입력하지 못하게 막아야 한다. 케이스마다 보이는 모습도, 동작도 다르다.

실제로 케이스는 계속 늘었다. 일반결제로 시작해 분할결제와 결제취소(환불)가 붙었고, 이번에는 쿠폰결제까지 들어왔다. 새 수단이 들어올 때마다 화면을 갈아엎을 수는 없었다.

## 케이스가 늘어도 뜯어고치지 않게 정해 둔 것

처음 이 영역을 만들 때 네 가지를 정해 뒀다. 모두 새 케이스가 들어왔을 때 기존 코드는 두고 새 코드만 더하면 되게 하려는 장치다.

첫 번째는 컴포넌트가 케이스를 모르게 하는 것이다. 결제건을 그리는 컴포넌트가 `if (쿠폰) … else …`를 들고 있으면 케이스가 늘 때마다 이 컴포넌트가 부풀어 오른다. 그래서 컴포넌트는 결제건 하나를 받아 그리기만 하고, 그게 무슨 케이스인지는 밖에서 판단한다.

두 번째로, 케이스 판단을 한곳에 모았다. 보여 줄지, 무슨 색으로 그릴지 같은 판단을 컴포넌트 안에 흩어 두지 않고 helper로 모았다. 케이스가 늘 때 고칠 곳을 한 군데로 좁히려는 것이다.

```ts
<Timeline
  items={payments
    .filter(isVisible)     // 표시 여부 판단
    .map((p) => ({
      color: getColor(p),  // 색상 판단
      children: <PaymentRow payment={p} />,
    }))}
/>
```

세 번째는 케이스를 union 타입으로 모델링하는 것이다. 결제건을 수단별 union으로 두면 컴파일러가 빠진 케이스를 잡아 주고, 분기 안에서 타입도 정확히 좁혀진다.

```ts
type PaymentItem =
  | { method: 'NORMAL'; amount: number }
  | { method: 'COUPON'; amount: number; couponName: string };
```

곁가지로, 이 폼을 다루는 antd Form은 `getFieldValue('xxx')`가 `any`를 돌려줘서 필드가 많아지면 오타에 약하다. 그래서 폼 값에 타입이 따라오는 래퍼 `createTypedForm`을 만들어 썼다. union으로 케이스를 가르는 것과는 별개로, 타입이 새는 구멍을 막는 장치다.

마지막으로 UI 표시 모델을 서버 모델과 분리했다. 서버는 결제 상태를 완료, 대기, 처리중, 취소처럼 도메인 그대로 준다. 화면이 쓰는 표시 케이스는 이걸 베끼지 않고 별개 모델로 두고, `status` + `method` + `id`를 조합해서 만들어 낸다.

```ts
// 같은 'COMPLETED'라도 method로 케이스가 갈린다
const isCompleted = (p) => p.method === 'NORMAL' && p.status === 'COMPLETED'; // 결제완료
const isCanceled  = (p) => p.method === 'CANCEL' && p.status === 'COMPLETED'; // 결제취소(취소 거래의 완료)
```

취소 status가 따로 있을 텐데 왜 method로 판별하는지 궁금할 수 있다. 우리 도메인에서 결제를 취소하면 기존 건의 status는 그대로 두고, 취소 거래가 새 건(method: `CANCEL`)으로 쌓인 뒤 그 건이 완료(`COMPLETED`)된다. 그래서 status 하나만 봐서는 화면 케이스가 나오지 않고 method와 조합해야 한다. 같은 `COMPLETED`라도 일반결제 거래면 '완료'로, 취소 거래면 '취소'로 표시된다. 덕분에 **서버가 status를 몇 개로 두든 UI 표시 케이스는 흔들리지 않는다.** UI가 서버 스키마 변화에 휘둘리지 않는다는 점이 표시 모델을 따로 둔 가장 큰 이득이었다.

## 새 케이스(쿠폰)를 더하며

쿠폰결제는 일반결제와 다른 점이 꽤 있었다. 문구가 다르고, 취소하면 쿠폰을 복원해야 하고, 확정도 다른 API로 갔다. 구조는 멀쩡했지만 넣는 과정에서는 세 번 헤맸다.

처음에는 삼항 연산자로 그냥 박았다. 빨리 보여 주고 싶어서 `method === 'COUPON' ? '쿠폰' : '일반'` 식으로 문구부터 넣었는데, 편집과 완료 케이스까지 곱해지면서 분기가 description, 색상, 노출 여부에 하나씩 퍼졌다. 이미 분할과 취소가 있는데 쿠폰까지 이렇게 넣으면 다음 케이스 때 또 다 찾아다녀야 한다. 그래서 분기를 `ts-pattern`으로 한곳에 모았다.

```ts
match(payment)
  // 미저장(클라 제어): 값이 없거나 아직 id가 없음 → 그 안에서 다시 method로
  .with(P.union(P.nullish, { id: P.optional(P.nullish) }), (p) =>
    match(p)
      .with({ method: 'COUPON' }, () => <CouponDescriptions />)
      .otherwise(() => <WaitingDescriptions />),
  )
  // 저장됨 → 런타임 상태로: 취소 → 완료 → 그 외 대기
  .when(isCanceled, () => <CanceledDescriptions />)
  .when(isCompleted, () => <CompletedDescriptions />)
  .otherwise(() => <WaitingDescriptions />);
```

다만 `.exhaustive()`로 컴파일 보장까지 받지는 못했다. 분기 축이 저장 유무와 런타임 상태 둘이라 깔끔한 discriminated union이 되지 않았다. 대신 흩어질 분기를 `match` 한곳에 모았고, 케이스를 추가하든 상태를 추가하든 고칠 곳이 이 함수 하나로 좁혀졌다.

두 번째로 헤맨 건 타입을 나누지 않아서 생긴 옵셔널 지옥이다. 쿠폰에는 `couponName`이 있고 일반결제에는 없다. 귀찮아서 `couponName?: string` 옵셔널로 뭉쳤더니 곳곳에 `?.` 체이닝이 늘었고, 쿠폰인데 couponName이 없는 말이 안 되는 케이스가 타입상 가능해졌다. 그래서 앞에서 말한 union으로 갈랐다. `method`로 좁히는 순간 `couponName`이 보장된다. 타입을 나누는 일과 분기를 정리하는 일이 한 세트로 굴러간 셈이다.

세 번째는 폼을 읽기전용으로 막았더니 취소 버튼까지 죽은 일이다. 쿠폰 확정 케이스는 폼을 읽기전용으로 막아야 했는데, antd `Form`에 `disabled`를 주면 하위 컨트롤 전부에 전파된다(`DisabledContext`). 그래서 "예약 취소"처럼 읽기전용이어도 살아 있어야 하는 버튼까지 같이 죽었다. 그 컨트롤만 `disabled={false}`로 컨텍스트를 덮어썼다. `disabled`를 생략하면 상속되고, `false`를 명시하면 빠져나온다는 걸 이때 알았다.

취소할 때 복원하고 금액을 고치면 쿠폰을 초기화하는 쿠폰만의 흐름은 결제내역 렌더링을 건드리지 않고 전부 `CouponDescriptions` 안에 가뒀다. 일반결제 코드는 이게 있는지도 모른다. 컴포넌트가 케이스를 모르게 한 첫 번째 설계가 여기서 한 번 더 일을 했다.

## diff를 다시 보니

쿠폰을 다 붙이고 diff를 봤다. 기존 렌더링 코드는 거의 그대로였고, 추가된 건 union 멤버 하나, ts-pattern 분기 하나, 쿠폰 전용 description 정도였다. 헤맨 것도 모두 이미 있는 구조에 새 케이스를 맞게 넣는 과정에서였다.

설계가 괜찮았는지는 새 케이스가 들어올 때 드러난다. 쿠폰결제가 이 구조의 시험이었는데, 사실 처음 치른 시험도 아니었다. 분할결제와 결제취소(환불)도 이미 같은 방식으로 들어와 있었고, 쿠폰이 거기에 더해진 것뿐이다.

돌아보면 확장에는 열려 있고 수정에는 닫혀 있게 하라는 OCP(개방-폐쇄 원칙) 그대로다. 케이스가 늘어난다는 사실에서 출발해 짰는데, 짜고 보니 원칙과 같은 곳에 와 있었다.

## 같은 설계가 챗봇에도

UI 표시 모델을 서버 모델과 따로 두는 방식은 챗봇에서도 똑같이 썼다. 서버가 주는 상태(`ai`/`live`/`hold`/`done`)에 서버에는 없는 UI 전용 케이스 `connecting`(상담사 수락 대기)을 더하고, 둘을 타입으로 갈라 뒀다.

```ts
type ServerStatus = 'ai' | 'live' | 'hold' | 'done'; // 서버(SSE)가 주는 기준 상태(source of truth)
type ChatStatus = ServerStatus | 'connecting';        // + UI 전용 상태
```

결제내역은 서버 데이터에서 표시 케이스를 만들어 냈고, 챗봇은 서버 상태에 UI 전용 케이스를 더했다. 방식은 달라도 UI가 쓸 표시 모델을 서버 모델과 나눴다는 점은 같다. 서버는 도메인을 책임지고, UI는 자기 케이스를 자기 모델로 갖는다. 그래서 서버 스키마를 건드리지 않고도 `connecting` 같은 UI 케이스를 자유롭게 더할 수 있었다.

## 남은 것

아쉬운 곳도 있다. 타임라인 색상은 아직 하드코딩이고(`getColor`가 색 문자열을 직접 반환한다), 배열을 조립하는 부분도 좀 지저분하다. 구조와는 상관없는 마감 문제라서 뒤로 미뤘다.

거창한 패턴을 쓰지는 않았다. 컴포넌트는 케이스를 모르게, 판단은 helper로, 타입은 union으로, 표시는 서버 모델과 분리해서 둔다는 몇 가지를 처음부터 끝까지 지켰을 뿐이다.
