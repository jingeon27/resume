# 케이스가 계속 늘어나는 UI를 확장 가능하게 짜기 — 결제내역에 쿠폰결제를 '개조'가 아닌 '추가'로 넣다

어떤 화면은 처음부터 "케이스가 여러 개고, 앞으로 더 늘어난다"가 정해져 있다. 결제내역이 그랬다. 결제 한 건은 수단(일반/취소/쿠폰…) × 상태(완료/대기/처리중…) × 저장 유무로 갈리고, 그 조합 하나하나가 화면에 다르게 그려져야 할 케이스다. 이런 화면은 **케이스가 늘 때마다 기존 코드를 안 뜯어고치게** 짜는 게 전부다.

이번에 결제내역에 쿠폰결제를 새 케이스로 더했다. 기능 자체는 복잡하지 않았고, 끝내고 보니 기존 코드를 거의 안 고쳤다. 운이 아니라, 처음부터 "케이스는 늘어난다"를 전제로 *확장 가능하게* 짜뒀기 때문이다. 그 설계가 뭐였고 새 케이스를 넣으며 뭘 헤맸는지 정리해둔다. 코드는 회사 코드 대신 핵심만 단순화·마스킹한 예시다.

## 케이스는 곱셈으로 늘어난다

우리 서비스는 병원·의원 시술을 예약하고 결제까지 가는 플랫폼이고, 나는 병원이 쓰는 어드민을 맡고 있다. 환자가 예약하면 담당자가 시술을 확정하고, 그 뒤로 **결제내역**이 시간순으로 쌓인다.

결제 한 건은 수단(`method`), 금액(`amount`), 상태(`status`), 저장 여부(`id`)로 구성된다. 문제는 화면에 보여야 할 "표시 케이스"가 이 축들의 **곱**이라는 거다 — 결제완료(일반 × 완료), 결제취소(취소 × 완료), 결제대기(일반 × 대기), 편집 중(일반 × 미저장)… 같은 상태값이라도 어느 수단·저장 상태와 조합되느냐에 따라 다른 케이스가 된다. 게다가 도메인 규칙도 얽혀 있다. 결제일이 들어가면 "받은 돈"이 되어 정산에 잡히고, 잔액이 0이면 더 입력을 막아야 한다. 즉 케이스마다 표시도, 동작도 다르다.

그리고 이 케이스는 실제로 계속 늘었다. 일반결제로 시작해 분할결제·결제취소(환불)를 거쳤고, 이번엔 쿠폰결제까지. 새 수단이 들어올 때마다 화면을 갈아엎을 순 없었다.

## 케이스가 늘어도 안 뜯어고치게 — 네 가지 설계

처음 이 영역을 만들 때 네 가지를 정해뒀다. 전부 새 케이스가 '개조'가 아니라 '추가'가 되게 만드는 장치다.

**① 컴포넌트는 케이스를 모른다.** 결제건을 그리는 컴포넌트가 `if (쿠폰) … else …`를 들고 있으면, 케이스가 늘 때마다 이 컴포넌트가 부풀어 오른다. 그래서 컴포넌트는 "결제건 하나"를 받아 그리기만 하고, 그게 무슨 케이스인지는 밖에서 판단한다.

**② 케이스 판단을 한 곳에 모은다.** "보여줄지", "무슨 색인지" 같은 판단을 컴포넌트 안에 흩어놓지 않고 helper로 모았다. 케이스가 늘 때 고칠 데를 한 군데로 좁히려는 거다.

```ts
<Timeline
  items={payments
    .filter(isVisible)     // 표시 여부 판단
    .map((p) => ({
      color: getColor(p),  // 색상 판단
      children: <PaymentRow payment={p} />,
    }))}
/>
```

**③ 케이스를 union 타입으로 모델링한다.** 결제건을 수단별 union으로 두면, 컴파일러가 케이스 누락을 잡아주고 분기 안에서 타입이 정확히 좁혀진다.

```ts
type PaymentItem =
  | { method: 'NORMAL'; amount: number }
  | { method: 'COUPON'; amount: number; couponName: string };
```

(곁가지 하나 — 이 폼을 다루는 antd Form은 `getFieldValue('xxx')`가 `any`를 돌려줘서 필드가 많아지면 오타에 취약하다. 그래서 폼 값에 타입이 따라오는 래퍼 `createTypedForm`을 만들어 썼다. union으로 케이스를 가르는 것과는 별개로, 타입이 새는 구멍을 막는 장치다.)

**④ UI 표시 모델을 서버 모델과 분리한다.** 서버는 결제 상태를 도메인 그대로 준다(완료·대기·처리중·취소 등). 화면이 쓰는 "표시 케이스"는 그걸 그대로 베끼지 않고 *별개 모델*로 두고, `status` + `method` + `id`를 **조합해서 파생**시킨다.

```ts
// 같은 'COMPLETED'라도 method로 케이스가 갈린다
const isCompleted = (p) => p.method === 'NORMAL' && p.status === 'COMPLETED'; // 결제완료
const isCanceled  = (p) => p.method === 'CANCEL' && p.status === 'COMPLETED'; // 결제취소(취소 거래의 완료)
```

"취소 status가 따로 있을 텐데 왜 method로 판별하나" 싶을 수 있는데, 우리 도메인에서 결제취소는 기존 건의 status가 바뀌는 게 아니라 **취소 거래가 새 건(method: `CANCEL`)으로 쌓이고, 그 건이 완료(`COMPLETED`)되는 흐름**이다. 그래서 status 하나만 봐서는 화면 케이스가 안 나오고, method와 조합해야 나온다. `COMPLETED`라는 *같은* 서버 status가, 일반결제 거래면 '완료'로 취소 거래면 '취소'로 표시된다. 덕분에 **서버가 status를 몇 개로 두든 UI 표시 케이스 집합은 흔들리지 않는다.** UI가 서버 스키마 변화에 휘둘리지 않는 것 — 이게 표시 모델을 따로 두는 가장 큰 이득이었다.

## 새 케이스(쿠폰)를 더하며

쿠폰결제가 들어왔다. 일반결제와 다른 점이 꽤 있었다 — 문구가 다르고, 취소하면 쿠폰을 복원해야 하고, 확정이 다른 API로 갔다. 구조는 멀쩡했지만 *넣는 과정*에선 세 번 헤맸다.

**1. 처음엔 그냥 삼항으로 박았다.** 빨리 보여주고 싶어서 `method === 'COUPON' ? '쿠폰' : '일반'` 식으로 문구부터 넣었다. 근데 편집/완료 케이스까지 곱해지면서 분기가 description·색상·노출에 하나씩 퍼졌다. 이미 분할·취소까지 있는 마당에 쿠폰까지 이러면 다음 케이스 때 또 다 찾아다녀야 한다. 그래서 분기를 `ts-pattern`으로 한 곳에 모았다.

```ts
match(payment)
  // 미저장(클라 제어): 값이 없거나 아직 id가 없음 → 그 안에서 다시 method로
  .with(P.union(P.nullish, { id: P.optional(P.nullish) }), (p) =>
    match(p)
      .with({ method: 'COUPON' }, () => <CouponDescriptions />)
      .otherwise(() => <WaitingDescriptions />),
  )
  // 저장됨 → 런타임 상태로: 취소 → 완료 → 그 외 대기
  .when(isCanceled, () => <CanceledDescriptions />)
  .when(isCompleted, () => <CompletedDescriptions />)
  .otherwise(() => <WaitingDescriptions />);
```

솔직히 `.exhaustive()`의 컴파일 보장까진 못 갔다. 분기 축이 둘(저장 유무 + 런타임 상태)이라 깔끔한 discriminated union이 안 됐다. 얻은 건 보장 그 자체가 아니라 **흩어질 분기를 `match` 한 곳에 모은 것** — 케이스를 추가하든 상태를 추가하든 고칠 데가 이 함수 하나로 좁혀졌다.

**2. 타입을 안 나눠서 옵셔널 지옥이 됐다.** 쿠폰엔 `couponName`이 있고 일반엔 없다. 귀찮아서 `couponName?: string` 옵셔널로 뭉쳤더니, 곳곳에 `?.` 체이닝이 늘고 "쿠폰인데 couponName이 없는" 말 안 되는 케이스가 타입상 가능해졌다. 그래서 위 ③의 union으로 갈랐고, `method`로 좁히는 순간 `couponName`이 보장됐다. 타입 분리와 분기 정리가 한 세트로 굴러갔다.

**3. 읽기전용으로 막았더니 취소 버튼까지 죽었다.** 쿠폰 확정 케이스는 폼을 읽기전용으로 막아야 했는데, antd `Form`에 `disabled`를 주면 하위 모든 컨트롤로 전파된다(`DisabledContext`). "예약 취소"처럼 읽기전용이어도 살아야 하는 버튼까지 같이 죽었다. 그 컨트롤만 `disabled={false}`로 컨텍스트를 덮어썼다 — `disabled`를 *생략*(상속)하는 것과 `false`를 *명시*(옵트아웃)하는 게 다르다는 걸 이때 알았다.

쿠폰만의 흐름(취소 시 복원, 금액 수정 시 쿠폰 초기화)은 결제내역 렌더링을 안 건드리고 전부 `CouponDescriptions` 안에 가뒀다. 일반결제 코드는 이게 있는지조차 모른다 — 설계 ①이 여기서 한 번 더 일을 했다.

## 결과 — '추가'였지 '개조'가 아니었다

쿠폰을 다 붙이고 diff를 봤다. 의도한 대로, 기존 렌더링 코드는 거의 그대로였다. 추가된 건 union 멤버 하나, ts-pattern 분기 하나, 쿠폰 전용 description 정도. 헤맨 것도 "구조를 바꾸는" 헤맴이 아니라 "이미 있는 구조에 케이스를 맞게 넣는" 헤맴이었다.

설계가 좋았는지는 짤 때가 아니라 새 케이스가 들어왔을 때 드러난다. 이 구조는 처음부터 "케이스가 늘어나는 순간"을 시험대로 상정하고 짠 거고, 쿠폰결제가 그 시험이었다. 그리고 통과했다 — 사실 처음도 아니다. 분할결제·결제취소(환불)도 이미 같은 방식으로 들어와 있었고, 쿠폰이 거기 더해진 것뿐이다.

돌아보면 이 설계는 OCP(개방-폐쇄 원칙) — 확장엔 열려 있고 수정엔 닫혀 있게 — 그대로다. 원칙을 먼저 놓고 코드를 맞춘 게 아니라, "케이스는 늘어난다"는 사실에서 출발해 거기에 닫히지 않게 짜다 보니 같은 곳에 도착해 있었다.

## 같은 설계가 챗봇에도

돌아보니 설계 ④("UI 표시 모델을 서버 모델과 따로 둔다")는 결제내역만의 얘기가 아니었다. 챗봇에서도 똑같이 했다 — 서버가 주는 상태(`ai`/`live`/`hold`/`done`)에 **서버엔 없는 UI 전용 케이스** `connecting`(상담사 수락 대기)을 더해, 둘을 타입으로 갈라뒀다.

```ts
type ServerStatus = 'ai' | 'live' | 'hold' | 'done'; // 서버(SSE)가 주는 기준 상태(source of truth)
type ChatStatus = ServerStatus | 'connecting';        // + UI 전용 상태
```

결제내역은 서버 데이터에서 표시 케이스를 *파생시켰고*, 챗봇은 서버 상태에 UI 전용 케이스를 *더했다*. 방식은 달라도 같은 선택이다 — **UI가 쓸 표시 모델을 서버 모델과 분리한다.** 서버는 도메인을 책임지고, UI는 자기 케이스를 자기 모델로 가진다. 그래서 서버 스키마를 안 건드리고도 `connecting` 같은 UI 케이스를 자유롭게 더할 수 있었다.

## 남은 것

물론 아쉬운 데도 있다. 타임라인 색상이 아직 하드코딩으로 남아 있고(`getColor`가 색 문자열을 직접 반환한다), 배열 조립도 좀 지저분하다. 마감 문제지 구조 문제는 아니라서 뒤로 미뤘다.

거창한 패턴을 쓴 게 아니다. **"케이스는 늘어난다"는 전제를 처음부터 끝까지 설계에 깔아둔 것** — 그게 전부다. 컴포넌트는 케이스를 모르게, 판단은 helper로, 타입은 union으로, 표시는 서버 모델과 분리해서. 이 몇 개를 일관되게 지키면, 새 케이스는 "추가"지 "개조"가 아니게 된다.
