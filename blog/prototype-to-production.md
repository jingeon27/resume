# 프로토타입을 실사용 서비스로 옮기며 코드보다 규칙을 먼저 짠 이유

빠르게 검증만 하려고 만들어둔 프로토타입 하나를 실사용 단계로 옮기는 작업을 맡았습니다. 클라이언트 라우팅 기반의 가벼운 SPA였는데, 실사용으로 가려면 SSR, SEO, 다국어, 폼 검증까지 다시 갖춰야 해서 사실상 새로 짜는 것에 가까웠어요. Claude Code로 진행했는데, 이번엔 평소와 달리 코드부터 안 짜고 설정부터 짰습니다.

---

## 왜 설정부터인가

반복 규모를 먼저 가늠해봤습니다. 정적 페이지 수십 개, 폼 여러 개, 도메인 몇 개 — 같은 패턴이 계속 반복될 걸 알고 있었어요. 매번 "우리는 이렇게 짭니다"를 설명하느니, 첫날에 아키텍처, 폼, 조회, i18n, 코드스타일 컨벤션을 스킬 문서로 미리 박아두는 쪽이 낫다고 판단했습니다. 실제로 이후 마이그레이션은 대부분 이 스킬들 안에서 굴러갔고, 새로 설명해야 했던 건 거의 없었어요.

---

## 그런데도 AI가 놓친 것들

컨벤션을 미리 적어놔도, 실제로 코드가 나오면 잡아야 하는 것들이 있었습니다.

**1. 마운트 게이트를 걷어내라고 했더니, 이름만 바꿔서 돌려줬다.**

`typeof window`로 분기하는 마운트 게이트 컴포넌트가 레거시에 남아 있었어요. 제거하라고 했더니 AI는 이걸 `useMounted()` 훅으로 리팩터했습니다.

```tsx
// AI가 낸 것 — 컴포넌트를 훅으로 옮겼을 뿐, 마운트 게이트라는 본질은 그대로
function useMounted() {
  const [mounted, setMounted] = useState(false);
  useEffect(() => setMounted(true), []);
  return mounted;
}
```

형태만 바뀌었지 여전히 "마운트 전엔 아무것도 안 그린다"는 같은 패턴이었습니다. 이 프로젝트는 Suspense 경계를 레이아웃 최상단에 이미 두고 있어서, CSR 전용 훅 때문에 생기는 문제는 그 경계가 이미 처리하고 있었어요. 그래서 훅으로 감싸는 대신 마운트 분기 자체를 전부 걷어냈습니다. "고쳤다"와 "옮겼다"는 다른데, AI는 후자를 고친 걸로 내놓을 때가 있습니다.

**2. 훅으로 바로 얻을 수 있는 값을, 계속 prop으로 내리려 했다.**

라우터 인스턴스, 현재 언어, 뷰포트 여부 — 세 가지가 전부 부모에서 훅으로 얻어서 자식에 prop으로 넘겨지고 있었습니다. 각각 다른 시점에 지적했는데도 매번 같은 이유였어요. AI는 "이미 그렇게 짜여 있으니" prop 체인을 유지한 채로 리팩터를 마무리하려 했습니다.

```tsx
// ❌ 훅으로 바로 얻을 수 있는데 prop으로 내려받음
function Card({ lang, isMobile }: { lang: Lang; isMobile: boolean }) { ... }

// ✅ 필요한 곳에서 훅으로 직접
function Card() {
  const lang = useLang();
  // 뷰포트는 훅도 아니고 CSS 미디어쿼리로
}
```

세 번 다 같은 지적이었다는 게 오히려 신경 쓰였습니다. 규칙 하나("훅으로 얻는 값은 prop으로 내리지 않는다")로 스킬에 박아두고 나서야, 이후 컴포넌트들은 처음부터 이 문제가 없었어요.

**3. mutation을 쓰면서도, 파생 상태를 따로 들고 있었다.**

폼 제출 처리를 `useMutation`으로 옮긴 뒤에도, "제출 완료 여부"와 "제출 시점 스냅샷"을 별도 `useState`/`useRef`로 복제하고 있는 코드가 남아 있었습니다. mutation이 이미 `isSuccess`, `variables`로 그 값을 들고 있는데도요. 이건 걷어내되, 같은 컴포넌트의 "현재 활성화된 탭 인덱스" 같은 상태는 mutation과 무관한 진짜 원시 상태라 그대로 뒀습니다. 파생 상태를 거를 때 제일 헷갈리는 지점은 "상태를 줄여라"가 아니라 "이게 정말 파생인지"를 구분하는 거였어요.

---

## 리팩터가 몇 라운드 쌓인 뒤: 감사, 그리고 코드보다 규칙

마이그레이션과 정리 작업이 몇 라운드 쌓인 시점에 전체 코드 감사를 한 번 돌렸습니다. 크고 작은 문제가 여럿 나왔는데, 우선순위를 코드 수정이 아니라 스킬 문서 갱신에 먼저 뒀습니다. 발견된 버그 하나를 고치는 것과, AI가 다음에도 같은 실수를 반복하지 않게 규칙 자체를 갱신하는 건 다른 일이라고 봤어요. 후자를 먼저 해두면, 남은 코드 수정도 그 갱신된 규칙 안에서 다시 어긋나지 않게 진행됩니다.

---

## 결과, 그리고 남은 것

정적 페이지, 폼, 다국어, 관리자 도구까지 포함해서 프로토타입을 실사용 가능한 서비스로 옮기는 작업 자체는 예상보다 빨랐습니다. 다만 그 속도는 "AI가 코드를 빨리 짜서"가 아니라, 초반에 박아둔 규칙 덕분에 같은 실수를 반복해서 잡을 필요가 없어서였다고 생각합니다. 반대로 규칙에 없던 부분(감사에서 새로 드러난 것들)은 여전히 사람이 하나하나 봐야 했고요.

이 프로젝트를 하면서 다시 확인한 건, AI가 빨라질수록 개발자의 일이 "코드를 짠다"에서 "무엇을 규칙으로 박아둘지, 그리고 그 규칙 밖에서 뭐가 새는지 판단한다"로 옮겨간다는 겁니다. 프로토타입 하나를 실사용 단계로 옮기는 것도 결국 이 판단을 몇 번 더 반복하는 일이었어요.
