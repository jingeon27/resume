# 프로토타입을 실사용 서비스로 옮기며 코드보다 규칙을 먼저 짠 이유

빠르게 검증만 하려고 만들어 둔 프로토타입 하나를 실사용 단계로 옮기는 작업을 맡았습니다. 클라이언트 라우팅 기반의 가벼운 SPA였는데, 실사용으로 가려면 SSR, SEO, 다국어, 폼 검증까지 다시 갖춰야 해서 사실상 새로 짜는 것에 가까웠어요. Claude Code로 진행했는데, 이번에는 평소와 달리 코드보다 설정을 먼저 짰습니다.

---

## 왜 설정부터인가

먼저 반복 규모를 가늠해 봤습니다. 정적 페이지가 수십 개, 폼이 여러 개, 도메인도 몇 개라 같은 패턴이 계속 반복될 게 보였어요. 매번 "우리는 이렇게 짭니다"를 설명하느니, 첫날 아키텍처, 폼, 조회, i18n, 코드 스타일 컨벤션을 스킬 문서로 박아 두는 게 낫다고 판단했습니다. 실제로 이후 마이그레이션은 대부분 이 스킬 안에서 굴러갔고, 새로 설명해야 했던 건 거의 없었어요.

---

## 그런데도 AI가 놓친 것들

컨벤션을 미리 적어 둬도 막상 코드가 나오면 잡아야 할 것들이 있었는데요. 그중 세 가지를 적어 봅니다.

### 마운트 게이트를 걷어 내라고 했더니 이름만 바꿔 왔다

`typeof window`로 분기하는 마운트 게이트 컴포넌트가 레거시에 남아 있었어요. 제거하라고 했더니 AI는 이걸 `useMounted()` 훅으로 리팩터했습니다.

```tsx
// AI가 낸 것 — 컴포넌트를 훅으로 옮겼을 뿐, 마운트 게이트라는 본질은 그대로
function useMounted() {
  const [mounted, setMounted] = useState(false);
  useEffect(() => setMounted(true), []);
  return mounted;
}
```

형태만 바뀌었을 뿐, 마운트 전에는 아무것도 안 그린다는 패턴은 그대로였어요. 이 프로젝트는 레이아웃 최상단에 이미 Suspense 경계를 두고 있어서, CSR 전용 훅 때문에 생기는 문제는 그 경계가 처리하고 있었습니다. 그래서 훅으로 감싸는 대신 마운트 분기를 전부 걷어 냈어요. AI는 코드를 옮겨 놓고 고쳤다고 내놓을 때가 있는데, 이번이 그런 경우였습니다.

### 훅으로 바로 얻을 수 있는 값을 계속 prop으로 내리려 했다

라우터 인스턴스, 현재 언어, 뷰포트 여부 세 가지를 모두 부모에서 훅으로 얻은 뒤 자식에게 prop으로 넘기고 있었습니다. 각각 다른 시점에 지적했는데 이유는 매번 같았어요. AI는 이미 그렇게 짜여 있다는 이유로 prop 체인을 그대로 둔 채 리팩터를 마무리하려 했습니다.

```tsx
// ❌ 훅으로 바로 얻을 수 있는데 prop으로 내려받음
function Card({ lang, isMobile }: { lang: Lang; isMobile: boolean }) { ... }

// ✅ 필요한 곳에서 훅으로 직접
function Card() {
  const lang = useLang();
  // 뷰포트는 훅도 아니고 CSS 미디어쿼리로
}
```

세 번 다 같은 지적이었다는 게 오히려 신경 쓰였습니다. "훅으로 얻는 값은 prop으로 내리지 않는다"는 규칙 하나를 스킬에 박아 두고 나서야, 이후 컴포넌트에서는 처음부터 이 문제가 나오지 않았어요.

### mutation을 쓰면서도 파생 상태를 따로 들고 있었다

폼 제출 처리를 `useMutation`으로 옮긴 뒤에도 제출 완료 여부와 제출 시점 스냅샷을 `useState`/`useRef`로 따로 복제해 두는 코드가 남아 있었습니다. mutation이 이미 `isSuccess`와 `variables`로 그 값을 들고 있는데도요. 이 부분은 걷어 냈고, 같은 컴포넌트의 현재 활성화된 탭 인덱스처럼 mutation과 상관없는 원시 상태는 그대로 뒀습니다. 파생 상태를 걸러 낼 때 제일 헷갈렸던 건 이게 정말 파생인지 가려내는 일이었어요.

---

## 리팩터가 몇 라운드 쌓인 뒤의 감사

마이그레이션과 정리 작업이 몇 라운드 쌓였을 때 전체 코드 감사를 한 번 돌렸습니다. 크고 작은 문제가 여럿 나왔는데, 코드보다 스킬 문서를 먼저 고쳤어요. 발견한 버그 하나를 고치는 것과 AI가 다음에 같은 실수를 하지 않게 규칙을 고치는 건 다른 일이라고 봤거든요. 규칙을 먼저 고쳐 두면 남은 코드 수정도 그 규칙 안에서 다시 어긋나지 않게 진행됩니다.

---

## 결과, 그리고 남은 것

정적 페이지, 폼, 다국어, 관리자 도구까지 포함해 프로토타입을 실사용 서비스로 옮기는 작업은 예상보다 빨리 끝났습니다. 초반에 박아 둔 규칙 덕분에 같은 실수를 반복해서 잡을 필요가 없었던 게 컸다고 생각해요. 반대로 규칙에 없던 부분, 그러니까 감사에서 새로 드러난 것들은 여전히 사람이 하나하나 봐야 했고요.

AI가 빨라질수록 개발자의 일은 무엇을 규칙으로 박아 둘지, 그 규칙 밖에서 무엇이 새는지 판단하는 쪽으로 옮겨 가는 것 같은데요. 프로토타입 하나를 실사용 단계로 옮기는 일도 결국 이 판단을 몇 번 더 반복하는 일이었어요.
