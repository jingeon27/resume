# 글 제목: 실제로 부딪힌 장면이 떠오르게 쓴다

![글의 핵심 문제를 표현한 커버](../assets/covers/example.jpg)

첫 문단에서는 실제로 막혔던 장면을 바로 꺼낸다. 기술 이름과 성과를 먼저 요약하지 않는다. "새 파일을 만들 때마다 위치가 달라졌다", "테스트는 성공했는데 화면은 깨져 있었다"처럼 그때 겪은 일을 두세 문장으로 보여준다.

문장은 `~했어요`, `~였어요`, `~인데요`를 기본으로 쓴다. 모든 문장을 같은 어미로 맞추지는 않고, 짧은 단정과 질문을 섞는다. 독자에게 가르치는 말투보다 당시 내가 무엇을 보고 어떻게 생각을 바꿨는지 설명하는 말투를 사용한다.

<div class="note note-summary">
  <strong>이 글에서 다루는 것</strong>
  <p>재현 조건, 검토한 선택지, 최종 결정, 검증 결과와 남은 한계를 다룹니다.</p>
</div>

## 1. 처음에는 문제가 단순해 보였어요

관찰한 증상과 발생 조건을 적는다. 개발 환경과 운영 환경이 달랐다면 구분한다. 이때 결론을 미리 말하지 않고 당시의 첫 판단도 함께 적는다.

```text
재현 환경:
사용자 행동:
기대한 결과:
실제 결과:
```

## 2. 그런데 범위를 넓혀 보니 달랐어요

한 화면의 문제인지 공통 구조의 문제인지 확인한 과정을 적는다. 수동 점검 수치는 자동 검증처럼 표현하지 않는다.

## 3. 문제를 다시 정의했어요

프레임워크·브라우저·서버의 책임을 구분해 설명한다. 내부 구현은 결정에 필요한 만큼만 보여준다.

| --- | --- | --- | --- |
| A |  |  |  |
| B |  |  |  |
| C |  |  |  |

## 5. 그래서 이렇게 바꿨어요

핵심 코드만 싣는다. import와 주변 코드가 결론에 필요하지 않으면 생략한다.

```ts
// 핵심 결정이 드러나는 최소 코드
```

## 6. 성공했다는 말도 다시 확인했어요

- 실제 개발 서버에서 확인한 것
- 프로덕션 빌드에서만 확인할 수 있었던 것
- 테스트로 고정한 것
- Sentry나 Web Vitals로 운영에서 확인한 것

## 7. 결과와 아직 모르는 것을 나눴어요

측정한 결과와 관찰한 결과를 분리한다. 전후 수치는 측정 조건을 함께 적는다.

## 말투와 전개의 기준

- 보고서처럼 `문제-설계 판단-적용 결과`를 반복하지 않는다. 한 사건이 시간순으로 이어지게 쓴다.
- 처음부터 정답을 알았던 것처럼 쓰지 않는다. 첫 접근, 피드백, 반례, 철회한 선택을 숨기지 않는다.
- 기술 개념은 지식을 과시하기 위해 따로 설명하지 않는다. 그 개념이 실제 구현 결정을 바꾼 지점에서만 깊게 들어간다.
- 숫자는 결과를 돋보이게 붙이는 장식이 아니라 범위와 검증 조건을 설명하는 데 사용한다.
- `우아한`, `견고한`, `혁신적인`, `효율적인`처럼 근거 없는 평가어는 피한다. 코드나 전후 상태가 대신 말하게 둔다.
- 소제목만 읽어도 사고가 바뀐 흐름이 보이게 한다. "도입 배경", "문제 해결", "성과" 같은 범용 소제목은 피한다.
- 한 문단에는 하나의 생각만 둔다. 길어진 문단은 기술 난도가 아니라 전환 지점을 기준으로 나눈다.
