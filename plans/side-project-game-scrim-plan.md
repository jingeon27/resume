# 사이드 프로젝트: 게임 내전 운영 서비스 계획

> 목적: 프로덕트 엔지니어로 커리어를 넓히기 위해, 사용자 문제 찾기 → 출시 → 측정 → 실험 → 개선을 혼자 끝까지 돌려 본다. 마케팅까지 직접 한다.

## 한 줄 정의

롤 5:5 내전을 여는 방장이 링크 하나로 사람을 모으고, 팀을 자동으로 나누고, 결과와 랭킹을 쌓는 웹 서비스.

## 왜 이 제품인가

- **방 하나가 곧 확산이다.** 방장이 방을 만들면 참가자 10명이 링크로 들어온다. 사람을 모으는 일을 방장이 대신 한다.
- **처음부터 사용자가 몰려 있을 필요가 없다.** 방장이 자기 사람들을 데려오므로 공개 방이 적어도 첫날부터 쓸 수 있다.
- **방장의 고통이 분명하다.** 인원 모으기, 팀 나누기, 노쇼, 참가비 확인, 결과 기록을 지금은 오픈채팅·디스코드·엑셀로 손으로 한다.
- **다시 올 이유가 있다.** 내전은 매주 반복되고, 전적과 랭킹이 쌓이면 다시 온다.
- **빈자리가 있다.** 축구는 플랩풋볼 같은 큰 서비스가 있지만, 게임 내전은 작은 도구만 흩어져 있다.

## 처음부터 지킬 원칙

- **카테고리는 하나로 시작한다.** 데이터에는 카테고리 필드를 두되 마케팅은 롤 내전 하나로 한다. 발로란트는 반응을 본 뒤에 추가한다.
- **참가비는 표시와 입금 확인 체크만 한다.** 앱이 돈을 받거나 보관하지 않는다(전자금융·결제 대행 규제). 송금은 토스·카카오페이 링크로 밖에서 한다.
- **결과에 따라 돈이나 경품을 주는 기능은 만들지 않는다.** 사행성 문제가 생길 수 있고, 게임 내전은 참가자 중 미성년자도 많다.
- **앱이 아니라 웹 링크로 시작한다.** 카톡·디스코드에 링크를 던지면 설치 없이 바로 참가해야 한다. 설치 단계가 하나 생길 때마다 참가자가 빠진다. 모바일 웹(PWA)으로 시작하고 반응이 오면 앱을 검토한다.
- **무료로 운영한다.** 산업기능요원 복무 중에는 겸직·영리 활동 제한이 있고, 회사 취업 규칙의 겸업 조항도 있다. 수익화는 병무청·회사 규정을 확인한 뒤에 한다.

## 대상 사용자

- **방장:** 롤 5:5 내전을 정기적으로 여는 오픈채팅·디스코드 운영자. 이 제품의 고객이다.
- **참가자:** 방장이 보낸 링크로 들어오는 사람. 확산의 통로다.

## 4주 계획

### 0주차 (3일): 만들기 전에 방장 5명과 이야기하기

- 내전을 한 번 열 때 가장 시간이 많이 드는 일은? (인원 모으기·팀 나누기·노쇼·참가비 확인·기록)
- 지금 팀을 어떻게 나누는가? 결과에 대한 불만이 나오는가?
- 참가비를 받는가? 얼마를, 어떻게 확인하는가?
- 전적과 랭킹을 따로 관리하는가?

이 대답으로 1~3주차 기능의 우선순위를 정한다. 이것이 첫 가설 검증이다.

### 1주차: 방 만들기와 참가

- 방장이 방 이름·일시·정원·참가비(표시만)·티어 조건을 넣어 방을 만든다.
- 참가자는 링크로 들어와 닉네임·티어·주/부 포지션만 넣는다. 처음에는 로그인 없이 참가하고, 방장만 디스코드 로그인을 쓴다.
- 정원이 차면 대기열로 가고, 빠진 자리가 생기면 자동으로 올라온다.
- 카톡·디스코드에 붙였을 때 방 정보가 OG 이미지로 보이게 한다.

### 2주차: 팀 자동 나누기 (핵심 기능)

- 티어를 점수로 바꾸고, 10명을 5:5로 나누는 경우의 수(126가지)를 전부 계산한다. 점수 차이가 가장 작으면서 두 팀 모두 다섯 포지션을 채울 수 있는 조합을 고른다. 인원이 적어 근사가 아니라 최적의 조합을 바로 찾을 수 있다.
- 결과에 균형도를 보여 주고, 방장이 손으로 선수를 바꿀 수 있게 한다.
- 참석 확정, 입금 확인 체크, 시작 전 리마인드를 넣는다.

### 3주차: 결과와 랭킹

- 경기 결과를 입력하면 그 커뮤니티 안의 전적과 Elo 랭킹이 쌓인다.
- 공유용 결과 카드(승리 팀, MVP)를 만든다. 참가자가 공유한 카드가 다음 방장을 데려오는 장치다.

### 4주차: 방장 10명 데려오기와 첫 실험

- 인터뷰한 방장부터 시작해, 다음 내전 한 번을 이 서비스로 돌려 보게 한다.
- 첫 실험: 리마인드 타이밍(전날 vs 1시간 전)에 따른 노쇼율 비교. 실험군 배정과 노출 기록을 직접 만들고 결과로 결정한다.

## 기술 스택

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 프론트엔드 | Next.js App Router | 가장 익숙한 스택 |
| 백엔드 | Supabase (Postgres, 인증, Realtime) | 참가자 명단이 실시간으로 바뀌는 것이 이 제품의 재미 요소 |
| 로그인 | 디스코드 OAuth (방장) | 게이머에게 가장 익숙하다 |
| 배포 | Vercel | 링크 공유와 OG 이미지 생성이 쉽다 |
| 오류 추적 | Sentry | 운영 오류 수집·추적 |
| 측정·실험 | PostHog | 이벤트·퍼널·기능 플래그 실험을 한곳에서 |

## 데이터 모델 (처음 기준)

| 테이블 | 내용 |
| --- | --- |
| `community` | 방장이 운영하는 그룹 |
| `room` | 카테고리, 이름, 일시, 정원, 참가비, 티어 조건, 상태 |
| `participant` | 닉네임, 티어, 주/부 포지션, 상태(참가·대기·확정·입금·노쇼) |
| `match` | 팀 구성, 승리 팀, MVP |
| `rating` | 커뮤니티별 선수 Elo |

## 마케팅

- **대상:** 내전을 운영하는 방장. 롤 내전 오픈채팅방, 디스코드 서버, 커뮤니티 내전 게시판에서 찾는다.
- **처음 방법:** 방장 10명에게 직접 연락해 다음 내전 하나를 이걸로 돌려 보게 한다. "팀 나누기를 대신 해 준다"가 가장 쉬운 설득 포인트다.
- **확산 장치:** 경기 뒤 전적 카드와 MVP 이미지를 공유하게 만든다.
- **채널 비교:** 채널마다 UTM을 달아 어디서 온 방장이 실제로 방을 만드는지 비교한다.

## 볼 지표

| 대상 | 지표 |
| --- | --- |
| 방장 | 방을 다시 만드는 비율(주 단위) |
| 방 | 정원이 차는 비율, 차기까지 걸린 시간 |
| 참가자 | 노쇼율, 다음 내전 재참가율 |

퍼널: 방장 방문 → 방 생성 → 링크 공유 → 정원 충족 → 팀 확정 → 결과 입력 → 다음 방 생성.

## 미리 알아 둘 리스크

- **노쇼와 비매너:** 방장이 참가자를 평가하는 기능이 필요해질 수 있다.
- **Riot API:** 티어 자동 조회는 개발용 키 한도가 작다. 서비스용 키 승인 조건을 확인한 뒤 붙이고, 처음에는 직접 입력으로 충분하다.
- **경품 요청:** 반드시 나온다. 결과에 따라 돈이나 경품을 주는 기능은 넣지 않는다.
- **초기 정착:** 처음 방장 몇 명이 계속 쓰느냐에 전부 달려 있다. 첫 10명은 손으로 붙인다.
