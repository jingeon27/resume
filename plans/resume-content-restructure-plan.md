# 이력서 내용을 다시 배치하는 계획

작성일: 2026-10-09

참고: [진유림 님 이력서](https://milooy.github.io/resume/)

메인 페이지의 소개, 경력, 프로젝트, 외부 활동, 학력·언어까지 공개된 본문을 읽었다. 이미지·GIF의 실제 내용과 연결된 발표·글은 각각 확인하지 않았다. 이번에는 적용 계획만 작성하며 이력서·지원서·포트폴리오 본문은 바꾸지 않는다.

## 참고할 부분

참고 이력서는 소개에서 일하는 관점과 맡아 온 책임을 먼저 보여준다. 경력 요약과 프로젝트를 구분하고, 프로젝트에는 사업 목적과 협업에서 한 행동을 적는다. 서비스 화면과 글 링크도 설명에 붙여 놓았다. [원문](https://milooy.github.io/resume/)

내 문서에도 이 흐름을 적용한다. 리드·코칭·채용 경험은 가져올 내용이 아니다. 지금까지 맡은 제품과 기술적 판단을 더 잘 읽히게 하는 데 집중한다. 웹 이력서의 긴 분량과 모든 분류를 제출용 PDF에 그대로 옮기지는 않는다.

## 지금 문서에서 먼저 고칠 부분

- [공통 이력서](../resumev6.md)는 409줄의 상세 기록이다. 사례를 분량 때문에 삭제하지 않고, 회사별 이력서를 만드는 기준 문서로 유지한다.
- [모임 이력서](../resumes/daangn/resume-daangn-moim.md)는 소개가 여섯 문단이다. 담당 범위, 사용성, 오류 대응, 기술 이해, 개인적인 지원 이유, 실험 경험이 한꺼번에 나온다. 소개와 지원동기의 역할부터 나눈다.
- 모임 이력서의 첫 프로젝트는 SSR·라우팅이다. 기술적인 깊이는 잘 보이지만, 어떤 제품을 만들었고 사용자와 운영팀의 어떤 일을 해결했는지는 뒤에서 읽게 된다. 건강검진과 모바일 사용성 사례를 먼저 보여주는 구성을 시험한다.
- [포트폴리오](../portfolio-v2.md)는 첫 부분에 blame 비율·커밋 수·파일 수가 많다. 담당 범위와 변경량을 확인하는 자료로 남기되, 첫 페이지는 제품과 대표 작업을 이해하는 데 쓴다.
- 최근 확인한 A/B 테스트 환경 구축과 페이지 방문 기록에 근거한 코드 제거 경험은 모임 지원서에 반영돼 있다. 공통 이력서와 포트폴리오에도 역할과 표현을 맞출 필요가 있다.

## 앞에서 보여줄 사람

현재 자료로 보여줄 수 있는 강점은 다음과 같다.

- 작은 팀에서 제품 기능과 기존 코드의 유지보수를 함께 맡았다.
- 요구사항에 빠진 동작을 찾아 의견을 내고, 담당자와 맞춘 뒤 구현했다.
- 상태·조회·검증 책임이 섞인 코드를 읽고, 변경할 때 확인하기 쉬운 구조로 정리했다.
- AI 개발 workflow를 운영하며 반복되는 판단을 skills·lint rule·테스트에 남겼다.
- 출시 후 오류를 추적하고, 수정한 뒤 같은 문제가 다시 발생하는지 확인했다.

소개는 이 내용을 모두 나열하지 않고 세 문단으로 정리한다.

- 첫 문단: 어떤 개발자인지와 실제 제품 경험. 프레임워크 버전·사용자 수·단독 담당 시기는 경력 요약에서 보여준다.
- 두 번째 문단: 요구사항의 빈틈과 코드 구조를 다루는 방식. 대표 행동 하나로 설명한다.
- 세 번째 문단: AI 개발 workflow에서 본인이 하는 판단과 검증. 상세 단계는 프로젝트로 보낸다.

첫 문장 후보:

> 제품을 만들며 불편한 사용 흐름과 복잡해진 코드를 함께 고쳐 온 프론트엔드 엔지니어입니다. React·TypeScript·Next.js로 채용 SaaS와 의료복지 서비스를 개발했습니다.

게임 커뮤니티에서 시작된 관계와 모임에 지원하는 이유는 지원동기에 둔다. 기술 소개에 섞지 않고 개인적인 이유로 살린다. 팀에서 문제 정의부터 함께 일하고 싶다는 방향도 여기에 연결한다.

### 기술 설명을 바꾸는 예시

현재 SSR 항목에는 API 동작과 회귀 원인이 한꺼번에 나온다. 첫 설명은 다음처럼 시작하고, 원인 분석은 아래 bullet과 글 링크에 둔다.

> 서버 컴포넌트에서 `ensureQuery` 결과를 render props로 전달하던 데이터 조회 전반을 TanStack Query prefetch·hydration으로 바꿨습니다. 서버는 초기 데이터를 준비하고, 클라이언트는 같은 캐시를 읽어 이후 조회·갱신·캐시 무효화를 처리하도록 했습니다.

이후 클라이언트 조회·무효화와 History API를 쓸 수 있는 조건을 설명한다. 재귀 조건부 타입과 Zod도 같은 방식으로, 먼저 잡으려던 오류를 보여주고 구현 원리를 설명한다. 기술 용어를 전부 빼지는 않는다.

### 협업 태도를 보여줄 예시

> 검진 항목을 모두 고르면 다음 그룹으로 넘어가자는 요청을 받았습니다. 기존 선택을 수정할 때도 화면이 이동하는 점을 짚어 담당자와 논의했고, 선택 수를 채우면 고르지 않은 항목만 비활성화하도록 구현했습니다.

‘소통을 잘한다’는 자기평가를 붙이지 않아도 어떤 의견을 냈고 어떻게 결정했는지 읽힌다. 리뷰 UI 제안, 백엔드에 조회 응답 문제를 전달한 일, 왓타임에서 CTO 리뷰를 받아 NestJS를 걷어낸 일도 해당 경험 옆에 짧게 적는다.

## AI 개발 workflow의 개선 흐름

현재 작업 순서만 보여주면 도구를 연결한 자동화로 읽힐 수 있다. 그 순서로 일할 수 있게 저장소와 검증 방식을 바꾼 과정을 함께 쓴다. 모델 성능의 향상과 skills 보강이 겹치면서 원하는 스타일의 결과가 늘었고, 처음부터 지금의 위임 범위로 시작하지 않았다는 설명도 남긴다.

| 시기 | 바꾼 것과 이유 |
| --- | --- |
| 2026.04부터 | 생성된 결과를 검토하면서 의도와 달랐던 판단을 skills에 누적. 티켓·plan과 완성본을 확인하는 방식 개선 |
| 2026.07부터 | 새 기능의 기대 동작과 운영 오류의 회귀 테스트를 구분. 실제 컴포넌트·dev API 서버로 확인 범위를 넓히고, 앱 간 E2E는 9월에 추가 |
| 2026.08부터 | Sentry로 운영 오류를 수집·추적. 테스트와 화면 확인에서 놓친 문제를 이후 검증에 반영 |
| 2026.08~09 | 저장소별 FSD의 배치 기준과 의존 경계를 정리. 자동으로 검사할 수 있는 기준을 lint rule로 옮기고 기존 위반을 정리 |

현재 순서는 그대로 보여준다.

티켓·plan 검토 → 테스트 작성 → 에이전트 구현·에이전트 코드 리뷰 → 변경분 테스트·lint·typecheck → 제 diff 리뷰·화면을 띄워 동작 확인 → 전체 CI(테스트·knip·lint) → QA 더블 체크 요청

- 구현과 테스트 작성은 에이전트에 맡긴다. 본인은 요구사항·plan, 컴포넌트별 빠진 스펙, 제출된 코드와 동작을 검토하고 부족한 결과를 반려한다.
- 새 기능은 BDD 형식의 `*.spec`, 운영·QA 오류는 `*.test`에 적는다. 새 테스트 패턴은 제품 코드를 일부러 깨뜨려 실패하는지도 확인한다.
- 변경분 검사는 병렬 worktree의 전체 검사가 CPU 경합을 만들었던 문제와 연결한다. 전체 CI와 검사 책임을 나눈 이유를 설명한다.
- 반복되는 판단은 skills, 정적으로 검사할 수 있는 기준은 lint rule, 미사용 코드는 Knip으로 관리한다. 저장소마다 구조와 제약이 다르다는 점을 유지한다.
- 테스트 체계와 Sentry는 독립 프로젝트로 남긴다. AI 개발 workflow에서는 이 경험들이 어떻게 이어지는지만 설명한다.

### 공통 이력서

대상: [resumev6.md](../resumev6.md)

- 상세 사례는 보존한다. 소개·핵심 경험·경력 요약에서 우선순위를 정하고, 본문은 경험을 찾기 쉽게 묶는다.
- 세이프닥은 제품 개발, 구조·조회·폼 개선, 오류 대응·검증, AI 개발 workflow 순으로 경험을 찾을 수 있게 한다. 독립 프로젝트의 상세 내용은 유지한다.
- 왓타임은 채용 업무 기능과 동료와의 개발 경험을 먼저, 공통화·Electron 판단을 다음으로 둔다.
- A/B 테스트 환경 구축과 사용 기록에 근거한 코드 제거 경험을 모임 지원서와 맞춘다.

- 건강검진·Sentry·테스트는 각각 독립 프로젝트로 유지한다.

- Tailwind·Radix·공통 필터처럼 비용을 알고 선택한 사례를 선별한다. 모든 프로젝트 뒤에 트레이드오프 문장을 억지로 추가하지 않는다.
- 지원동기는 개인적인 관계 경험과 앞으로 맡고 싶은 제품 개선으로 정리한다. 현재 회사를 평가하는 문장은 넣지 않는다.
- 공백 포함 500자 답변은 별도로 유지한다. 리뷰 개선 당시에는 Amplitude가 없었다는 시점을 지킨다.

### 포트폴리오

대상: [portfolio-v2.md](../portfolio-v2.md)

- 첫 부분은 맡은 제품·역할과 대표 사례로 구성한다. 커밋 수와 blame 비율은 기여 범위의 보조 자료로 옮긴다.
- 제품 사례는 사용자의 동작과 관리자 업무가 어떻게 바뀌었는지 보여준다. 건강검진은 세 제품의 역할과 화면 흐름을 함께 보여준다.
- 기술 사례는 실제 전후 구조를 나란히 둔다. 예약 폼의 상태 소유권, 조회 구조, FSD 폴더와 테스트 배치, 정산 코드의 책임 분리, Bottom Sheet와 RHF 조합을 후보로 삼는다.
- 파일 수·줄 수 감소만으로 설명하지 않는다. 무엇을 함께 읽어야 했고 변경 뒤에는 어디를 확인하면 되는지 설명한다.
- 공개 가능한 화면이나 재구성한 예제만 사용한다. 병원·환자·결제 정보는 노출하지 않는다. 자료 공개 가능 여부는 제작 전에 확인한다.
- 사례 바로 옆에 관련 글을 연결한다. 건강검진 글 등 현재 본문에 필요한 링크가 빠진 곳을 확인한다.

## 실제 수정할 때 확인할 것

- [ ] 첫 부분만 읽어도 맡은 제품, 본인 기여, 일하는 기준이 이해된다.
- [ ] 건강검진·Sentry·테스트와 왓타임의 주요 제품 경험이 남아 있다.
- [ ] 기술적 설명에는 선택 이유와 비용, 적용 조건이 함께 보인다.
- [ ] 협업은 성격을 평가하는 문장 대신 실제 의견과 결정 과정으로 설명한다.
- [ ] 2026년 1월 사내 유일, 4월 단독 담당을 구분한다.
- [ ] A/B 테스트 환경 구축·실험 참여와 가설·분석 주도를 구분한다. 코드 제거는 페이지 방문 기록을 확인한 판단으로 적는다.
- [ ] 예약 증가·전환율 향상·팀 전체 도입 등 확인하지 않은 성과를 만들지 않는다.
- [ ] 소스맵은 브라우저 범위, 크래시 수치는 확인 날짜와 기간을 함께 유지한다.
- [ ] 소개·프로젝트·지원서가 같은 내용을 반복하지 않는다.
- [ ] 상세 마스터 기록을 보존하고, 제출용 분량은 HTML·PDF 시안에서 정한다.

다음 작업에서는 소개와 대표 프로젝트 두 개부터 시안을 만들어 말투와 배치가 맞는지 확인한다. 그 뒤 나머지 이력서와 포트폴리오에 적용하고, 마지막에 HTML·PDF의 페이지 나눔과 링크를 확인한다.
