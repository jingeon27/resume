# 사이드 프로젝트: 면접 꼬리질문 연습 서비스 계획 (로컬 오픈소스 LLM)

> 목적: 프로덕트 엔지니어로 커리어를 넓히기 위해, 사용자 문제 찾기 → 출시 → 측정 → 실험 → 개선을 혼자 끝까지 돌려 본다. 비용 0으로 운영하기 위해 오픈소스 모델을 내 장비에서 돌린다.

## 한 줄 정의

질문에 답하면 꼬리질문이 이어지고, 어디서 답이 무너졌는지 짚어 주는 프론트엔드 면접 연습 웹 서비스.

## 왜 이 제품인가

- **질문 목록은 많은데 꼬리질문 연습은 어렵다.** 면접에서 떨어지는 지점은 첫 질문이 아니라 두세 번째 꼬리질문이다.
- **직접 겪었고 재료가 있다.** 면접 준비에서 질문 은행, 30초·2분 답, 꼬리질문, 사실 잠금(말하면 안 되는 것)을 직접 만들어 봤다.
- **콘텐츠로 사용자를 모을 수 있다.** 블로그·링크드인·개발 커뮤니티에 면접 질문 해설을 올리고 제품으로 잇는다. 글쓰기가 강점이다.

## 핵심 설계: 콘텐츠가 중심, LLM은 보조

- **질문 트리를 직접 만든다.** 질문마다 "이 답이 나오면 이 꼬리질문"으로 이어지는 갈래와, 갈래별 핵심 개념·흔한 오답을 적는다. 맞고 틀림의 기준이 사람이 검증한 내용이라 틀린 피드백이 나오지 않는다. 이것이 따라 하기 어려운 경쟁력이다.
- **LLM은 답변을 트리의 어느 갈래로 보낼지만 고른다.** 짧은 분류라 작은 모델로도 된다.
- **LLM이 응답하지 않으면 트리의 기본 꼬리질문으로 진행한다.** 장비가 꺼져 있어도 서비스는 멈추지 않는다.
- **피드백 문장은 트리에 적힌 내용을 보여 준다.** LLM이 지어낸 "그 답은 틀렸어요"가 사용자에게 잘못된 지식을 가르치는 것을 막는다.

## LLM 운영: 오픈소스 모델을 내 장비에서

- **실행:** Ollama(OpenAI 호환 API). 속도가 아쉬우면 애플 실리콘용 MLX 서버로 바꾼다.
- **모델 후보:**

| 모델 | 크기 | 한국어 | 라이선스 |
| --- | --- | --- | --- |
| Qwen2.5-7B / Qwen3-8B | 4비트 약 5GB | 괜찮음 | 대부분 Apache 2.0 (모델별 확인) |
| Gemma 3 4B / 12B | 4비트 약 3~8GB | 괜찮음 | Gemma 약관 |
| EXAONE 3.5 7.8B | 4비트 약 5GB | 가장 좋음 | 상업적 이용 제한 — 조건 확인 |

- **사양 기준:** M1 Pro 16GB면 7~8B 4비트는 무리 없고, 짧은 분류 응답은 요청당 1~3초다. 12~14B는 다른 앱과 같이 쓰면 빠듯하다.
- **외부 연결:** Next.js 앱(Vercel)의 서버 라우트 → Cloudflare Tunnel → 내 장비의 Ollama. Ollama에는 인증이 없으므로 포트를 직접 열지 않고, 터널 앞에서 토큰 헤더를 검사한다.
- **보호 장치:** 응답 10초 타임아웃, 동시 처리 수 제한, 사용자별 하루 연습 한도, 같은 질문·비슷한 답의 분류 결과 캐시.
- **용량 감:** 연습 한 번에 호출 10번, 한 번에 2초면 순서대로 처리해도 시간당 100명 이상을 받는다. 초기에는 충분하다.
- **장비:** 개발과 실험은 지금 맥에서 한다. 실사용자를 받는 서버는 회사 노트북이 아니라 24시간 켜 둘 수 있는 개인 장비(개인 맥, 맥 미니 등)로 옮긴다. 회사 장비를 개인 서비스로 외부에 여는 것은 보안 정책 위반이 될 수 있다. 장비가 마련되기 전에는 무료 API 등급으로 열고, 약관(입력 데이터 사용 여부, 실서비스 허용)과 호출 한도를 먼저 확인한다.
- **내세울 점:** 답변이 외부 AI 회사로 가지 않고 학습에도 쓰이지 않는다. 이력서·회사 이야기를 넣는 면접 연습에서 설득력 있는 장점이다(무료 API 등급을 쓰는 동안에는 내세우지 않는다).

## 시작 전 반나절 실험: 모델 고르기

1. 실제 질문과 답 20쌍(맞는 답·틀린 답·애매한 답을 섞어서)을 준비한다.
2. 후보 모델 두세 개에 같은 프롬프트로 갈래 분류를 시킨다.
3. 결과를 직접 채점해 정확도와 응답 시간을 비교한다.
4. 가장 덜 틀리는 모델을 고른다. 판정 품질이 낮으면 LLM은 갈래 고르기에만 쓰고 피드백은 전부 트리 내용으로 보여 준다.

이 비교는 그대로 블로그 글감이다.

## 4주 계획

### 0주차 (3일): 사용자 5명과 이야기하기

- 면접 준비를 어떻게 하는가? 꼬리질문은 어떻게 연습하는가?
- 최근 면접에서 어느 질문, 몇 번째 꼬리질문에서 막혔는가?
- 답변을 AI 서비스에 넣는 것이 꺼려지는가?

### 1주차: 질문 트리와 연습 화면

- 프론트엔드 핵심 주제 5개(React 렌더링·상태, Next.js 서버/클라이언트 경계, 브라우저·HTTP, 테스트, 성능)로 질문 트리 20개를 만든다.
- 질문 → 답변 입력 → 꼬리질문 → 마지막에 무너진 지점 요약으로 이어지는 화면을 만든다. LLM 없이 트리의 기본 경로로 먼저 동작하게 한다.

### 2주차: LLM 갈래 분류 붙이기

- 모델 고르기 실험 결과로 모델을 정하고, Ollama + Cloudflare Tunnel + 토큰 검사 + 타임아웃 대체 경로를 붙인다.
- 하루 한도와 분류 결과 캐시를 넣는다.

### 3주차: 다시 오게 만들기

- 약했던 주제만 다시 연습하기, 주간 복습 알림.
- 결과 요약 카드(어느 주제의 몇 번째 꼬리질문에서 막혔는지)를 공유할 수 있게 한다.

### 4주차: 사용자 데려오기와 첫 실험

- 블로그·링크드인·커뮤니티에 면접 질문 해설 글을 올리고 채널별로 UTM을 단다.
- 첫 실험: 첫 화면에서 바로 질문을 보여 줄지, 주제를 고르게 할지에 따른 첫 연습 완료율 비교. 실험군 배정과 노출 기록을 직접 만들고 결과로 결정한다.

## 기술 스택

| 영역 | 선택 |
| --- | --- |
| 프론트엔드 | Next.js App Router |
| 데이터 | Supabase (Postgres, 인증) — 질문 트리와 연습 기록 |
| LLM | Ollama + 오픈소스 모델, Vercel AI SDK(OpenAI 호환 공급자) |
| 연결 | Cloudflare Tunnel + 토큰 헤더 |
| 배포 | Vercel |
| 오류 추적·측정 | Sentry, PostHog |

## 볼 지표

| 지표 | 의미 |
| --- | --- |
| 첫 연습 완료율 | 들어온 사람이 꼬리질문 끝까지 가는가 (활성화) |
| 7일 재방문율 | 다시 연습하러 오는가 (리텐션) |
| 사용자당 연습 수 | 얼마나 쓰는가 |
| LLM 실패율·대체 경로 비율 | 장비·모델이 버티는가 |

퍼널: 콘텐츠 유입 → 첫 질문 답변 → 꼬리질문 완료 → 결과 요약 → 재방문.

## 리스크

- **틀린 피드백:** 가장 큰 위험이다. 판정 기준은 트리에 두고, LLM이 만든 문장을 정답처럼 보여 주지 않는다.
- **장비 가용성:** 장비가 꺼지면 대체 경로로만 돈다. 실사용자가 생기면 24시간 장비를 마련한다.
- **비슷한 서비스:** 면접 AI 서비스는 많다. "검증된 꼬리질문 트리"와 "답변이 밖으로 나가지 않음"으로 좁고 날카롭게 차별화한다.
- **콘텐츠 품질 유지:** 트리를 늘리는 데 시간이 든다. 처음 20개로 반응을 본 뒤 늘린다.
- **복무 중 제약:** 산업기능요원 겸직·영리 제한과 회사 겸업 규정 때문에 무료로 운영한다.
